# Tributary design: every commit is one conditional put on a per-aggregate chain in DynamoDB, with bytes in S3 and folds on NVMe

## Summary

Tributary is one Rust binary, pinned upstream git, a React web app, and two AWS stores, DynamoDB and S3. It is wire compatible with GitHub Enterprise Server (GHES) 3.22, and it is built fresh for less downtime and for scale by adding cells, which is what the operator asked for (`FRAME.md`, "Operator decision, 2026-10-24, on the store"). Each repository and fork network has a gap-free chain of entries in a DynamoDB table, and each owner (user, org, enterprise) has two, `Authz` and `Identity`. Every acknowledged change is one conditional put of the chain's next entry, made after every byte it names is already in S3. Every read is a node-local fold of chains, proven current by a strongly consistent GetItem on the chain's next key that started after the request arrived and found no item. No database transaction, SQL server, connection pool, outbox table, request-path lease, or clock bound sits under git, pull requests, issues, or authorization (`arena/round4/candidate-3/DESIGN.md`, Summary).

- A push, merge, issue, comment, review, or rule change is acknowledged when its entry's put returns. A Paired cell's tables are MRSC global tables in two Regions plus a witness, so the put returned only after a second Region held it, and an acknowledged write survives the permanent loss of a Region with no failover step (`research/uptime.md#29`, `#37`, `#38`).
- Refs, pull request state, reviews, rules, required check conclusions, and the event stream of a repository are entries on its one chain, so a merge decides on every input committed before it, and an event exists if and only if its change committed.
- Each repository fold has two tiers. The core tier (refs, rules, collaborators, pull request heads, review verdicts, required checks) loads first and alone gates git, merges, and authorization. The metadata tier (issues, comments, review bodies, labels) loads lazily from its own snapshot, so a node loss or a new metadata schema never delays git or a merge (`arena/round4/SYNTHESIS.md`, graft 5).
- Managed is one public namespace at `tributary.dev`. A worldwide MRSC `global` table on three continents holds logins, token hashes, SSH fingerprints, installations, and the slot map, so no continent's loss loses or stalls a name claim. Memberships, teams, grants, policies, installations, and rulesets are entries on the owner's `Authz` chain in its home cell, and a `Mirror` consumer copies them into every cell that hosts the owner's repositories, so an allow never reads another cell. A hosting cell's mirror lease runs from a heartbeat that the home cell sends outside Streams, and a denial that rests on a mirrored fact re-reads the home `Authz` tail, so an acknowledged grant is never refused. A removal's 204 waits until every hosting cell has applied it, or at most 30 s, the lease, because a cell that has not applied it by then has fenced itself.
- Token revocation binds writes within 5 s and reads within 60 s, because a write re-reads its token from the local `global` replica every 5 s and an alarm fires when replication lag passes 2 s. A Single cell enters stale mode only on sustained tail-read failure (three failed reads within 10 s, or a signed flag), then serves fetches and reads from warm folds at their last proven seq for a signed limit (default 2 hours) and answers writes with 503. Paired cells have no stale mode while both replica Regions serve, and a Paired install running on one replica and the witness may enter it.
- Single-Region installs run on plain DynamoDB tables in any of 34 Regions, and Paired installs use any two of the 15 MRSC Regions plus a witness (`research/dynamodb.md#24`, `#25`). Managed, BYOC, and self-hosted ship one signed bundle through the vendor's existing BYOC release machinery, and an in-account `operator` role runs every lifecycle step from signed intents ("Install operations").
- Milestone 0 measures one chain's append rate, tail reads, phantom reads, throttle ceiling, and correctness under Region isolation, plus Streams, a race between the fold engine and candidate 1's index lists, merges on cold nodes, and restore, before any git code exists. The append gate can flip the base, the race picks the list engine, and "Build order" states both.

`arena/round4/SYNTHESIS.md` records why this foundation was picked, its eight grafts, and what was rejected. "Synthesis decision" summarizes rounds 1 to 4 and the tie that the foundation attack found (`review/round4-foundation-attack.md`).

## Problem

Tributary must look exactly like a GHES host to unmodified clients, keep git, pull requests, and the APIs up before anything else, and never lose an acknowledged push, in three modes that ship as one artifact (`FRAME.md`). The operator wants "an entire new, better scalable github that has less downtime", so downtime and scalability outrank build convenience when a foundation is compared (`FRAME.md`, "on the store"). Six research facts set the shape.

1. A Region and its data can vanish for good, as me-central-1 and me-south-1 did in 2026 (`research/uptime.md#37`, `#38`). "Never lose a push" needs a copy outside the Region when the client is told done.
2. Database incidents dominate GitHub's core outage minutes, about 2,500 incident-minutes: an engine version bug, a misconfigured index, a dropped column still read, a migration at peak, overloaded shared clusters (`research/uptime.md#43`, `#44`). Removing the shared query engine, DDL, and engine upgrades from the core path removes those classes instead of containing them [inference].
3. Recovery must never call a control-plane API or launch capacity (`research/uptime.md#32`-`#35`), so failover cannot be a promotion call (`#24`, `#25`). An MRSC write returns after a second Region has it, conditions evaluate against the latest version, and a replica keeps writing while one other Region of its three is reachable, with no failover call (`research/uptime.md#29`; https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/V2globaltables_HowItWorks.html).
4. MRSC has no transactions, TTL, or local indexes, every GSI and stream read is eventually consistent, and Streams keep 24 hours with at most two readers per shard (`research/dynamodb.md#6`, `#11`, `#13`, `#14`, `#17`, `#18`). So invariants cannot live in transactions and lists cannot live in indexes. This design puts every input to a decision on one chain and every list in a node-local fold.
5. No Rust library can serve git, so upstream git stays the pack engine (`research/git-storage.md#44`-`#49`). Refs, pull request state, and the webhook stream are facts about one event, and hosts that keep them in separate stores show divergence races, for example Praefect's PostReceiveHook firing before replication (`research/git-storage.md#10`).
6. On February 9, 2026 a cache TTL cut and a tenfold read increase overloaded GitHub's auth database, and in May 2023 expensive writes on a shared permissions cluster broke App tokens for about 12 hours (`research/uptime.md#47`, `#44`). Identity load must follow fleet size, not request rate or a TTL.

The managed service is one public, github.com-style namespace (`FRAME.md`, "Operator decision, 2026-10-24"), it runs worldwide, and DynamoDB global tables are allowed (`FRAME.md`, "later"). A key that every owner on Earth competes for, such as a login or an SSH fingerprint, is one item in a worldwide MRSC table, and its conditional write is the commit point. Every other identity fact belongs to one owner and lives on that owner's `Authz` or `Identity` chain in its home cell. Repositories are placed by fork network, because GitHub opens pull requests only within one network (https://docs.github.com/en/rest/pulls/pulls), so `bob/widgets` sits in `acme/widgets`'s cell and a fork merge touches one chain.

Where this design answers each required fact from `arena/TASK.md`. (1) Region loss and RPO: "Chains and commits", the `region` rows of "Failure modes", and RPO zero in Paired cells. (2) Object storage as truth: chains in DynamoDB and bytes in S3 are the only durable state, and NVMe holds only derived folds and caches. (3) Upstream git stays the engine: `trib-git` and "Build order". (4) Toolkit hostname heuristics and SHA pins: "Actions". (5) `use_v2_flow: true`: "Actions". (6) The GHES look: "Wire compatibility". (7) Token and id formats: "Identity and tokens" and "Namespace and cell placement". (8) BYOC machinery gaps and upgrade downtime: "Change safety", "Deployment modes", and "Install operations". (9) No launch or control-plane call in recovery: every `control-plane` row. Paired cells meet it. Single cells do not, because a Region loss there needs a `dr` promotion that launches nodes, or a restore.

## Usage (caller's view)

**Operator quickstart, self-hosted.**

A self-hoster runs three EC2 instances of one binary, five on-demand DynamoDB tables, three versioned S3 buckets, and one NLB in its home Region. Setting a `dr` Region adds an MREC replica of each table, replicated buckets, and a small standby node group there. There is no database server, no cluster, no Redis, and no replica set to repair. The deploy tool, bootstrap, and signed registry are the vendor's existing BYOC machinery with a Tributary product profile (`research/byoc-grounding.md#22`, `#23`), and the install's own `operator` role runs every step they request ("Install operations").

```sh
# 1. One time, in a dedicated AWS account. The bootstrap's product variable selects trib- prefixes, the Tributary
#    deploy policy, and the PassRole services, and creates the install's multi-Region keys, control buckets, and deployer launcher.
tofu -chdir=bootstrap/customer apply \
  -var product=tributary -var deploy_principal_arn=arn:aws:iam::111122223333:role/ci-deploy
# 2. Fetch and verify the signed release (ECDSA P-256, create-only registry), then copy its AMI into each Region.
platform-deploy release fetch --registry prod --release tributary-2027.03.1
tributary release import-ami --release tributary-2027.03.1 --regions eu-central-2,eu-central-1
# 3. Describe the install. The "tributary" block is the only product-specific part of the target.
cat > target.json <<'EOF'
{ "version": 1, "name": "git-prod", "profile": "tributary-customer",
  "aws": { "accountId": "111122223333", "region": "eu-central-2" },
  "terraform": { "stateBucket": "platform-terraform-state-111122223333" },
  "tributary": {
    "hostname": "git.example.ch",
    "durability": { "class": "single", "dr": "eu-central-1", "pitrDays": 35 },
    "nodes": { "layout": "combined", "azs": 3, "perAz": 1, "instanceType": "i8g.2xlarge" } } }
EOF
# Two-Region instead: "durability": { "class": "paired", "regions": ["eu-central-1", "eu-west-1"], "witness": "eu-west-3" }
# 4. Preflight every install Region, copy the release into releases/ in each control bucket, and submit the rollout
#    intent. The operator role runs it, and the tool polls. Its apply:infra stage, under the deployer role, creates the log,
#    checks, actions, inbox, and global tables with PITR, deletion protection, Streams, warm and maximum throughput, the buckets, and nodes.
platform-deploy deploy --target target.json --bundle tributary-2027.03.1
# 5. First admin. Runs on a node through SSM and prints a one-time sign-in link.
tributary admin bootstrap --host git.example.ch --first-admin alice
```

A dead node or AZ needs no repair by hand. The Auto Scaling group replaces a dead node whenever EC2 can launch, and the surviving nodes already serve every repository from DynamoDB and S3. A DynamoDB impairment in the home Region is the one 2am decision, and the runbook in "Install operations" ends it in waiting while warm folds serve stale fetches, with the stale limit raised to AWS's projected recovery time, `tributary dr promote`, or a restore. Upgrades are `platform-deploy deploy` with a newer bundle, which submits an intent that the operator role runs, and never need a maintenance window. [unverified that i8g is offered in three eu-central-2 AZs; the preflight checks it and the target may name another NVMe type]

eu-central-2 is not one of the 15 MRSC Regions, and Switzerland has no second Region, so a Zurich install cannot be Paired and its `dr`, eu-central-1 above, keeps a copy in Germany (`research/dynamodb.md#25`). An install whose data must stay in Switzerland runs Single without `dr`, and the preflight says so.

**Operator quickstart, BYOC.**

The customer applies the same bootstrap with `product=tributary` and `deploy_principal_arn` set to the vendor's deploy principal and an ExternalId. It creates the install's multi-Region keys, among them the config key and a customer-only key that no deploy role can use, the control buckets, the deployer launcher, the Tributary deploy policy, which keeps the deploy principal from reading repository data or deleting stateful resources, and the read-only observer role. The customer delegates one DNS subzone (for example `git.example.com`) or uploads a certificate, and chooses the durability class. Paired is the BYOC default and needs two replica Regions and a witness Region from the 15 MRSC Regions enabled in the same account, which the target preflight checks (`research/dynamodb.md#25`). A Region outside that list, such as Sydney, gets Single ("Deployment modes"). The vendor's pipeline then runs the same `deploy` command, which copies the verified release into the install's control buckets and submits a signed rollout intent that the install's `operator` role runs. The customer grants nothing else, and the install keeps serving, renewing certificates, and rotating keys with the vendor unreachable ("Install operations").

**Operator quickstart, managed.**

Nothing is provisioned per customer. A user signs up at `tributary.dev`, and the signup's commit point is one conditional put of the login item in `global`, whose account id carries a slot of the account's home cell, by default a cell on the continent of the front that served the page. An org's creator picks the org's residency, which selects its home cell's Regions. An enterprise account adds SAML or OIDC on its orgs, a managed-user shortcode, and optionally a residency (for example EU, whose cells run in eu-central-1 and eu-west-1 with an eu-west-3 witness). The fleet control plane adds cells ahead of demand and moves slots between cells. No signup calls a control-plane API.

**What a `gh` user types.**

```sh
gh auth login --hostname tributary.dev               # device flow with gh's own client id 178c6fc778ccc68e1d6a
git clone https://tributary.dev/torvalds/linux.git   # anonymous, public
gh repo fork acme/widgets --clone && cd widgets
git switch -c fix && git commit -am fix && git push origin fix
gh pr create --repo acme/widgets --head bob:fix --fill && gh pr checks --watch
```

gh classifies the host as GHES because it is not `github.com`, `*.ghe.com`, or `github.localhost` (`research/clients.md#1`), derives `/api/v3/` and `/api/graphql` (`#3`), and reads `installed_version` from `/api/v3/meta` (`#9`). Nothing else is configured. BYOC and self-hosted users type the same commands against their own host.

**A maintainer** writes every state change as a pure `decide` over a fresh fold, and every read against a fresh fold:

```rust
// receive-pack, after `index-pack --strict` and the connectivity check against the fresh core tier
let acked = commit(&cell, ChainId::Repo(r), Push { updates, pack: packs.place(net, staged).await?, actor, atomic: true },
                   req.arrived).await?;                          // decide re-runs authorize on the fresh Authz and repo folds
report_status(&acked);                                           // takes &Acked, so "ok" cannot precede the put
// GET /repos/{o}/{r}/issues?labels=bug&sort=updated
let view = folds.fresh(ChainId::Repo(r), Tier::Metadata, req.arrived).await?;  // one strong tail read, shared
let page = view.issues(&IssueQuery::from_rest(&params)?, cursor)?;             // SQL over the node's SQLite fold
```

**Journeys.** Managed cell `c1` is Paired in us-east-2 and us-west-2 with a us-east-1 witness. "Durable" means what exists when the client is told done.

1. *Atomic three-branch push to busy `acme/mono` while the merge queue merges 10 pull requests a minute, bots move 50 refs a minute, and CI clones 2,000 times a minute.* The edge in us-east-2 finds the token and the route `(acme, mono) -> c1` in its cache. A push is write-class, so if the cached token entry is older than 5 s the edge re-reads the token item from the local `global` replica with an eventually consistent read, coalesced per token per node and drawn from its own re-check budget. A `c1` git node proves `acme`'s `Authz` chain (its home cell is `c1`) and the `mono` chain fresh with two strong tail reads on `log` and applies any new entries to their core tiers. A pack over 16 KiB is PUT with `If-None-Match: *` to the us-east-2, us-west-2, and us-east-1 buckets, and two answers suffice. `commit` appends one `Refs` entry with all three updates. Queue merges and bot updates append their own entries on the same chain, batched by the chain's preferred node, and a lost race re-runs `decide`, so a ref nobody else touched rebases and a contended one reports `fetch first`. Durable: the entry in at least two of three Regions (V2globaltables_HowItWorks, above) and the pack in two buckets. Next read: any node in either Region proves its fold fresh first, so every clone that starts after the "ok" sees all three refs, and a clone already running sees all three or none. The 33 clones a second cost one strong read per AZ's preferred node per read round trip, other serving nodes take the new entries from that node, and bytes come from NVMe (`arena/round4/candidate-3/DESIGN.md`, journey 1).
2. *A fork pull request merges while a review and a check run land, then `gh pr view` and `gh pr list` run at once.* PR 17 lives on `acme/widgets`'s chain in `c7`, and its head `bob/widgets:fix` is a chain in the same network and cell. The review is a `Review` entry on `acme/widgets`'s chain, so it lands before the merge, and the merge's `decide` sees it, or after, as a review of a merged pull request. The check run's conclusion is written to `checks`, and because `main`'s rule requires that check it is also appended to the same chain as a `RequiredCheck` entry, so it too lands before the merge or after it, never beside it (`arena/round4/SYNTHESIS.md`, graft 1). The merge plan pins the fork head's SHA from a fresh fold of `bob/widgets`, and `decide` emits one `Merged` entry carrying the base update, the head SHA, the verified tree-diff digest, and the inline pack. Durable: that entry in two Regions. Both `gh` calls route to `c7`, prove the chain fresh, and show `MERGED`.
3. *`gh issue create --label bug`, then `gh issue list --label bug`, then `gh api repos/o/r/issues?sort=updated`.* Create appends one `IssueOpened` entry whose number comes from the fold at the seq it was decided on, so numbering and labels commit together. Both lists prove the chain fresh, apply the new entry to the metadata tier, and run SQL over the SQLite fold, so the new issue is in both, first by `updated`. No index is eventually consistent.
4. *An owner removes a member.* `DELETE /orgs/acme/members/mira` appends `Member { user: mira, role: None }` to `acme`'s `Authz` chain in its home cell and returns 204 once every cell that hosts `acme`'s repositories has applied it to its `Mirror` chain, or after at most 30 s, the mirror lease, because a hosting cell that has not applied it by then has fenced its writes that read a mirrored fact. Every authorization reads the local `Authz` fold or mirror, and every write re-proves it just before its put, so mira's next push fails in every cell. Bound: zero after the 204 for any write that authorizes after it, plus at most one put round trip (about 20 ms [guess]) for a push already deciding, and reads in a cut-off hosting cell close at a signed limit. Her token stays valid, as on GitHub.
5. *The Region holding the newest writes is lost for good mid-push.* Managed `c1` loses us-east-2. An acknowledged entry is in us-west-2 or the witness, so us-west-2 still reads it strongly and keeps writing with the witness (`research/uptime.md#29`). A push whose put had not returned gets a broken connection, and its retry is idempotent because the entry records the request id and git re-sends expected old values. Route 53 health checks drop us-east-2's edges, which forward to us-west-2 ingress: no human, no control-plane call, RTO about 2 minutes [guess], RPO zero. A two-Region BYOC install (eu-central-1, eu-west-1, witness eu-west-3, a pack bucket in each) behaves the same. Losing a replica Region and the witness together stops writes and strong reads until one returns. us-east-2 is also one of `global`'s three Regions, and an MRSC table cannot add a replica (`research/dynamodb.md#18`), so the fleet control plane re-protects both by planned copies: a new `global` trio that edges read beside the old one until cutover, and slot moves out of `c1` into cells with three healthy Regions [inference: copy duration unmeasured].
6. *A bad release multiplies identity reads tenfold, and another writes a record shape the previous release cannot read.* Identity reads are edge cache misses and write re-checks on the local `global` replica, and `Authz` tail reads in cells. Misses and re-checks are capped per node by compiled constants, `trib-fleet` keeps those budgets times a Region's front nodes below that replica's maximum read throughput (https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/on-demand-capacity-mode.html), and `Authz` reads coalesce per node, so the canary wave's nodes answer 503 for uncached principals, abort on the 5xx gate, and swap back, while other front nodes keep their share. If the tenfold reads are real traffic from a client release, as in February 2026 (`research/uptime.md#47`), the principals repeat, so they hit edge caches and coalesced folds, store load stays flat, and admission by OAuth client id sheds only that client. A new entry format is written only after the signed `ReleasePointer` lists it as enabled, and the operator role records that only when every cell that can read the chain reports a release that reads it, from the fleet's `nodes` reports. Each entry carries its tier tag outside the encoded body, so an older node skips an unknown metadata event and the core tier never stalls. If a format escapes anyway, nodes on the old release refuse to apply that chain, answer 503 for it, and alarm. Swap-back below the reading release is refused and pages, and the fix rolls forward.
7. *A company self-hosts in eu-central-2, a Region the previous design could not reach, loses data to operator mistakes, and repairs it.* DynamoDB is offered in 34 Regions, and eu-central-2 has DynamoDB but not the previous design's store (`research/dynamodb.md#24`, `#26`). The install's preflight checks DynamoDB, the Streams interface endpoint, S3, and the instance type in three AZs. First mistake: a script force-pushes `main` in 12 repositories and deletes 3. `tributary admin repo-restore --refs main --to <t>` appends one `RestoredTo { to, refs }` entry to each of the 12 chains, which returns `main` to its target at the seq in force at `t` and leaves other branches, issues, and reviews as they are. Each delete appended `Deleted { retain_until }` and turned the repository's name into a `Deleted` entry, so `tributary admin undelete` appends `Undeleted` and puts the `Live` name back on the owner's `Authz` chain within 90 days. Later entries stay in the chains as history, packs survive under the GC rule, and no table is restored (`arena/round4/SYNTHESIS.md`, graft 2). Second mistake: a script deletes the org `acme`. That appended `Deleted { retain_until }` to `acme`'s `Authz` chain and made its login item `Deleted`, which hides its repositories, so `tributary admin undelete acme` reverses both, chain-local, and no other tenant's writes are rewound. Durable: every acknowledged write. Next read: `acme` exists with every repository and member it had. A point-in-time table restore stays for damage outside the chain model, such as items destroyed by a direct table write ("Backups and restore").
8. *`actions/runner` runs a job with `actions/checkout` and `actions/cache`.* Journey 1's `Refs` entry reaches the `ActionsTrigger` consumer through its `Dirty` marker ("Event fan-out"). The consumer reads `.github/workflows/*.yml` at the pushed SHA from the cache node, parses them with the Rust port of `GitHub.Actions.WorkflowParser` (`research/actions-protocol.md#60`), and writes run and job items in `actions` and check-suite and check-run items in `checks`, each idempotent on `(chain, seq, workflow path)`. The runner, registered through `use_v2_flow: true` (`research/actions-protocol.md#5`, `#6`, `#8`), long-polls the broker, which wins the job with a conditional update on its `version` (`Queued -> Assigned`). `acquirejob` returns the `AgentJobRequestMessage` with `CacheServerUrl`, `ResultsServiceUrl`, and the runtime token (`#16`, `#20`). `actions/checkout` fetches with the job's `ghs_` token through journey 1's read path. `actions/cache` uses cache v1, served from `actions` items and presigned S3 URLs (`#36`, `#43`). Logs go to S3 through the results service (`#23`). `completejob` commits `Completed { conclusion }` on the job item, the check-run conclusion in `checks`, and, when a rule requires that check, a `RequiredCheck` entry on the repository chain, each keyed by job attempt so a repeat changes nothing.

## Shape

A **cell** is one table set, one bucket set, and one node fleet that share nothing with other cells (`research/uptime.md#8`). Managed has many cells, and an install is one cell. Every canonical fact is a chain entry in DynamoDB, a single-item record in a work table, or an immutable S3 object that an entry names. Nodes keep only derived folds, caches, in-flight requests, and long-poll sessions, all rebuildable. Above the cells sit stateless front cells that authenticate and route, and in managed the worldwide `global` table. Each store has one job (`arena/round4/candidate-3/DESIGN.md`, Shape):

| Store | Holds | Chosen because |
| --- | --- | --- |
| DynamoDB `log` | Every chain entry for 30 days, checkpoint pointers, id blocks | One conditional put is linearizable and RPO zero across Regions with no failover step (`research/uptime.md#29`); a request API with no connection quota [inference]; 34 Regions [measured, `research/dynamodb.md#24`] |
| DynamoDB `checks`, `actions`, `inbox` | High-churn single-item state: check runs, Actions jobs, consumer markers and cursors, deliveries, notifications, cards | Separate tables carry separate maximum throughputs, so Actions or webhook load cannot throttle `log` (https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/on-demand-capacity-mode.html) |
| DynamoDB `global` | Logins, token hashes, SSH fingerprints, email digests, apps, installations, the slot map | MRSC spans any three of 15 Regions, across continents (`research/dynamodb.md#25`) |
| S3 | Packs, spilled entry bodies, fold snapshots, archived entries, bundles, control | $0.023 against $0.25 per GB-month (`research/pricing.md`, `research/dynamodb.md` section 7); conditional create (`research/uptime.md#31`) |
| SQLite on NVMe | One fold per chain and tier: the query index for every list, filter, and sort | Derived and rebuildable; a bad plan or schema touches one aggregate on one node [inference] |
| OpenSearch | Full-text search only | Off every core path (`research/uptime.md#49`) |

Every table in a Paired cell's Regions is a global table, so the 99.999% Global Tables SLA applies rather than the 99.99% Standard SLA, which applies when any table in the Region is not part of a global table (`research/dynamodb.md#22`; `arena/round4/SYNTHESIS.md`, graft 8). Single cells use plain tables under the Standard SLA.

### Chains and commits

```rust
// ---- DynamoDB `log`, one per cell. pk = ChainId, or "s#" + slot for a slot's id blocks; sk = LogSk. No GSI, LSI, TTL, or transactions. ----
/// One gap-free chain per repository and per fork network, and two per owner (user, org, enterprise): `Authz` gates
/// requests, and `Identity` holds credentials, sessions, SSO, and audit. Both live in the owner's home cell, the cell that
/// holds its id's slot. A `Mirror` chain copies an owner's `Authz` entries, seq and digest included, into each other cell
/// that hosts the owner's repositories. A new network takes a slot in its owner's home cell, and forks join it.
pub enum ChainId { Repo(RepoId), Network(NetworkId), Authz(AccountId), Identity(AccountId), Mirror(AccountId) }
pub struct Seq(u64);
/// Bumped by each `dr` promotion, so writes from the two sides of a partition never land on one item.
pub struct Epoch(u32);
pub enum LogSk { Entry(Epoch, Seq) /* "e#" + 10 digits + "#" + 20 digits */, Checkpoint(Tier) /* "c#" + tier */,
                 IdBlock(IdKind) /* "i#" + kind, under pk "s#" + slot, so it moves with the slot */ }
/// Put once with `attribute_not_exists(pk)`. That put is the commit point for every event inside.
pub struct EntryItem { pub chain: ChainId, pub epoch: Epoch, pub seq: Seq, pub prev: Digest, pub format: Format,
    pub tiers: TierSet,                                   // outside the encoded body, so an old node skips unknown metadata
    pub at: Timestamp, pub requests: SmallVec<[RequestId; 4]>,   // a retried command finds its own id in the tail
    pub body: Body }
pub enum Body { Inline(Vec<Event>) /* item <= 350 KB */, Spilled { key: S3Key, digest: Digest } }
pub struct CheckpointItem { pub tier: Tier, pub upto: Seq, pub snapshot: S3Key, pub archives: S3Key /* manifest */,

/// The only write path for chained state. Proves the chain and `deps` fresh, runs the pure `decide`, appends the
/// result at head + 1 in the current epoch, and on ConditionalCheckFailed or ReplicatedWriteConflict refolds and reruns

    fn deps(&self) -> SmallVec<[ChainId; 3]>;            // re-proven just before the put: the local Authz chain or Mirror, and the enterprise's

/// A fold that includes every entry acknowledged before `arrived`, because its tail read started after it. A tail read is a
/// strong GetItem on `e#E#(applied + 1)`, E the current promotion epoch, repeated until that key is absent. That key's
/// `attribute_not_exists` put is the commit point, and AWS documents that a strong MRSC read returns an item's latest version
/// but not that a range Query sees every item created before it (V2globaltables_HowItWorks), so Query only fetches entries
/// in bulk. Only `FoldCache::fresh` builds one, and `decide` and write authorization accept nothing else.
pub struct Fresh<'a> { view: FoldView<'a>, proven_after: Instant }
/// Graft 4, Single cells and Paired installs running on one replica and the witness: a warm fold at its last proven seq,
/// built only by `FoldCache::stale` while the cell is in stale mode, and only within the signed limit.

Invariants the structure enforces (`arena/round4/candidate-3/DESIGN.md`, Shape):

- **Acknowledgment point.** A write is acknowledged when, and only when, its entry's put returned. Bytes it names are inline or already in S3 (`DurablePack`), and `report_status` takes `&Acked`. In Paired cells the put returned after a second Region had it (`research/uptime.md#29`).
- **Gap-free, linearizable chains.** Only `commit` puts entries, and it puts seq N+1 only from a fold at N, in the current epoch, so a put of any seq at or below the head fails its condition and seq order is commit order. `apply` refuses an entry whose seq is not `applied + 1` or whose `prev` digest does not match, and alarms. Two entries at one seq in different epochs are a fork that only a `dr` partition can cause, and promotion records the losing side as stated loss. Two commands on one chain serialize, and every input on that chain is in the fold `decide` saw, so a merge cannot race a review, a rule change, a required check, or a push. There is no write skew, unlike Repeatable Read (`research/uptime.md#27`).
- **An event exists if and only if its change committed**, because the entry is both. Consumers read chains, never a separate outbox.
- **One writer per fold** (`apply`), **one owner per fact** (the chain whose events set it). Pull request state lives only in its repository chain.
- **Bounded store calls.** `trib-store` exposes GetItem, BatchGetItem, conditional PutItem and UpdateItem, DeleteItem, and single-partition Query with a limit. CI fails on a transaction API, a secondary index, or a Scan anywhere outside the operator's `Remark` and restore steps.
- **The seal is the move fence.** After `Sealed`, `commit` refuses the chain, and the source redirects to the entry's target, which serves the chain once it has caught up to that entry. A writer that decided before the seal loses its put to it. While the source still owns the slot, an `Unsealed` entry reopens the chain there and aborts its move.
- **Every multi-chain operation names its commit point, its finisher, and its abort path.** A transfer's commit point is a `Reserved` `RepoName` on the destination owner's `Authz` chain, which `decide` treats as taken. `Settings { owner }` on the repository chain, the `Live` name, and the old owner's `Alias` follow, and none can be refused. A fork's commit point is its `RepoName` on the fork owner's `Authz` chain. Whoever first touches the fork appends `ForkAdded` to the network chain, then `Genesis`, both idempotent by repository id, and if `ForkAdded` meets a sealed or taken-down network, the finisher tombstones the fork's name instead. A signup's commit point is the login claim in `global`, which carries the account record, and the owner's two chains begin from it on first touch. The `Audit` consumer finishes any chain operation that nobody touched within a minute, and a sweeper in `trib-global` that reads the `global` stream finishes untouched signups.

Dominant access patterns traced through the keys:

- *Fetch or clone.* Edge cache: token and route. Cell: `fresh` on the owner's `Authz` chain or local `Mirror` and on the repository's core tier, two strong GetItems on each chain's next key `e#E#(K + 1)`, 1 read unit each when absent [inference: 4 KB strong read unit, https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/read-write-operations.html], made by the AZ's preferred node for that chain, from which other serving nodes take the entries. If the key exists, a Query `sk > "e#E#K"` fetches the new entries in bulk, `apply` takes them, the probe repeats at the new head, and the node writes changed refs into the reftable and pulls missing packs. Then upstream `git upload-pack` runs on NVMe.
- *Push.* The same reads, S3 PUTs for a stored pack, one PutItem.
- *Issue or PR list, PR page.* `fresh(Repo, Metadata)`, SQL on the fold. A PR page adds one strong Query on `checks` pk `(repo, head)` for checks that no rule requires.
- *Authorization.* Inside the fresh repository core tier and the local `Authz` fold or mirror, plus the enterprise's for an enterprise-owned org. Only a denial that rests on a mirrored fact reads another cell: one strong read of the home `Authz` tail, coalesced per owner per node.
- *`/user/repos`, `/orgs/{o}/repos`.* The user's `Authz` fold, each org's `Authz` fold (parallel, cross-cell when needed), and a BatchGetItem of `Card` items, which lag pushes by up to 60 s.
- *Webhook.* Stream record, `Dirty` marker in the dispatcher's own Region, consumer Query from its `Cursor`, render from the entry's captured fields, `Delivery` item, POST.

### Namespace and cell placement

A **cell** is the unit above. A **front cell** is a Regional fleet of `edge` nodes with its own NLB, holding only read-through caches. A user's or org's **home cell** is the cell that holds its account id's slot. It holds the owner's `Authz` and `Identity` chains, its stars, watches, notifications, feed, and listing cards, and the networks it creates.

Invariants and decisions:

- **One namespace, one key.** Users, orgs, and enterprises share one login item per `LoginKey` in `global`. Logins are ASCII, so lowercasing is exact. An enterprise's one `Shortcode` item covers all its managed users ("Public service concerns").
- **Claims are `global` items, and repository names are `Authz` entries.** Creating an account or org, renaming a login, adding an SSH key, verifying an email, creating an app, and flipping a slot each make one conditional write in `global`, which decides every race. Creating, renaming, transferring, or deleting a repository is a `RepoName` entry on the owner's `Authz` chain, whose `decide` rejects a taken or reserved key with 422 `already_exists` (`research/wire-census.md#20`). A miss in an edge cache reads the local replica, then strongly, before it says "no", so a new login or token resolves at once at every edge (`arena/round4/candidate-3/DESIGN.md`, Shape).
- **`NameEpoch` catches a stale route where it is served.** The edge caches `(owner, repo) -> (cell, repo, epoch)` from the home cell's answer and sends the owner's login version and the epoch. The serving cell checks both inside the fresh folds it already reads, and a mismatch makes the edge re-resolve, so no rename touches more than a few entries whatever the owner's repository count.
- **Renames.** A repository rename leaves `Alias` at the old key, which the API answers with 301 and git with 200 (`research/wire-census.md#23`). An owner rename leaves `Former { account }` on the old login item, because GitHub frees an old username and keeps old repository links working (https://docs.github.com/en/account-and-profile/reference/username-reference). A new claim of the old login overwrites `Former` at a higher `v`, which ends the redirect and fails every cached route that carries the old version.
- **Retirement.** When an owner renames or is deleted, each public repository with more than 100 clones or Actions uses in the prior week, or with a Marketplace action, gets a `Retired` item under the old login, written before the old login can be claimed, and later claims of that pair fail with GitHub's text (same page). The owner's home cell reads the counts from the cards it holds.
- **Transfers** first append a `Reserved` `RepoName` on the new owner's `Authz` chain, which is the commit point, then `Settings { owner }` on the repository chain, the `Live` name, and an `Alias` on the old owner's chain, and bump the epoch. The network and its slot do not move, so a transfer that would move a resident network's owner outside its residency gets 422 ("Known deviations from GitHub"). A transfer between owners whose home cells differ gets 422 until Milestone 7.
- **Ids route by arithmetic.** A repository-scoped id names its slot and the slot map names the cell, so `/repositories/{id}`, node ids, and check-run ids route without a name lookup. A slot allows 2^37 ids per kind, ample against a live GitHub check-run id near 1.2e11 (`research/wire-census.md#28`). Issue numbers stay per repository.
- **The network is the unit of placement, the slot the unit of movement.** Every fork joins its network's slot, so a pull request from any fork touches chains in one cell. A slot above 20% of a cell's limits moves to a dedicated cell. A network is never split, so the largest network must fit one cell.
- **The cell is the blast radius.** A bad deploy, a hot network, or a store problem that Tributary causes stops at the cell (`research/uptime.md#8`). Three things are wider. A home cell that is down blocks new installation tokens, stars, notifications, feeds, and cross-cell listings for the accounts homed there, service-wide. After 30 s without that home cell's heartbeat, each hosting cell fails closed the writes whose decision reads one of those owners' mirrored facts (installations, teams, org roles, rulesets), in that cell only, while owner and collaborator checks and reads continue, and reads close at a signed limit. A stopped `Mirror` consumer or event path only delays grants, because leases run from the heartbeat, and `Mirror` code ships in the last wave. A failed local `global` replica leaves that Region's writes on cached token entries for up to 60 s, after which edges read the nearest other replica, and `global` without quorum stops claims service-wide. A bad deploy of `trib-global` can write wrong claims service-wide, so claim code ships in the last wave ("Failure modes").
- **Front cells are the router, built as cells** (`research/uptime.md#8`-`#10`). Each Region with cells runs at least three front cells, each with its own NLB and Auto Scaling group. Route 53 latency records return multivalue answers across a Region's front cells, with health checks that send a synthetic routed request through each one (data plane, `#15`). An edge holds only the read-through cache of `global` and the route cache, and it reloads both on restart from `global` and the cells, bounded by the per-node miss budget.
- **Cells accept only fronts and peers.** Each cell exposes an internal NLB per Region through PrivateLink to front cells and peer cells, with mTLS, and accepts only front-signed `Principal` assertions that name one target cell and live 10 s. Fronts probe each cell Region's deep endpoint `/_t/health/region`, which appends to a canary chain and reads a canary S3 object, and forward only to healthy Regions.
- **SSH routes like github.com.** Fronts hold one service host key set, authenticate the client key by its service-wide unique fingerprint in `global`, read the repository path from the exec command, and route it like HTTPS (`research/wire-census.md#45`).
- **GraphQL** goes straight to the target cell when every root field resolves to one cell. Only queries that span cells enter at the caller's home cell, which delegates subtrees per cell in batches under assertions the front signs for each cell, and returns partial data with `errors` paths when a cell fails.

### Repository chains and packs

**Push, up to 10,000 refs atomically.** Receive-pack quarantines and indexes the pack, checks connectivity against the fresh core tier, and places it: at most 16 KiB inline in the entry, else S3. `commit` runs `Push::decide`: each update's expected old value must equal the fold (else `Stale`, git's `fetch first`), rules come from the fold's `Rule` rows and the owner's rulesets, `AllOrNothing` rejects everything on one failure, and `PerRef` marks only that ref. A body above 350 KB spills to S3 (2 of 3 buckets in Paired) before the put, which keeps items under DynamoDB's 400 KB (`research/dynamodb.md#7`). Admission caps a push at 10,000 refs [guess at GitHub's own limit], and a push over 1,000 refs takes the chain's put alone instead of sharing a batch. Each chain has a preferred node per Region and a preferred Region, both by rendezvous hash, and while both Regions are healthy the other Region forwards a busy chain's commands there, which avoids `ReplicatedWriteConflictException` (`research/dynamodb.md#18`). Correctness never depends on that preference: any node in either Region may put (`arena/round4/candidate-3/DESIGN.md`, "Commit and read paths").

Invariants the structure enforces:

- **Acknowledgment point.** At the put, the pack bytes are inside the entry or in S3 Standard in at least three AZs, and in a Paired cell in two Regions (`research/git-storage.md#54`). `Acked` and `DurablePack` make the order a type error to get wrong.
- **Linearizable per chain, atomic per push.** A multi-ref push is one entry, so readers see all of it or none of it, and pushes to one repository serialize on its chain with group commit, about GitHub's 2026 per-reference ordering obtained from a chain instead of a quorum protocol (`research/git-storage.md#6`).
- **Reachability and retention.** Every ref target is reachable from the network's live packs, because the entry names its pack. Compaction follows git's cruft-pack model, never drops an object, places its packs first, and then appends `Compacted`, so a push that lands during compaction stays live. GC deletes only objects unreachable from every member chain's fresh fold for 14 days, at a capped rate, and bucket versioning keeps deleted objects 35 days. A deleted repository's fold keeps its refs until `retain_until`, so GC keeps its objects that long. A sweeper deletes pack and spill objects that no entry names after 24 hours, which removes objects placed for a put that failed. The bucket policy denies any `PutObject` without `If-None-Match` on packs, spills, snapshots, and archives, so even a buggy release cannot overwrite one (`research/uptime.md#31`).
- **Caches are disposable.** A cache node holds a bare repository per network on NVMe with `--ref-format=reftable`, packs copied from S3 or inline entries, and refs written from the core tier with `git update-ref --stdin`. Upstream `git upload-pack` serves fetches from it. Losing it costs a re-download.
- **Bounded stale fetches in Single cells** (`arena/round4/SYNTHESIS.md`, graft 4, from round 4's candidate 1 and the previous design). A Single cell enters stale mode cell-wide on sustained failure, three failed tail reads within 10 s or a signed flag, and never on latency alone, so a slow tail read stays a slow fresh read. In stale mode, fetches and reads take `ReadView::Stale` from warm folds at their last proven seq, for at most a signed per-cell limit (default 2 hours), and writes get 503, because `decide` and write authorization take only `Fresh`, so durability is unchanged. Read authorization uses the warm `Authz` fold, so revocations made before the outage hold and none can be made during it [inference]. Edges keep expired positive token and session entries for the signed limit, and every node snapshots its positive token and session entries to its Region's control bucket every minute, so stale-mode authentication works on any node behind the NLB, including one replaced during the outage. A stale read may miss a write acknowledged in the seconds before the outage ("Known deviations from GitHub"). A fallback mode rots untested (`research/uptime.md#5`), so a weekly drill blackholes a canary install's table endpoint under live traffic ("Drills"). Paired cells have no stale mode while both replica Regions serve. A Paired install running on one replica and the witness may enter it, because one more Region outage would then stop reads as well as writes.
- **Repository repair from the chain** (graft 2, from round 4's candidate 1). `RepoRestore` first brings back any noncurrent pack versions that the named refs' targets at `to` need, then appends one `RestoredTo { to, refs }` entry, whose `decide` checks that each target is reachable from live or cruft packs. `apply` returns those refs to their targets at `to` and leaves every other ref and the metadata tier alone, and the `Refs`-shaped difference emits `push` events. A whole-fold reset is the separate `RepoReset` intent, whose `ResetTo { to }` entry makes both tiers their state at `to` by loading the newest snapshot at or below `to` and replaying to it. Entries between stay in the chain as history. Deleting a repository or an org appends `Deleted { retain_until }`, 90 days by default, and turns its name entry `Deleted`, so undelete is chain-local. Any `to` within the last 35 days restores, the same window as PITR, because GC keeps unreachable objects 14 days and buckets keep noncurrent versions 35 days [inference]. No repair of a repository or an org needs a table restore.
- **Cross-Region RPO, stated per class.** Paired cells: RPO zero for every acknowledged entry and pack. A `worker` consumer copies each pack to its missing Regional bucket within seconds. Single cells with `dr`: entries reach the MREC replica in seconds (`research/uptime.md#30`) and stored packs within S3 replication, up to 15 minutes [unverified RTC SLA], and promotion truncates each chain at its first gap or first missing pack, recording the cut entries as stated loss, and writes later entries in a new epoch. Single cells without `dr`: the newest cross-Region backup copy [unverified for DynamoDB]. Single recovery launches capacity, so Single cells do not meet fact 9.

Dominant access patterns: a fetch is two strong GetItems that usually find no item; a push is the same reads, at most three S3 PUTs, and one PutItem; `GET /repos/{o}/{r}/branches/{b}` and GraphQL `ref` read the fresh core tier with no git process; maintenance runs one `maint` item per network, scheduled by pack count and bytes, geometric factor 2, a full repack with bitmaps weekly above 1 GiB; per-repository admission defaults to 200 pushes a second, raisable to 800 [guess].

Decisions:

- **`Authz` chains own the authorization graph, `Identity` chains own credentials, `global` owns what an edge resolves.** The `Authz` chain in the home cell holds memberships, teams, repository grants, repository names, org policies (base permission, SSO enforcement, residency, custom roles, rulesets, webhooks, Actions secrets as ciphertext), apps' installations with their repository selections, and the installation `not_before`. The `Identity` chain holds the account record, password hashes, second factors, sessions, SSO authorizations, and the identity audit log, so sign-in churn never touches what gates requests, and one partition no longer carries both an org's authorization and its sign-ins. `global` holds what any edge must resolve without a cell: logins, token hashes with scopes and expiry, SSH fingerprints, email digests, app keys, installation ids, verifying keys, and the slot map (`arena/round4/candidate-3/DESIGN.md`, "Changes to DESIGN.md").
- **Hosting cells authorize from a local mirror.** The `Mirror` consumer in the home cell copies each `Authz` entry, seq and digest included, into a `Mirror` chain in every cell that hosts the owner's repositories, a set derived from the slot map, so no allow reads another cell. Entries reach the other hosting cells within seconds [inference]. Separately, the home cell writes a timed heartbeat every second [guess] per home and hosting cell pair to a `Heartbeat` item in the hosting cell's `inbox` over PrivateLink, outside Streams and the event path. Each heartbeat names, for each owner the hosting cell mirrors, the seq of that owner's newest revocation-class entry, and the hosting cell's mirror lease for that owner runs 30 s from the newest heartbeat whose named seq its mirror has applied. The lease covers only decisions that read a mirrored fact (installations, teams, org roles, rulesets). Owner and collaborator checks read the repository chain and never wait on it, so most user-owned forks sit outside its blast radius. A cell whose lease has lapsed fails those writes closed for that owner in that cell only, keeps reads on the last applied entry, and closes those reads after a signed limit (default 15 minutes [guess]). A revocation-class `Authz` entry (member, team, grant, installation, and policy removals) goes from its writer straight to each hosting cell's ingress as well as through the consumer [inference], and its 204 waits until every hosting cell has applied it, or at most 30 s, the lease, because a hosting cell that has not applied it by then has fenced itself. A denial that rests on a mirrored fact makes one strong read of the home `Authz` tail, coalesced per owner per node, so a grant acknowledged before the request is never refused. A stopped `Mirror` consumer or event path therefore delays grants and never fails writes closed, and `Mirror` code ships in the last wave. Enterprise policy is the enterprise's `Authz` chain, mirrored the same way, a third dependency for enterprise-owned orgs.
- **Authenticate at the front, authorize in the cell.** Sign-in routes to the home cell, which checks the password hash and second factor in the `Identity` fold, appends a session entry there, and signs a session cookie checked at the front against `sessions_not_before`. A traveler on another continent pays one forward to the home cell at sign-in only.
- **Revocation.** Membership, team, grant, ruleset, and installation changes are `Authz` entries, and visibility and collaborator changes are repository entries, so they bind every request that authorizes after the acknowledgment, plus one put round trip for a write already deciding, and at most the coalescing window (20 ms, or under 1 s for an owner served by 1,000 nodes) for reads. Token revocation, account suspension, and sign-out-everywhere change `global` items. Graft 3 (`arena/round4/SYNTHESIS.md`, from round 4's candidate 2) re-reads a token for any write-class request whose cached entry is older than 5 s. The re-read is an eventually consistent read of the local `global` replica from its own per-node budget, so it never waits on another continent, and an alarm fires when replication lag passes 2 s. Token revocation binds writes within 5 s while lag stays under that alarm, and reads within the 60 s cache. App uninstall bumps `not_before` on the `Authz` chain, so its stateless tokens fail at once.
- **Stored tokens** (`ghp_`, `github_pat_`, `gho_`, `ghu_`, `ghr_`). Creating a PAT or finishing an OAuth flow puts the hash in `global` conditionally, and a first use at any edge misses, reads strongly, and finds it. In managed that put waits one cross-continent round trip [guess: 95 to 225 ms]. A revoked token stays as `revoked` for 30 days, so it gets 401 from cache instead of a strong read.
- **Installation tokens are stateless**, matching github.com since 2026-10-02 (`research/wire-census.md#30`), and signed by the installation owner's home cell, so a compromised cell mints only for its own accounts and slots. Signing keys are Ed25519, wrapped by the cell's KMS multi-Region key, each replica of which works on its own in its Region (https://docs.aws.amazon.com/kms/latest/developerguide/multi-region-keys-overview.html, `review/round4-byoc-walk.md` finding 2), and kept on local disk, so minting and verification need neither KMS nor DynamoDB at request time. Tokens are about 400 characters and match `ghs_[A-Za-z0-9\.\-_]{36,}`, which Renovate accepts (`research/clients.md#38`). `authorize` also intersects the claims with the installation's current selection in the `Authz` fold or mirror, and each job's `GITHUB_TOKEN` jti is recorded on the job item and denied when the job ends.
- **SSO** attaches to orgs and enterprises, with SCIM provisioning at T1. The SAML or OIDC endpoint appends an `Sso` entry to the member's `Identity` chain and records the org in the token item's `sso_orgs` or in the session, and `authorize` checks the principal's `sso_orgs` when the owner's `Authz` policy enforces SSO. Break-glass owners are local accounts with hardware keys and no IdP dependency (`research/uptime.md` implication 25).
- **Instance sign-in in installs.** An install chooses built-in accounts, SAML, or OIDC at launch, with LDAP at T1 (`InstanceAuth`). A `SiteAdmin` actor bypasses org and repository permissions, and every bypass is audited in the same entry as the action. `tributary admin bootstrap` runs on a node through SSM, creates the first site admin, and prints a one-time sign-in link that lives 15 minutes [guess]. Installs send email through SES with production access or customer SMTP, which the preflight checks.
- **OAuth**: authorization code and device flow on the bare host at `/login/oauth/*` and `/login/device/code`. First-party apps are seeded once in `global` with GHES-era callbacks (`http://localhost/` for gh and GCM, `http://127.0.0.1/` also accepted, `x-github-desktop-auth://` for Desktop [unverified exact path]) and treated as public clients, so the embedded secrets are accepted and ignored (`research/clients.md#44`-`#47`).

Access patterns: every HTTPS request does one edge cache lookup by token hash, one more local `global` read per token per node per 5 s for writes, and an assertion check in the cell. `global` sees writes only at the rate of signups, token creation, renames, and slot flips, and reads only on misses and write re-checks, both bounded per node and kept below each replica's maximum read throughput, so its load follows fleet size and no TTL change can move load onto it (`research/uptime.md#47`).

### Issues and pull requests

**Same-repository merge.** The plan reads the fresh fold (PR, head ref, base ref, reviews, rule, required checks), then asks the git role for `merge-tree`, `commit-tree`, and the check that the result equals base plus the PR's own diff (`research/uptime.md#49`, implication 19). `Merge::decide` re-checks on the fold it is given: head moved gives `Head branch was modified. Review and try the merge again.`, base moved gives `Base branch was modified. Review and try the merge again.`, and a new review, rule, or required conclusion gives the protection error. It emits one `Merged` entry, with head-branch deletion in `also`. A 409 is never retried into success, because a rerun of `decide` re-runs protection (`arena/round4/candidate-3/DESIGN.md`, "Commit and read paths").

**Required checks are race-free and bounded** (`arena/round4/SYNTHESIS.md`, graft 1, from round 4's candidate 2). A conclusion for a check that a branch rule requires is also a `RequiredCheck` entry on the repository chain, so a merge's `decide` sees every required conclusion committed before its put, and one committed after it is a check of a merged pull request. Commit statuses that a rule requires take the same path, so a Jenkins-style status cannot race a merge either. Only conclusions for SHAs that are heads of open pull requests, merge-queue refs, or protected branch tips are appended, and `apply` prunes the row when the pull request closes or its head moves, so the core tier stays small. Other check runs and statuses stay in `checks` only. If a rule change newly requires a check whose conclusion already sits in `checks`, the merge planner appends that conclusion as a `RequiredCheck` entry before it plans, idempotent by run and version, so a merge never waits on a check that already ran [inference: GitHub counts existing runs]. Pinning check versions at plan time instead would reopen the race between a failing required check and a merge.

**Fork merge.** The head is the fork's chain, in the same network and cell. The plan proves it fresh and pins the head SHA, and GitHub's `sha` parameter, when given, must match. The `Merged` entry goes on the base chain alone. A push to the fork in the one put round trip between plan and commit is not merged, and the pull request closes merged at the reviewed head, which is a valid ordering of the merge before that push (`review/round4-judge.md`, Correctness).

**Merge queue.** `Queue` events on the base chain record entry, group building, and temporary `gh-readonly-queue/*` refs. When a group's required checks pass, one entry carries a `Merged` per pull request and the base fast-forward, each tree diff verified separately, so a group lands whole or not at all.

**Branch-rule changes.** A repository rule is a `Rule` entry on the same chain as pushes, so a push decided before it loses its put and re-decides under it. An org ruleset is an `Authz` entry, and every push re-proves the local `Authz` fold or mirror just before its put.

Can pull request state diverge from refs? No state that decides anything. An open PR's head is the head branch's ref in the fork's fresh core tier, and the merge sets the base ref and `Merged { final_head }` in one entry. `refs/pull/N/head` and `refs/pull/N/merge` are derived refs that the `PrSync` consumer moves within seconds in a coalesced bot `Refs` entry, below user entries in the batch order. Issues and pull requests share one number space. Comments, reviews, and timeline events are entries, and review comments anchor to `(commit, path, line)` and re-anchor lazily on read. Comments and reactions share the chain under a per-repository cap of 50 entries a second, so a viral issue cannot starve pushes, and stars and check runs that no rule requires stay off the chain.

### Folds

```rust
/// Graft 5. Each repository chain has two folds. `Authz`, `Identity`, `Mirror`, and network chains have only a core tier.
pub enum Tier { Core, Metadata }
/// Core: ref, rule, collaborator, deploy_key, pull_head(n, head, base, state), review_verdict(n, reviewer, state, commit),
/// required_check(sha, name, conclusion) pruned when its pull request closes or its head moves, and settings. Metadata: issue,
/// issue_label, issue_assignee, issue_mention, pull, review bodies, comment, timeline, reaction. The entry's `tiers` tag says
/// which tiers must decode it.
pub fn tier_of(e: &RepoEvent) -> TierSet;   // Merged, PrOpened, and Review touch both tiers; Refs only Core; Comment only Metadata
/// One SQLite file per chain and tier on NVMe, plus a bare cache repository with a reftable per network. Derived only.
pub struct Fold { pub chain: ChainId, pub tier: Tier, pub applied: Seq, pub schema: FoldSchema, db: rusqlite::Connection }
/// The only writer. Refuses an entry whose seq is not applied + 1 or whose `prev` digest is wrong. A tier applies the
/// events it owns and advances `applied` past every entry, so both tiers check the same digest chain.
pub fn apply(fold: &mut Fold, e: &EntryItem) -> Result<(), FoldError>;
impl FoldCache {
    /// Single flight per chain per node: joins an in-flight tail read only if that read started after `arrived`. Only the
    /// AZ's preferred node tail-reads a chain. Another node fetches the entries from it under a single flight that started
    /// after its own request arrived, and falls back to its own strong read if that is slow. Loads the tier's newest
    /// snapshot if cold. A Core request, a merge included, never waits for a Metadata load.
    pub async fn fresh(&self, chain: ChainId, tier: Tier, arrived: Instant) -> Result<Fresh<'_>, StoreError>;
    /// Graft 4, Single cells and Paired installs on one replica and the witness, in stale mode and within the signed limit.
    pub fn stale(&self, chain: ChainId, tier: Tier) -> Result<Stale<'_>, StaleError>;
}
/// Every 10,000 entries or 10 minutes, and once for each fold-schema refold, the chain's preferred node writes a snapshot
/// per tier to S3 and a checkpoint item, and other nodes load that snapshot instead of folding the chain themselves.
/// Entries older than 30 days move to immutable `Archive` objects, so every fold can be rebuilt from genesis.
pub async fn checkpoint(f: &Fold, store: &Store) -> Result<CheckpointItem, FoldError>;
/// Refolds sampled chains from genesis on each release and daily, compares `fold_digest`, and alarms on any mismatch.
pub async fn fold_audit(sample: &[ChainId]) -> Result<AuditReport, FoldError>;
```

**The two tiers answer the fold-engine flaw.** The judge's top flaw in this foundation was that every repository-scoped list, PR page, and authorization needed a warm SQLite fold, so after a node loss, an AZ loss, or a new SQLite schema, a giant repository's git and authorization would wait on a 2 GB snapshot load or a refold storm (`review/round4-judge.md`, "Most serious flaw"). Graft 5 splits the fold. The core tier holds what git, merges, and `authorize` read: refs, rules, collaborators, deploy keys, pull request heads, review verdicts (reviewer, state, and commit), required checks, and settings. It is small, because it has one row per ref, rule, collaborator, open pull request, and current verdict [inference: tens of MB for the largest repositories, measured in Milestone 0]. Its snapshot loads first and alone gates fetches, pushes, merges, and authorization. The metadata tier holds issues, comments, review bodies, labels, and the timeline, loads lazily from its own snapshot the first time a list or PR page needs it, and refolds in the background when its schema changes, while the old schema's file keeps serving until the new one catches up [inference]. So a node loss costs git and merges one small snapshot load, an AZ loss costs lists a lazy reload on the surviving nodes, and a metadata schema release never touches git. Milestone 0 measures the core-tier cold load separately from the metadata gate, and merge p99 on a cold node after an AZ drop.

**List endpoints.** The metadata tier has tables `issue(number, kind, state, author, milestone, created, updated, comments, locked)`, `issue_label`, `issue_assignee`, `issue_mention`, `pull(number, head, base, draft, ...)`, `review`, `comment`, each with indexes per GitHub filter. `GET /repos/{o}/{r}/issues` maps `milestone`, `state`, `assignee`, `creator`, `mentioned`, `labels` (all must match), `since`, `sort` (created, updated, comments), and `direction` to one indexed SQLite query. Pulls add `head`, `base`, and `sort=popularity|long-running`. GraphQL `filterBy` and `orderBy` use the same queries with keyset cursors. Cross-repository lists (`/issues`, `/user/repos`, notifications) read `inbox` and `Authz` folds and lag by seconds. `/search/*` and `gh pr status` read OpenSearch and lag by seconds, as GitHub's search does [inference] (`arena/round4/candidate-3/DESIGN.md`, "List endpoints"). When OpenSearch is off, as in the small-install profile ("Install operations"), the metadata tier also holds SQLite FTS5 tables over issue and pull request titles, bodies, and comments, which `apply` updates with the other metadata tables, and issue and pull request search reads them with no lag behind the fold.

**Serving set and warmth.** Each chain stays warm on one node per AZ, chosen by rendezvous hash, and that preferred node is the only node in its AZ that tail-reads the chain. The serving set widens to at most 32 nodes per chain under load, and the others take new entries from their AZ's preferred node, so a chain's strong reads do not grow with the serving set. A tail read costs one unit per next-key probe plus its fetched bytes in 4 KB units, so the serving cap and the inline rule count readers times bytes: the set stops widening, and the chain stops inlining packs, before projected tail-read units, fallback reads included, pass 30% of the partition's 3,000 a second [guess at the threshold] ("Scale"). A huge owner's read-class proofs coalesce over `max(20 ms, nodes / 1,000 s)`, while writes always re-prove. Per-fold disk caps and per-chain CPU cgroups keep one giant aggregate from starving a node.

**Schema change.** No table schema exists to migrate. A fold schema change ships in a release that reads both schemas and refolds lazily per aggregate, canary cell first, with abort on fold lag or list p99. Each chain's preferred node builds the refold once and publishes it as a snapshot that other nodes load. The core tier reads both schemas until each chain's refold snapshot is published, so git never waits on a core refold. Snapshots carry their release and fold digest, and a release marked bad has its snapshots ignored and refolded from the archive.

    async fn poll(&self, session: RunnerSessionId, wait: Duration) -> Option<RunnerMessage>;
    async fn acquire(&self, runner: RunnerId, job: JobId) -> Result<AgentJobRequestMessage, AcquireError>;
    async fn renew(&self, job: JobId) -> Result<Timestamp, RenewError>;

```

Invariants: a job has one runner at a time, because `Queued -> Assigned` is a conditional update on the job item's version. A lease that expires (no `renewjob` for 10 minutes) moves the job to `Completed { Failure }` with GitHub's infrastructure-failure category, or back to `Queued` if it was never acquired. Job items write only on state changes, and the lease is rewritten only when less than 5 minutes remain, so a 2-hour job writes it about 24 times, not 120. Run creation is idempotent on `(chain, seq, workflow path)`: a `Creating` run item, the job items, then the flip to `Queued`, each conditional. `completejob` writes the job item, the check-run conclusion in `checks`, and, through `record_check`, a `RequiredCheck` entry when a rule requires that check, each keyed by job attempt. An `actions` impairment stops job dispatch, and merges that require checks wait, while git, other merges, and the API keep serving, because `actions` has its own throughput cap.

Access patterns: each broker node keeps, per runner scope, an in-memory table of the distinct label sets of queued jobs and their hashes, refreshed by the queue notice and a 2 s poll. A runner's poll tests each queued set for being a subset of the runner's labels in memory, then queries the oldest queued jobs on the 16 queue shards for matching hashes only. Labels are lowercased at registration and job creation [unverified that GitHub matches labels case-insensitively]. Busy check partitions (one SHA with a 256-job matrix) write about 13 units a second, and suites shard 16 ways above 256 runs.

### Event fan-out

```rust

- **Events reach consumers through markers, not the stream.** In each replica Region one dispatcher reads that replica's stream and raises markers keyed by its own Region. MRSC streams are identical on every replica (`research/dynamodb.md#15`), so both Regions' dispatchers run at once and either alone suffices, and because no two Regions write one marker, MRSC raises no `ReplicatedWriteConflictException` on the normal path (`#18`). Consumers read both Regions' marker partitions, and only the consumer's lease holder writes its cursor. Markers last until their consumer finishes, so a consumer outage of any length loses nothing. The 24-hour stream retention (`#13`) binds only the dispatchers. Past 24 hours, the operator's `Remark { since }` command scans `log` once and raises markers for every chain with newer entries, and a weekly drill runs it (`arena/round4/candidate-3/DESIGN.md`, Shape).
- **Poll interval.** The dispatcher's poll interval per stream shard is signed config. The default polls twice a second, and the small-install profile polls once a second, which halves its Streams reads, so its webhooks and Actions triggers can fire up to about half a second later ("Install operations").
- **Order and identity.** Events reach each consumer in chain order, which is commit order, so a webhook for a repository never arrives before an earlier one from the same chain. The `X-GitHub-Delivery` GUID derives from `(restore_epoch, chain, seq, index, hook)`, so a redelivery after a crash keeps its GUID and a restore never reuses one (`research/wire-census.md#36`).
- **Isolation.** Each consumer has its own markers and cursors, so a stuck consumer holds only its own work. A handler that fails 10 times on one entry parks that chain for that consumer, which the status document lists and a `ReplayParked` intent replays. Oldest marker age and parked chains per consumer are SLO signals and deploy gates.
- **Webhooks.** The consumer renders each payload from the entry's captured fields, so a delayed `pull_request.synchronize` still shows its own head SHA, writes `Delivery` items and payloads to S3, and returns. Delivery workers POST with a 10 s deadline and shuffle-sharded concurrency per hook owner and make one automatic attempt, as GitHub does (`research/wire-census.md#37`). A hook that opts in gets automatic retries with backoff for 3 days under the same GUID ("Known deviations from GitHub").
- **Other consumers.** `PrSync` writes bot `Refs` entries. `ActionsTrigger` writes runs, jobs, and check items. `CacheHint` warms peer-Region caches. `Notify`, `Cards`, and `Search` feed home cells and the search tier ("Cross-cell features"). An install with no search domain does not deploy `Search`, because its FTS5 tables live in the folds ("Folds"). `Mirror` copies each `Authz` entry to every hosting cell's `Mirror` chain, and mirror leases run from the home cell's heartbeat, not from this consumer ("Identity and tokens"). `Audit` finishes multi-chain operations that nobody touched within a minute. A consumer whose target is unreachable pauses without counting attempts.

### Cross-cell features

```rust
/// Sent by a source cell's consumer to a destination cell's ingress over PrivateLink, batched, idempotent by (source chain,
/// seq, index). The source keeps a `Cursor` per consumer, chain, and destination cell, so a destination that is down holds
/// back only its own deliveries.
pub enum HomeDelivery {
    Star { user: UserId, repo: RepoId, on: bool, version: u64 }, Watch { user: UserId, repo: RepoId, level: WatchLevel, version: u64 },
    Notify { user: UserId, thread: ThreadRef, reason: NotifyReason, at: Timestamp }, Feed { account: AccountId, item: FeedItem },
    Card(RepoCard), CardSubscribe { repo: RepoId, on: bool },
    OfferJob { org: OrgId, job: JobId, labels: LabelSet },   // an org runner's job from another cell ("Actions")
    Mirror(Box<EntryItem>),                                  // an `Authz` entry for a hosting cell's `Mirror` chain
}
/// Listing fields owned by the repository's cell, sent only to home cells that list the repository, at most once per 60 s.
pub struct RepoCard { pub repo: RepoId, pub version: u64, pub pushed_at: Timestamp, pub updated_at: Timestamp,
    pub stargazers: u32, pub forks: u32, pub open_issues: u32, pub language: Option<Lang>, pub description: Box<str>,
    pub default_branch: RefName, pub archived: bool, pub clones_7d: u32, pub actions_7d: u32, pub marketplace: bool }
```

- **Every account's home cell** holds its starred list, watch subscriptions, notifications, activity feed, and the cards of repositories it lists, as `inbox` items. Destinations apply last writer wins by `version`, so duplicates and reordering change nothing.
- **Notifications are never dropped.** The source cell's `Notify` consumer computes recipients from its own folds, groups them by home cell from the edge cache over `global`, and delivers. A destination that is down holds back only its own deliveries, through its own cursors, kept with no time limit, and drains in order when it returns, while every other destination keeps receiving. Stars, watches, feeds, and cards can also be rebuilt by a resync from source chains.
- **Cards make listings local.** `/user/repos`, `/users/{u}/repos`, `/orgs/{o}/repos`, `/user/starred`, and `viewer.repositories` route to the account's home cell, which answers from `Authz` folds and the cards it holds. A grant, membership, or star change that gives an account a reason to list a repository makes its home cell send `CardSubscribe`. Fields that change on every push lag by up to 60 s.
- **Search** is a sharded OpenSearch tier per residency domain (US, EU, APAC) fed by every cell's `Search` consumer. A query filters by public visibility or by the viewer's reach from `Authz` folds. A domain that misses its deadline yields `incomplete_results: true`, and failure stays on search endpoints (`research/uptime.md#49`).
- **Synchronous cross-cell calls** are three: GraphQL queries that span cells, org-runner job claims ("Actions"), and the strong read of the home `Authz` tail behind a denial that rests on a mirrored fact. Every allow reads the local `Authz` fold or mirror, so a fork in another owner's network never reads its owner's home cell on an allowed request.

### Scale

A chain's tail lives in one partition, which delivers at most 1,000 write and 3,000 read units a second (`research/dynamodb.md#8`) [inference that monotonically increasing sort keys stay in one partition]. Numbers are from `arena/round4/candidate-3/DESIGN.md`, "Scale", and are guesses until Milestone 0.

- *Writes to one repository:* at about 1 KB per non-inline push entry [guess], a chain carries about 1,000 entries a second, bytes-bound. Unbatched it carries 1 / L, about 50 a second at L = 20 ms [guess], so group commit reaches the bytes bound. A chain stops inlining packs above 30% of its write budget or of its tail-read budget counted as readers times bytes ("Folds"). GitHub's Spokes took about a third of a second per update under a repository lock (`research/git-storage.md#4`).
- *Merges:* each merge on one base branch needs the previous one's result, so about 1 / (plan + put), roughly 4 a second at a 200 ms plan [guess]; merge-queue groups multiply that by group size. Journey 1 needs 10 a minute.
- *Clones:* freshness costs one strong read per AZ's preferred node per read round trip, so 3 readers per replica Region whatever the serving set, and each read costs its returned bytes in 4 KB units. At 1,000 entries a second of 1 KB and a 20 ms round trip, each reader returns about 20 KB 50 times a second, so about 750 read units a second per replica against the 3,000 limit [inference]. Inline packs and spilled bodies raise the bytes, which is why the serving cap and the inline rule count them. 32 nodes at about 300 MB/s [guess] serve about 120 shallow 80 MB clones a second, and full clones go to S3 bundles through bundle-uri (`research/git-storage.md#42`).
- *Fleet:* 3.35 billion pushes a month (`research/git-storage.md#5`) is 1,275 a second on average and about 3,800 at a 3 times peak [guess]. At about 16 write units per push including consumers (`arena/round4/candidate-3/cost.py`), that is about 61,000 units a second, 122,000 replicated, which at 200 cells is about 610 a second per cell against the default 40,000 per table (`research/dynamodb.md#9`). Nothing is serialized fleet-wide: `global` sees claims, token writes, and slot flips only.

| Hot key | Load | Limit | Spread |
| --- | --- | --- | --- |
| `log` repository chain | Pushes, merges, issues, comments, required checks | 1,000 WCU/s, 3,000 RCU/s per partition | Group commit, preferred writer Region per chain, one tail reader per AZ, a serving cap and inline rule counted in readers times bytes, per-repository and comment caps, stars and other checks off-chain |
| `log` `Authz` chain or mirror of a huge org | SCIM bursts; every authorization in its repositories in that cell | Same | Sign-in and audit churn sit on `Identity`; each hosting cell reads its own `Mirror` partition; writes batch; read proofs and verify-on-deny reads of the home tail coalesce per owner per node |
| `checks` (repo, SHA) | Matrix check updates | Same | 16-way suite sharding above 256 runs |
| `actions` queue index | Queued jobs per runner scope | Same | 16 shards per (scope, label set) |
| `inbox` dirty buckets | One write per record per consumer per dispatcher Region | Same | 256 buckets per consumer by chain hash, in a separate partition per dispatcher Region |
| `inbox` stars, notifications | Viral repository or thread | Same | 16 star shards; per-user partitions with a per-thread cap |
| `global` login and token items | Edge misses and write re-checks | Same | Hash keys; 60 s positive cache; re-checks are local eventually consistent reads, coalesced per token per node; per-node miss and re-check budgets below each replica's maximum |
| S3 pack prefix | Pushes to one network | 3,500 PUT/s per prefix (`research/git-storage.md#54`) | Hashed prefix per network |

### Service and crate map

Deployables:

- **`tributary`**, one Rust binary with roles selected by config. On front cells, `edge` terminates TLS (rustls, SNI) and SSH (russh, one service host key set), runs `authenticate` and `route` over its caches, enforces rate limits, signs the `Principal` assertion, and serves the web app's static assets. In cells, `ingress` verifies assertions, forwards to role nodes, and serves `/_t/health/region`. `api` serves REST under `/api/v3`, GraphQL at `/api/graphql`, OAuth, uploads, LFS batch, sign-in, and claims through `trib-global`. `git` owns the NVMe folds and caches, receive-pack, upload-pack spawning, merge plans, archives, and diffs. `actions` serves registration, broker, run service, launch, results, cache, artifacts, and OIDC. `worker` runs the dispatchers, consumers, webhook delivery, compaction, GC, the orphan sweeper, checkpoints, the fold audit, and the `operator` role ("Install operations"). Small installs run every role on every node. Managed front cells run `edge` alone, and managed cells run `ingress+api`, `git`, `actions`, and `worker` as separate Auto Scaling groups.
- **Upstream git**, pinned (2.56 at design time), shipped inside the node image, so a git change is an image roll. It does index-pack, upload-pack, pack-objects, repack, merge-tree, archive, and fsck (`research/git-storage.md` implication 8).
- **`tributary-web`**, the React app, built into the release and embedded in the `edge` role.
- **`tributary-runner-host`**, managed and optional BYOC only. It runs unmodified `actions/runner` in Firecracker microVMs in separate runner accounts.
- **`tributary-fleet`**, managed only. It places networks, moves slots, deploys front cells, provisions certificates, and feeds <vendor-fleet-app>.

Crates. Each crate's internals are private, and only the listed items are public.

- `trib-domain`: ids, names, slots, refs, events, rules, `decide` functions, Actions state machines. Pure, no IO.
- `trib-store`: the only crate with a DynamoDB client. GetItem, BatchGetItem, conditional PutItem and UpdateItem, DeleteItem, and single-partition Query, retry budgets, warm and maximum throughput settings, and the CI lint that rejects transactions, secondary indexes, TTL, and Scan.
- `trib-chain`: `commit`, `Command`, the seal and unseal, `move_slot`, `RepoRestore`, `RepoReset`, and undelete.
- `trib-fold`: tiers, SQLite schemas, `apply`, `FoldCache::fresh` and `stale`, snapshots, archive, refold, and the fold audit.
- `trib-global`: claims, the edge read-through cache, the write re-check, the miss and re-check budgets, and the signup sweeper.
- `trib-pack`: `PackStore`, bucket quorum, inline packs, cruft packs, GC, the orphan sweeper, cache materialization.
- `trib-git`: the receive-pack protocol in Rust (commands, capabilities, side-band, `report-status-v2`, push options; about 2,000 lines [guess], checked by diffing its `report-status` output against upstream on a shared push corpus), git subprocess supervision, cache repositories, merge plans, and archives. Rust owns receive-pack so that `report_status` can require `&Acked`.
- `trib-auth`: tokens, OAuth, sessions, SSH keys, `authenticate`, `authorize`, `authorize_write`, `kid_allowed`, node ids.
- `trib-wire`: GitHub conventions shared by REST and GraphQL: headers, error bodies, the 404 rule, pagination links, ETags, media types, API versions, rate-limit headers.
- `trib-rest` and `trib-graphql`: routes, types, and schema generated from the pinned `ghes-3.22` OpenAPI file and SDL, plus handlers, resolvers, and cost accounting.
- `trib-actions`: the Rust port of `GitHub.Actions.WorkflowParser`, scheduler, broker, run service, launch, results, cache v1 and v2, artifacts, OIDC, the Azure Blob dialect shim. Wire types stay private.
- `trib-hooks`: dispatchers, consumers including `Mirror`, webhook rendering and delivery, home deliveries.
- `trib-edge`: TLS, SSH, the edge caches, `route`, assertion signing, admission control, and cell ingress.
- `trib-ops`: the operator role's intents, stages, cursors, and status documents, the drills, the signed `ReleasePointer` with its enabled formats, and the `tributary` admin CLI.

Rust does not pay for itself in pack generation, repacking, or merge computation, which stay in upstream git, or in the web UI, which is React.

AWS services on the request path: NLB, Route 53 resolution and health checks, PrivateLink between front cells and cells, DynamoDB through gateway endpoints, and S3 through gateway endpoints with presigned URLs computed locally, all data plane. Only DynamoDB Streams needs an interface endpoint, and nodes take its `vpce-` URL per Region from signed config, because Streams PrivateLink does not support private DNS (https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/privatelink-streams.html). The small-install profile has no Streams interface endpoint, and its nodes in public subnets call the public Streams endpoint ("Install operations"). KMS is off the request path: node start decrypts the wrapped keys from local disk once through its own Region's endpoint, using multi-Region keys. CloudFront serves the isolation subdomains with front cells as origin. OpenSearch is on the search path only. SES is off every request path.

Cross-cutting conventions (`research/wire-census.md` section B) live in `trib-wire`, so no handler can skip them. Every response, git smart HTTP included, carries `X-GitHub-Request-Id` (front, cell, node, and trace id in GitHub's colon-separated hex shape) and `X-GitHub-Enterprise-Version: 3.22.0`. REST responses carry `x-github-media-type: github.v3; format=json` and `x-github-api-version-selected`. `X-GitHub-Api-Version` selects `2022-11-28` (default) or `2026-03-10`, an unknown value returns 400, and the `2026-03-10` breaking changes (`#13`) are encoded as per-version response shapes generated from the two versioned OpenAPI files. ETags are weak and derive from the seq of the last entry that changed the resource, so a `304` costs one fresh tail read and does not count against the rate limit (`#17`). Pagination emits `link` headers with `/repositories/{id}/...` URLs, clamps `per_page` to 100 silently, and uses keyset scans behind `page`, `since`, `before`, and `after`. Error bodies use `basic-error` and `validation-error` with string `status`. The 404 rule (`#21`) is the `Decision::Hidden` variant: a handler cannot render 403 for a private resource because `authorize` never returns `Forbidden` there. Requests without `User-Agent` are rejected. Renamed repositories resolve through `Alias` entries that return 301 to `/repositories/{id}` in the API and serve git transparently (`#23`). GHES rate limits are off by default (`#19`) in BYOC and self-hosted and on in managed.

Hostname heuristics (`research/clients.md` and `research/actions-protocol.md` section H): the install host is validated at install time and may not end in `github.com`, `ghe.com`, or `localhost`, so every client classifies Tributary as GHES. Managed is one host, `tributary.dev`. That is the target: `/api/v3`, `/api/graphql`, `/api/uploads`, `/login/oauth/*`, and `/login/device/code` on one bare host on port 443, because gh rejects ports and the runner drops them (`research/clients.md#4`, `research/actions-protocol.md#4`). `GET /status` returns 200 with `X-GitHub-Request-Id` for Dependabot, `GET /api/v3/status` returns a body starting `GitHub lives!` for VS Code Pull Requests, and `GET /api/v3/` returns the root document with `rate_limit_url` for Jenkins (`research/clients.md` implication 4). Self-hosters are told that a `github.` label (for example `github.example.com`) lets GCM and Desktop skip their probe. Subdomain isolation (`raw.`, `codeload.`, `uploads.`, `objects.`) is on in managed, where the service certificate covers `tributary.dev` and `*.tributary.dev` (`research/wire-census.md#33`), and optional elsewhere. `RESERVED` keeps every first path segment the host serves out of the login namespace.

OAuth client ids: the five first-party ids in `FirstPartyClient` are seeded once in `global`, managed or install, when the service or install is created and cannot be deleted. Ids: every numeric id is `i64` in storage and JSON, allocation stops below 2^53, and GraphQL exposes `databaseId: Int` only where the value fits and `fullDatabaseId: BigInt` as a string everywhere (`research/wire-census.md#28`). Node ids use GitHub's new MessagePack format with the repository id first for repository-scoped types, accept the legacy base64 form as input, and honor `X-Github-Next-Global-ID: 1` (`#26`, `#27`).

**What keeps serving while each store is impaired.** `log` impaired in one Region of a Paired cell: the other Region serves everything. `log` without quorum, or a Single cell's `log` impaired: that cell stops writes, a Single cell serves stale fetches and reads within its limit once the failure is sustained, and other cells serve. S3: inline pushes, merges, issues, and warm folds serve, and large pushes and cold folds fail. OpenSearch: only `/search`.

### SLOs

Targets are per cell and per month (43,200 minutes), for Paired cells. A minute is bad when more than 5% of the journey's requests in that cell fail, GitHub's own SLA definition (`research/uptime.md#51`), or when the external probe fails. Paired targets rest on the 99.999% Global Tables SLA that every table in the cell's Regions qualifies for (`research/dynamodb.md#22`). Single cells lower the 99.99% rows to 99.95%, because their tables carry the 99.99% Standard SLA and only fetches and reads have the stale mode [inference]. `global` is wider than a cell, so identity writes and edge token resolution are measured per Region in managed, and push, merge, and write minutes count failures that `global` causes.

| Journey | Target | Error budget (min/month) | Measured by |
| --- | --- | --- | --- |
| git fetch and clone | 99.99% | 4.3 | Edge logs per cell, plus a synthetic `git clone` of a 50 MB repo every minute from three external vantage points |
| git push acknowledged | 99.95% | 21.6 | Receive-pack outcomes excluding client-caused rejections, plus a synthetic push every minute per AZ |
| Pull request merge | 99.95% | 21.6 | `mergePullRequest` and `PUT .../merge` outcomes excluding rule failures, plus a synthetic merge every 5 minutes |
| REST and GraphQL reads | 99.99% | 4.3 | Edge logs by route class, 5xx and deadline overruns |
| REST and GraphQL writes | 99.95% | 21.6 | Edge logs by route class |
| Web page load (repository, PR, issue) | 99.9% | 43.2 | Browser RUM beacons plus a synthetic Playwright run every minute |
| Actions job start (first log line within 5 minutes of trigger) | 99.9% | 43.2 | Run-owner timestamps, GitHub's Actions SLA definition (`research/uptime.md#51`) |
| Webhook first attempt within 60 s | 99.9% | 43.2 | `Delivery` first-attempt latency |
| Identity writes (signup, token creation, login renames, SSH key changes) | 99.95% | 21.6 | Claim outcomes, plus a synthetic signup and token creation every minute from each continent |
| Edge token resolution (misses and write re-checks on the local `global` replica, or the cached entry when it fails) | 99.99% | 4.3 | Edge logs per Region, plus the `global` replication-lag alarm at 2 s |
| Fold freshness (dispatcher lag p99 under 2 s, `Mirror` lag p99 under 2 s, core-tier cold load p99 under 2 s [guess]) | 99.9% of minutes | 43.2 | Dispatcher stream lag, oldest `Dirty` marker per consumer, mirror lag per hosting cell, and fold load timings per cell |
| Token revocation bound (writes refused within 5 s, reads within 60 s) | 99.9% | 43.2 | A synthetic token revoked every 5 minutes per Region, then probed with a push and a read |
| Acknowledged push durability | 100% | 0 | Daily replay of every `Refs` and `Merged` entry from the previous day: its packs resolve in S3 or inline and its refs fold to the recorded values |

Durability is an invariant, not a budget: zero acknowledged pushes lost. The durability row is checked by the daily replay of every real push, and by the linearizability harness from Milestone 1.

### Failure modes

Every row is per cell unless it names `global` in managed. "Instance" for a managed store means a storage or request node behind its endpoint. Work tables are `checks`, `actions`, and `inbox`. The authz mirror is the `Mirror` consumer and the `Mirror` chains it writes in hosting cells. Folds, caches, and edge caches hold only rebuildable state and are listed because they hold it. The operator role runs every lifecycle step, so a fault in it could stop rollouts beyond one node (`arena/round4/candidate-3/DESIGN.md`, Failure modes, with grafts 3, 4, and 7).

**Drills.** Managed flips one internal dogfood cell to its peer Region every month and one customer canary cell every quarter by failing that Region's health-check flag object, a data-plane switch (`research/uptime.md` implication 5), with no routing-control cluster. AZ evacuation runs weekly through zonal autoshift practice. A boot drill starts a front node and a cell node in the peer Region with the home Region blocked at the network layer and checks that each serves from its own Region's config, certificates, and keys. Every week a drill blackholes the DynamoDB endpoint of a canary Single install under live traffic and checks that token-authenticated fetches and reads keep serving from warm folds within the stale limit and writes return 503, so the stale mode never goes untested (`research/uptime.md#5`, graft 4). Every week `Remark { since }` runs on the canary cell and must raise zero markers that the dispatchers missed. Every month AWS FIS isolates one Region of a Paired staging cell and one `global` Region, and puts, strong reads, claims, and token re-checks must continue (https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/V2globaltables_HowItWorks.html, "Fault injection testing" [unverified section name]). Every month a staging hosting cell is cut off from a home cell's heartbeat and must fail closed, after 30 s, that owner's writes that read a mirrored fact, while owner and collaborator writes, reads, and other owners' writes continue, and a stopped `Mirror` consumer must fail no write. Every month a repository restore runs on a canary repository and must return its named refs to the target seq and leave its lists unchanged. Every quarter a staging Region dies for good under a Paired staging install, with zero lost acknowledged writes, and a `Reprotect` then builds a full trio while serving. A failed practice run or drill blocks deploys (`research/uptime.md` implication 20). In installs the operator role runs the drills ("Install operations"), and the evaluation profile skips any drill that takes a node out of rotation.

**Velocity caps.** Background work that competes with users runs under fixed caps: compaction touches at most 5% of networks per hour per cell, fold reloads after an AZ loss run core tiers first and metadata tiers one stream per node at a bounded rate, and GC deletes at a fixed rate. A recovering cell spends its spare DynamoDB and S3 capacity on user traffic first.

### Change safety

**Deploys.** A release rolls one cell at a time in <vendor-fleet-app> waves, the internal canary cell first, and inside a cell one AZ at a time (`research/uptime.md#4`). Inside an AZ each new role process starts beside the old one with `SO_REUSEPORT`, takes new connections, and the old process drains: API requests finish, long clones get 10 minutes, broker long polls end with a reconnect. The NVMe folds and caches stay warm because the instance never stops, and the new process opens the same SQLite files. A gate after each AZ checks the SLO burn rate, the put conflict and throttle rates, the oldest `Dirty` marker per consumer, fold lag, and the pack copy backlog. A failure swaps back to the kept binary automatically, unless that binary is older than the oldest release that reads an enabled format, in which case swap-back is refused and pages. The in-account operator role runs these steps from a signed rollout intent, with a cursor in the control bucket and a safe point after each AZ gate, and a node-local watchdog swaps a new process back if it hears no "gate passed" before its deadline, so a lost session or a revoked deploy role never strands an ungated process ("Install operations"). This is the in-install abort that the BYOC machinery lacks (`research/byoc-grounding.md` item 11). Node image changes (OS and git) replace instances per AZ through the Auto Scaling group with the same gates, so a single-node evaluation install takes a short outage for one. That launches capacity during a deploy, never during recovery.

**Trust roots, config, and feature flags.** Config is code (`research/uptime.md` implication 16). Three keys sign every release, intent, and config a node trusts. The vendor's release key signs only releases, action packs, and pin maps. Each install, and each managed cell, has KMS asymmetric keys that the bootstrap creates in its account as multi-Region keys, with replicas in every install Region and in `dr`, because KMS cannot convert a single-Region key later (https://docs.aws.amazon.com/kms/latest/developerguide/multi-region-keys-overview.html). The config key, usable by the vendor's deploy role and the customer, signs rollouts, `formats:enable`, and routine config. The customer-only key, which no deploy role can use, signs `Uninstall`, `Restore`, `RepoRestore`, `RepoReset`, `Reprotect`, `DrPromote`, `DrFailback`, `Halt` and `Abort` during a revocation, and any config that changes tables, buckets, the `dr` Region, or the identity provider. A customer may pre-authorize the config key to sign `DrPromote`, through a customer-only setting, so a vendor SRE can promote at 2am. In self-hosted the customer's CI is the deploy principal, so the customer holds both keys. The operator role signs no intent or config. It signs status documents with the status-signing key, and the `ReleasePointer` with its enabled formats with a pointer-signing key that cannot sign intents. Flags and settings ship as a signed config bundle per cell, rolled through the same waves, validated on load, with last known good kept, and nodes load each generation straight from their Region's control bucket with no operator step, so config applies while a table is impaired. There is no runtime flag service. `tributary config sign` and `tributary config apply` change the customer-signable settings. The config key covers the hostname and isolation subdomains, the TLS certificate and key, the stale-mode flag and stale limit, the DynamoDB Streams endpoint URL per Region, the air-gapped byte proxy, SES or SMTP, the alarm SNS topic, rate limits, and the PITR window. The customer-only key covers table names, bucket names, the `dr` Region, the `DrPromote` pre-authorization, and instance sign-in and IdP settings. Apply rolls back to the last known good generation when nodes reject it. Release-scoped values, such as the runner floor, the formats a release may enable, and the core-tier fold schema, are signed only in the release. The operator role renews certificates and rotates key epochs, and expiry alarms reach the customer's SNS topic 30 days ahead ("Install operations").

**Record formats, not schema migrations.** No table has a schema, index, or DDL to migrate, which removes GitHub's index, migration, and dropped-column incident classes (`research/uptime.md#44`). Every stored format that outlives a release (entry bodies, event kinds, `global` items, work-table items, snapshot framing, stored webhook payloads, home deliveries) follows a two-release rule: release N learns to read format k+1, and release N+1 starts writing it only after the signed `ReleasePointer` lists it as enabled (graft from round 1's candidate 2; journey 6). The operator records that only when every cell that can read the chain, through mirrors, slot moves, and home deliveries, reports a release that reads it, from the fleet's `nodes` reports, so in managed the gate is fleet-wide. Each entry carries its tier tag outside the encoded body, so an older node skips an unknown metadata event and the core tier never stalls. Once a format is enabled, swap-back below the reading release is refused and pages. CI decodes release N+1's corpus with release N and fails on any record N cannot read. `global` items take only additive attributes, and only `trib-global` writes them, through a fixed set of condition expressions that CI checks.

**Fold schemas.** A fold is derived, so a fold schema change is a refold, never a migration. A metadata-tier schema change ships in an ordinary release, refolds lazily per aggregate, canary cell first, and keeps the old file serving until the new one catches up, so it never touches git ("Folds"). Each refold is built once by the chain's preferred node and published as a snapshot that other nodes load. A core-tier schema change ships only in a release dedicated to it, after two weeks on the canary cell, because every fetch, push, merge, and authorization reads the core tier, and the core tier reads both schemas until each chain's refold snapshot is published. Snapshots carry their schema and release, and a release marked bad has its snapshots ignored and refolded from the archive. An install rehearses a core-tier refold with the operator's `Stage::RehearseRefold`, the install's form of the canary cell, and the rollout gates on its result ("Install operations").

**Zero-downtime upgrades in every mode.** The hot swap and two-release format rules are the same everywhere. A single-node evaluation install upgrades its binary the same way, by process handoff on one host, and takes a short outage for a node image change, because its one instance is replaced. An install several releases behind submits one rollout intent whose `steps[]` chain names every retire boundary in order, and the operator role walks it with a resumable journal, so no step leaves the N-1 and N+1 format window. CI tests every release pair in that window. DynamoDB and S3 have no engine version for Tributary to upgrade [inference], and AWS-side deploys of DynamoDB do not follow Tributary's waves, which "Open questions and risks" names. The upgrade never needs maintenance mode, unlike GHES feature releases (`research/uptime.md#55`).

**What the BYOC machinery gets.** Its deploy tool stops running long stages itself. It keeps `publish:image`, copies each verified release into `releases/` in every control bucket, submits a signed intent to the install's control bucket in each Region, and polls the status documents with fresh short sessions ("Install operations"). The operator role runs the stages `apply:infra`, `RehearseRefold`, `formats:enable`, `roll:nodes` (the per-AZ hot swap and gates), the soak, `roll:operator`, and `formats:retire`. It needs no stateful-fleet stage with fencing, leader handoff, or replica catch-up (`research/byoc-grounding.md` item 7), because no node holds canonical state. Observation moves from API Gateway routes to the signed status documents, which carry the `nodes` report, a storage section (put conflict, throttle, and error rates and put and tail-read p99 per table, dispatcher lag, oldest `Dirty` marker and parked chains per consumer, fold lag and cold loads per tier, unrepaired pack copies), a `dr` section with MREC replication lag, S3 replication backlog, and the `dr` bucket's pack inventory, and an identity section (`global` miss and re-check rates, replication lag, and latency per Region). Deploy-plane gains `nodes-at-version`, `storage-healthy`, `consumers-fresh`, and `dr-fresh` gate checks in place of `components-healthy` and `lambda-code-matches`, plus `global-healthy` in managed (item 8). `dr-fresh` passes only when the `dr` pack inventory names every pack that a chain names. For private installs, <vendor-fleet-app>'s `liveness` check, an unauthenticated GET that a private NLB fails and whose fail cannot be overridden (`#32`, `#33`), becomes a check that the newest status document is fresh.

What collapses in an install. An install is one cell holding all 65,536 slots, so it has no slot moves, no fleet control plane, no `Mirror` chains, and no cross-cell deliveries: home deliveries go to the same cell's `inbox` through the same code path. Its `global` table is its own, MRSC when Paired and plain when Single, so its logins never collide with the managed namespace and it has no cross-continent round trip. Front cells collapse to the `edge` role on the install's nodes. CI runs a two-cell install in staging so cross-cell paths, mirrors included, stay tested in every release [inference].

What the customer provisions and the preflight checks. Paired installs enable two replica Regions and a witness Region, and the target preflight checks that the trio is among the 15 MRSC Regions (`research/dynamodb.md#25`). Single installs run in any of the 34 commercial DynamoDB Regions (`#24`), with `dr` in any other, because MREC accepts any Region (V2globaltables_HowItWorks). In every install Region the preflight checks that an opt-in Region is enabled, that every install key is multi-Region with a replica there, DynamoDB, a `DescribeStream` call through the configured Streams endpoint URL, S3, the instance type in the target's count of AZs (three, or one for evaluation), the vCPU quota, the account-level DynamoDB throughput quota against the warm throughput it will set, SES production access or SMTP reachability, and the certificate format (PEM import or an exportable certificate), because the edge terminates TLS itself. In an air-gapped install it probes every VPC endpoint in the list generated from the stage table ("Install operations"). The target's `tributary` block gains `durability { class: paired, regions, witness }` or `durability { class: single, dr }`, and `nodes.azs`. Tables and buckets take the `trib-` prefix, because installs own unprefixed account singletons (`#2`).

Regions outside the MRSC list. An install whose home Region is not among the 15 MRSC Regions, such as Sydney (ap-southeast-2) or Zurich (eu-central-2), runs Single, and the quickstart and preflight say so. Zurich has no MRSC trio and no in-country `dr`, because Switzerland has one Region. The offer is Single with or without `dr`: the Single SLOs (99.95% where the Paired table says 99.99%), RPO zero without a Region loss, RPO for stored packs up to S3 replication with `dr`, a write RTO of the runbook's wait plus about 60 minutes of promotion [guess], and no claim to fact 9. A Paired trio from other Regions, such as Singapore and Tokyo for Sydney, takes the data out of the country, so it is offered only on the customer's written choice [inference].

Bootstrap and deploy policy. The bootstrap takes a `product` variable that selects Tributary's `trib-` name prefixes and the PassRole services it needs, EC2, Auto Scaling, and FIS, and it creates the service-linked roles it needs explicitly instead of relying on `PowerUserAccess` (`research/byoc-grounding.md#4`-`#6`), including the one DynamoDB uses for global table replication [inference]. The bootstrap is the install's first apply, and it creates only the control buckets, the keys, the deployer role, the replicated OpenTofu state bucket, and a deployer launcher that the customer authorizes once: a launch template for the one-shot deployer instance, running only the release's signed deployer image, which the deploy principal may start but not change. The keys are the CMK, the config key, the customer-only key, the status-signing key, the pointer-signing key, and the CA-wrapping key, all multi-Region with replicas in every install Region and in `dr`, because KMS cannot convert a single-Region key later. Tables are created only by `apply:infra` under the deployer role, which holds the data-plane permissions that global table replica creation needs (`review/round4-byoc-walk.md` finding 1), and launch templates change only through the deployer. The bootstrap grants the Auto Scaling service-linked role use of the install's CMK, so instances launch from the re-encrypted AMI. A Tributary deploy policy replaces `PowerUserAccess`. It denies reading repository data, meaning pack-bucket `GetObject` and every DynamoDB data-plane read or write on the install's tables, denies `ssm:StartSession` and `ssm:SendCommand`, and limits the deploy role's bucket writes to `intents/*` and `releases/*`. That read deny protects against the deploy principal, not against vendor code, which already runs in the account through signed releases. The deploy policy and the permissions boundary of every workload role, the operator's and the deployer's included, deny `DeleteTable`, `DeleteTableReplica`, `DeleteGlobalTableWitness`, and `dynamodb:PutResourcePolicy` on install tables, `kms:DisableKey`, `ScheduleKeyDeletion`, `PutKeyPolicy`, and `RevokeGrant` on install keys, and lifecycle, versioning, bucket-policy, and delete calls on install buckets, so no intent reaches them through the operator. The boundary lets the operator delete only `trib-rehearsal-*` tables. A `RetireTables` intent, signed with the customer-only key, deletes superseded tables and replicas through a `trib-retire` role that only the operator can assume, which may disable protection on and delete only tables tagged `trib:retired`, a tag only it may set, after the operator checks that the current signed config names none of them [inference]. Turning off deletion protection on live tables stays with the customer's admin role and `tributary uninstall --finalize`.

Reuse of the existing BYOC machinery (`research/byoc-grounding.md`): the release registry, signing, retention, and `rollback-check` transfer with a Tributary bucket and key (item 1). `comparedWith` is computed per release line, so a customer pinned at N-2 keeps its rollback (`#34`), and every retire-phase release, with its source AMI, is retagged `retention=customer` (`#15`). The bootstrap trust pattern transfers through the `product` variable (items 2 and 5). The target document gains a `tributary` block, the release record gains `product` and `phase` fields, and <vendor-fleet-app> reads one contract per product (item 12). The fleet model, waves, gates, and the rule that automatic advance never starts wave 1 transfer, with a <vendor-fleet-app> "install" standing for a cell or a front cell (items 4 and 13). Tributary requires its own dedicated account per install (item 6). What Tributary adds: the operator role with its intents and status documents, `apply:infra`, `roll:nodes`, and the format stages, `publish:image` and the release copy in the deploy tool, the Tributary gate checks, the automatic in-cell abort, and, for managed only, network placement, slot moves, front cells, and the `global` table's own last-wave release lane.

## Install operations

The vendor's deploy tool runs outside the customer's account, so it cannot drive a step that outlasts the one-hour chained session, that must survive a customer revoking the deploy role or a week-long vendor outage, that runs with no internet route, or that observes health through a role allowed only to call API Gateway (`review/byoc-walk.md` findings 1, 2, 10, and 12, `research/byoc-grounding.md#7`, `#21`). So the install operates itself. An in-account `operator` role, part of `worker`, owns every lifecycle step under a lease: rollout stages, infrastructure applies, refold rehearsals, format changes, node rolls, certificate renewal, key rotation, action-pack sync, backup checks, restores, repository restores, `dr` enablement, promotion, failback, re-protection, table retirement, drills, and the export that starts uninstall. People and tools only submit signed intents and read status. Two jobs stay with the deploy tool, or with the customer's CLI: `publish:image`, and copying each verified release create-only into `releases/` in every control bucket, so the operator never needs registry access. Managed cells use the same path, with the vendor as the only submitter, so the three modes run one artifact.

pub struct StatusDoc { pub at: Timestamp, pub release: ReleaseDigest, pub phase: ReleasePhase, pub intents: Vec<IntentState>,

**Intents and status.** An operator writes a signed, create-only intent (a rollout plan, a config generation, or a command from the allowlist) to the install's control bucket in each Region, and reads signed status documents from the `status/` prefix there. The operator role derives the submitter from the key that verifies the signature, so a vendor signature cannot pass as the customer's, and it signs no intent or config, only its status documents and the `ReleasePointer`, so a restore or promotion carries its new table names in the customer-signed intent ("Trust roots, config, and feature flags"). The vendor's deploy tool submits an intent and then polls with fresh short sessions, so no stage outlives the one-hour chained session (`research/byoc-grounding.md#48`). Intents carry a short `not_after` (1 hour [guess]), and an intent not started by then is refused. `Halt { intent }` stops a rollout at its next safe point, and `Abort { intent }` swaps it back to the last safe point. The runbook for revoking the deploy role is: revoke the role, then submit `Halt` signed with the customer-only key, then `Resume`, `Abort`, or a new rollout. The observer role reads the status documents through `s3:GetObject` in every install Region, so no API Gateway is needed, a private NLB is fine, and observation survives the loss of the home Region. Deploy-plane gates read the same documents. The installation record lives in the control bucket and is copied into each status document, so no install needs a control table (`#17`).

**Stages, leases, and the watchdog.** Every stage is idempotent and resumable from its cursor, with a safe point after each AZ gate. Every stage keeps its lease and cursor in the acting Region's control bucket, written with `If-Match`, so a swap-back, halt, abort, config change, restore, promotion, or failback runs while a table is impaired, and no stage holds a database connection. Nodes load each signed config generation straight from their Region's control bucket with no operator step. A node-local watchdog swaps a new process back to the kept binary if it receives no "gate passed" within its deadline (15 minutes [guess]), so a dead operator, a revoked role, or an absent vendor never leaves an ungated process serving. One stage of each kind runs at a time under its lease.

**Stage table.** Each stage, what runs it, and the AWS services it calls. CI derives the last column from each stage's code and the release's OpenTofu module, and generates the air-gapped endpoint list from it.

| Stage | Runs as | AWS services it calls |

| `apply:infra` | A one-shot instance under the deployer role, started through the deployer launcher | The services the step's OpenTofu module declares, the DynamoDB data-plane calls that replica creation needs, and S3 for its state |
| `RehearseRefold` | Operator, restoring into a `trib-rehearsal-*` table that it then deletes | DynamoDB, S3 |
| `formats:enable`, `refold`, `formats:retire` | Operator | S3, KMS for the pointer signature |
| `roll:nodes`, `roll:operator`, `SwapBack` | Operator, then each node's watchdog | EC2, Auto Scaling, Elastic Load Balancing, S3 |

**Release order, formats, and rollback.** A release is `publish:image` by the deploy tool, then `apply:infra`, then `RehearseRefold` when the release changes the core-tier fold schema, then `formats:enable` for any record format the release adds, then `roll:nodes` across every Region and the `dr` node group, then a soak, then `roll:operator`, then `formats:retire`. No table has a schema, so nothing else migrates. `RehearseRefold` restores the install's `log` into a `trib-rehearsal-*` table, refolds a sample of chains' core tiers there, reports to the status document, and deletes the table, and the rollout gates on its result. `formats:enable` is an intent under the config key. The operator executes it only after the `nodes` reports of every cell that can read the chain, the whole fleet in managed, show every process on a release that reads it, and records the format as enabled in the signed `ReleasePointer`, and only then does any node write it (journey 6). From then on, swap-back below that release is refused and pages. A fold schema change runs as `refold`, lazily per aggregate and tier, canary cell first, built once per chain by its preferred node ("Folds"). `Stage::ApplyInfra { step }` applies that step's OpenTofu module, which also points every launch template at the new AMI, as a short-lived in-account task under its own deployer role, which no serving node can assume: a one-shot instance running the release's deployer image, whose provider mirror needs no registry access (`research/byoc-grounding.md#16`) [inference: the instance form]. An install's first apply is the bootstrap, which creates no table ("Deployment modes"). The OpenTofu state bucket replicates to the peer or `dr` Region. `roll:nodes` leaves out the operator processes, and `roll:operator` swaps them only after the soak, so the previous release's operator runs every stage up to `formats:retire`, and the cursor and journal follow the two-release format rule. `roll:nodes` moves the `ReleasePointer`, so a node that Auto Scaling launches later boots release N, never N-1. `formats:retire` runs only when the `nodes` status shows every process at version N or later, no swap-back pending, and every launch template at N, and it removes only the previous release's reader of a format no chain still holds below its archive. The release record's `phase` (enable, retire, or none) feeds the compatibility check, so only a retire phase sets `compatibility.rollbackBarrier` (`research/byoc-grounding.md` item 9). OpenTofu removes a resource only two releases after the code stops using it, and stateful resources carry `prevent_destroy`, so a tool rollback never destroys a table, bucket, or key (`research/byoc-grounding.md#36`). Retire-phase releases are always retained, and recovery after a barrier is roll-forward only. A long skip, such as N to N+4, is one intent whose `steps[]` chain the operator role walks with a resumable journal, verifying each release from `releases/` and applying each step's module just before that step's stages, so a later module never removes a resource that a running release still uses. The chain's preflight checks registered runners against the final step's runner floor, because four floor raises in one chain would otherwise shrink the one-release warning to hours.

**Images and action packs.** `publish:image` belongs to the deploy tool. It shares the release's source AMI and grants its KMS key to the install's account in each Region, then copies the AMI into every install Region, re-encrypts it with the install's key, and grants the Auto Scaling service-linked role its use, so node replacement never depends on a vendor share (`research/byoc-grounding.md#46`). Self-hosters run the copy as `tributary release import-ami`, and the vendor shares each release's AMI and grants its key to a self-hoster's account at registration, so the copy needs no vendor credentials. Source AMIs follow their release's retention, so a `retention=customer` release keeps its AMI (`#15`). Nodes verify the image digest at boot, and the release names AMIs by that digest, not by id. `tributary actions import` loads a signed actions pack, and an in-install sync job pulls new packs when the install has outbound access, as GHES's `actions-sync` does [unverified]. The pack carries an allowlist of third-party actions, such as `aws-actions/*`, and an admin can add any public action to the install's `actions` mirror, as GHES's `actions-sync` allows [unverified]. The install serves `RunnerRefresh` download URLs itself, and each release publishes the next runner floor one release ahead, so a runner fleet with updates disabled is warned a release before it is refused.

**Certificates and keys.** The operator role renews the TLS certificate 30 days before expiry through ACME DNS-01 in a delegated Route 53 subzone, or validates a customer upload written to `certs/` in the control bucket and alarms before it expires. It rotates each key epoch on a schedule: a new verifying key is published at least one token lifetime before it signs, and the old one retires after the last token's `exp`. A per-install private CA, whose private key the CA-wrapping key holds wrapped, issues the internal mTLS certificates and rotates with the key epochs.

**Backups and restore.** Every table has PITR with 35 days at per-second granularity, deletion protection, and a 35-day system backup if deleted anyway, and a restore always creates a new table (`research/dynamodb.md#19`; https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/PointInTimeRecovery_Howitworks.html). PITR on MRSC replicas is [unverified], and Milestone 0 asks AWS. Buckets keep noncurrent versions 35 days. Entries older than 30 days move to immutable `Archive` objects, so S3 holds full history and every fold can be rebuilt from genesis. Repairs stay inside the chains wherever they can. `tributary admin repo-restore <repos> --refs <refs> --to <t>` submits a `RepoRestore` intent signed with the customer-only key, which restores any noncurrent pack versions the targets need, appends `RestoredTo { to, refs }` to each named repository chain at the seq in force at `t`, and returns only those refs, within 35 days, with no table restore and no downtime for other repositories (graft 2). `tributary admin repo-reset <repo> --to <t>` submits the separate `RepoReset` intent for a whole-fold reset. `tributary admin undelete` is an audited site-admin call that appends `Undeleted` and puts back the name entry or login item before `retain_until`. A point-in-time restore is kept for damage outside the chain model. `tributary admin restore --to <t>` submits two `Restore` intents signed with the customer-only key. The first restores all five tables to the same second `t` into new tables and reports their names in the status document. A restored replica is a single-Region table and an MRSC table can be created only empty (`research/dynamodb.md#18`), so a Paired install's first intent also copies the restored items into a new empty MRSC table set [inference: the same copy a slot move uses]. The second intent carries the new table names and runs the cutover: it re-enables Streams, PITR, and deletion protection and re-applies tags, CloudWatch alarms, and resource policies, which a restore does not copy (https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/pointintimerecovery_restores.html), adopts the restored tables into the OpenTofu state, re-creates the `dr` replica on the restored tables, restores the pack versions the restored chains name from noncurrent S3 versions, re-appends every revocation record in the home control bucket newer than `t` (below), clamps consumer cursors above a restored head, runs `Remark { since: t - 24h }` so a marker lost between independently restored tables is raised again, bumps `restore_epoch` in every control bucket, and runs the push-durability replay as its verification. A later `RetireTables` intent deletes the superseded tables. Nodes drop their folds, reftables, and caches when the epoch changes and refold from snapshots at or below each restored head, so no node serves rewound state. A restore calls DynamoDB's control plane, so a control-plane outage holds it at its last safe point. Every revocation-class entry (member, team, grant, collaborator, and installation removals, and token revocations) also writes a create-only record to the home control bucket before it returns, so a restore never brings a revoked grant back.

**The recovery Region.** `Single { home, dr: Option<Region> }`. With no `dr`, a Region loss is recovered from the newest cross-Region backup copy [unverified for DynamoDB], and the evaluation profile uses that. With `dr`, every table has an MREC replica in the `dr` Region, which accepts any Region and replicates in seconds (`research/uptime.md#30`), buckets replicate there, and the install keeps its key replicas, wrapped keys, certificates, and SSH host keys in the `dr` control bucket. MREC replicates by itself, so connected Regions need no peering or transit gateway [inference] ("Air-gapped installs"). Revocation-class entries also write their record to the `dr` control bucket before they return. Setting `dr` on a running install is a customer-only config change that the operator runs as `Stage::EnableDr`: `apply:infra` adds the MREC replicas, the `dr` buckets, and the standby node group, S3 Batch Replication copies the existing packs that live replication never copies (`review/round4-selfhost-walk.md` finding 2), and `dr-fresh` passes only once the `dr` pack inventory is complete. `tributary dr promote` and `tributary dr failback` submit intents signed with the customer-only key, or with the config key for `DrPromote` once the customer has pre-authorized it, and the operator role runs them from the `dr` Region with its lease and journal in the `dr` control bucket. MREC checks conditions only in the local Region and resolves concurrent writes to one item by last writer wins (`research/uptime.md#30`), so promotion fences by a lease and by key, not by condition. Every home put requires a "no promotion" read of the `dr` control bucket from the last 10 s, cached per node, so a home node that cannot make that read stops writing. Promotion writes a higher `promotion_epoch` to every control bucket it can reach and waits 10 s plus the clock error bound (1 s [guess]) before it takes writes, so no write acknowledged at the old home after promotion exists. Every later entry goes to an `e#<epoch>#<seq>` key, so the two sides never land on one item. Promotion truncates each chain at its first gap or first missing pack and records what it cut as stated loss, refuses tables that the current `restore_epoch` does not name, re-appends the revocation records, rotates key epochs, starts the standby node group's serving roles, and publishes a CloudWatch metric that only `DrPromote` and `DrFailback` publish. The failover record's health check follows an alarm on that metric, so it is sticky, uses only the data plane, and never fails back by itself when the home Region heals (`arena/round4/SYNTHESIS.md`, graft 7). Once the old home reconnects, the operator re-scans each chain's old epoch past its cut and records every entry that arrived late. The write RTO is the runbook's wait plus about 60 minutes of promotion [guess]. No ARC routing-control cluster exists in any install, because one costs about $1,825 a month (`research/pricing.md`).

**Failback.** `DrFailback`, signed with the customer-only key once the old home Region is healthy, runs in steps with a safe point after each. The operator first finishes the late-entry re-scan. It then deletes the stale old-home replica of each table through `trib-retire`, and `apply:infra` adds a fresh MREC replica there from the promoted tables and adopts it into the OpenTofu state. S3 Batch Replication copies to the old home's buckets every pack written since promotion and every object that arrived there as a replica, which live replication does not copy again, and `dr-fresh` gates on the old home's pack inventory. The old home's node group then starts in standby. When the customer chooses, the operator promotes back by the same steps as `DrPromote`: a higher `promotion_epoch`, the 10 s and clock-error wait, truncation, and the `DrFailback` metric, which moves the health check back. The `dr` Region returns to a standby node group.

**Re-protection and class changes.** A Paired install that loses its home Region for good keeps its deploy machinery: the peer Region's operator takes the lease, `apply:infra` reads the replicated OpenTofu state there, and rollouts resume within 1 hour [guess]. While it runs on one replica and the witness it may enter stale mode. An MRSC table cannot add a Region (`research/dynamodb.md#18`), so a `Reprotect { to, tables }` intent, signed with the customer-only key, creates a new table set, a new MRSC trio or a Paired set for a Single install, through `apply:infra`. The operator copies every chain into it while serving and hands each chain over with a `Sealed` entry between table sets inside the one cell, so the new set serves a chain once it has caught up to that entry and no chain waits on its neighbors. It then swaps the Regions in config and removes a dead Region from the target and the OpenTofu state, so no every-Region step stalls on it, and a `RetireTables` intent deletes the old set. The quarterly drill and a Milestone 6 gate cover `Reprotect`.

**Monitoring and the 2am runbook.** Every install exports CloudWatch metrics and alarms and a Prometheus endpoint, and it can send alarms to a customer SNS topic. The runbook for an impaired home Region is a decision tree keyed on AWS Health, the tail-read failure rate, and the stale-limit clock. With no DynamoDB or S3 event in AWS Health, the fault is Tributary's, and the operator swaps back the last rollout. With an event and the stale-limit clock under 1 hour, the operator waits while warm folds serve fetches and reads. When AWS projects recovery beyond the stale limit, one branch raises the stale limit to that projected time with a config-key setting, so fetches keep serving on any node until the table returns, and this is the only branch without `dr`, short of a restore that calls the impaired Region's control plane. Past 1 hour with `dr`, or when AWS projects recovery beyond the write RTO, the customer, or the vendor SRE with a pre-authorized config key, runs `tributary dr promote`, and writes return after that wait plus about 60 minutes of promotion [guess]. A home Region that is still alive cannot acknowledge a write after promotion, because of the 10 s fence, or overwrite a promoted entry, because of the promotion epoch. Every branch is recovery-class, so each works with the tables impaired. Self-hosters are told to drill a promotion and failback every quarter. The weekly stale-mode drill runs with live traffic on a canary install: managed keeps a canary Single install for it, and a self-hoster runs it on a staging install [inference]. The operator role reports every drill in the status document, and a failed drill blocks the next rollout until a signed intent acknowledges it. The evaluation profile skips drills that take a node out of rotation.

**Air-gapped installs.** A connected host runs `platform-deploy release fetch` and writes the release, the actions pack, and each AMI stored as an S3 object by EC2's store-image task [unverified in every Region] to the customer's transfer medium. Store-image needs the AMI shared with the account directly, which the vendor does at registration, and the restored AMI's new id still matches its release by image digest. Inside, the CLI copies the release into `releases/`, and `tributary release import-ami` and `tributary actions import` load the rest. Each install Region needs a VPC endpoint for every service in the stage table, and the list is generated from that table, AWS Backup and Route 53 included: DynamoDB and S3 (gateway endpoints), DynamoDB Streams, KMS, STS, EC2, Auto Scaling, Elastic Load Balancing, CloudWatch and CloudWatch Logs, SSM with `ssmmessages` and `ec2messages`, SNS, AWS Backup, Route 53, and any other service the OpenTofu module declares, plus an internal SMTP relay for email. The Streams endpoint URL per Region is customer-signable config, because Streams PrivateLink does not support private DNS, and the preflight calls `DescribeStream` through it. Gateway endpoints do not serve on-premises networks, so an air-gapped install either proxies LFS, Actions cache, and artifact bytes through its own nodes, a config-key setting, or requires S3 interface endpoints with private DNS. A gateway endpoint serves only its own Region, so an install with `dr` requires inter-Region connectivity or a replicated control bucket. The preflight probes every endpoint in every install Region. Health checks run as CloudWatch alarms on the deep regional endpoint instead of public Route 53 health checks, and a `dr` promotion moves traffic by a failover record in a private hosted zone whose health check follows the `DrPromote` alarm, which Route 53 supports in private hosted zones (`review/round4-selfhost-walk.md` finding 9). The small-install profile's network layout, public subnets with no NAT gateway and no Streams interface endpoint, does not apply to an air-gapped install, and the preflight refuses `"profile": "small"` there.

**Evaluation profile and uninstall.** The evaluation profile is one node in one AZ with no `dr` (`azs: 1, perAz: 1`), and it has no availability SLO. Growing it means raising `azs` from 1 to 3. New nodes join the rendezvous sets and fill their caches from S3 under the velocity caps, so fetch latency stays above baseline until the caches warm, and the 33% removal cap and 66% sizing apply only from three nodes. Uninstall finishes outside the install. The operator's `Uninstall` stage, signed with the customer-only key, only exports data (repositories as bundles, metadata as a migration archive). The customer then runs `tributary uninstall --finalize` with its own admin role, which adopts tables created at runtime into the OpenTofu state, turns off deletion protection and `prevent_destroy`, destroys the install, empties the versioned buckets including noncurrent versions, schedules deletion of replica keys and then primary keys, and destroys the bootstrap last from the admin's local bootstrap state (`research/byoc-grounding.md#22`).

**Small-install profile.** A target that sets `"profile": "small"` gets the cheapest layout that keeps three AZs and an availability SLO, priced for 50 developers in `research/costs.md`. It runs three t4g.medium nodes, burstable in unlimited mode, one in each of three AZs, and keeps the 66% sizing rule. Alarms on surplus-credit spend and on memory pressure tell the operator to move to `m8g.large`, because 4 GiB of memory limits repacks of large fork networks [inference]. The nodes sit in public subnets whose security groups admit only the NLB and outbound traffic, so the install has no NAT gateway and no DynamoDB Streams interface endpoint. That also removes a NAT gateway as a single-AZ dependency. The preflight refuses the profile for an air-gapped install ("Air-gapped installs"). DynamoDB and S3 traffic still goes through gateway endpoints. The profile has no OpenSearch domain. Issue and pull request search reads SQLite FTS5 tables in each repository's metadata tier ("Folds"). Cross-repository search queries the folds of the repositories the viewer can read under a deadline and returns `incomplete_results` past it [inference]. Code search runs `git grep` on cache nodes. Logs go to S3, where Athena queries them, and CloudWatch keeps only the 12 alarms on SLO metrics. The dispatcher polls each Streams shard once a second, so webhooks and Actions triggers can fire up to about half a second later ("Event fan-out"). A cold recovery Region is set by default, so `dr` holds table replicas and replicated buckets, and promotion launches nodes there ("The recovery Region"). `research/costs.md` prices the profile at $226 a month on demand (`scrappy`) and at $189 on a 3-year Compute Savings Plan (`scrappy-3yr`), whose t4g.medium rate is inferred from t4g.large's. A Paired small install, which loses no acknowledged write on a Region loss, costs $388 (`scrappy-paired`). Replacing the NLB with Route 53 health-checked records to node IPs costs $195 (`scrappy-dns`) and is not recommended, because a dead node keeps receiving connections until DNS catches up [guess on timing], and git does not retry them. The `floor` row, $121, is the evaluation profile with a cold recovery Region, and it has no availability SLO.

## Public service concerns

**Anonymous access and rate limits.** Anonymous callers get public reads only, keyed at the front by source IP (the /64 for IPv6). REST allows 60 requests per hour (`research/wire-census.md#18`), GraphQL requires authentication as on GitHub [unverified], and git allows 600 negotiations per hour and 8 concurrent per IP [guess]. Authenticated limits follow GitHub's numbers: 5,000 REST requests per hour per user, 1,000 per repository for `GITHUB_TOKEN`, 5,000 GraphQL points per hour, and secondary limits of 100 concurrent requests and 80 content-creating requests per minute (`#18`, `#35`). Each front node enforces its share of a Region-wide limit, as round-2 candidate 3 described (`arena/round2/candidate-3/DESIGN.md`, journey 1), so limits do not multiply with node count. Counts are approximate, because GitHub documents per-Region variation (`#18`), and excess gets 429 before any git byte. Inside a cell each repository's rendezvous set admits authenticated traffic first and sheds anonymous requests first with 503 and `Retry-After`. For public clones, `uploadpack.packObjectsHook` points at a response cache on NVMe keyed by wants, haves, and capabilities, so a clone storm at one tip costs disk reads instead of `pack-objects` CPU [inference: identical full clones dominate anonymous traffic].

**Abuse and spam.** Signup is one `global` claim behind front limits per IP and per ASN, with email verification and 24 hours of reduced content-creation limits for new accounts. Repository creation and forks are capped per account per hour, because each writes the owner's `Authz` chain. Suspension is one `global` write, so within the 60 s edge cache fronts reject the account's credentials, and cells hide its content at render time from the account item. Abuse aimed at one repository (clone floods, comment spam) stays in its network's cell, and a slot that dominates a cell moves to a dedicated cell.

**Takedowns.** A repository takedown is a `Takedown` entry on its chain, which every request for that repository reads through the fresh core tier, so it applies at once to git, the API, raw files, and archives. A takedown of a whole fork network is a `Takedown` entry on the network chain, which first-touch completion copies onto every member chain in parallel, and each member stops serving when its entry commits [inference: minutes for the largest networks]. Country-scoped takedowns return 451 [unverified that GitHub uses 451] using a GeoIP table on the front, passed in the assertion. An account takedown is a suspension.

**CDN for public content.** Managed enables subdomain isolation (`research/wire-census.md#33`), and `raw.tributary.dev`, `codeload.tributary.dev`, and `objects.tributary.dev` sit behind CloudFront with front cells as the origin. CloudFront serves only immutable public bytes: raw files and archives keyed by commit SHA, release assets, and avatars. The cell checks the repository's core tier and answers 302 to a CloudFront signed URL that lives 10 minutes and carries the repository's `content_epoch`. A takedown or a switch to private bumps the epoch in its own entry, so no new URL is issued and old ones expire within 10 minutes, with no CloudFront invalidation on the request path. CloudFront's control plane lives in us-east-1 (`research/uptime.md`, summary), so distributions are created at install, and each subdomain has a Route 53 failover record to the front cells. Git smart HTTP and the APIs are never cached. Public repositories advertise `bundle-uri` with CloudFront bundles for clients that enable it, which default clients do not [inference], so the pack response cache carries anonymous clone load.

**Residency.** An org or enterprise with residency has its home cell, all its networks, its Actions runners, and its search documents in its residency domain. A fork into a resident org of a network that lives outside the residency is created detached: a new network in a resident slot, objects copied, `fork: true`, and a pull request back upstream gets 422 with a message that names the residency rule. A fork of a resident network by anyone joins the network in its cell. A transfer that would move a resident network's owner outside its residency, or bring an outside network into a resident org, gets the same kind of 422 ("Known deviations from GitHub"). Resident orgs' Actions secrets are ciphertext on the org's `Authz` chain in its home cell.

What stays in the owner's home cell, with Europe as the example. Everything on the owner's `Identity` chain never leaves it: password hashes, TOTP seeds, recovery codes, WebAuthn credentials, sessions, plaintext email addresses and their verification state, OAuth client secrets, IdP configuration and SCIM tokens, sign-in history with IP addresses, and the identity audit log. The `Authz` chain (memberships, teams, grants, org policies, installations, repository names) is copied only into `Mirror` chains in cells that host the owner's repositories, which for a resident owner sit in its residency domain [inference]. A European home cell is Paired inside Europe, so these survive a Region loss and leave Europe only if the owner's networks do. No escrow exists, because no other continent needs these facts to authorize, and a European continent loss loses them with the repositories homed there [inference].

What leaves Europe, and why. `global`'s three Regions hold the login, the account id, whose slot names the home cell, SHA-256 hashes of stored tokens with their scopes and expiry, SSH key fingerprints, HMAC digests of verified emails, app slugs, installation ids, verifying keys, and retired pairs, because any edge must resolve each one without a cell. Cards in other home cells hold the public listing fields of repositories that their accounts list. An enterprise that needs every identity fact in one geography, logins and token hashes included, gets its own namespace through BYOC, as GitHub offers `*.ghe.com`.

**Enterprise managed users.** An enterprise claims a shortcode in `global`, and the claim reserves the whole login suffix `_<shortcode>`. Managed users get `<base>_<shortcode>` logins that only the enterprise's SCIM endpoint can create, one claim per enterprise rather than one per user. A public login cannot collide, because public logins contain no underscore [inference from GitHub's EMU naming].

## Actions

**Workflow engine.** The server owns triggers and filters, matrix expansion, the `needs` graph, job-level `if`, concurrency groups, reusable workflows and `secrets: inherit`, environments and approvals, `GITHUB_TOKEN` minting and `permissions`, OIDC, label matching, job outputs, and retention (`research/actions-protocol.md#62`). The parser is a Rust port of the runner's MIT `GitHub.Actions.WorkflowParser` including `MatrixBuilder`, with `workflow-v1.0.json` as data and `@actions/workflow-parser` as a differential oracle (`#59`, `#60`). The template-token and context-data JSON converters are ported byte-exact (`#19`). Triggering is a chain consumer, so a run exists only if its push or PR entry committed, and run creation is idempotent on `(chain, seq, workflow path)`.

**Runner protocol.** Tributary returns `use_v2_flow: true` and implements the runner admin registration, broker, run service, launch service, and results service (`research/actions-protocol.md#5`, `#6`, `#12`, `#16`, `#17`, `#22`). The legacy distributedtask family is frozen and needs the VSS location service. The broker family is where GitHub invests, and the launch service is the one place Tributary controls which bytes run for each `uses:` (`#17`). Each Tributary release pins one tested runner version, sends `RunnerRefresh` to older runners with a download URL that the install itself serves from the actions pack's runner tarballs, publishes the next floor one release ahead with a warning to runners below it, and refuses versions below the current floor with `RunnerVersionTooOld` (`#25`). JIT configs always set `GitHubUrl` and `IsHostedServer=false` (`#2`). ARC scale-set endpoints (`_apis/runtime/runnerscalesets`, sessions, message queue, `acquirejobs`, `generatejitconfig`) ship at T1 against a pinned ARC range (`#30`).

**Org runners across cells.** An org-level runner registers in the org's home cell. Jobs in other cells that match no repository-level runner are offered to it by the source cell's `ActionsTrigger` consumer as a home delivery ("Cross-cell features"). The broker claims a job with one conditional-update RPC to the job's cell. `RunServiceUrl` carries the job id, and fronts route it by the job's slot, so acquire, renew, logs, and completion reach whichever cell holds the slot, through a slot move too, because job items and leases move under their chain's seal. The claim is the one cross-cell call in Actions.

**Toolkit hostname heuristics and SHA pins.** Tributary is GHES to the toolkit, and nothing on the server can change that, because `isGhes()` reads only `GITHUB_SERVER_URL` (`research/actions-protocol.md#43`, `#44`). The T0 contract is the GHES contract: cache v1 for `actions/cache@v4+`, legacy artifacts for `upload-artifact@v3.2.2` and `download-artifact@v3`, and the runner protocol. Tributary never alters the bytes of an action. The launch service resolves every `uses:` to the exact upstream bytes, from the install's `actions` mirror org, which holds byte-for-byte copies of upstream tags and commits that managed syncs directly and installs load from the signed actions pack ("Install operations"). For `upload-artifact@v4+`, `download-artifact@v4+`, `upload-pages-artifact`, and `deploy-pages`, the vendor publishes forks under `tributary-actions/*` that differ from upstream only in the `isGhes()` test (they also trust `TRIBUTARY_ACTIONS=true`, which every job sets). Each fork release is built reproducibly by CI from the upstream tag, and CI regenerates a signed **pin map** from upstream SHA to fork SHA for every upstream release, so the map is derived, not hand-kept. Substitution is an org policy with two settings. With tag substitution on (the managed default for orgs migrating from github.com), `actions/upload-artifact@v4` resolves to `tributary-actions/upload-artifact@v4`. SHA pins are substituted only when an org admin has approved the vendor's signed pin map, and then only for SHAs that appear in it. Every substitution prints one log line naming both references and both SHAs, and the job's OIDC token and run metadata record the bytes that ran. An unapproved SHA pin to `upload-artifact@v4+` fails exactly as it does on GHES, with an annotation that links the pin-map approval page and names the fork SHA that matches the pinned upstream SHA, so a team can pin the fork directly (graft from `arena/candidate-2`). I chose this over Gitea's JavaScript rewriting (`#57`) because rewriting changes the bytes behind a SHA without anyone approving it and depends on string patterns in 118 bundles.

**Hosted runner fleet.** Managed hosted runners run unmodified `actions/runner` inside Firecracker microVMs on long-lived metal hosts in separate runner AWS accounts per Region. One VM runs one job and is destroyed. The VM gets a JIT config and reaches cells only through the public front cells, exactly like a customer's runner, so a compromised VM holds only that job's runtime token, `ghs_` token, and OIDC capability. Runner accounts have no IAM trust into cell accounts and no network route to them other than the front. The instance metadata service is blocked inside VMs, and egress goes through per-pool NAT with published ranges in `/meta`. Warm VM pools on running hosts absorb EC2 launch outages. Pool growth uses EC2 launches, so the Actions job-start SLO, not the core SLOs, carries that risk. Images are built by porting `runner-images` Packer templates to an `amazon-ebs` source (`research/actions-protocol.md#64`, `#65`), starting with a smaller curated Ubuntu image.

**Cache.** Cache v1 (`_apis/artifactcache`) at T0 and twirp `CacheService` v2 at T1, with the Azure dialect shim that accepts Put Blob, Put Block, and Put Block List and returns `x-ms-request-id` (`#35`, `#39`). Downloads are presigned S3 URLs (`#36`). Entries are scoped by repository and ref, with GitHub's restore order (current ref, then default branch) and LRU eviction per repository at 10 GB by a worker consumer.

**Artifacts.** Legacy pipelines artifacts (`#40`) at T0. Twirp `ArtifactService` v4 at T1, uploads through the block shim that maps 8 MiB blocks onto S3 multipart parts in order, and downloads by 302 to presigned S3 URLs (`#37`, `#38`).

**Logs.** Results service twirp with Tributary-signed URLs that accept `comp=appendblock` and `seal=true` (`#22`, `#23`). Blocks land as S3 chunk objects and a worker compacts them per step. Live logs stream over the `FeedStreamUrl` WebSocket and `WorkflowStepsUpdate`.

**OIDC.** Issuer `https://HOST/_services/token`, which in managed mode is `https://tributary.dev/_services/token` for the whole service, with the claim set and legacy `sub` format of GHES and the `OWNER@ID/REPO@ID` format as an opt-in (`#41`, `#42`). The job's cell signs with its own key epoch, private keys never leave the cell, and the JWKS under the issuer publishes every cell's current and previous epochs from the verifying-key items in `global`.

**Coping with GitHub changing the toolkit.** The runner is pinned per release. A nightly conformance job runs the newest runner, the newest major of each first-party action, and the newest `@actions/cache` and `@actions/artifact` against the canary cell, and opens a ticket on the first failure. Fork rebuilds and pin-map regeneration run in the same job. If GitHub merges a vendor-neutral escape such as trusting `ACTIONS_RESULTS_URL` (toolkit issue #2439, `#51`), the forks become unnecessary and the substitution policy is retired.

## Frontend and native app

**Web.** React 19 with Primer React, the stack GitHub itself ships (`research/clients.md#62`-`#64`). The app reads data through the same public GraphQL and REST endpoints that clients use, with persisted queries, plus a small private `/_t/ui/*` API for diffs, file trees, and blame computed by the `git` role. Dogfooding the public API means a UI regression is often a wire regression caught by the same oracles. There is no Node server-side rendering tier, because that would add a runtime and a stateful-looking fleet to every mode. Instead the front `edge` serves the HTML shell and, for the first route, sends that route's persisted GraphQL query to the routed cell and inlines the JSON, so first paint needs no second round trip. Static assets are embedded in the edge binary and served with immutable cache headers, and managed mode puts CloudFront in front of the asset path and the isolation subdomains ("Public service concerns").

**Staying up when backends degrade.** The shell and assets come from edge memory, so the UI loads whenever the edge does. Each page region (file tree, diff, checks, timeline, search box) is its own error boundary with its own query, so a search outage empties the search box and nothing else (`research/uptime.md#49`). The client retries only idempotent reads, with a retry budget and jitter, and it never polls faster than `x-poll-interval`. Long diffs virtualize lines, following GitHub's 2026 diff work (`research/clients.md#62`).

**GPUI native app.** It does not earn a place at launch. Unmodified gh, GitHub Desktop, VS Code, and JetBrains already cover native workflows against a GHES-shaped host, and that compatibility is the product. GPUI is pre-1.0 with frequent breaking changes and is tied to Zed's repository (`research/clients.md#57`-`#59`). One narrow scope could justify it later: an offline-capable review inbox for very large pull requests, if the web diff misses its latency target on PRs above 10,000 changed lines. That decision waits for measurements from the web app, and the app would be a pure API client with no private endpoints.

## Synthesis decision

**Round 1** chose the cell. Three runners bet on a Spokes-style quorum on local NVMe, an S3 write-ahead log, and refs as Aurora DSQL rows. The lead scored them 19, 26, and 28 of 30 and the cross-judge 19, 25, and 26, and both picked refs as DSQL rows (`arena/SYNTHESIS.md`, `review/arena-judge.md`).

**Round 2** added the public namespace after the operator's decision (`FRAME.md`, "Operator decision, 2026-10-24"). The lead scored network-placed cells under a replicated global tier, owner-home cells with a DynamoDB claim registry, and a `graph` cluster over network stripes 26, 21, and 24 of 30, the cross-judge 25, 20, and 19, and both picked network-placed cells (`arena/round2/SYNTHESIS.md`, `review/round2-judge.md`). Network placement survives into this design.

**Round 3** made identity worldwide after the operator allowed DynamoDB global tables. The lead scored geo-homed DSQL authorities under an MRSC claim registry 25 and the all-DynamoDB global tier 21 against a baseline near 22, the cross-judge 22 and 21 against 21, and both picked the authorities (`arena/round3/SYNTHESIS.md`, `review/round3-judge.md`).

**Round 4** replaced the store. The operator asked whether the design needed Aurora DSQL and answered that the goal is a better, more scalable GitHub with less downtime, not a port (`FRAME.md`, "on the store"). Three runners designed all-DynamoDB foundations and the round 1 to 3 design was the baseline (`arena/round4/SYNTHESIS.md`):

| Design | Lead (first read) | Lead (after the judge) | Cross-judge |
| --- | --- | --- | --- |
| Baseline, Aurora DSQL | 36 | 33 | 30 |
| Candidate 1, one head per fork network | 41 | 38 | 36 |
| Candidate 2, home-Region transactions plus a journal | 33 | 31 | 30 (33 before a fact cap) |
| Candidate 3, a chain per repository, network, and owner | 39 | 41 | 41 |

Candidate 3 is this design's base. The judge put it ahead because candidate 1's revocation lease couples a continent's writes to its identity table, and because candidate 3 had fewer protocols (`review/round4-judge.md`). The sixth-pass fixes removed both reasons. The `Mirror` brought back a fail-closed lease like candidate 1's, and the protocol count grew to about 13 against about 8 or 9 for candidate 1 with the same grafts, so the two now tie at about 36 (`review/round4-foundation-attack.md`, findings 1 and 3) [inference]. Two tie-breaks keep candidate 3: chains per repository instead of one head per fork network, and epoch-keyed promotion instead of last-writer-wins heads. Its eight grafts are applied: required checks on the chain (graft 1, "Issues and pull requests"), repository restore from the chain (graft 2, "Repository chains and packs"), the write-class token re-check (graft 3, "Identity and tokens"), bounded stale fetches in Single cells (graft 4, "Repository chains and packs"), tiered folds (graft 5, "Folds"), the Milestone 0 throttle test (graft 6, "Build order"), no routing-control cluster in installs (graft 7, "Install operations"), and one SLA class per Paired cell (graft 8, "Shape"). Everything the foundation does not decide, such as the wire table, change safety, the install machinery, public service concerns, Actions, and the frontend, is carried over from the round 1 to 3 design with only the edits the foundation forces.

## Tradeoffs accepted

- We accept building and owning a fold engine (SQLite per chain and tier, snapshots, archive, refold, audit) in exchange for list endpoints with no shared query engine and no eventually consistent index. It is the largest new build risk, Milestone 0 races it against candidate 1's index lists, and graft 5 keeps it off the git and merge paths.
- We accept that every repository-scoped write in one repository serializes on one chain, capped near 1,000 entries a second, about 4 merges a second per base branch, and 50 comments a second, in exchange for every input to a decision living in one fold (`review/round4-judge.md`, Scale).
- We accept one strong tail read per chain per AZ's preferred node per read round trip, shared by the other serving nodes in that AZ, costing one cross-Region round trip within the cell's continent [inference from V2globaltables_HowItWorks], in exchange for read-your-writes everywhere without a replica protocol.
- We accept that a Paired cell has no stale-read mode while both replica Regions serve, so a cell whose `log` has no quorum stops, in exchange for never serving a fold that is not proven fresh, resting on the 99.999% Global Tables SLA (`research/dynamodb.md#22`). Single cells, and Paired installs left on one replica and the witness, accept the stale mode (graft 4): fetches and reads up to a signed limit behind, possibly missing writes acknowledged in the seconds before the outage, revocations frozen and expired token entries honored for the outage, and a fallback that a weekly drill keeps exercised (`research/uptime.md#5`).
- We accept token revocation within 5 s for writes and 60 s for reads, and suspension within 60 s, in exchange for edges that read `global` only on misses and write re-checks, never on a TTL that a config change can shorten into an overload. The 5 s write bound holds only while local replication lag stays under its 2 s alarm, and a failed local replica stretches it to 60 s.
- We accept one cross-continent round trip on every managed signup, login rename, token creation, and SSH key addition [guess: 95 to 225 ms], in exchange for RPO zero on the namespace with no reconstitution after a continent loss.
- We accept review verdicts in the core tier, one row per current verdict, in exchange for merges that never wait for a metadata load.
- We accept that a fork merge merges the reviewed head even if the fork moved within the put round trip, in exchange for merges that touch one chain.
- We accept multi-chain operations (fork, transfer, signup) that finish on first touch, each with a named commit point, finisher, and abort path, and a transfer that reserves the destination name before the repository moves, in exchange for having no transaction across chains.
- We accept that cross-repository lists, cards, notifications, and search lag by seconds, and that `refs/pull/N/head` lags a push by seconds as a derived ref.
- We accept a witness Region that holds table data (V2globaltables_HowItWorks), which a residency customer must accept as one of its three Regions, and that BYOC Paired runs only in the 15 MRSC Regions.
- We accept that DynamoDB is the single database under every cell, so an AWS-side DynamoDB regression in both Regions of a cell stops it. Cells span two Regions and managed cells avoid us-east-1 replicas (`research/uptime.md` implication 22).
- We accept that a fork network is never split, so the largest network must fit one cell, and that a slot move carries every network in the slot, in exchange for single-chain merges for every pull request and ids that route by arithmetic.
- We accept that a home cell is a service-wide dependency for its accounts' new installation tokens, stars, notifications, feeds, and cross-cell listings, and, 30 s after its heartbeat stops, for their writes that read a mirrored fact in other hosting cells, and that a compromised cell can mint installation tokens for its own accounts and job tokens for its own slots until its `kid` is revoked, in exchange for token minting with no shared service on the path.
- We accept a `Mirror` copy of each `Authz` entry in every hosting cell, a heartbeat per cell pair, a revocation's 204 that waits up to 30 s for a hosting cell, reads in a cut-off cell that stay on the last applied entry up to a signed limit, and grants that reach other hosting cells seconds late, in exchange for allows that never read another cell.
- We accept synchronous cross-cell calls for GraphQL queries that span cells, for org-runner job claims, and for the home tail read behind a denial that rests on a mirrored fact, with partial results or the denial standing on failure.
- We accept that Single cells do not meet fact 9, because a Region loss needs a `dr` promotion that launches nodes and may truncate chains within the stated RPO, in exchange for a single-Region cost for self-hosted installs. Paired cells meet fact 9 and are the managed and BYOC default.
- We accept an operator role in every install, with leases and cursors in the control buckets, intents under two keys, a watchdog, a deployer role, and status documents, in exchange for rollouts, renewals, and recovery that survive the one-hour session cap, a revoked deploy role, a week-long vendor outage, an air gap, and an impaired table.
- We accept a customer-only key for restores, promotions, failbacks, re-protection, table retirement, repository restores, uninstall, endpoint-changing config, and halts during a revocation, so in BYOC those wait for a customer with KMS access unless it pre-authorizes the config key for `DrPromote`, in exchange for a deploy role that cannot reach data or delete state through the operator.
- We accept that operator processes run the previous release until after the soak, so new operator code soaks less than the serving roles, in exchange for an operator that never upgrades itself mid-rollout.
- We accept that a table restore takes two customer-signed intents, calls DynamoDB's control plane, re-creates the `dr` replica, and leaves every fold cold, in exchange for never serving rewound state. Deletes keep their data 90 days, which costs storage, so most repairs never need a restore.
- We accept that once a format is enabled, swap-back below its reading release is refused and the fix rolls forward, and that entries cut at promotion or arriving late from the old epoch become stated loss rather than an overwrite.
- We accept that a Single install with `dr` stops home writes whenever its nodes cannot read the `dr` control bucket for 10 s, and that promotion waits 10 s plus the clock error, in exchange for no write acknowledged at the old home after promotion.
- We accept every mechanism that exists only because state lives on one chain per aggregate, listed here so that growth stays visible (`review/round4-foundation-attack.md`, census): the fold engine (SQLite per chain and tier, checkpoints, archive, refold, and audit); the tier split, with review verdicts in the core tier; the next-key `fresh` probe; the read-side machinery for hot chains (one preferred tail reader per AZ, peer fetch, a serving cap counted in readers times bytes, the inline rule, and the coalescing window for huge owners); forks across three chains with a finisher and an abort path, and GC that reads every member chain's fresh fold; chain-by-chain slot moves and `Reprotect` handovers with `Sealed` and `Unsealed`; the epoch in the entry key, with truncation and the late-entry re-scan at `dr` promotion; `RequiredCheck` entries with append, prune, and backfill; and `Mirror` chains that copy entries with seq and digest, with a format gate that counts every cell reading a mirror. Markers, cursors, `Remark`, the seal fence, stale mode, and the mirror lease are shared with candidate 1 and not counted. A change that adds such a mechanism adds it here.
- We accept that a single-node evaluation install takes a short outage for each node image change, carries no availability SLO, and skips drills that take a node out of rotation.
- We accept, in the small-install profile, 4 GiB burstable nodes whose surplus credits cost extra under sustained load, nodes with public IPs behind security groups, issue search from FTS5 tables in folds instead of an index, cross-repository search that can return `incomplete_results`, and webhooks and Actions triggers up to about half a second later, in exchange for a 50-developer bill of $226 a month instead of $1,288 (`research/costs.md`).
- We accept that third-party secret scanners will classify a leaked Tributary token as a GitHub token and may send it to `api.github.com` to validate [inference], in exchange for GitHub's token prefixes, which Renovate branches on (`research/clients.md` implication 6). Tributary runs its own push-time secret scanning for these prefixes.

## Alternatives considered

- **Round 1 to 3: everything in Aurora DSQL** (`arena/round4/baseline-DESIGN.md`). It keeps every invariant inside one transaction, which is its strength. It loses on downtime and reach. DSQL is offered in 20 Regions against DynamoDB's 34 (`research/dynamodb.md#24`, `#26`), so 14 Regions, Zurich included, cannot install it (journey 7). Multi-Region DSQL cannot cross continents (`#27`), which forced three geo authorities, a claim registry, freshness boards, writer leases, ClockBound, escrow, and `reconstitute`, about a dozen novel protocols whose bugs reach every identity write; one MRSC table replaces them. Each cluster allows 10,000 connections and 100 new a second (`research/uptime.md#27`), its git path depends on a query planner and optimistic concurrency on shard rows, Repeatable Read admits write skew unless every input bumps a version, a DSQL engine regression under every cell at once had no bulkhead, and atomic pushes stopped at 1,000 refs because of the 3,000-row limit. Its 2,000-developer Paired install costs $24,879 a month against $20,636 here (`arena/round4/candidate-3/cost.py`). The cross-judge scored it 30 (`review/round4-judge.md`). It is the flip target if the chain append gate fails.
- **Round 4 candidate 1: one head item per fork network** (`arena/round4/candidate-1/DESIGN.md`). Lists are DynamoDB index items read strongly, so it needs no fold engine, and fork merges are atomic. The judge ranked it second for its continent-wide revocation lease and its larger protocol count (`review/round4-judge.md`). This design's `Mirror` lease and its own protocol growth cancelled both, so after the sixth-pass fixes the two tie at about 36 (`review/round4-foundation-attack.md`) [inference]. Two tie-breaks keep this design: chains per repository instead of one network head, whose one partition carries every metadata event and cannot be split, and epoch-keyed promotion instead of a last-writer-wins head. Its index lists race the fold engine in Milestone 0 and become the list engine if they win.
- **Round 4 candidate 2: home-Region transactions plus a journal** (`arena/round4/candidate-2/DESIGN.md`). It has the strictest merge and spreads load best. It lost because RPO zero rests on a home-grown prepare, transaction, and commit-mark protocol with a home lease, promotion, and standby, which halts the cell whenever the lease cannot renew, and its 99.999% claim did not hold for single-Region tables (`review/round4-judge.md`, fact check 22).
- **All DynamoDB with lists in GSIs and Streams as the outbox** (round 3's candidate 2 shape). GSIs are eventually consistent (`research/dynamodb.md#11`), so `gh issue list --label bug` right after create can miss the issue, 20 GSIs a table cannot index GitHub's filters, and streams as the outbox lose events after a day-long consumer outage (`#13`).
- **Aurora PostgreSQL with Global Database.** Unplanned cross-Region failover loses seconds and is an RDS control-plane call that may not fence the old primary (`research/uptime.md#24`, `#25`), and it brings back every GitHub database incident class at once (`#44`).
- **S3 write-ahead log with a CAS manifest per repository (Continuity, walgit).** S3 has no synchronous cross-Region compare-and-swap (`research/git-storage.md` implication 6), so RPO zero needs a second mechanism, and refs and pull requests live in two stores with no shared commit point.
- **Spokes-style replica quorum on local NVMe** (`research/git-storage.md#2`-`#6`). Every node holds canonical state, so every deploy needs fencing and replica catch-up that the vendor's BYOC machinery lacks (`research/byoc-grounding.md` item 7), and pull requests still need a separate database.
- **MemoryDB for queues, rate limits, or sessions.** Its shards fail over primary to replica, the class of GitHub's March 2026 Redis failover with no writable primary (`research/uptime.md#47`). Single-item DynamoDB writes cover each use.
- **Kinesis Data Streams for events.** It adds a store to every install for retention that per-consumer markers already give, since the chain is the durable log.
- **OpenSearch as the list engine.** It is GitHub's April 2026 failure (`research/uptime.md#49`).
- **Owner-home cells with forks in the fork owner's cell.** `bob/widgets` and `acme/widgets` then sit in different cells, so the common public pull request needs a cross-cell merge.
- **A synchronous global identity service behind caches.** This is GitHub's shape, whose load scales with requests and every cache setting, the February 2026 failure (`research/uptime.md#47`).
- **An ARC routing-control cluster for installs.** It costs about $1,825 a month per cluster (`research/pricing.md`), more than a whole 50-developer Single install, and Route 53 failover records with health checks do the job (graft 7).
- **The vendor's deploy tool driving every stage from outside the account.** A Paired rollout outlives the one-hour chained session, a revoked role or vendor outage strands a rollout mid-AZ, and an air-gapped install has no path in (`review/byoc-walk.md` findings 1, 2, 10, and 12).

## Open questions and risks

- MRSC put and strong-read latency for each trio are unpublished (`research/uptime.md` open question 3). Every latency number here is a guess until Milestone 0.
- Do MRSC replicas support PITR and AWS Backup cross-Region copy, and how long does a 100 GB PITR restore take? (`review/round4-judge.md`, fact checks 20 and 27) [unverified]
- Does the Global Tables SLA apply per account, so that the managed `global` account's tables and a cell account's tables are judged separately? (`review/round4-judge.md`, fact check 22) [inference that it does]
- Does a strong GetItem on an absent key cost one read unit, and do MRSC strong reads cost the same units as single-Region ones? `cost.py` assumes yes [unverified].
- Do monotonically increasing sort keys keep a chain's tail in one partition, so its ceiling is exactly 1,000 write units a second (`research/dynamodb.md#8`)?
- How does AWS deploy DynamoDB changes across Regions and cells? A simultaneous regression in both Regions of every cell is the one failure no bulkhead here covers.
- Scale ceilings the judge flagged remain: about 4 merges a second per base branch, 50 comments a second per repository, and an unmeasured fold-engine ceiling. Is SQLite's single-writer model enough at 1,000 entries a second on one fold? (`review/round4-judge.md`, Scale)
- Is a t4g.medium with 4 GiB enough for a small install's folds, caches, and repacks of large fork networks, and how often will surplus-credit spend or memory pressure force a move to `m8g.large`? [guess]
- How slow is cross-repository FTS5 search for a viewer who can read thousands of repositories, and how often does it hit its deadline and return `incomplete_results`? [unverified]
- Reads keep a 60 s token-revocation bound after graft 3. Is that acceptable to security teams used to GitHub's revocation, and does MRSC replication to each local replica stay under 2 s at p99, so the 5 s write bound holds? [unverified]
- How long does a planned copy of `global` into a new trio take, and how do edges read both trios during it without letting one login be claimed twice? [unverified]
- Is a 10 s no-promotion lease with a 1 s clock error bound right, and how often will an S3 fault in the `dr` Region stop home writes through it? Can a replicated control bucket, which S3 may replicate up to 15 minutes late, serve an air-gapped install's no-promotion read at all? [guess]
- Is a 1 s heartbeat and a 15-minute read limit for a cut-off hosting cell right, and how large does a heartbeat grow for a cell pair that shares many owners? [guess]
- How long do `Reprotect` of a large install and the Batch Replication behind `EnableDr` take while serving? [unverified]
- Is a witness Region holding data acceptable to residency customers?
- How large does an edge's cache need to be at managed scale for misses and re-checks to stay under their budgets, and is 1,000 re-checks a second per node right? [guess]
- Can the target catch a hot chain up to its `Sealed` entry within 1 s while the rest of its slot is still copying?
- Can the largest public fork network fit one cell, and what happens when it cannot? Can one home cell carry an account that stars or watches millions of repositories?
- Is the signed pin map an acceptable answer for security teams that pin SHAs?
- Does returning `GitHub lives!` and GitHub documentation URLs raise trademark issues for the vendor?
- Does any GHES-targeted client assume 40-character installation tokens?
- Is a 15-minute watchdog deadline long enough for a 10-minute clone drain and a gate on a slow AZ? [guess]
- Will BYOC customers keep the customer-only key usable by someone on call at 2am, or pre-authorize the config key for `DrPromote`? [guess]
- Are SHA-256 token hashes and SSH fingerprints of a resident enterprise's managed users acceptable outside its residency in `global`? [inference: hashes of random secrets identify no person, unverified legally]
