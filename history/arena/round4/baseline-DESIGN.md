# Tributary design: refs are rows in each cell's Aurora DSQL core cluster, under one global namespace

## Summary

Tributary is one Rust binary, pinned upstream git, a React web app, and two AWS stores for cells, Aurora DSQL and S3, plus a DynamoDB claim registry in managed only. Each cell runs two DSQL clusters. `core` holds every fact git, merges, and authorization depend on: refs, the pack manifest, small packs, issues, pull requests, a replica of the authorization graph, check runs, and the event outbox. `aux` holds Actions state, webhook deliveries, notifications, inter-cell logs, and audit, so Actions load or an `aux` migration cannot stop git. Pack bytes above 1 MiB live in S3. Node disks hold only caches that can be thrown away. Managed Tributary is one public, github.com-style namespace at `tributary.dev`. A worldwide claim registry in DynamoDB MRSC decides every name that must be unique on Earth, three Aurora DSQL geo authorities, one per continent group, commit every other account, credential, and authorization fact in its owner's home geography, and every request reads those facts from local replicas, never from the registry or an authority.

- A push is acknowledged when its DSQL transaction commits. Paired cells commit in two Regions plus a witness, so an acknowledged push and every metadata write survive the permanent loss of a Region, which AWS suffered in me-south-1 in 2026.
- A merge moves the base ref, marks the pull request merged, and writes the webhook event in one transaction, so pull request state cannot contradict the refs. This holds for every pull request, cross-owner ones from forks included, because a fork network lives in one cell.
- While `core` is unreachable, git fetches are served from node caches at their last proven refresh for at most a signed per-cell limit (default 2 hours), and pushes return 503. Every other surface serves no stale reads.
- Managed is one host, `tributary.dev`, with public repositories, anonymous read, forks and pull requests across owners, stars, follows, and search. BYOC and self-hosted installs keep their own namespace, as each GHES instance does. On every host, unmodified git, gh, GCM, Desktop, VS Code, JetBrains, Renovate, Terraform, ARC, and `actions/runner` see GitHub Enterprise Server 3.22.
- Identity writes (signup, sign-in, token creation, name claims, forks, grants) need the home authority of the account or org they write, in managed a writer lease that renews through the registry's two-of-three quorum, and for name claims one registry write on another continent. An authority outage stops identity writes only for the roots homed in its geography. Fetches, pushes, merges, issues, Actions, and installation tokens keep working in every cell while the registry or any authority is down, and "no" answers stay immediate during the outage, because every create and every revocation returns only after each serving replica has applied it or has stopped answering "no". No replica says "no" about a fact whose write was acknowledged. Losing a Region makes no survivor lag, because a replica that reads its authority proves its own freshness. A cell cut off from an authority while the rest of the fleet advances fails closed, after 30 s of lag, the writes that depend on that geography, so a removed grant cannot keep authorizing writes there.
- Managed, BYOC, and self-hosted ship the same signed bundle through the vendor's existing BYOC release machinery. In every mode an in-account `operator` role runs each lifecycle step from signed intents, so no rollout, renewal, backup, or recovery depends on a vendor session ("Install operations"). Upgrades never need maintenance mode, except that a single-node evaluation install takes a short outage for a node image change.
- Milestone 0 is a benchmark and three gates. They decide whether DSQL can carry a hot repository, whether the `core` bulkheads hold, and whether one geo authority's change log stays gap-free and fresh for about 130 followers on other continents. If a `core` gate fails, or if AWS cannot stage DSQL engine upgrades cluster by cluster, the S3 write-ahead-log design in `arena/candidate-2/DESIGN.md` becomes the base. If the authority gate fails, the global tier switches to `arena/round3/candidate-2/DESIGN.md`, whose freshness needs no commit-ordered log.

`arena/SYNTHESIS.md` records how the cell design was chosen from three candidates, `arena/round2/SYNTHESIS.md` how the global namespace layer was chosen, and `arena/round3/SYNTHESIS.md` how that layer became worldwide.

## Problem

Tributary must look exactly like a GitHub Enterprise Server (GHES) host to unmodified clients, keep git, pull requests, and the APIs up before anything else, and never lose an acknowledged push, in three modes that ship as one artifact. Five research facts make the shape non-obvious. A Region and its data can vanish for good (`research/uptime.md#37`, `#38`), so "never lose a push" needs a copy outside the Region at acknowledgment time, not later. Every large host that keeps refs on local disks pays for a replica quorum, placement database, checksums, and sweepers (`research/git-storage.md#2`-`#6`), and the vendor's BYOC machinery has no deploy stage for stateful fleets and cannot observe storage health (`research/byoc-grounding.md` reuse items 7 and 8). No Rust library can serve git, so upstream git must stay the pack engine (`research/git-storage.md#44`-`#49`). Pull request state, refs, and the webhook stream are three facts about one event, and hosts that keep them in separate stores show divergence races, for example Praefect's PostReceiveHook firing before replication (`research/git-storage.md#10`). Finally, recovery must never call a control-plane API or launch capacity (`research/uptime.md#32`-`#35`), which rules out any database whose cross-Region failover is an API call (`research/uptime.md#24`, `#25`). This candidate bets that the Azure DevOps lineage (`research/git-storage.md#22`, options table last row) is now the strongest shape on AWS because Aurora DSQL commits synchronously across Regions with no failover step (`research/uptime.md#26`): refs, pack manifests, small packs, issues, pull requests, permissions, and the outbox live in each cell's `core` DSQL cluster, Actions state lives in a second `aux` cluster, pack bytes live in S3, and every disk is a cache.

The operator then made managed Tributary one public namespace (`FRAME.md`, "Operator decision, 2026-10-24"), so three kinds of fact span the service. A login is unique across users, orgs, and enterprises, a repository name must resolve at any edge, and an authorization fact can be needed in any cell, because any user may fork, push to, review, or merge in any repository they can reach. Two GitHub failures shape that layer. On February 9, 2026 a cache TTL cut and a tenfold read increase from two client releases overloaded GitHub's core auth and user database (`research/uptime.md#47`), and in May 2023 expensive writes on a shared permissions cluster broke GitHub App tokens for about 12 hours (`#44`). A store of global facts that requests read synchronously inherits both. Partitioning identity and repositories by owner breaks the public workflow instead, because `bob/widgets` and `acme/widgets` would sit in different cells and their merge could no longer be one transaction. This design separates writing a global fact from reading it. A claim registry and three geo authorities commit, data cells and front cells read local replicas fed by the authorities' gap-free change logs, and repositories are placed by fork network, because GitHub opens pull requests only within one network (https://docs.github.com/en/rest/pulls/pulls).

The operator later required worldwide operation and allowed DynamoDB global tables (`FRAME.md`, "Operator decision, 2026-10-24, later"). One DSQL cluster in North America would make every European and Asian identity write cross an ocean, stop identity writes worldwide when that Region set fails, and store no identity fact in its owner's geography. Four AWS facts, read on 2026-10-24 (`review/round3-judge.md`, fact checks), set the global tier's shape. DSQL multi-Region clusters stay inside one of three Region sets, North America, Europe, and Asia-Pacific (https://docs.aws.amazon.com/aurora-dsql/latest/userguide/what-is-aurora-dsql.html). An MRSC global table spans exactly three of 15 Regions in any combination, including one per continent. A write returns after it replicates to at least one other Region, conditional writes evaluate against the latest version, and a Region keeps accepting writes while one other Region of the three is reachable, but MRSC has no transactions (https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/V2globaltables_HowItWorks.html; https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/bp-global-table-design.html). DynamoDB Streams orders records per item only (https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/Streams.html), so no stream can prove that a follower has seen every write before a time. MREC resolves concurrent writes by last writer wins and lets other Regions see partial transactions (`research/uptime.md#30`). So a key that every owner on Earth competes for is one MRSC item whose conditional write is its commit point. Every other global fact belongs to one account or org, needs multi-row transactions and a commit-ordered log, and lives in the DSQL authority of its owner's continent.

Where this design answers each required fact from `arena/TASK.md`. (1) Region loss and RPO: the commit rule in "Repository storage and ref transactions", the `region` failure rows, and the durability class in "Deployment modes", with RPO zero in Paired cells. (2) Object storage as truth: S3 plus DSQL is the only durable state, and NVMe repositories are disposable caches. (3) Upstream git stays the engine: `trib-git` and "Build order". (4) Toolkit hostname heuristics and SHA pins: "Actions" and the `actions-artifacts` row. (5) `use_v2_flow: true`: "Actions". (6) The GHES look: "Wire compatibility". (7) Token and id formats: "Identity and tokens" and "Namespace and cell placement". (8) BYOC machinery gaps and upgrade downtime: "Change safety", "Deployment modes", and "Install operations". (9) No launch or control-plane call in recovery: every `control-plane` row. Paired cells meet it, and Regional cells do not, because Regional recovery launches node capacity (the DSQL `region` row).

## Usage (caller's view)

**Operator quickstart, self-hosted.**

A self-hoster runs three EC2 instances of one binary, two Aurora DSQL clusters (`core` and `aux`), one S3 bucket, and one NLB in its home Region. Setting a `dr` Region, as below, adds warm `core` and `aux` clusters, a recovery bucket, and a small `dr-apply` node group there, four clusters in all. There is no database server, no Redis, and no replica set to repair. The deploy tool, bootstrap, and signed registry are the vendor's existing BYOC machinery with a Tributary product profile (`research/byoc-grounding.md#22`, `#23`), and the install's own `operator` role runs every step they request ("Install operations").

```sh
# 1. One time, in a dedicated AWS account. The bootstrap's product variable selects trib- prefixes, the Tributary
#    deploy policy, and the PassRole services, and creates the install's config key and customer-only key.
tofu -chdir=bootstrap/customer apply \
  -var product=tributary -var deploy_principal_arn=arn:aws:iam::111122223333:role/ci-deploy
# 2. Fetch and verify the signed release (ECDSA P-256, create-only registry), then copy its AMI into each Region.
platform-deploy release fetch --registry prod --release tributary-2027.03.1
tributary release import-ami --release tributary-2027.03.1 --regions eu-west-1,eu-central-1
# 3. Describe the install. The "tributary" block is the only product-specific part of the target.
cat > target.json <<'EOF'
{ "version": 1, "name": "git-prod", "profile": "tributary-customer",
  "aws": { "accountId": "111122223333", "region": "eu-west-1" },
  "terraform": { "stateBucket": "platform-terraform-state-111122223333" },
  "tributary": {
    "hostname": "github.example.com",
    "durability": { "class": "regional", "drRegion": "eu-central-1" },
    "nodes": { "layout": "combined", "perAz": 1, "instanceType": "i8g.2xlarge" } } }
EOF
# 4. Preflight every install Region, copy the release into releases/ in each control bucket, and submit the rollout
#    intent. The operator role runs it, and the tool polls.
platform-deploy deploy --target target.json --bundle tributary-2027.03.1
# 5. First admin. Runs on a node through SSM and prints a one-time sign-in link.
tributary admin bootstrap --host github.example.com --first-admin alice
```

A dead node or AZ needs no repair by hand. The Auto Scaling group replaces a dead node whenever EC2 can launch, and the two surviving nodes already serve every repository from S3 and DSQL. An impaired DSQL `core` is the one 2am decision, and the runbook in "Install operations" ends it in `tributary dr promote` or in waiting. Upgrades are `platform-deploy deploy` with a newer bundle, which submits an intent that the operator role runs, and never need a maintenance window.

**Operator quickstart, BYOC.**

The customer applies the same bootstrap with `product=tributary` and `deploy_principal_arn` set to the vendor's deploy principal and an ExternalId. It creates the install's config key, a customer-only key that no deploy role can use, the Tributary deploy policy, which can neither read repository data nor delete stateful resources, and the read-only observer role. The customer delegates one DNS subzone (for example `git.example.com`) or uploads a certificate, and chooses the durability class. Paired is the BYOC default and needs a second Region and a witness Region enabled in the same account, all three inside one DSQL Region set, which the target preflight checks. The vendor's pipeline then runs the same `deploy` command, which copies the verified release into the install's control buckets and submits a signed rollout intent that the install's `operator` role runs. The customer grants nothing else, and the install keeps serving, renewing certificates, and rotating keys with the vendor unreachable ("Install operations").

**Operator quickstart, managed.**

Nothing is provisioned per customer. A user signs up at `tributary.dev` and picks a home geography, by default the continent of the front cell that served the page (South America maps to North America, Africa and the Middle East to Europe, and Oceania and India to Asia-Pacific). An org's creator picks the org's home. Each signup or org creation is one registry claim between two transactions in the home authority ("Geographies, the claim registry, and the authorities"). An enterprise account adds SAML or OIDC on its orgs, a managed-user shortcode, and optionally a residency (for example EU, whose networks land in cells on eu-west-1 and eu-central-1 with an eu-west-3 witness). The fleet control plane adds data cells and front cells ahead of demand and moves slots between cells. No signup calls a control-plane API.

**What a `gh` user types.**

```sh
gh auth login --hostname tributary.dev               # device flow with gh's own client id 178c6fc778ccc68e1d6a
git clone https://tributary.dev/torvalds/linux.git   # anonymous, public
gh repo fork acme/widgets --clone && cd widgets
git switch -c fix && git commit -am fix && git push origin fix
gh pr create --repo acme/widgets --head bob:fix --fill && gh pr checks --watch
```

gh classifies the host as GHES because it is not `github.com`, `*.ghe.com`, or `github.localhost` (`research/clients.md#1`), derives `/api/v3/` and `/api/graphql` (`#3`), and reads `installed_version` from `/api/v3/meta` (`#9`). Nothing else is configured. BYOC and self-hosted users type the same commands against their own host.

**Journey 1: `git push` to a protected branch.**

`git push origin main` to `https://tributary.dev/acme/payments.git` from a user without bypass rights.

1. Route 53 latency records, health-checked by a synthetic routed request through each front cell, return the nearest Region's front cells as multivalue answers (data plane only, `research/uptime.md#15`). The NLB passes TCP to a front `edge`, which terminates TLS with the service certificate from memory and stamps `X-GitHub-Request-Id`.
2. `GET /acme/payments.git/info/refs?service=git-receive-pack`. The edge validates the Basic password as a `gho_` token, prefix and CRC32 offline, then finds its hash in the projection on local disk. `route` maps login `acme` to its account, `(acme, payments)` to repository R with epoch e, R's slot bits to slot 7, and slot 7 to data cell `c7`: four point lookups and no network I/O. The edge forwards over PrivateLink to `c7`'s ingress with a signed `Principal` assertion stamped `asked_at`. Datastore: the front projection.
3. Ingress verifies the assertion and forwards to the `git` role on the repository's rendezvous-preferred cache node in the caller's AZ. That node reads one DSQL snapshot: `slot_state` (Serving), `g_repo_dir(R)` (epoch e, so the route is current), the `ref_shard` versions, and the live pack list. It compares them with its cache, pulls missing packs from S3 or inline rows, applies changed refs to the local reftable, and advertises `report-status report-status-v2 delete-refs side-band-64k ofs-delta atomic object-format=sha1 quiet push-options` (`research/wire-census.md#44`). Datastores: DSQL `slot_state`, `g_repo_dir`, `ref_shard`, `ref`, `pack`; S3 pack bucket; local NVMe.
4. `POST /git-receive-pack`. Rust parses the commands and streams the pack into upstream `git index-pack --stdin --fix-thin --strict` in a quarantine directory, then runs `git rev-list --objects --stdin --not --all` for connectivity against the cache.
5. Rule evaluation in Rust over one DSQL snapshot of `branch_rule` and the replica rows `g_repo_grant`, `g_team_member`, `g_membership`, and `g_org_policy`: `main` requires a pull request and the user has no bypass, so `refs/heads/main` gets `ng refs/heads/main protected branch hook declined` with the `GH006: Protected branch update failed` text on side-band 2. Other refs in a non-atomic push continue. With `--atomic`, the whole push is rejected.
6. For refs that pass, the pack is placed. A pack with no objects, such as a new branch at an existing commit, writes no row and no object. At most 1 MiB goes inline into the commit transaction. Larger packs are PUT to S3 with `If-None-Match: *` under `n/<network>/<pack-id>.pack|.idx`, where the pack id is fresh for each placement, to two of the three Regional buckets in a Paired cell, before the transaction opens.
7. One DSQL transaction: read `slot_state`, compare-and-set every accepted ref row (an insert for a new ref, a delete plus a tombstone for a deleted one), bump the touched `ref_shard` rows, insert the `pack` row if the push carried objects, the `push` row, and the `ref_log` rows, and insert the `push` outbox event with one pending row per subscribed consumer. Commit. Datastores: DSQL `slot_state`, `ref`, `ref_tombstone`, `ref_shard`, `pack`, `pack_inline`, `push`, `ref_log`, `outbox`, `outbox_pending`. Seconds later the `pr-sync` consumer moves `refs/pull/N/head` for each open PR that this branch heads and emits `pull_request.synchronize` with the new head SHA captured in its own transaction.
8. Only after the commit returns does `report-status` say `ok` for each accepted ref. The local cache then moves the quarantine objects into its repository. If the node dies between commit and report, the push is durable and the client sees a broken connection, the same contract git gives for any server crash after the ref update.

**Journey 2: `bob` forks `acme/widgets`, pushes, opens a pull request, and a maintainer merges.**

1. `POST /api/v3/repos/acme/widgets/forks` routes by `acme/widgets` to network N's cell `c7`. `c7`'s `api` authorizes read from its snapshot (public), and `place_fork` returns N's slot. It allocates R2 from that slot's `id_block`. `writer_geo` names bob's home geography, and when that is not `c7`'s, `c7` calls the `identity` handler of a cell in bob's home over PrivateLink. The handler runs one transaction in bob's home authority that inserts `repo_name(bob, widgets) = Live { R2 }` and `repo_dir(R2)`, appended to bob's shared log partition, and bob's unique key decides any collision. It returns once every serving edge and data cell covers that commit, as every create does. A taken name gets GitHub's numbered suffix [unverified exact rule]. One `core` transaction then creates R2 in network N and copies branch ref rows in chunks of 1,000, and the API returns 202, as GitHub's fork API does. If `c7` crashes between the two, the pending-emit row that its applier wrote for the slot makes the slot's owner create the missing rows.
2. `git push origin fix` to `bob/widgets`. The fork returned only after every serving front covered R2's name, so the front finds R2 and routes by its slot to `c7`, where `commit_push` runs as in journey 1. A front named lagging for bob's geography does not trust a miss, and waits until its watermark passes `asked_at`.
3. `gh pr create --repo acme/widgets --head bob:fix` routes by the base repository to `c7`. The PR row, the head ref row `(R2, fix)`, and the base ref row all live in `c7` `core`. Notifications to `acme`'s watchers leave through `c7`'s inter-cell log (journey 5).
4. A maintainer runs `gh pr merge 17 --squash`, which sends the GraphQL `mergePullRequest` mutation. The PR's node id carries the repository id first, so the front routes it by slot to `c7`, whose `api` role reads one DSQL snapshot to plan the merge: the PR row, the head branch's own ref row (`head.repo`, `head.branch`), the base ref, reviews, `branch_rule`, `check_run` rows for the head SHA, and the maintainer's `g_*` grants. It evaluates protection in Rust to reject early. Datastores: DSQL `pull_request`, `ref`, `review`, `branch_rule`, `check_run`, `g_*`.
5. It asks the `git` role on the network's cache node for a merge plan. The node runs `git merge-tree --write-tree base head`, `git commit-tree`, verifies that the tree diff of the result equals the PR's diff (the April 2026 merge-queue lesson, `research/uptime.md#49`), and packs the new commit and trees with `git pack-objects`. The plan returns the new commit id and the pack bytes.
6. The `api` role places the pack (inline in practice) and runs one DSQL transaction. Inside the `run_tx` closure, on the transaction's own snapshot, it re-reads those rows and re-runs `check_protection`. It then compare-and-sets the head branch's ref row against the plan's head (a version bump with `WHERE target = plan.head`, or the delete if the head branch is to be deleted), sets the PR to `Merged` with `WHERE state = 'open' AND review_version = :seen` and bumps `review_version`, compare-and-sets `refs/heads/main` from the plan's base SHA to the merge commit, inserts `merged` and `closed` timeline events, bumps ref shards, inserts the pack row, and emits `pull_request` (`closed`, merged) and `push` outbox events with the PR's head SHA, base SHA, state, and labels captured. Datastores: DSQL `ref`, `ref_shard`, `pull_request`, `issue_event`, `pack`, `pack_inline`, `outbox`, `outbox_pending`.
7. If any input changed, the merge fails with a non-retryable error and GitHub's text: `Head branch was modified. Review and try the merge again.` when the head ref moved, `Base branch was modified. Review and try the merge again.` when `main` moved, or the protection failure when a review or rule now blocks the merge. A 40001 retry re-runs the whole closure, protection check included, so a concurrent change never retries into success. A merged PR whose base ref did not move is impossible, and so is the reverse.

The merge is one `core` transaction for every PR, cross-owner ones included. What weakens is authorization freshness: the maintainer's permission comes from the replica in the same snapshot as the refs, which trails the authorities by the apply lag, so a grant committed before the request is never missed and a removal in the last second can allow one merge. Step 1 writes bob's home authority, so bob's forks fail with 503 while it is unreachable. Steps 2 to 7 touch nothing outside `c7` except the front.

**Journey 3: `actions/runner` runs a job with `actions/checkout` and `actions/cache`.**

1. The `push` event from journey 1 has one pending row per subscribed consumer. The `worker` that holds the `ActionsTrigger` consumer's lease on partition `hash(network) % 256` reads its pending row, reads `.github/workflows/*.yml` at the pushed SHA from the cache node, and parses them with the Rust port of `GitHub.Actions.WorkflowParser` (`research/actions-protocol.md#60`). One `aux` transaction, idempotent on `(event id, workflow path)`, inserts `workflow_run` and `job` rows in `Queued`. Then one `core` transaction inserts `check_suite` and `check_run` rows keyed by job attempt plus `workflow_run` and `workflow_job` outbox events, and deletes the pending row. A crash between the two repeats both idempotently. Datastores: `aux` `workflow_run`, `job`; `core` `check_suite`, `check_run`, `outbox`, `outbox_pending`.
2. The runner was registered earlier: `POST /api/v3/actions/runner-registration` with `RemoteAuth` returned `use_v2_flow: true`, then `POST /api/v3/actions/runners/register` created a `runner` row and the runner exchanged its RSA-signed assertion for a JWT at `authorizationUrlV2` (`research/actions-protocol.md#5`, `#6`, `#8`).
3. The runner long-polls `GET /_services/broker/message?sessionId=...` on the `actions` role. The broker matches its labels against queued jobs and wins the job with a compare-and-set in `aux`, `Queued -> Assigned{runner, lease}`. It returns a `RunnerJobRequest` with `RunServiceUrl`. Datastore: `aux` `job`, `runner_session`.
4. `POST {run}/acquirejob` returns the `AgentJobRequestMessage`. Its `SystemVssConnection` data carries `CacheServerUrl`, `ResultsServiceUrl`, `GenerateIdTokenUrl`, and the runtime token, and `system.github.launch_endpoint` points at the launch service (`research/actions-protocol.md#16`, `#20`). The job becomes `InProgress`.
5. The runner posts `runnerresolve/actions` for `actions/checkout@v5` and `actions/cache@v4`. The launch service resolves both in the service's `actions` mirror org (byte-identical copies of upstream, which managed syncs and installs load from signed actions packs) and returns `https://tributary.dev/_codeload/actions/checkout/legacy.tar.gz/<sha>`. The codeload path is served by `git archive` on a cache node and cached in S3 by `(repo, sha, format)`.
6. `actions/checkout` runs `git fetch` with the job's `ghs_` token. That is the upload-pack half of journey 1: DSQL snapshot read, local cache, upstream `git upload-pack`.
7. `actions/cache` classifies the host as GHES (`research/actions-protocol.md#43`) and uses cache v1: `GET {ACTIONS_CACHE_URL}_apis/artifactcache/cache?keys=...&version=...`. The `actions` role reads `cache_entry` by `(repo, scope ref, key, version)` in `aux` and returns a presigned S3 URL, and the runner does a plain GET because the host is not `*.blob.core.windows.net` (`#36`). On a miss, the post step reserves (`POST caches`), uploads `Content-Range` chunks (`PATCH caches/{id}`) that the role streams into an S3 multipart upload, and finalizes (`POST caches/{id}`), which commits the `cache_entry` row. Datastores: `aux` `cache_entry`; S3 cache bucket.
8. Logs go through the results service: `GetStepLogsSignedBlobURL` returns a Tributary-signed URL with `BLOB_STORAGE_TYPE_UNSPECIFIED`, and the role accepts `comp=appendblock` and `seal=true` into S3 chunk objects (`research/actions-protocol.md#23`). `renewjob` extends the lease in `aux`. `completejob` commits `Completed{conclusion}` and a `check_relay` row in one `aux` transaction. The `worker` check relay then writes the `check_run` conclusion and `workflow_job.completed` in one `core` transaction keyed by job attempt, so a repeat changes nothing, and merges see the conclusion seconds after the job ends. The run's own status is derived by the run's single owner from job events, so parallel matrix jobs never contend on one row.

**Journey 4: two users race to create `newco`, then `newco/a` becomes `newco/b`.**

1. Both submit the new-organization form with home `Na`. The front routes each identity write to a healthy cell in North America, the caller's index cell first, and each cell's `identity` handler runs `run_claim`. A pending transaction in `auth-na` records the saga, a conditional `PutItem` on `login#newco` in the registry decides the race, and an activate transaction inserts `name("newco") = Live { O, Org }` with the claim's `ClaimVersion`, `account(O)` with its index cell, and `membership(O, caller, Admin)`. Exactly one conditional put wins. The loser gets `Taken`, deletes its pending row, and returns 422 with `errors[].code = "already_exists"` (`research/wire-census.md#20`). The winner's 201 returns once every serving applier, publisher, and edge covers the activation, about 1 s in North America and 1.5 s on other continents, so no front answers 404 for `newco` after it.
2. `gh repo create newco/a` runs in `newco`'s index cell `c9`. `place_network` picks one of `c9`'s slots, one `auth-na` transaction claims `repo_name(O, a)` and writes `repo_dir(Ra)`, and `c9` `core` then creates the repository. 201.
3. `PATCH /api/v3/repos/newco/a` with `{"name":"b"}` routes by `(O, a)` to `c9`, which authorizes admin from the replica. A front still holding the old `Live` entry sends epoch e, `c9` sees e+1 in `g_repo_dir`, and the front re-resolves instead of serving a stale name.
5. Creating a new `newco/a` later overwrites the alias with a `Live` entry for a new repository and bumps Ra's epoch, which ends the redirect as on GitHub (`#23`). Step 1 writes the registry and `auth-na`. Steps 2, 3, and 5 write only `auth-na`, because repository names are unique per owner. Step 4 reads only the front's projection and `c9`.

**Journey 5: `alice` belongs to `acme` (repositories in `c7`), `beta` (`c12`, EU residency), and `gamma` (`c20`), her index cell is `c4`, and the `deploybot` app (77) is installed on `acme` (installation 501) and `beta` (502).**

## Shape

A data cell is two Aurora DSQL clusters, `core` and `aux` (both single-Region or both multi-Region), a set of S3 buckets, and one fleet of identical `tributary` nodes running role subsets. Everything canonical is a DSQL row or an immutable S3 object addressed from a DSQL row. Nodes keep only caches, in-flight requests, and long-poll sessions, all rebuildable. Above the data cells sit the global tier, a DynamoDB MRSC claim registry and three DSQL geo authorities, plus stateless front cells that authenticate and route, and pull-based logs that carry derived data between cells ("Namespace and cell placement", "Geographies, the claim registry, and the authorities", "Cross-cell features").

**Two clusters per cell.** `core` holds `slot_state`, refs, packs, `push`, `ref_log`, the `g_*` authorization replica, branch rules, PRs, reviews, `check_suite`, `check_run`, and the outbox. `aux` holds Actions runs, jobs, runners, runner sessions, leases, the cache index, artifacts, the log index, `hook_delivery`, notifications, account index rows, inter-cell logs, and audit, plus its own `slot_state` rows for the move fence. The split is a bulkhead: Actions load, an `aux` migration, or a bad `aux` query plan cannot spend `core`'s connections or capacity, so git, merges, and authorization keep serving (`review/corebet-a.md`, `review/corebet-b.md`, `review/corebet-c.md`). No transaction spans both clusters. The only cross-cluster writes are the Actions trigger and the check relay, both idempotent ("Actions runs and jobs"). The cost is a second cluster per cell (a second multi-Region setup in Paired cells), a second migration stream, two clusters for self-hosters, and check conclusions that reach the merge decision seconds after a job ends.

**Why Aurora DSQL, defended against its limits.** DSQL multi-Region commits synchronously to two Regions with a witness, with "zero replication lag on commit" and no failover operation (`research/uptime.md#26`). That answers fact 1 for every row in both clusters at once, including refs, and needs no control-plane call during Region loss. Aurora PostgreSQL Global Database loses seconds on unplanned failover, its failover is an RDS control-plane call, and it does not guarantee to fence the old primary (`#24`, `#25`). DynamoDB MRSC has no transactions (`#29`), so a merge could not commit the ref, the PR, and the outbox together. DSQL's limits (`#27`) are real, apply to each cluster, and each has a specific answer here:

| DSQL limit (`research/uptime.md#27`) | Design answer |
| --- | --- |
| 3,000 rows and 10 MiB per transaction | An atomic push carries at most 1,000 ref updates, of which at most 800 deletions. A create or update writes two rows (ref, ref log) and a deletion three (ref, tombstone, ref log), so the worst case is about 2,860 rows with shards and outbox rows. The limit is listed under "Known deviations from GitHub". Non-atomic pushes above that size commit in chunks within the same budget with per-ref status, which git's non-atomic semantics allow. Inline packs are capped at 1 MiB. Bulk operations (org permission changes, transfers, deletes) are outbox sagas of idempotent steps of at most 1,000 rows. |
| 5-minute transactions | No transaction spans network I/O to clients or S3. Pack upload and git work finish before `BEGIN`. Request transactions have a 2 s deadline, scaled by batch size for large pushes. `run_tx` enforces a hard 30 s deadline on every transaction, which is the horizon a slot-move freeze waits out ("Namespace and cell placement"). Authority writers also abort any transaction whose writer lease expires before COMMIT, and survivors wait out the full 5-minute server limit before they treat a fenced geography as final (`Quiet`). |
| Optimistic concurrency, SQLSTATE 40001 | A ref compare-and-set is already optimistic, so a 40001 retry re-reads the snapshot and reports `fetch first` if the expected value is gone. Each touched shard gets one set-based `UPDATE ... FROM (VALUES ...)` per kind of update, not one statement per ref, and pushes above 100 refs are serialized per repository under the merge-queue lease row, so a 1,000-ref push does not lose OCC races to a stream of small pushes on a busy repository. Retries are capped at 3 with jitter under a per-node retry budget of 10% of calls. No push path writes a per-repository counter. The only per-repository hot rows are the 40 ref-shard rows (32 for user refs, 8 for `refs/pull/*`) and the issue-number counter. Only the `pr-sync` consumer writes the 8 pull shards. It coalesces `refs/pull/N/head` and `refs/pull/N/merge` writes last-writer-wins and runs behind user pushes, so bot ref traffic never conflicts with a person's push (graft from `arena/candidate-2`). |
| Repeatable Read, so write skew is possible | The merge transaction re-runs `check_protection` on its own snapshot and compare-and-sets every row its decision rests on: the head ref, the PR row (`state = 'open' AND review_version = :seen`), and the base ref. Every PR-scoped input to the decision (reviews, dismissals, draft state, protection overrides) bumps `pull_request.review_version`, so a concurrent one conflicts with the merge, and the 40001 retry re-runs the check on a fresh snapshot. |
| No triggers, PL/pgSQL, or TRUNCATE | All rules live in Rust. The outbox event and its pending rows are written by the same `Tx` handle as the data, never by a trigger. Deletes are chunked. |
| One DDL per transaction, DDL separate from DML | The migration runner applies one statement per transaction under a lease, expand and contract only ("Change safety"). |
| 10,000 connections, 100 new per second, 1 hour lifetime | Each role runs as its own OS process with its own DSQL database role. On `core`, git and api reserve 3,000 of the cell's 4,000 connections and 60 of the 100 new connections per second. Workers, migrations, `auth-apply`, and `dr-apply` share the rest and are shed first, except one reserved connection for the operator role, which is never shed, and the `actions` role reaches `core` only through that remainder. `aux` has its own quotas [inference: DSQL quotas are per cluster] and per-role budgets, so Actions traffic never draws on `core`'s. Each geo authority has its own budget: 8 writer connections per Region for each data cell in its geography and one per follower worldwide ("Identity and tokens"). The pool code enforces the split, because server-side per-role limits are unverified, and CI checks that the sums stay under DSQL's quotas. Connections recycle at a jittered 40 to 55 minutes. After an AZ loss each node's reconnects queue behind its role's share of the new-connection rate, and new processes in a hot swap ramp their pools gradually instead of opening them at once. |
| 1 KiB keys, C collation | Ref names are capped at 900 bytes, which leaves room for the other key columns. `ref_log` is keyed by a hash of the name. Milestone 0 measures DSQL's key encoding to confirm the margin. Case-insensitive names (logins, repository names) store a lowercased shadow column with a unique index. |
| 1,000 tables, 24 indexes | The schema budget is 400 tables per cluster. The CI schema linter fails the build above it. |

### Namespace and cell placement

A **data cell** is the cell described above. A **front cell** is a Regional fleet of `edge` nodes with its own NLB and a projection on local disk, and it holds no canonical state. The **claim registry** is the worldwide DynamoDB MRSC table for keys that need one answer on Earth. A **geo authority** is the DSQL multi-Region cluster of one continent group, and it commits every other global fact for the accounts and orgs homed there. The **replica** is the set of `g_*` tables in each data cell's `core`. Each account has an **index cell** in its home geography that holds its stars, watches, notifications, and feed ("Cross-cell features").

Invariants and decisions:

- **One namespace, one key.** Users, orgs, and enterprises share `name`. Logins are ASCII, so lowercasing is exact. GitHub logins are case-insensitive [inference]. An enterprise's one `ShortcodeClaim` covers all its managed users ("Public service concerns").
- **Claims are registry items with sagas, and repository names are authority unique keys.** Creating an account or org, renaming a login, adding an SSH key, verifying an email, creating an app, and flipping a slot each run `run_claim`: a pending transaction in the home authority, one conditional write to the registry, and an activate transaction. The conditional write decides every race (journey 4). Creating, renaming, transferring, or deleting a repository is one transaction of 3 to 8 rows in the owner's authority, whose unique key decides collisions. The replica is read only to fail fast with a friendly 422.
- **Negative answers are never wrong after acknowledgment.** A replica never answers "no such name", "no such token", or "not allowed" about a fact whose write was acknowledged. Each answer depends on named partitions (`depends_on`). Every create (signup, token creation, fork, repository creation, membership and grant additions) and every revocation returns only after coverage ("Geographies, the claim registry, and the authorities"), so a member that holds a live lease for the geography and no unpassed lagging notice has applied every acknowledged fact and answers "no" at once (`absent_allowed`). A member named lagging stops answering "no" for that geography until its watermark passes the named commit, and any member may answer once its watermark passes `asked_at`. Between a commit and its acknowledgment, up to 5 s, two observers can disagree. No follower writes to an authority to move a watermark, so while an authority is down everywhere or cut off on its continent, "no" about its partitions stays immediate and correct, because nothing committed there can be acknowledged without coverage. A replica that may not answer waits up to `BEHIND_WAIT` and then answers 503. Positive answers are served at once, but a data cell fails closed the write-class grants that depend on a geography it lags for more than 30 s, and its private reads continue only within ACT-14's signed stale limit (default 2 hours). A member that reads its authority lags only when its own watermark ages past 30 s, and one that cannot compares with the boards of the Regions it does not excuse, so losing a Region makes no survivor lag. An edge in that state for a geography fails its health check and leaves DNS and NLB rotation if another front cell in its Region is current for that geography, and otherwise stays in rotation and answers 503 to principals homed there. An anonymous git request for a repository that is not visibly public gets git's 401 challenge at once, because a challenge is not a final answer. None of this reads the registry or an authority on the request path.
- **`NameEpoch` catches a stale route where it is served** (graft from round-2 candidate 3). The front's repository entry and the cell's `g_repo_dir` row carry the repository epoch, the front's name entry and `g_name` carry the owner login's `ClaimVersion`, and the front sends both in the assertion. A cached route is valid only when both match in the serving cell's replica, so no rename touches more than a few rows, whatever the owner's repository count, and a reclaim in another geography writes nothing in the former owner's authority. A write that removes a name from a repository returns once that repository's cell has applied it, within the 5 s `revoke` wait, so the serving cell knows before the client does.
- **Renames.** A repository rename leaves `Alias` at the old key, which the API answers with 301 and git with 200 (`research/wire-census.md#23`). An owner rename turns the old login's registry item from `Active` to `Alias` and leaves `Former { account }` in its `name` row, because GitHub frees an old username for anyone and keeps old repository links working (https://docs.github.com/en/account-and-profile/reference/username-reference). A new claim of the old login moves the item back to `Active` at a higher `ClaimVersion`, and the new holder's `name` row overwrites `Former` in every `g_name`, which ends the redirect and fails every cached route that carries the old version.
- **Retirement.** When an owner renames or is deleted, each public repository with more than 100 clones or more than 100 Actions uses in the prior week, or with a Marketplace action, gets a `Retired` registry item under the old login, written in 1,000-item saga steps that finish before the login can become `Alias`, and later claims of that pair fail with GitHub's text (same page). A reclaim returns the retired pairs, and `activate` copies them into the claimer's authority, so repository creation never reads the registry. The handler runs in the owner's index cell and reads the counts from the cards it holds there.
- **Transfers** set `repo_dir.owner`, write the new `repo_name`, leave `Alias` under the old owner, and bump the repository epoch. The network and its slot do not move, so a transfer that would move a resident network's owner outside its residency, or bring an outside network into a resident org, gets 422 with a message that names the residency rule ("Known deviations from GitHub"). A transfer between owners homed in different geographies also gets 422 until the deferred `Owned::Handoff` saga ships.
- **Ids route by arithmetic** (graft from round-2 candidates 2 and 3). A repository-scoped id names its slot and the slot map names the cell, so `/repositories/{id}`, node ids, and check-run ids route without a name lookup, and the projection holds names plus a 65,536-entry slot map instead of a route per repository. A slot allows 2^37 ids per kind, ample against a live GitHub check-run id near 1.2e11 (`research/wire-census.md#28`), and a slot past 2^36 for any kind takes no new networks. Issue numbers stay per repository.
- **The network is the unit of placement, the slot the unit of movement.** Every fork joins its network's slot, so `bob/widgets` sits beside `acme/widgets`, and `merge` is one `core` transaction for every pull request, including every cross-owner one. A slot above 20% of a cell's limits moves to a dedicated cell with its other networks. A network is never split, so the largest network must fit one cell.
- **The cell is the blast radius.** A data cell is its two DSQL clusters, its buckets, its node fleet, and its slots, sharing nothing with other cells (`research/uptime.md#8`). A bad deploy, a hot network, or a DSQL problem that Tributary causes stops at the cell, except that an index cell that is down blocks new installation tokens, stars, notifications, feeds, and cross-cell listings for the accounts indexed there, service-wide ("Failure modes"). The registry and the three authorities are the shared stores, and no request reads them. A DSQL engine regression that AWS rolls out under every cell at once is not contained ("Tradeoffs accepted").
- **Each cell's applier owns convergence with the authorities, outside the slot fence.** The `auth-apply` follower set, one lease, cursor, and watermark per geography plus the resident partitions of the cell's own geography only, writes only `g_*` rows and pending-emit rows, never through the fenced `run_tx`, so a frozen slot never stops replication. It upserts an after-image only when its `version` is newer than the row's, so a row whose owning geography changes cannot revert, and the revocation partitions apply independently under the same rule. Each authority change that concerns a slot with a `slot_state` row in the cell (a new `repo_dir`, rename, transfer, visibility, grant) becomes a pending-emit row keyed by its log entry. The slot's current owner drains it in a fenced transaction that creates missing local rows idempotently by repository id and inserts the webhook outbox event under the entry's key, so a move neither loses nor wedges the event and the source's and target's copies yield one. Account-scoped changes emit their events in the account's index cell only, so each event has exactly one producer.
- **Front cells are the router, built as cells** (`research/uptime.md#8`-`#10`). Each Region with data cells runs at least three front cells, each with its own NLB, Auto Scaling group, control bucket, and publisher. Route 53 latency records return multivalue answers across a Region's front cells, with health checks that send a synthetic routed request through each one (data plane, `#15`).
- **Projections come from S3, not from the authorities.** Each front cell's publisher, one active under a lease, pulls all three authority logs (resident partitions of its own geography only) and writes 250 ms segments and an hourly verified full snapshot to its control bucket with `If-None-Match: *`. Edges tail their own bucket through `apply_segment`, whose guards (graft from round-2 candidate 2) cover only slot-map moves and name and repository removals, and keep their store on disk, so a fleet restart reads S3 and puts no load on any authority.
- **Data cells accept only fronts and peers.** Each data cell exposes an internal NLB per Region through PrivateLink to front cells and peer cells, with mTLS, and accepts only front-signed `Principal` assertions. Each assertion names one target cell as its audience and lives 10 s, so a compromised data cell cannot replay a principal to another cell. Fronts probe each cell Region's deep regional endpoint `/_t/health/region`, which commits a canary DSQL write and reads a canary S3 object, and forward only to healthy Regions (ACT-7).
- **SSH routes like github.com.** Fronts hold one service host key set, authenticate the client key by its service-wide unique fingerprint in the projection, read the repository path from the exec command, and route it like HTTPS (`research/wire-census.md#45`).
- **GraphQL** goes straight to the target cell when every root field (`repository(...)`, a node id, an account root) resolves to one cell, because the front reads the root fields against its projection. Only queries that span cells enter at the caller's index cell, which delegates subtrees per cell in batches, each under an assertion that the front signs for that cell at the entry executor's request, and returns partial data with `errors` paths when a cell fails. Cost accounting happens once, at the cell the query enters.

Dominant access pattern: per request, two to four point lookups in the projection and one forwarded hop, then the data cell's one snapshot read. Against `research/uptime.md#47`: routing is a pure function over a local file, name reads never reach the registry or an authority, and no TTL exists to cut. The edge never reads DSQL to route, so a DSQL problem cannot stop it from returning a well-formed 503 with `Retry-After`.

### Geographies, the claim registry, and the authorities

The registry decides, and the authorities publish. A claim is one MRSC conditional write, and it becomes visible only when its home authority appends it, with its `ClaimVersion`, to a commit-ordered DSQL log, so `Lookup::Absent` never rests on a DynamoDB stream. `trib-claims` has replicas in us-east-2, eu-central-1, and ap-northeast-1, so a claim waits on one round trip to another continent (Frankfurt to Ohio about 95 ms, Tokyo to Frankfurt about 225 ms [guess]). `auth-na` runs in us-east-2 and us-west-2 with a us-east-1 witness, `auth-eu` in eu-central-1 and eu-west-1 with an eu-west-3 witness, and `auth-ap` in ap-northeast-1 and ap-southeast-1 with an ap-northeast-2 witness, so their writes wait only inside their continent. DynamoDB is used only where one item is the commit point. Accounts, credentials, memberships, grants, and installations stay in DSQL, because MRSC has no transactions and MREC's last writer wins can drop a removal that races a write (`arena/round3/SYNTHESIS.md`).

Invariants and decisions:

- **One owner per fact.** `root_of` and the root's `Home` pick the authority. No transaction spans authorities, and writers connect only within their own continent. Beyond claim sagas, the one multi-authority write is an account deletion with memberships in orgs homed elsewhere, which tombstones them in each org's authority in idempotent saga steps.
- **A claimed but unactivated name is taken for claimers and invisible to readers**, and its user has not been told that it succeeded. The sweeper finishes or undoes any saga older than 10 minutes by reading its claim. No follower reads the registry for facts, except `Revocation` items while an authority is unreadable. A `RegistryGeneration` flip is a signed config generation that pauses claims for seconds.
- **Writer leases fence a cut-off continent** (managed only). A renewal needs two of three continents, so a geography on the minority side of a cut stops opening transactions within 10 s, and its writers abort any transaction that reaches COMMIT after expiry. DSQL ends every transaction within 5 minutes (`research/uptime.md#27`), so survivors call the geography `Quiet` only after every lease has been expired that long plus the clock margin, about 5 minutes 10 s after the last renewal [inference: the server enforces the limit from `BEGIN`]. Until then it is `Blind`. Only `reconstitute` waits for `Quiet`, and no "no" waits on either state.
- **Acknowledgment waits for coverage.** Every create (signup, token creation, fork, repository creation, membership and grant additions) and every `revoke` returns only when each member in every Region its writer does not excuse shows, on its board row, that it has applied the commit, has seen a lagging notice for it, or has let its lease for that geography end. After 5 s the writer posts a lagging notice for each remaining member to that member's Region board. `revoke` then returns `covered: false` with those members named, and a create returns once their rows show the notice or their leases end. A writer counts a lease as ended only from a board read made after its end or from a strong read of its Region's `BoardLease`. So a writer cut off from the fleet cannot acknowledge: its caller gets 503 with `Retry-After`, the commit stands, and a retry with the same saga id returns it.
- **Revocations survive a continent cut.** In managed, a revocation-class write also commits one conditional `Revocation` item in the registry before it returns, so it is durable on a second continent. Appliers apply these items while the authority is unreadable, and `reconstitute` applies them too. Revocations are rare, so the added cross-continent write is cheap.
- **One board row cannot fail the fleet closed.** Each Region's board is one row object per member plus one summary, all in that Region's control bucket. Readers drop rows stamped after ClockBound `latest()` plus the margin, and a lead over MAX_LAG counts only when two front cells corroborate it or the reader finds the named commit in the authority, so a member with a bad clock or a bad build moves no one. At about 1,000 members in about 12 Regions [guess], boards cost about 1,000 row PUTs, 1,000 row GETs by summary writers, and 12,000 summary GETs per second, roughly $27,000 a month at S3 Standard request prices [guess], plus cross-Region transfer of the summaries. An install has one board per Region and a few dozen members.
- **Reconstitution seals first.** `reconstitute` seals the lost geography in the registry before it writes anything, so a cut that heals cannot bring its writers back, and after-images order by `(geo_epoch, version)`. A healed authority rejoins only through `rejoin`, which records its unreplicated commits as stated loss. CI checks that every authority table carries a `RecoveryClass`, and the input set comes from those classes, so token hashes and org secret ciphertext come back from the escrow. Index cells move to live cells, and the old cell stays the previous index cell for `kid_allowed` for one token lifetime.
- **Clocks come from ClockBound.** Every node runs the ClockBound daemon, which bounds true time from below and above (https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/compare-timestamps-with-clockbound.html, cited by round-3 candidate 2) [unverified]. Lease use, lease expiry, and the clock margin read those bounds instead of an assumed 50 ms.
- **Every data cell and front publisher follows all three logs.** Each authority's follower load is fixed by fleet size: about 130 followers polling every 100 ms, about 1,300 queries per second [guess], two thirds of them across an ocean. Milestone 0's authority gate tests exactly that load.
- **Tokens carry their geography** (`OpaqueToken`), so "no such token" depends on one geography's log, and a stored token's first use waits only on that geography.
- **Deferred.** Rehomes and repository transfers between owners homed apart need `Owned::Handoff` sagas, which ship in Milestone 7. Until then a home is fixed at creation and such a transfer gets 422. `reconstitute` needs no `Handoff`, because a sealed geography writes nothing.

Tables (every key leads with an id that carries its slot): `repository(repo) -> network, content_epoch, takedown, default_branch` with name, visibility, and `NameEpoch` read from `g_repo_dir`; `ref(repo, name) -> target, shard, version, written_at`, where `written_at` is the shard version that wrote the row, secondary index `(repo, shard, written_at)`; `ref_tombstone(repo, shard, written_at, name)`; `ref_shard(repo, shard) -> version`; `pack(network, pack_id) -> checksum, kind, state, location, bytes`, where `pack_id` is the fresh placement id; `pack_inline(network, pack_id) -> bytes`; `push(repo, push_id)`; `ref_log(repo, name_hash, push_id) -> name, old, new, actor`, where `name_hash` is SHA-256 of the ref name; `maintenance_lease(network) -> owner, fence, expires`; `slot_state(slot) -> state, generation`.

Invariants the structure enforces:

- **Acknowledgment point.** A push is acknowledged when, and only when, the DSQL transaction that contains its ref updates and, if the push carried objects, its pack row has committed. At that instant the pack bytes are either inside that transaction (inline) or already in S3 Standard in at least three AZs, and in a Paired cell in two Regions (`research/git-storage.md#54`). The ref rows themselves are in DSQL across AZs, and in a Paired cell across two Regions. `Acked` and `DurablePack` make the order a type error to get wrong.
- **Linearizable per ref, atomic per push.** Each ref is one row, and the update is a conditional write on its expected value inside an optimistic transaction, so concurrent updates to one ref serialize and the loser sees `Stale`. A multi-ref push is one transaction, so readers see all of it or none of it. Pushes to different refs commit concurrently unless they share a shard row, which is GitHub's 2026 per-reference ordering (`research/git-storage.md#6`) obtained from row granularity instead of a new quorum protocol.
- **Reachability and retention.** Every ref target is reachable from the network's live pack set, because the pack row commits with the ref, and a push with no new objects references objects already in live packs. Compaction follows git's cruft-pack model and never drops an object: unreachable objects go into a cruft pack with per-object times, and a later compaction rescues any that became reachable, for example through a Git Data API commit. Compaction supersedes only the pack ids it read, so a push that lands during compaction stays live. Only GC deletes objects, and only those unreachable in GC's own snapshot and older than 14 days. A superseded pack's bytes leave S3 7 days after `Superseded.at`, because every object in it is already in a live pack, at a capped delete rate, with bucket versioning keeping deleted objects as noncurrent versions for at least the backup retention, so a restore can bring back every pack it names ("Install operations"). A sweeper deletes S3 pack objects that no `pack` row references after 24 hours, which removes packs uploaded before a commit that failed. This is the fenced-write lesson of the DynamoDB enactor race (`research/uptime.md#32`, implication 11). The pack bucket policy denies any `PutObject` on pack keys that lacks `If-None-Match`, so even a buggy release cannot overwrite a pack (`research/uptime.md#31`, graft from `arena/candidate-2`).
- **Caches are disposable.** A cache node holds a bare repository per network on NVMe with `--ref-format=reftable`, packs copied from S3 or inline rows, and refs written from DSQL with `git update-ref --stdin`. Upstream `git upload-pack` serves fetches from it. Losing it costs a re-download.
- **Bounded stale fetches while `core` is unreachable.** If the `core` snapshot read fails or exceeds 200 ms, the git role serves upload-pack from its cache at its last proven refresh, for at most a signed per-cell limit (default 2 hours). The front still authenticates from its projection, and the git role authorizes from a per-cell snapshot of exactly the `g_*` rows its repositories need, which `auth-apply` writes to the cell's control bucket and every node keeps on local disk. Pushes and merges return 503, so durability is unchanged. Staleness stops growing while `core` is down, because nothing commits [inference], but revocations freeze for the outage, and during a partial partition a node can serve a fetch that misses pushes committed through other nodes ("Tradeoffs accepted"). This is a fallback mode, which AWS warns rots untested (`research/uptime.md#5`), so a weekly drill exercises it ("Drills").
- **Small pushes do not touch S3.** Most pushes are small [guess: well over 90% under 1 MiB]. They commit with one DSQL transaction, which in a Paired cell is the whole cross-Region durability story. Compaction moves inline packs into S3 within minutes and deletes the inline rows, in a Regional cell only after the replacement object is confirmed in the recovery bucket.
- **Cross-Region RPO, stated per class.** Paired cells: RPO zero for an acknowledged push and zero for metadata. Inline packs and every row commit synchronously in two Regions (`research/uptime.md#26`), larger packs are in two of three Regional buckets before the commit, and LFS objects reach the second Region before `verify` returns. A `worker` consumer copies each bucket-placed pack to its missing Regional bucket within seconds and updates the row's location set. Regional cells with a `dr` Region: push RPO up to 15 minutes, bounded by S3 Replication Time Control for bucket packs [unverified SLA], and metadata RPO (which includes inline packs) targeted at 5 minutes through DSQL CDC [unverified lag]. The `dr-apply` worker role in the recovery Region applies each cluster's stream to its warm counterpart one whole source transaction at a time, under a lag alarm and the `dr` section of the status document. Metadata can run ahead of pack replication, so promotion runs a mandatory reconcile: it walks `ref_log`, moves each ref back to its newest value whose packs exist in the recovery Region, and records each rollback as stated loss within the RPO. Regional cells without `dr` have an RPO of the backup interval for a Region loss and recover by restore. Regional recovery launches node capacity, so Regional cells do not meet fact 9. Paired cells do. The price of zero is the Paired column of "Tradeoffs accepted": a second Region sized for full load, a witness Region bucket, and one cross-Region round trip per commit.

Dominant access patterns traced:

- *Fetch or clone* (the hottest path): one DSQL snapshot read of 40 `ref_shard` rows by primary-key range. If nothing changed, upload-pack runs on the local cache with no further reads. If shards changed, one indexed range read of changed rows and tombstones per changed shard plus the live pack list. A CI fan-out of 1,000 clones of one SHA costs 1,000 small reads and spreads across the repository's rendezvous set, which widens from 3 to 9 nodes when per-repository concurrency exceeds 64.
- *Push*: one set-based statement per touched shard and kind of update, a few shard updates, a few inserts, one commit. No S3 call for small packs.
- *API reads of refs* (`GET /repos/{o}/{r}/branches/{b}`, GraphQL `ref`): primary-key reads, no git process.
- *Maintenance*: one lease per network, scheduled by pack count and bytes, geometric factor 2, full repack with bitmaps weekly for networks above 1 GiB. Commit-graph and multi-pack-index files are rebuilt locally by each cache, because both are cheap and derivable.
- *Admission*: each repository admits about 100 commits per second and each account and network has a concurrent-push cap, so one runaway bot cannot turn a repository's shard rows into an OCC storm for its neighbors (graft from `arena/candidate-2`).

Decisions:

- **Authorities own the authorization graph, cells own content.** The root's home authority holds names, accounts, stored-token hashes, SSH user and deploy keys (their fingerprints claimed in the registry as one service-wide index), GPG keys, sessions, orgs, memberships, teams, repository grants, org policies (base permission, SSO, residency, custom roles, org rulesets, org webhooks, and org Actions secrets as ciphertext, except a resident org's, which its residency's cells store), apps, installations with their repository selections, and verifying keys. Cells hold everything else: repository content and metadata, branch rules, issues, pull requests, Actions, stars, watches, notifications. Repository grants live in the authorities so that `GET /user/repos` and search visibility can be computed in any cell from one replica, while the repository's own cell enforces the same rows.
- **Authenticate at the front, authorize in the data cell.** The projection holds what authentication and routing need. The replica holds the authorization graph and display facts. Neither holds password hashes, 2FA seeds, recovery codes, or OAuth client secrets (`HomeOnly`). Only the home authority does, and only the `identity` handler reads them, inside a sign-in transaction that also inserts the session row, so sign-in is a write and fails while the home authority is unreachable. Sign-in, OAuth token exchange, and token creation run in any healthy data cell of the home geography, because each is only a home-authority write, so a down index cell does not stop them. A traveler signing in on another continent pays one forward from the local front to a home cell, at sign-in only. Existing sessions keep working, because the cookie is a signed session id with `iat`, checked at the front against the service session key and the account's `sessions_not_before`.
- **Stored tokens** (`ghp_`, `github_pat_`, `gho_`, `ghu_`, `ghr_`). The front checks prefix and CRC offline, reads the minting geography from the first character, then looks up the SHA-256 hash in the projection. Creating a PAT or finishing an OAuth flow writes the hash to the home authority and returns only after coverage, so a first use finds the hash at every front that holds a live lease, and a front named lagging answers `Behind` on that geography's partitions only. A revoked token stays in the projection as `revoked` for 30 days, so it gets 401 at once instead of waiting. A burst of random tokens with valid CRCs costs local lookups and a bounded wait, with at most 16 waiters per IP before the front answers 503.
- **Installation tokens are stateless**, matching github.com since 2026-10-02 (`research/wire-census.md#30`), and signed by the installation account's index cell (`kid`). A front accepts a token only when `kid_allowed` holds, so a compromised cell mints for its own accounts and slots, never for every installation (round-2 synthesis drop). Minting stays in that index cell, so while it is down no new installation token is issued for its accounts in any cell, and tokens already issued keep working until `exp` ("Failure modes"). Each cell's Ed25519 signing keys are wrapped by its KMS multi-Region key [unverified that multi-Region keys serve Decrypt in each Region independently] and kept on local disk, so a node decrypts them once at start, and minting and verification need neither KMS nor DSQL at request time. Tokens are about 400 characters and match `ghs_[A-Za-z0-9\.\-_]{36,}`, which Renovate accepts (`research/clients.md#38`). GHES itself still issues 40-character tokens, so a client that assumes 40 would break. I found none, and the gh, Renovate, and ARC oracles exercise this.
- **Installation token revocation.** Each installation's `not_before` lives in the target account's home authority and reaches every front through the projection. Uninstall, suspension, repository removal, and permission changes bump it through `revoke`, which returns once every serving edge and data cell covers it, so no serving front accepts an older token after 5 s, and an edge that cannot apply it leaves rotation within 30 s. `authorize` also intersects the claims with the installation's current `g_*` rows on every request. Each job's `GITHUB_TOKEN` jti is recorded on the job row and denied in the cell that holds the repository's slot when the job ends.
- **Denials wait, grants race.** A grant committed before the request is always honored, because a denial that cannot yet rule it out is retried. A removal can be missed for the apply lag. In a cell or edge cut off while the fleet advances, it can be missed for at most 30 s of writes, and for reads within ACT-14's stale limit. After `revoke` returns `covered`, no serving edge and no cell honors the removed fact.
- **SSO** attaches to orgs and enterprises, as on GitHub Enterprise Cloud, with SCIM provisioning at T1. The SAML or OIDC endpoint writes `sso_authorization(credential or session, org, expires)` to the org's home authority, the front passes the credential id, and the cell checks `g_sso_authorization` when the resource's owner enforces SSO. Break-glass owners are pre-provisioned local accounts with hardware keys and no IdP dependency (`research/uptime.md` implication 25).
- **Instance sign-in in installs.** An install chooses its sign-in at launch at instance scope, as GHES does: built-in accounts, SAML, or OIDC, with LDAP at T1 (`InstanceAuth`). Org SSO still works inside it. A `SiteAdmin` actor bypasses org and repository permissions, and every bypass writes an audit row in the same transaction as the action. `tributary admin bootstrap` runs on a node through SSM, so it writes the authority through that node's `identity` handler and instance role, creates the first site admin, and prints a one-time sign-in link that lives 15 minutes [guess]. The first `gh auth login` then signs in through the chosen identity source. Installs send email through SES with production access or through customer SMTP, which the preflight checks.
- **OAuth**: authorization code (web flow) and device flow on the bare host at `/login/oauth/*` and `/login/device/code`, both identity writes. First-party apps are seeded once in each authority (an install's one authority) with GHES-era callbacks (`http://localhost/` for gh and GCM, `http://127.0.0.1/` also accepted, `x-github-desktop-auth://` for Desktop [unverified exact path]) and are treated as public clients, so the embedded secrets are accepted and ignored (`research/clients.md#44`-`#47`). Issue and PR numbers come from `repo_counter(repo)`, one hot row per repository on creation only.

Access patterns: every HTTPS request does one projection lookup by token hash and one assertion check in the cell. A permission check reads `g_membership`, `g_team_member`, `g_repo_grant`, and `g_org_policy` by primary key in the snapshot the operation already reads. The registry and the authorities see writes only, at roughly the rate of signups, token creation, and membership changes. Against `research/uptime.md#47` and `#44`: no request reads them. Each authority's read load is the follower set, one applier per data cell and one publisher per front cell worldwide, each pulling every partition of that geography in one query every 100 ms, about 1,300 queries per second at 100 data cells and 30 front cells [guess]. No follower writes an authority, because a watermark is a read's snapshot time and freshness travels through the S3 boards. That load is fixed by fleet size, not by request rate, and replicas are pushed, not expired, so no TTL change can move load onto an authority. Expensive writes such as an org-wide membership saga slow only other writes in that org's authority, writers are admitted by class with revocations first, and token verification never touches an authority. Each data cell holds at most 8 writer connections per Region to its own geography's authority and each follower one per authority, so an authority sees about 130 follower connections plus its geography's writers, under 1,000 of DSQL's 10,000, and they reconnect within 2 s at 100 new per second (`#27`). `auth-na` keeps us-east-1 as its witness, out of the write quorum (implication 22), and no authority needs a failover call (`#26`). Only claims and, in managed, revocations wait on another continent, for one registry write each.

Can pull request state diverge from refs? Not any state that decides something. An open PR's head is the head branch's own ref row, read in the same snapshot as the PR, and a merge compare-and-sets the head ref, moves the base ref, and sets `Merged { final_head }` in one transaction. `refs/pull/N/head` and `refs/pull/N/merge` are derived refs for git clients. The `pr-sync` consumer moves them within seconds of each push, idempotently on the head ref's version, and GitHub also updates them after the push returns [inference]. Other decisions: issues and PRs share one number space and one table, as on GitHub. Invariants: a job has one runner at a time, because `Queued -> Assigned` is a compare-and-set on the job row's version. A lease that expires (no `renewjob` for 10 minutes) moves the job to `Completed{Failure}` with GitHub's infrastructure-failure category, or back to `Queued` if it was never acquired. Job rows write only on state changes: `renewjob` arrives every 60 s, but the lease row is written only when less than 5 minutes remain, so a 2-hour job writes its lease about 24 times, not 120. Run creation inserts at most about 900 jobs per transaction; larger runs are created in chunks under a `Creating` run marker and flipped to `Queued` in a final idempotent step. Concurrency groups are one `concurrency_group(repo or org, key)` row each, won by compare-and-set.

An `aux` outage stops job dispatch and holds back conclusions, so merges that require checks wait, while git, other merges, and the API keep serving.

Brokers also poll DSQL every 2 s, so a lost notice costs latency, not a job.

Invariants: an event exists if and only if its data change committed, because both are in one transaction. Producers only insert events and pending rows, and each consumer deletes only its own pending rows, so producers never conflict with consumers and consumers never wait on each other. Delivery is at least once. The `X-GitHub-Delivery` GUID is derived from `(outbox id, hook id)`, so a redelivery after a crash keeps the same GUID, as GitHub's does (`research/wire-census.md#36`). Order is per partition by ULID, except that a transaction that commits late can deliver after a later one. Consumers that care (search, run owner) compare `entity_version` and drop stale events. Webhook ordering is not guaranteed by GitHub either [inference].

The webhook consumer renders each payload from the event's captured fields, so a delayed `pull_request.synchronize` still shows the head SHA of its own push, writes `hook_delivery` rows to `aux` and payloads to S3, then returns. Separate delivery workers POST with a 10 s deadline and shuffle-sharded concurrency per hook owner and make one automatic attempt, as GitHub does (`research/wire-census.md#37`). Failed deliveries are redelivered manually through the deliveries API for 3 days. A hook that opts in gets automatic retries with backoff for the same 3 days under the same GUID, which "Known deviations from GitHub" lists. A failing consumer, for example `CacheHint` with a peer Region unreachable, accumulates only its own pending rows and parks each row after 10 failures, while every other consumer reads only its own rows and moves on. Oldest-pending-row age and parked-row count per consumer are SLO signals and deploy gates.

Where consumer state lives: the outbox, every pending row, and every consumer lease live in `core`, so a fenced delete and the event it consumes share a cluster. `PrSync` writes refs in `core`. `CacheHint` warms peer-Region caches. `ActionsTrigger` writes runs and jobs in `aux` and check rows in `core`. `RunOwner`, `Webhooks` (`hook_delivery`), `Audit`, and the four inter-cell producers (`Notifications`, `IndexFeed`, `CardPublish`, `SearchFeed`) write in `aux`. Events about authority facts come from the pending-emit rows that the applier writes and the slot's owner drains ("Namespace and cell placement"), so each has one producer. A consumer whose target cluster is unreachable pauses without counting attempts, so an `aux` outage leaves pending rows to drain later instead of parking them.

### Cross-cell features

Decisions:

- **One log mechanism, two uses.** Each geo authority's change log has 64 shared partitions keyed by aggregate root plus revocation, resident, and escrow partitions. Each data cell's inter-cell log has one partition per destination cell and 8 search partitions. Writers batch one append per transaction per partition, so a head row commits a few times per second, not once per event. Milestone 0 tests the mechanism, with followers on other continents, before anything rests on it.
- **Every account has an index cell**, recorded on its account row in the home authority, which holds its starred list, watch subscriptions, notifications, activity feed, and the cards of the repositories it lists. It is set at creation to the handling cell, which is in the home geography, and moves under the slot fence pattern keyed by account.
- **Producers.** The outbox gains `IndexFeed` (stars, watches, feed items), `CardPublish` (coalesces card changes per repository), and `SearchFeed`. `Notifications` computes recipients in the source cell from its own rows (watchers, participants, mentions), groups them by `g_account.index_cell`, and appends to each index cell's partition in `aux`, so fan-out never writes `core`.
- **Followers.** Each data cell runs one `xcell-follow` lease per source cell and pulls every 200 ms. A destination outage pauses only that destination's pulls, and the source never waits. Destinations admit each source at a fair share, so one source's storm cannot starve the others.
- **Notifications park, never expire** (round-2 synthesis drop). Retention trims a partition only below its follower's cursor, 3 days after the follower passed an entry. A partition whose destination stays down parks: the source keeps every entry, alarms after one day, and the destination drains in order when it returns. Stars, watches, feeds, and cards are derived and can also be rebuilt by a resync scan of the source rows.
- **Cards make listings local without a full copy** (round-2 synthesis drop). `/user/repos`, `/users/{u}/repos`, `/orgs/{o}/repos`, `/user/starred`, and `viewer.repositories` route to the account's index cell, which answers from `g_repo_dir` and the cards it holds. A card goes only to the index cells that list its repository, so cell storage grows with what a cell's accounts list, not with the whole service. Fields that change on every push lag by up to 60 s.
- **Search** is a sharded OpenSearch tier per residency domain (US, EU, APAC) that follows every cell's search partitions. A query filters by public visibility or by the viewer's reach, computed from the replica as owner ids whose base permission grants read plus explicit repository ids. A domain that misses its deadline yields `incomplete_results: true`, and failure stays on search endpoints (`research/uptime.md#49`, implication 18).
- **Org runners** claim jobs in other cells with one compare-and-set RPC ("Actions"), the one cross-cell call in Actions.

Against `research/uptime.md#47`: pull-based logs mean a slow destination cannot slow its sources, and each cell sizes its own follower budget. A viral repository's fan-out is bounded per source by per-thread caps, coalescing, and fair-share admission at destinations.

### Service and crate map

Deployables:

- **`tributary`**, one Rust binary with roles selected by config. On front cells, `edge` terminates TLS (rustls, SNI) and SSH (russh, one service host key set), runs `authenticate` and `route` against the projection, enforces rate limits, signs the `Principal` assertion, and serves the web app's static assets, and `front-publish` writes projection segments and its Region's board summary. In data cells, `ingress` verifies front assertions, forwards to role nodes, and serves the deep regional health endpoint `/_t/health/region`. `api` serves REST under `/api/v3`, GraphQL at `/api/graphql`, OAuth, uploads, LFS batch, and the `identity` handler, which writes the registry and its geography's authority through `trib-authority`. `git` owns the NVMe cache, receive-pack, upload-pack spawning, merge plans, archives, and diffs. `actions` serves registration, broker, run service, launch, results, cache, artifacts, and OIDC. `worker` runs outbox consumers, `auth-apply`, `escrow-apply`, the claim sweeper, `xcell-follow`, the check relay, webhook delivery, workflow triggering and run ownership, compaction, GC, the orphan sweeper, and the `operator` role, which runs migrations and every other lifecycle step ("Install operations"). `dr-apply`, in Regional cells with a `dr` Region only, runs on a small standing node group there and applies each cluster's DSQL CDC stream to its warm recovery cluster one whole source transaction at a time, with a lag alarm and the `dr` section of the status document. Each role runs as its own OS process with its own DSQL database role and its own pools, so a pool leak in one role cannot spend another's connections. Small installs run every role process on every node. Managed front cells run `edge` alone, and managed data cells run `ingress+api`, `git`, `actions`, and `worker` as separate Auto Scaling groups.
- **Upstream git**, pinned (2.56 at design time), shipped inside the node image, whose per-Region AMI ids and digest the signed release carries, so a git change is an image roll. It does index-pack, upload-pack, pack-objects, repack, merge-tree, archive, and fsck (`research/git-storage.md` implication 8).
- **`tributary-web`**, the React app, built into the release and embedded in the `edge` role.
- **`tributary-runner-host`**, managed and optional BYOC only. It runs unmodified `actions/runner` in Firecracker microVMs in separate runner accounts.
- **`tributary-fleet`**, managed only. It places networks, moves slots, deploys front cells, provisions certificates, and feeds <vendor-fleet-app>.

Crates. Each crate's internals are private, and only the listed items are public.

- `trib-domain`: ids, names, slots, refs, PRs, Actions state machines, events, rules. Pure, no IO.
- `trib-store`: the only crate that contains SQL. `CellStore` over `core` and `aux`, `run_tx`, per-role pools that enforce the connection split, retry budgets, the fixed prepared-statement set of the git path, the migration runner, the schema linter.
- `trib-pack`: `PackStore`, bucket quorum, inline packs, cruft packs, GC, the orphan sweeper, cache materialization.
- `trib-git`: the receive-pack protocol in Rust (commands, capabilities, side-band, `report-status-v2`, push options; about 2,000 lines [guess], checked by diffing its `report-status` output against upstream `git receive-pack` on a shared push corpus), git subprocess supervision, cache repositories, merge plans, and archives. Rust owns receive-pack so that `report_status` can require `&Acked`. Candidates 1 and 2 drive upstream `receive-pack` through hooks instead, which leaves the order of acknowledgment to git's hook state machine.
- `trib-auth`: tokens, OAuth, sessions, SSH keys, `authenticate`, `authorize`, `kid_allowed`, node ids.
- `trib-authority`: `Authority` and `Registry` (the only crate with an authority connection or a registry client), `run_claim`, the sweeper, writer leases, `Lookup`, the change logs, the freshness boards and `GeoView`, `revoke`, `auth-apply`, `escrow-apply`, `reconstitute`, and `front-publish`.
- `trib-xcell`: `XcellEvent`, `follow`, `apply_xcell`, card subscriptions, and parked-partition handling.
- `trib-wire`: GitHub conventions shared by REST and GraphQL: headers, error bodies, the 404 rule, pagination links, ETags, media types, API versions, rate-limit headers.
- `trib-rest`: routes and request and response types generated from the pinned `ghes-3.22` OpenAPI file, plus handlers.
- `trib-graphql`: schema generated from the GHES 3.22 SDL, resolvers, cost accounting.
- `trib-actions`: the Rust port of `GitHub.Actions.WorkflowParser`, scheduler, broker, run service, launch, results, cache v1 and v2, artifacts, OIDC, Azure Blob dialect shim. Wire types stay private.
- `trib-hooks`: outbox dispatch, webhook payload rendering, delivery.
- `trib-edge`: TLS, SSH with the service host key set, the projection and `apply_segment`, `route`, assertion signing, admission control, and data-cell ingress. `check_route` is pure and lives in `trib-domain`.
- `trib-ops`: the operator role's intents, stages, cursors, and status documents, the drills, and the `tributary` admin CLI.

Rust does not pay for itself in pack generation, repacking, or merge computation, which stay in upstream git, or in the web UI, which is React.

AWS services on the request path: NLB (data plane), Route 53 DNS resolution and health checks (data plane), PrivateLink between front cells and data cells (data plane), Aurora DSQL `core` for git, merges, authorization, and the API and `aux` for Actions, webhook delivery, and inter-cell logs (data plane, IAM auth tokens signed locally with instance credentials, one DSQL database role per Tributary role), and S3 (data plane, presigned URLs computed locally, projections, and the per-cell authorization snapshot behind stale fetches). DynamoDB (the registry) and the geo authorities are on the identity-write and follower paths only. KMS is off the request path: node start decrypts the wrapped keys from local disk once through its own Region's KMS endpoint, using multi-Region keys, and S3 uses bucket keys for SSE-KMS [unverified that bucket keys remove per-request KMS calls in every case]. CloudFront serves the isolation subdomains with front cells as origin. OpenSearch is on the search path only. SES (email) is off every request path.

Cross-cutting conventions (`research/wire-census.md` section B) live in `trib-wire`, so no handler can skip them. Every response, git smart HTTP included, carries `X-GitHub-Request-Id` (front, cell, node, and trace id in GitHub's colon-separated hex shape) and `X-GitHub-Enterprise-Version: 3.22.0`. REST responses carry `x-github-media-type: github.v3; format=json` and `x-github-api-version-selected`. `X-GitHub-Api-Version` selects `2022-11-28` (default) or `2026-03-10`, an unknown value returns 400, and the `2026-03-10` breaking changes (`#13`) are encoded as per-version response shapes generated from the two versioned OpenAPI files. ETags are weak and derive from row `version` columns, so a `304` costs one primary-key read and does not count against the rate limit (`#17`). Pagination emits `link` headers with `/repositories/{id}/...` URLs, clamps `per_page` to 100 silently, and uses keyset scans behind `page`, `since`, `before`, and `after`. Error bodies use `basic-error` and `validation-error` with string `status`. The 404 rule (`#21`) is the `Decision::Hidden` variant: a handler cannot render 403 for a private resource because `authorize` never returns `Forbidden` there. Requests without `User-Agent` are rejected. Renamed repositories resolve through `Alias` entries that return 301 to `/repositories/{id}` in the API and serve git transparently (`#23`). GHES rate limits are off by default (`#19`) in BYOC and self-hosted and on in managed.

Hostname heuristics (`research/clients.md` and `research/actions-protocol.md` section H): the install host is validated at install time and may not end in `github.com`, `ghe.com`, or `localhost`, so every client classifies Tributary as GHES. Managed is one host, `tributary.dev`. That is the target: `/api/v3`, `/api/graphql`, `/api/uploads`, `/login/oauth/*`, and `/login/device/code` on one bare host on port 443, because gh rejects ports and the runner drops them (`research/clients.md#4`, `research/actions-protocol.md#4`). `GET /status` returns 200 with `X-GitHub-Request-Id` for Dependabot, `GET /api/v3/status` returns a body starting `GitHub lives!` for VS Code Pull Requests, and `GET /api/v3/` returns the root document with `rate_limit_url` for Jenkins (`research/clients.md` implication 4). Self-hosters are told that a `github.` label (for example `github.example.com`) lets GCM and Desktop skip their probe. Subdomain isolation (`raw.`, `codeload.`, `uploads.`, `objects.`) is on in managed, where the service certificate covers `tributary.dev` and `*.tributary.dev` (`research/wire-census.md#33`), and optional elsewhere. `RESERVED` keeps every first path segment the host serves out of the login namespace.

OAuth client ids: the five first-party ids in `FirstPartyClient` are seeded once in `auth-na`, or in an install's one authority, when the service or install is created and cannot be deleted. Ids: every numeric id is `i64` in storage and JSON, allocation stops below 2^53, and GraphQL exposes `databaseId: Int` only where the value fits and `fullDatabaseId: BigInt` as a string everywhere (`research/wire-census.md#28`). Node ids use GitHub's new MessagePack format with the repository id first for repository-scoped types, accept the legacy base64 form as input, and honor `X-Github-Next-Global-ID: 1` (`#26`, `#27`).

## Availability

### SLOs

Targets are per cell and per month (43,200 minutes), for Paired cells. A minute is bad when more than 5% of the journey's requests in that cell fail, GitHub's own SLA definition (`research/uptime.md#51`), or when the external probe fails. Regional cells lower the two 99.99% targets to 99.95%, because a single-Region DSQL cluster carries a 99.99% SLA (`#26`) and only git fetches have a stale-read fallback. Identity writes, replica freshness, and revocation coverage are measured per geography, because each depends on that geography's authority, and name claims service-wide, because they depend on the registry.

| Journey | Target | Error budget (min/month) | Measured by |
| --- | --- | --- | --- |
| git fetch and clone | 99.99% | 4.3 | Edge logs per cell, plus synthetic `git clone` of a 50 MB repo every minute from three external vantage points |
| git push acknowledged | 99.95% | 21.6 | Receive-pack outcomes excluding client-caused rejections, plus a synthetic push every minute per AZ |
| Pull request merge | 99.95% | 21.6 | `mergePullRequest` and `PUT .../merge` outcomes excluding rule failures, plus a synthetic merge every 5 minutes |
| REST and GraphQL reads | 99.99% | 4.3 | Edge logs by route class, 5xx and deadline overruns |
| REST and GraphQL writes | 99.95% | 21.6 | Edge logs by route class |
| Web page load (repository, PR, issue) | 99.9% | 43.2 | Browser RUM beacons plus a synthetic Playwright run every minute |
| Actions job start (first log line within 5 minutes of trigger) | 99.9% | 43.2 | Run-owner timestamps, GitHub's Actions SLA definition (`research/uptime.md#51`) |
| Webhook first attempt within 60 s | 99.9% | 43.2 | `hook_delivery` first-attempt latency |
| Identity writes per home geography (signup, sign-in, token creation, claims, renames, forks, membership and grant changes) | 99.95% | 21.6 | `identity` handler outcomes by home geography, plus a synthetic signup and token creation every minute from each continent |
| Name claims (registry writes) | 99.9% | 43.2 | Claim outcomes, plus a synthetic claim and release from each continent every minute |
| Replica freshness per geography (apply lag p99 under 1 s within a continent and under 1.5 s across, plus 1 s more at fronts [guess]) | 99.9% of minutes | 43.2 | Watermarks on the freshness boards against the newest commit any follower has read, per geography, data cell, and front cell |
| Acknowledged push durability | 100% | 0 | Daily replay of every `push` row from the previous day: its pack resolves in S3 or `pack_inline`, and its `ref_log` rows match |
| Revocation coverage (`revoke` returns `covered` within 5 s) | 99.9% | 43.2 | `RevocationReceipt` outcomes and the lagging edges and cells they name |

Durability is an invariant, not a budget: zero acknowledged pushes lost. The durability row is checked by the daily replay of every real push, not only synthetic ones, and by the linearizability harness from milestone 1 (graft from `arena/candidate-1`).

### Failure modes

Stateful components on the request path or the identity-write path. The git cache node and the front cell (edge nodes and their projection) hold only rebuildable state, and they are listed because they hold it. The cell replica is `auth-apply` and the `g_*` tables. Admission rows are keyed by network, account, or IP. The `continent` rows cover the loss of every Region of one continent group (`research/uptime.md#37`, `#38`). The claim registry rows are managed only, because installs keep claims in `core`. The freshness boards are each Region's board objects and its `BoardLease`, and the operator role runs every lifecycle step ("Install operations"). Both are listed because a fault in either could stop writes or rollouts beyond one node.

**Drills.** Managed mode flips one internal dogfood cell to its peer Region every month and one customer canary cell every quarter, using only ARC routing controls. AZ evacuation runs weekly through zonal autoshift practice. A boot drill starts a front node and a data cell node in the peer Region with the home Region blocked at the network layer and checks that each serves from its own Region's projection or config, certificates, and keys. Every week a drill blackholes `core` on the canary cell and checks that fetches keep serving from caches within the stale limit and pushes return 503, so the stale-fetch fallback never goes untested (`research/uptime.md#5`, implication 8). Every week a 30-minute cut of the canary data cell's path to every authority, while the rest of the fleet advances, must show zero failed fetches, write-class 503s that begin within 30 s of the cut and end when it heals, and git's 401 challenge at once for real `git` with a credential helper and no pre-emptive auth. Every month the staging fleet blackholes one of its authorities for 30 minutes and must show zero failed fetches, pushes, or merges and 404 and 401 answers served at once, and every month one Region's front cells are evacuated. Every month AWS FIS isolates one production registry Region, and claims and lease renewals must continue on the other two. Every quarter a staging continent-cut drill blocks a canary geography's authority and registry replica from every other continent and checks that its writers stop within 10 s, that "no" stays immediate elsewhere with no wrong answer, that a revocation acknowledged a second before the cut holds in every cell, `Quiet` after the 5-minute limit plus the clock margin, and no wrong "no" after the cut heals. Every quarter a staging Region dies for good, once in the staging fleet and once under a Paired staging install. No surviving cell may lag or fail a write, and `revoke` must return `covered` again within 20 s of the loss, once the dead Region's `BoardLease` has expired. Every year `reconstitute` rebuilds a canary geography into a shadow authority, then the cut heals, `rejoin` must report the shadow-side commits as stated loss, and no sealed writer may renew. A failed practice run or drill blocks deploys (`research/uptime.md` implication 20, graft from `arena/candidate-1`). In installs the operator role runs the drills ("Install operations"), and the evaluation profile skips any drill that takes a node out of rotation.

**Velocity caps.** Background work that competes with users runs under fixed caps: compaction touches at most 5% of networks per hour per cell, cache refill after an AZ loss runs one stream per node at a bounded rate, and GC deletes at a fixed rate. A recovering cell therefore spends its spare DSQL and S3 capacity on user traffic first (graft from `arena/candidate-1`).

### Change safety

**Deploys.** A release rolls one cell at a time in <vendor-fleet-app> waves, the internal canary cell first, and inside a cell one AZ at a time (`research/uptime.md#4`). Inside an AZ each new role process starts beside the old one with `SO_REUSEPORT`, ramps its DSQL pools gradually within its role's share of each cluster's connection budget, takes new connections, and the old process drains: API requests finish, long clones get 10 minutes, broker long polls end with a reconnect. The NVMe cache stays warm because the instance never stops. A gate after each AZ checks the SLO burn rate, OCC retry rate, outbox age, and pack quorum backlog. A failure swaps back to the kept binary automatically. The in-account operator role runs these steps from a signed rollout intent, with a cursor in `core` and a safe point after each AZ gate, and a node-local watchdog swaps a new process back if it hears no "gate passed" before its deadline, so a lost session or a revoked deploy role never strands an ungated process ("Install operations"). This is the in-install abort that the BYOC machinery lacks (`research/byoc-grounding.md` item 11). Node image changes (OS and git) replace instances per AZ through the Auto Scaling group with the same gates, so a single-node evaluation install takes a short outage for one. That launches capacity during a deploy, never during recovery.

**Trust roots, config, and feature flags.** Config is code (`research/uptime.md` implication 16). Three keys sign everything a node trusts. The vendor's release key signs only releases, action packs, and pin maps. Each install, and each managed cell, has two KMS asymmetric keys that the bootstrap creates in its account. The config key, usable by the vendor's deploy role and the customer, signs rollouts and routine config. The customer-only key, which no deploy role can use, signs `Uninstall`, `Restore`, `DrPromote`, `DrFailback`, `Halt` and `Abort` during a revocation, and any config that changes endpoints, buckets, or the identity provider. In self-hosted the customer's CI is the deploy principal, so the customer holds both keys. The operator role signs no intent or config, only its status documents. Flags and settings ship as a signed config bundle per cell, rolled through the same waves, validated on load, with last known good kept, and nodes load each generation straight from their Region's control bucket with no operator step, so config applies while `core` is impaired. There is no runtime flag service. `tributary config sign` and `tributary config apply` change the customer-signable settings. The config key covers the hostname and isolation subdomains, the TLS certificate and key, the stale-fetch limit, SES or SMTP, the alarm SNS topic, rate limits, and the backup schedule. The customer-only key covers DSQL endpoints, bucket names, the `dr` Region, and instance sign-in and IdP settings. Apply rolls back to the last known good generation when nodes reject it. Release-scoped values, such as the runner floor and the frozen-path schema, are signed only in the release. The operator role renews certificates and rotates key epochs, and expiry alarms reach the customer's SNS topic 30 days ahead ("Install operations").

**Schema migrations.** DSQL needs one DDL per transaction, so the migration runner applies statements one at a time under a lease row, as a separate stream per cluster. Every change is expand, then backfill in 1,000-row idempotent chunks with the cursor in `core`, then contract, in the release order that "Install operations" sets. The release record gains `phase` (expand, contract, or none), which the compatibility check reads, so only a contract phase sets `compatibility.rollbackBarrier` (`research/byoc-grounding.md` item 9), not every `moved` block or record change that the git-diff rule flags (`#26`). Release N runs against schema N-1 and N+1. Index builds use DSQL's asynchronous index creation [unverified]. Migrations throttle on commit latency and OCC retry rate, the lesson of GitHub's May 2026 migration at peak (`research/uptime.md#44`). Stored formats that outlive a release, such as `pack_inline` framing, stored webhook payloads, authority log records, and inter-cell events, follow a two-release rule: release N learns to read format k+1, and release N+1 starts writing it (graft from `arena/candidate-2`).

**The authority schemas and the registry.** Every cell of a geography writes its authority and every cell reads it, so an authority has no canary cell. Its schema changes ship only in a release dedicated to that change, one authority per wave with AP first, after two weeks on that authority's shadow, a second cluster fed by DSQL CDC on which every migration and every new prepared statement runs under replayed production follower reads and writer statements (graft from round-2 candidate 3). An install has no shadow, so its authority-schema and git-path DDL first runs in the preflight against a restored copy of the install's latest backup, the install's form of the shadow canary. Registry items take only additive attributes, so they never add a migration barrier (`research/byoc-grounding.md#40`). Only `trib-authority` holds a connection or client, through a fixed prepared-statement set and a fixed set of condition expressions that CI checks, and the `g_*` replica tables in each `core` follow the frozen-path rule below.

**Frozen git path.** The `core` tables that the git and merge paths touch (`slot_state`, `repository`, the `g_*` tables that `authorize` reads, `branch_rule`, `ref`, `ref_shard`, `ref_tombstone`, `pack`, `pack_inline`, `push`, `ref_log`, `outbox`, `outbox_pending`, `pull_request`, `review`, `check_run`) take DDL only in a release dedicated to that change, after two weeks on the canary cell, and the migration runner refuses any other DDL on them. New fields go into new tables. The git and merge paths run only a fixed set of prepared statements, and CI checks their plans against a production-sized fixture, so our own migrations and query plans stay off the git path, the largest source of GitHub's core outage minutes (`research/uptime.md#43`, `#44`).

**Zero-downtime upgrades in every mode.** The hot swap and expand-contract rules are the same everywhere. A single-node evaluation install upgrades its binary the same way, by process handoff on one host, and takes a short outage for a node image change, because its one instance is replaced. An install several releases behind submits one rollout intent whose `steps[]` chain names every contract boundary in order, and the operator role walks it with a resumable journal, so no step leaves the N-1 and N+1 schema window. CI tests every release pair in that window. DSQL engine upgrades are AWS-managed and do not follow Tributary's waves [unverified that they cause no client-visible downtime or that AWS stages them cluster by cluster]. "Tradeoffs accepted" and "Open questions and risks" name that risk. The upgrade never needs maintenance mode, unlike GHES feature releases (`research/uptime.md#55`).

**What the BYOC machinery gets.** Its deploy tool stops running long stages itself. It keeps `publish:image`, copies each verified release into `releases/` in every control bucket, submits a signed intent to the install's control bucket in each Region, and polls the status documents with fresh short sessions ("Install operations"). The operator role runs the stages `apply:infra`, `migrate:expand`, `roll:nodes` (the per-AZ hot swap and gates), the soak, `roll:operator`, and `migrate:contract`. It needs no stateful-fleet stage with fencing, leader handoff, or replica catch-up (`research/byoc-grounding.md` item 7), because no node holds canonical state. Observation moves from API Gateway routes to the signed status documents, which carry the `nodes` report, a storage section (OCC retry rate, commit p99, and connection errors per cluster and role, oldest pending outbox row and parked rows per consumer, follower lag per authority partition and per inter-cell source, unrepaired pack locations, cache hit rate), a `dr` section with `dr-apply` lag, and an identity section (authority lag per geography, board freshness, lease state, the claim sweeper's backlog). Deploy-plane gains `nodes-at-version`, `storage-healthy`, `outbox-fresh`, and `dr-fresh` gate checks in place of `components-healthy` and `lambda-code-matches`, plus `replica-fresh` and `identity-fresh` in managed (item 8). For private installs, <vendor-fleet-app>'s `liveness` check, an unauthenticated GET that a private NLB fails and whose fail cannot be overridden (`#32`, `#33`), becomes a check that the newest status document is fresh.

What collapses in an install. One geography means one authority schema with no writer leases, no `Quiet`, and no `reconstitute`. Every install, Paired included, keeps the registry as a table in `core`'s `authority` schema, so it has no DynamoDB, no cross-Region claim replica, and no claim audit, and a Paired install's claims are exactly as durable as `core`. A `dr` promotion moves that table with the rest of `core`, applies the revocation records from the `dr` control bucket first, and runs the same `ref_log` reconcile, and the sweeper finishes or undoes any saga the promotion cut between claim and activate. The applier copies the `authority` schema into `g_*` tables inside one cluster, and the one cell follows its own inter-cell log. That costs a second copy of a small graph and keeps one code path, because no handler has a branch that reads an authority directly. CI runs a two-geography install with two authority schemas in one DSQL cluster, so escrow, `reconstitute`, and cross-geography paths stay tested. Installs never talk to the managed namespace, so their logins never collide with it.

What the customer provisions and the preflight checks. Paired installs enable a peer Region and a witness Region, and the target preflight checks only that the trio sits inside one DSQL Region set, so a Region outside MRSC's list, such as ca-west-1, is accepted. In every install Region (home, `dr`, peer, and witness) the preflight checks Aurora DSQL and DSQL CDC availability, the instance type in three AZs (one for evaluation), the vCPU and DSQL cluster quotas, SES production access or SMTP reachability, and the certificate format (PEM import or an exportable certificate), because the edge terminates TLS itself. With `dr` it checks the inter-Region connectivity that `dr-apply` needs, and in an air-gapped install it probes every VPC endpoint that the stage table derives ("Install operations"). Before a release with authority-schema or git-path DDL, it runs that DDL against a restored copy of the install's latest backup ("Change safety"). The target's `tributary` block gains `regions { home, peer, witness }` or `regions { home, dr }`. Tables and buckets take the `trib-` prefix, because installs own unprefixed account singletons (`#2`).

Bootstrap and deploy policy. The bootstrap takes a `product` variable that selects Tributary's `trib-` name prefixes and the PassRole services it needs, EC2, Auto Scaling, and FIS, and it creates the service-linked roles it needs explicitly instead of relying on `PowerUserAccess` (`research/byoc-grounding.md#4`-`#6`). It also creates the install's config key and customer-only key, the deployer role for `apply:infra`, which no serving node can assume, and the replicated OpenTofu state bucket, and it grants the Auto Scaling service-linked role use of the install's CMK, so instances launch from the re-encrypted AMI. A Tributary deploy policy replaces `PowerUserAccess`. It denies reading repository data, meaning pack-bucket `GetObject` and connecting to DSQL as a data role or as admin, it denies `kms:DisableKey`, `ssm:StartSession`, and `ssm:SendCommand`, and it denies deleting stateful resources: DSQL clusters, pack buckets, tables, and KMS keys. The same delete denies sit in the permissions boundary of every workload role, the operator's and the deployer's included, so no intent reaches them through the operator. Deletion stays with the customer's admin role and `tributary uninstall --finalize`. Migrations need no deploy-role DSQL access, because the operator role runs them.

Reuse of the existing BYOC machinery (`research/byoc-grounding.md`): the release registry, signing, retention, and `rollback-check` transfer with a Tributary bucket and key (item 1). `comparedWith` is computed per release line, so a customer pinned at N-2 keeps its rollback (`#34`), and every contract-phase release, with its source AMI, is retagged `retention=customer` (`#15`). The bootstrap trust pattern transfers through the `product` variable (items 2 and 5). The target document gains a `tributary` block, the release record gains `product` and `phase` fields, and <vendor-fleet-app> reads one contract per product (item 12). The fleet model, waves, gates, and the rule that automatic advance never starts wave 1 transfer, with a <vendor-fleet-app> "install" standing for a data cell or a front cell (items 4 and 13). Tributary requires its own dedicated account per install (item 6). What Tributary adds: the operator role with its intents and status documents, `apply:infra`, `roll:nodes`, and the migration stages, `publish:image` and the release copy in the deploy tool, the Tributary gate checks, the automatic in-cell abort, and, for managed only, network placement, slot moves, front cells, and the per-authority release stream.

## Install operations

The vendor's deploy tool runs outside the customer's account, so it cannot drive a step that outlasts the one-hour chained session, that must survive a customer revoking the deploy role or a week-long vendor outage, that runs with no internet route, or that observes health through a role allowed only to call API Gateway (`review/byoc-walk.md` findings 1, 2, 10, and 12, `research/byoc-grounding.md#7`, `#21`). So the install operates itself. An in-account `operator` role, part of `worker`, owns every lifecycle step under a lease: rollout stages, infrastructure applies, migrations, node rolls, certificate renewal, key rotation, action-pack sync, backups, restore, `dr` promotion, failback, drills, and the export that starts uninstall. People and tools only submit signed intents and read status. Two jobs stay with the deploy tool, or with the customer's CLI: `publish:image`, and copying each verified release create-only into `releases/` in every control bucket, so the operator never needs registry access. Managed cells use the same path, with the vendor as the only submitter, so the three modes run one artifact.

**Intents and status.** An operator writes a signed, create-only intent (a rollout plan, a config generation, or a command from the allowlist) to the install's control bucket in each Region, and reads signed status documents from the `status/` prefix there. The operator role derives the submitter from the key that verifies the signature, so a vendor signature cannot pass as the customer's, and it signs no intent or config, only its status documents, so a restore or promotion carries its new endpoints in the customer-signed intent ("Trust roots, config, and feature flags"). The vendor's deploy tool submits an intent and then polls with fresh short sessions, so no stage outlives the one-hour chained session (`research/byoc-grounding.md#48`). Intents carry a short `not_after` (1 hour [guess]), and an intent not started by then is refused. `Halt { intent }` stops a rollout at its next safe point, and `Abort { intent }` swaps it back to the last safe point. The runbook for revoking the deploy role is: revoke the role, then submit `Halt` signed with the customer-only key, then `Resume`, `Abort`, or a new rollout. The observer role reads the status documents through `s3:GetObject` in every install Region, so no API Gateway is needed, a private NLB is fine, and observation survives the loss of the home Region. Deploy-plane gates read the same documents. The installation record lives in `core` and is copied into each status document, so no install needs a DynamoDB control table (`#17`).

**Stages, leases, and the watchdog.** Every stage is idempotent and resumable from its cursor, with a safe point after each AZ gate. Routine stages keep their lease and cursor in `core`. Recovery-class stages keep both in the acting Region's control bucket, written with `If-Match`, so a swap-back, halt, abort, config change, restore, promotion, or failback runs while `core` is impaired. Nodes load each signed config generation straight from their Region's control bucket with no operator step, and the operator holds one reserved `core` connection that is never shed with other workers (the DSQL limits table). A node-local watchdog swaps a new process back to the kept binary if it receives no "gate passed" within its deadline (15 minutes [guess]), so a dead operator, a revoked role, or an absent vendor never leaves an ungated process serving. One stage of each kind runs at a time under its lease.

**Stage table.** Each stage, what runs it, and the AWS services it calls. CI derives the last column from each stage's code and the release's OpenTofu module, and the air-gapped endpoint list is its union.

| Stage | Runs as | AWS services it calls |

| `apply:infra` | A one-shot instance under the deployer role | The services the step's OpenTofu module declares, and S3 for its state |
| `migrate:expand`, backfill, `migrate:contract` | Operator, `core` lease | DSQL |
| `roll:nodes`, `roll:operator`, `SwapBack` | Operator, then each node's watchdog | EC2, Auto Scaling, Elastic Load Balancing, S3 |

**Release order, migrations, and rollback.** A release is `publish:image` by the deploy tool, then `apply:infra`, then expand, then `roll:nodes` across every Region and the `dr` node group, then a soak, then `roll:operator`, then contract. `Stage::ApplyInfra { step }` applies that step's OpenTofu module, which also points every launch template at the new AMI, as a short-lived in-account task under its own deployer role, which no serving node can assume: a one-shot instance running the release's deployer image, whose provider mirror needs no registry access (`research/byoc-grounding.md#16`) [inference: the instance form]. An install's first apply runs from the deploy tool or the customer's CLI, because no operator exists yet [inference]. The OpenTofu state bucket replicates to the peer or `dr` Region. `roll:nodes` leaves out the operator processes, and `roll:operator` swaps them only after the soak, so the previous release's operator runs every stage up to contract, and the cursor and journal follow the two-release format rule. `roll:nodes` moves the `ReleasePointer`, so a node that Auto Scaling launches later boots release N, never N-1. Contract runs only when the `nodes` status shows every process at version N or later, no swap-back pending, and every launch template at N, and it removes only the previous release's deprecated shapes. The backfill cursor lives in `core`, and the release record's `phase` feeds the compatibility check. OpenTofu removes a resource only two releases after the code stops using it, and stateful resources carry `prevent_destroy`, so a tool rollback never destroys a cluster, bucket, or key (`research/byoc-grounding.md#36`). Contract-phase releases are always retained, and recovery after a barrier is roll-forward only. A long skip, such as N to N+4, is one intent whose `steps[]` chain the operator role walks with a resumable journal, verifying each release from `releases/` and applying each step's module just before that step's stages, so a later module never removes a resource that a running release still uses. The chain's preflight checks registered runners against the final step's runner floor, because four floor raises in one chain would otherwise shrink the one-release warning to hours.

**Images and action packs.** `publish:image` belongs to the deploy tool. It shares the release's source AMI and grants its KMS key to the install's account in each Region, then copies the AMI into every install Region, re-encrypts it with the install's key, and grants the Auto Scaling service-linked role its use, so node replacement never depends on a vendor share (`research/byoc-grounding.md#46`). Self-hosters run the copy as `tributary release import-ami`. Source AMIs follow their release's retention, so a `retention=customer` release keeps its AMI (`#15`). Nodes verify the image digest at boot. `tributary actions import` loads a signed actions pack, and an in-install sync job pulls new packs when the install has outbound access, as GHES's `actions-sync` does [unverified]. The pack carries an allowlist of third-party actions, such as `aws-actions/*`, and an admin can add any public action to the install's `actions` mirror, as GHES's `actions-sync` allows [unverified]. The install serves `RunnerRefresh` download URLs itself, and each release publishes the next runner floor one release ahead, so a runner fleet with updates disabled is warned a release before it is refused.

**Certificates and keys.** The operator role renews the TLS certificate 30 days before expiry through ACME DNS-01 in a delegated Route 53 subzone, or validates a customer upload written to `certs/` in the control bucket and alarms before it expires. It rotates each key epoch on a schedule: a new verifying key is published at least one token lifetime before it signs, and the old one retires after the last token's `exp`. A per-install private CA, whose private key the operator role's KMS key holds wrapped, issues the internal mTLS certificates and rotates with the key epochs.

**Backups and restore.** Both DSQL clusters back up through AWS Backup [verify in Milestone 0], hourly with 35 days of retention by default [guess]. S3 keeps noncurrent versions at least as long as the backup retention, so GC and superseded-pack deletes stay restorable across the whole window. `tributary admin restore --to <t>` submits two `Restore` intents signed with the customer-only key. The first makes the operator restore both clusters to one point in time and report their new endpoints in the status document [inference: AWS Backup restores into new clusters]. The second carries those endpoints and runs the cutover: it restores the pack versions that the restored `core` names, restarts every shard version above the pre-restore maximum, replays every revocation record in the home control bucket newer than `t`, bumps `restore_epoch` in `core` and every control bucket, and runs the push-durability replay as its verification. Nodes drop their reftables, caches, and auth snapshots when the epoch changes, so no node serves rewound state. Unlike `dr` promotion, restore calls DSQL's control plane, so a DSQL control-plane outage holds it at its last safe point. If AWS Backup offers only snapshots, `--to` picks the newest pair at or before `t`, and the operator role re-runs each check relay or run trigger that lost its other half, idempotently by event id [inference].

**The recovery Region.** `Regional { home, dr: Option<Region> }`. With no `dr`, RPO is the backup interval, and the evaluation profile uses it. With `dr`, the install keeps a KMS multi-Region key replica there, pre-stages wrapped keys, certificates, and SSH host keys in the `dr` control bucket, and requires inter-Region connectivity, peering or a transit gateway, so `dr-apply` reaches the home Region's DSQL and CDC. `tributary dr promote` and `tributary dr failback` submit customer-signed intents carrying the new endpoints, which the operator role runs from the `dr` Region with its lease and journal in the `dr` control bucket. Promotion applies the revocation records, runs the `ref_log` reconcile, rotates key epochs, and moves traffic (the DSQL `region` row). Failback rebuilds the old home as the new recovery side from a fresh CDC feed and promotes back when the customer chooses [inference], so commits stranded in the old home inside the RPO window stay stated loss. A Paired install that loses its home Region for good keeps its deploy machinery: the peer Region's operator takes the lease, `apply:infra` reads the replicated OpenTofu state there, and rollouts resume within 1 hour [guess], the deploy machinery's RTO. Re-adding a third Region is an open question.

**Monitoring and the 2am runbook.** Every install exports CloudWatch metrics and alarms and a Prometheus endpoint, and it can send alarms to a customer SNS topic. The runbook for an impaired DSQL is a decision tree keyed on AWS Health, CDC lag, and the stale-limit clock. With no DSQL event in AWS Health, the fault is Tributary's, and the operator swaps back the last rollout. With an event, CDC lag inside the RPO, and the stale-limit clock under 1 hour, the operator waits while fetches serve stale. Past 1 hour, or when AWS projects recovery beyond the 60-minute RTO, the operator runs `tributary dr promote`, or without `dr` keeps waiting or restores. Every branch is recovery-class, so each works with `core` impaired. Self-hosters are told to drill a promotion and failback every quarter. The operator role runs the weekly stale-fetch drill on one node taken out of rotation and reports every drill in the status document, and a failed drill blocks the next rollout until a signed intent acknowledges it. The evaluation profile skips drills that take a node out of rotation.

**Air-gapped installs.** A connected host runs `platform-deploy release fetch` and writes the release, the actions pack, and each AMI stored as an S3 object by EC2's store-image task [unverified in every Region] to the customer's transfer medium. Inside, the CLI copies the release into `releases/`, and `tributary release import-ami` and `tributary actions import` load the rest. Each install Region needs a VPC endpoint for every service in the stage table, so the list is derived, not kept by hand: DSQL, S3, KMS, STS, EC2, Auto Scaling, Elastic Load Balancing, CloudWatch and CloudWatch Logs, SSM with `ssmmessages` and `ec2messages`, SNS, AWS Backup, and any other service the OpenTofu module declares, plus an internal SMTP relay for email. An install with `dr` also needs its inter-Region connectivity. The preflight probes every endpoint in every install Region. Health checks run as CloudWatch alarms on the deep regional endpoint instead of public Route 53 health checks, and because ARC's routing-control endpoints are public [unverified], a `dr` promotion moves traffic by a private DNS change instead of ARC.

**Evaluation profile and uninstall.** The evaluation profile is one node in one AZ with no `dr`, and it has no availability SLO. Growing it means raising `perAz` from 1 to 3 across three AZs. New nodes join the rendezvous sets and fill their caches from S3 under the velocity caps, so fetch latency stays above baseline until the caches warm, and the 33% removal cap and 66% sizing apply only from three nodes. Uninstall finishes outside the install. The operator's `Uninstall` stage, signed with the customer-only key, only exports data (repositories as bundles, metadata as a migration archive) and disables deletion protection and `prevent_destroy`. The customer then runs `tributary uninstall --finalize` with its own admin role, which destroys the install, empties the versioned buckets including noncurrent versions, schedules deletion of replica keys and then primary keys, and destroys the bootstrap last from the admin's local bootstrap state (`research/byoc-grounding.md#22`).

## Public service concerns

**Anonymous access and rate limits.** Anonymous callers get public reads only, keyed at the front by source IP (the /64 for IPv6). REST allows 60 requests per hour (`research/wire-census.md#18`), GraphQL requires authentication as on GitHub [unverified], and git allows 600 negotiations per hour and 8 concurrent per IP [guess]. Authenticated limits follow GitHub's numbers: 5,000 REST requests per hour per user, 1,000 per repository for `GITHUB_TOKEN`, 5,000 GraphQL points per hour, and secondary limits of 100 concurrent requests and 80 content-creating requests per minute (`#18`, `#35`). Each front node enforces its share of a Region-wide limit, as round-2 candidate 3 described (`arena/round2/candidate-3/DESIGN.md`, journey 1), so limits do not multiply with node count. Counts are approximate, because GitHub documents per-Region variation (`#18`), and excess gets 429 before any git byte. Inside a data cell each repository's rendezvous set admits authenticated traffic first and sheds anonymous requests first with 503 and `Retry-After`. For public clones, `uploadpack.packObjectsHook` points at a response cache on NVMe keyed by wants, haves, and capabilities, so a clone storm at one tip costs disk reads instead of `pack-objects` CPU [inference: identical full clones dominate anonymous traffic].

**Abuse and spam.** Signup is a registry claim plus two home-authority writes behind front limits per IP and per ASN, with email verification and 24 hours of reduced content-creation limits for new accounts. Repository creation and forks are capped per account per hour, because each writes the owner's authority. Suspension is one home-authority write, and within the apply lag fronts reject the account's credentials and cells hide its content at render time from `g_account.suspended`. Abuse aimed at one repository (clone floods, comment spam) stays in its network's cell, and a slot that dominates a cell moves to a dedicated cell.

**Takedowns.** A takedown is a `takedown(network or repo, scope, reason)` row in the repository's own `core`, which every request for that repository reads, so it applies at once to git, the API, raw files, and archives. A DMCA takedown of a whole fork network is one network-scoped row, because a network lives in one cell. Country-scoped takedowns return 451 [unverified that GitHub uses 451] using a GeoIP table on the front, passed in the assertion. An account takedown is a suspension.

**CDN for public content.** Managed enables subdomain isolation (`research/wire-census.md#33`), and `raw.tributary.dev`, `codeload.tributary.dev`, and `objects.tributary.dev` sit behind CloudFront with front cells as the origin. CloudFront serves only immutable public bytes: raw files and archives keyed by commit SHA, release assets, and avatars. The data cell checks the repository row and answers 302 to a CloudFront signed URL that lives 10 minutes and carries the repository's `content_epoch`. A takedown or a switch to private bumps the epoch in its own transaction, so no new URL is issued and old ones expire within 10 minutes, with no CloudFront invalidation on the request path. CloudFront's control plane lives in us-east-1 (`research/uptime.md`, summary), so distributions are created at install, and each subdomain has a Route 53 failover record to the front cells. Git smart HTTP and the APIs are never cached. Public repositories advertise `bundle-uri` with CloudFront bundles for clients that enable it, which default clients do not [inference], so the pack response cache carries anonymous clone load.

**Residency.** An org or enterprise with residency places all its networks, its Actions runners, and its search documents in its residency domain. A fork into a resident org of a network that lives outside the residency is created detached: a new network in a resident slot, objects copied, `fork: true`, and a pull request back upstream gets 422 with a message that names the residency rule. A fork of a resident network by anyone joins the network in its cell. A transfer that would move a resident network's owner outside its residency, or bring an outside network into a resident org, gets the same kind of 422 ("Known deviations from GitHub"). Resident orgs' Actions secrets are stored in their residency's cells, not in an authority. Identity residency follows the owner's `Home`, as below, with Europe as the example.

What an `Open` European account or org keeps only in Europe: password hashes, TOTP seeds, recovery codes, WebAuthn credentials, session rows, plaintext email addresses and their verification state, OAuth client secrets, IdP configuration and SCIM tokens, sign-in history with IP addresses, and the identity audit log (`HomeOnly`). These never enter the shared log, so no follower outside Europe holds them, and sign-in runs in a European cell. The one exception is the escrow. An `Open` home's home-only rows are copied to a partner geography (Europe to North America) so that a continent loss does not wipe millions of passwords and email addresses. `Open` makes no residency promise, and the escrow is the price of recovering such accounts.

What leaves Europe for an `Open` home, and why. The registry's three Regions hold the login, the account id and home, SSH key fingerprints, HMAC digests of verified emails, app slugs, and retired pairs, because each needs one answer worldwide. Every data cell's replica holds the public profile, `sessions_not_before`, suspension, memberships, team memberships, repository grants, org policies without secrets, installations, repository names, SSH and GPG public keys, and email digests, because any cell must authorize any user in the same snapshot as the refs it guards. Every front projection holds names, credential hashes with scopes and expiry, fingerprints, and installation `not_before`, because any front must authenticate without a remote read.

What a `Resident` home keeps in Europe. Identity residency is offered to managed-user enterprises, as GitHub ties data residency to managed users [unverified]. Their orgs, managed users, credential hashes, memberships, teams, grants, installations, and repository names go on resident partitions that only EU followers apply, with no escrow. Only the shortcode, the org logins, and the managed users' logins leave Europe, as registry items and shared name records, because they are public names in one namespace. A front outside Europe that resolves a resident owner, or reads a resident token's class, forwards to a European front cell. Their repositories live only in European cells already. A cell outside Europe treats a resident principal only as an authenticated reader of public content, which is all a managed user may do outside its enterprise [inference]. The enterprise's IdP is the root of recovery, and a European continent loss loses these accounts with their repositories. An enterprise that needs every identity fact in one geography, logins included, still gets its own namespace through BYOC, as GitHub offers `*.ghe.com`.

**Enterprise managed users.** An enterprise claims a shortcode in the registry, and the claim reserves the whole login suffix `_<shortcode>`. Managed users get `<base>_<shortcode>` logins that only the enterprise's SCIM endpoint can create, one claim per enterprise rather than one per user. A public login cannot collide, because public logins contain no underscore [inference from GitHub's EMU naming].

## Actions

**Workflow engine.** The server owns triggers and filters, matrix expansion, the `needs` graph, job-level `if`, concurrency groups, reusable workflows and `secrets: inherit`, environments and approvals, `GITHUB_TOKEN` minting and `permissions`, OIDC, label matching, job outputs, and retention (`research/actions-protocol.md#62`). The parser is a Rust port of the runner's MIT `GitHub.Actions.WorkflowParser` including `MatrixBuilder`, with `workflow-v1.0.json` as data and `@actions/workflow-parser` as a differential oracle (`#59`, `#60`). The template-token and context-data JSON converters are ported byte-exact (`#19`). Triggering is an outbox consumer, so a run exists only if its push or PR event committed, and run creation is idempotent on `(event id, workflow path)`.

**Runner protocol.** Tributary returns `use_v2_flow: true` and implements the runner admin registration, broker, run service, launch service, and results service (`research/actions-protocol.md#5`, `#6`, `#12`, `#16`, `#17`, `#22`). The legacy distributedtask family is frozen and needs the VSS location service. The broker family is where GitHub invests, and the launch service is the one place Tributary controls which bytes run for each `uses:` (`#17`). Each Tributary release pins one tested runner version, sends `RunnerRefresh` to older runners with a download URL that the install itself serves from the actions pack's runner tarballs, publishes the next floor one release ahead with a warning to runners below it, and refuses versions below the current floor with `RunnerVersionTooOld` (`#25`). JIT configs always set `GitHubUrl` and `IsHostedServer=false` (`#2`). ARC scale-set endpoints (`_apis/runtime/runnerscalesets`, sessions, message queue, `acquirejobs`, `generatejitconfig`) ship at T1 against a pinned ARC range (`#30`).

**Org runners across cells.** An org-level runner registers in the org's index cell. Jobs in other cells that match no repository-level runner are offered to it through the inter-cell log. The broker claims a job with one compare-and-set RPC to the job's cell. `RunServiceUrl` carries the job id, and fronts route it by the job's slot, so acquire, renew, logs, and completion reach whichever cell holds the slot, through a slot move too. The claim is the one cross-cell call in Actions.

**Toolkit hostname heuristics and SHA pins.** Tributary is GHES to the toolkit, and nothing on the server can change that, because `isGhes()` reads only `GITHUB_SERVER_URL` (`research/actions-protocol.md#43`, `#44`). The T0 contract is the GHES contract: cache v1 for `actions/cache@v4+`, legacy artifacts for `upload-artifact@v3.2.2` and `download-artifact@v3`, and the runner protocol. Tributary never alters the bytes of an action. The launch service resolves every `uses:` to the exact upstream bytes, from the install's `actions` mirror org, which holds byte-for-byte copies of upstream tags and commits that managed syncs directly and installs load from the signed actions pack ("Install operations"). For `upload-artifact@v4+`, `download-artifact@v4+`, `upload-pages-artifact`, and `deploy-pages`, the vendor publishes forks under `tributary-actions/*` that differ from upstream only in the `isGhes()` test (they also trust `TRIBUTARY_ACTIONS=true`, which every job sets). Each fork release is built reproducibly by CI from the upstream tag, and CI regenerates a signed **pin map** from upstream SHA to fork SHA for every upstream release, so the map is derived, not hand-kept. Substitution is an org policy with two settings. With tag substitution on (the managed default for orgs migrating from github.com), `actions/upload-artifact@v4` resolves to `tributary-actions/upload-artifact@v4`. SHA pins are substituted only when an org admin has approved the vendor's signed pin map, and then only for SHAs that appear in it. Every substitution prints one log line naming both references and both SHAs, and the job's OIDC token and run metadata record the bytes that ran. An unapproved SHA pin to `upload-artifact@v4+` fails exactly as it does on GHES, with an annotation that links the pin-map approval page and names the fork SHA that matches the pinned upstream SHA, so a team can pin the fork directly (graft from `arena/candidate-2`). I chose this over Gitea's JavaScript rewriting (`#57`) because rewriting changes the bytes behind a SHA without anyone approving it and depends on string patterns in 118 bundles.

**Hosted runner fleet.** Managed hosted runners run unmodified `actions/runner` inside Firecracker microVMs on long-lived metal hosts in separate runner AWS accounts per Region. One VM runs one job and is destroyed. The VM gets a JIT config and reaches cells only through the public front cells, exactly like a customer's runner, so a compromised VM holds only that job's runtime token, `ghs_` token, and OIDC capability. Runner accounts have no IAM trust into cell accounts and no network route to them other than the front. The instance metadata service is blocked inside VMs, and egress goes through per-pool NAT with published ranges in `/meta`. Warm VM pools on running hosts absorb EC2 launch outages. Pool growth uses EC2 launches, so the Actions job-start SLO, not the core SLOs, carries that risk. Images are built by porting `runner-images` Packer templates to an `amazon-ebs` source (`research/actions-protocol.md#64`, `#65`), starting with a smaller curated Ubuntu image.

**Cache.** Cache v1 (`_apis/artifactcache`) at T0 and twirp `CacheService` v2 at T1, with the Azure dialect shim that accepts Put Blob, Put Block, and Put Block List and returns `x-ms-request-id` (`#35`, `#39`). Downloads are presigned S3 URLs (`#36`). Entries are scoped by repository and ref, with GitHub's restore order (current ref, then default branch) and LRU eviction per repository at 10 GB by a worker consumer.

**Artifacts.** Legacy pipelines artifacts (`#40`) at T0. Twirp `ArtifactService` v4 at T1, uploads through the block shim that maps 8 MiB blocks onto S3 multipart parts in order, and downloads by 302 to presigned S3 URLs (`#37`, `#38`).

**Logs.** Results service twirp with Tributary-signed URLs that accept `comp=appendblock` and `seal=true` (`#22`, `#23`). Blocks land as S3 chunk objects and a worker compacts them per step. Live logs stream over the `FeedStreamUrl` WebSocket and `WorkflowStepsUpdate`.

**OIDC.** Issuer `https://HOST/_services/token`, which in managed mode is `https://tributary.dev/_services/token` for the whole service, with the claim set and legacy `sub` format of GHES and the `OWNER@ID/REPO@ID` format as an opt-in (`#41`, `#42`). The job's cell signs with its own key epoch, private keys never leave the cell, and the JWKS under the issuer publishes every cell's current and previous epochs from the front projection.

**Coping with GitHub changing the toolkit.** The runner is pinned per release. A nightly conformance job runs the newest runner, the newest major of each first-party action, and the newest `@actions/cache` and `@actions/artifact` against the canary cell, and opens a ticket on the first failure. Fork rebuilds and pin-map regeneration run in the same job. If GitHub merges a vendor-neutral escape such as trusting `ACTIONS_RESULTS_URL` (toolkit issue #2439, `#51`), the forks become unnecessary and the substitution policy is retired.

## Frontend and native app

**Web.** React 19 with Primer React, the stack GitHub itself ships (`research/clients.md#62`-`#64`). The app reads data through the same public GraphQL and REST endpoints that clients use, with persisted queries, plus a small private `/_t/ui/*` API for diffs, file trees, and blame computed by the `git` role. Dogfooding the public API means a UI regression is often a wire regression caught by the same oracles. There is no Node server-side rendering tier, because that would add a runtime and a stateful-looking fleet to every mode. Instead the front `edge` serves the HTML shell and, for the first route, sends that route's persisted GraphQL query to the routed cell and inlines the JSON, so first paint needs no second round trip. Static assets are embedded in the edge binary and served with immutable cache headers, and managed mode puts CloudFront in front of the asset path and the isolation subdomains ("Public service concerns").

**Staying up when backends degrade.** The shell and assets come from edge memory, so the UI loads whenever the edge does. Each page region (file tree, diff, checks, timeline, search box) is its own error boundary with its own query, so a search outage empties the search box and nothing else (`research/uptime.md#49`). The client retries only idempotent reads, with a retry budget and jitter, and it never polls faster than `x-poll-interval`. Long diffs virtualize lines, following GitHub's 2026 diff work (`research/clients.md#62`).

**GPUI native app.** It does not earn a place at launch. Unmodified gh, GitHub Desktop, VS Code, and JetBrains already cover native workflows against a GHES-shaped host, and that compatibility is the product. GPUI is pre-1.0 with frequent breaking changes and is tied to Zed's repository (`research/clients.md#57`-`#59`). One narrow scope could justify it later: an offline-capable review inbox for very large pull requests, if the web diff misses its latency target on PRs above 10,000 changed lines. That decision waits for measurements from the web app, and the app would be a pure API client with no private endpoints.

## Build order

**Milestone 0: decide the base before building on it.** Before any git code exists, a small driver runs exactly the `commit_push` transaction as plain SQL against a single-Region and a multi-Region `core` cluster on the intended Region trio. It drives one repository at 10, 25, 50, and 100 commits per second, half the writers contending on `main` and half on distinct branches across shards, while 200 readers run the 40-row `refresh` query. It also writes refs with 900-byte names to measure DSQL's key encoding against the 1 KiB limit. It records sustained commits per second, the 40001 rate, commit p50 and p99, and read p99. **Load gate:** at least 50 commits per second, with commit p99 under 1 s single-Region and under 1.5 s multi-Region. Next to the load test, a prototype cache node that serves upload-pack with the stale-fetch fallback runs against `core` and `aux` clusters. **Failure gate:** `core` blackholed for 30 minutes while clones run keeps fetch success at or above 99 percent; an index build on a 100-million-row `aux` table at peak push load keeps push p99 within 1.5 times baseline; and 150 new connections per second from the `aux` role cause zero git errors. The vendor also asks AWS whether DSQL engine upgrades can be staged cluster by cluster and whether AWS Backup covers both DSQL clusters with point-in-time restore and cross-Region copy, and it tries the AMI copy path: a release AMI copied into a fresh account in two Regions, re-encrypted with that account's key, and launched by an Auto Scaling group whose service-linked role holds a grant on the key. If either gate fails, or if AWS cannot stage engine upgrades that way, `arena/candidate-2/DESIGN.md` becomes the base, because it keeps git ordering out of the metadata store and keeps git writes through a fleet-wide DSQL failure, and its Milestone 1 then measures S3 compare-and-swap throughput (`review/arena-judge.md`, flip condition).

**Authority gate**, about two days on a scratch account (`review/round3-judge.md`, flip condition; gate shape grafted from round-3 candidate 2). It builds `auth-eu` in eu-central-1 and eu-west-1 with an eu-west-3 witness, and the registry trio. 200 writers on three continents run signup, PAT, rename, and org-removal sagas whose batched appends bump the 64 partition head rows and whose org-scoped transactions bump 64 org rows. The follower-quota flip test runs at the same time: 65 followers each in us-east-2 and ap-northeast-1, about 130 in all, poll every 100 ms (about 1,300 queries per second), assert that `seq` has no gaps and `at` never decreases, and post to S3 boards. AWS FIS isolates each registry Region in turn (HowItWorks page, "Fault injection testing" [unverified section name]). A checker replays every acknowledged change and flags any that a follower whose board row claimed to cover it had not applied. The vendor asks AWS in parallel whether a DSQL read exposes a usable snapshot time [unverified], and if not, the gate adds the leased ticker that writes at most one entry per idle partition per second. The run reports commits per second per head, the 40001 rate, connection errors, claim p99 per continent, signup and `revoke` latency, and apply lag. **Pass:** no `seq` gap, no decrease, no missing acknowledged change, zero connection errors within the 10,000-connection and 100-new-per-second quotas, cross-ocean p99 apply lag at or under 1.5 s and in-continent p99 under 1 s, signup acknowledgment p99 under 2 s, `revoke` coverage p99 under 2 s with followers on three continents, and claims and lease renewals continuing through every isolation. **Flip:** if the 130 remote followers exceed the authority's connection or rate quotas, if the log shows a gap or an out-of-order commit, if cross-ocean p99 apply lag exceeds 1.5 s, or if DSQL exposes no usable snapshot time and the ticker cannot replace it, `arena/round3/candidate-2/DESIGN.md` becomes the global tier's base, because its freshness needs no commit-ordered log, and the cell model below it stays.

## Synthesis decision

The arena ran three runners with different storage bets: a Spokes-style quorum on local NVMe (`arena/candidate-1`), an S3 write-ahead log (`arena/candidate-2`), and refs as DSQL rows (`arena/candidate-3`). This document is candidate 3 with grafts. The lead scored the candidates 19, 26, and 28 of 30 and the cross-judge scored them 19, 25, and 26 (`review/arena-judge.md`). Both picked candidate 3, because one transaction boundary and four types (`Acked`, `DurablePack`, `Change<T>`, `Decision::Hidden`) carry its invariants, so a maintainer adds rows inside `run_tx` and cannot skip the outbox or acknowledge early. All three runners independently chose DSQL for metadata, one GHES hostname per install, `use_v2_flow`, a Rust port of the C# workflow parser, Firecracker runners in separate accounts, stateless `ghs_` tokens, and no GPUI app at launch. `arena/SYNTHESIS.md` lists each graft, its source, and each rejection.

Round 2 added the global namespace after the operator's decision in `FRAME.md`. Three runners designed the layer above the cell: network-placed cells under a replicated global tier (`arena/round2/candidate-1`), owner-home cells with a DynamoDB claim registry (`arena/round2/candidate-2`), and a `graph` cluster over network stripes (`arena/round2/candidate-3`). The lead scored them 26, 21, and 24 of 30 and the cross-judge 25, 20, and 19 (`review/round2-judge.md`). Both picked candidate 1, the only one in which no request reads a remote store when the global tier or another cell is down. `arena/round2/SYNTHESIS.md` lists its grafts, its drops, the rejected shapes, and the flip condition that Milestone 0 tests.

Round 3 made the global tier worldwide after the operator allowed DynamoDB global tables (`FRAME.md`, "Operator decision, 2026-10-24, later"). Two runners designed it: geo-homed DSQL authorities under a worldwide MRSC claim registry (`arena/round3/candidate-1`) and the whole global tier in DynamoDB global tables (`arena/round3/candidate-2`). The lead scored them 25 and 21 against a North American baseline near 22, and the cross-judge scored them 22 and 21 against a baseline of 21 (`review/round3-judge.md`). Both picked candidate 1, the only shape that makes identity writes worldwide and keeps the commit-ordered DSQL logs that `Lookup::Behind`, `revoke` coverage, and the 30 s fail-closed rule rest on. `arena/round3/SYNTHESIS.md` lists its grafts, its drops, and the flip condition that Milestone 0's authority gate tests.

## Tradeoffs accepted

- We accept Aurora DSQL's 3,000-row, 10 MiB, and 5-minute transaction limits, which cap atomic pushes at 1,000 refs and turn bulk operations into sagas, in exchange for synchronous cross-Region commits with no failover call and one database that holds every fact git, merges, and auth depend on.
- We accept a DSQL snapshot read on every git request in exchange for having no cache-coherence protocol, no gossip, and no replica quorum. A cache is either proven fresh by that read or refreshed by it.
- We accept bounded stale git fetches while `core` is unreachable: up to a signed per-cell limit (default 2 hours) behind the last proven refresh, with revocations frozen for the outage and, during a partial partition, fetches that can miss pushes committed through other nodes. In exchange git reads survive a `core` outage. It is a fallback mode, which AWS avoids (`research/uptime.md#5`), so the weekly drill keeps it exercised. Pushes, merges, and every other surface serve no stale reads, which caps Regional cells at DSQL's 99.99% SLA and is why Paired is the managed and BYOC default.
- We accept a second DSQL cluster per cell (a second multi-Region setup in Paired cells), a second migration stream, two clusters for self-hosters, and check conclusions that reach the merge decision seconds after a job ends, in exchange for Actions load and `aux` changes that cannot stop git, merges, or auth.
- We accept slower change to the frozen git-path tables, where new fields go into new tables, and fewer connections for any single role, in exchange for keeping our own migrations, query plans, and connection storms off the git path.
- We accept that a DSQL engine regression that AWS rolls out under every cell at once stops git writes, merges, and the API in every cell, and that no bulkhead covers it. Only the stale-fetch mode keeps git reads, for its time limit. `arena/candidate-2` would keep git writes through it, which is why Milestone 0 switches the base if AWS cannot stage engine upgrades cluster by cluster.
- We accept storing small packs as DSQL rows for minutes, which costs more per byte than S3 [unverified pricing ratio], in exchange for small pushes that are cross-Region durable at RPO zero with one commit and keep working when S3 is impaired.
- We accept about 2.2 times the compute, two to three copies of pack bytes, inter-Region transfer for every pushed byte, and one cross-Region round trip on every write commit (10 to 70 ms depending on the Region trio [guess]) for Paired cells, in exchange for RPO zero on pushes and metadata and Region-loss recovery with no human action.
- We accept a cold-cache penalty the first time a node serves a network in exchange for nodes with no canonical state, which removes the stateful-fleet problem from every deploy and every mode.
- We accept that identity writes for the roots homed in one geography (signup, sign-in, token creation, org and repository creation, forks, renames, membership and grant changes) stop while that geography's authority is unreachable or broken, and that in managed identity writes everywhere stop if the registry loses two of its three Regions, because writer leases renew through it. In exchange fetches, pushes, merges, issues, Actions, stars, and immediate "no" answers keep serving in every cell with no read of the registry or an authority, and a cut-off continent fences itself with no human step.
- We accept that a removal of access can be honored for up to the apply lag (p99 under 1 s within a continent and 1.5 s across), up to 5 s for callers of `revoke`, and, in a cell or edge cut off while the fleet advances, up to 30 s for writes and up to the signed stale limit for reads, in exchange for authorization read from the same snapshot as the refs. The price of the 30 s bound is that a cut-off cell fails its writes closed.
- We accept that an unknown name or token waits up to 2 s, and gets 503 instead of 404 or 401, at a replica named lagging or holding no live lease, in exchange for never answering "no" about a fact whose write was acknowledged.
- We accept that every create waits for coverage as `revoke` does, about 1 to 1.5 s and longer when a member must be named lagging, that a writer cut off from the fleet answers 503 for a write it has committed, and that two observers can disagree for up to 5 s between a commit and its acknowledgment. In managed each revocation also waits on one cross-continent registry write. In exchange "no" is never wrong after acknowledgment and stays immediate during an authority outage.
- We accept a full copy of the authorization graph in every data cell, with N-fold storage and apply writes [guess: tens of GB per cell at launch scale], in exchange for permission checks and viewer listings that read one cell. Repository cards go only to the index cells that list the repository, so card storage does not grow with the whole service.
- We accept that every login claim, SSH key change, email verification, app creation, and slot flip waits on one cross-continent round trip (95 to 225 ms [guess]), even next to a replica, and that an unknown login depends on three logs, two across oceans, so a cross-continent stall longer than 30 s turns some 404s into a 2 s wait or a 503. A fenced geography waits about 5 minutes 10 s for `Quiet` before `reconstitute` may start, because survivors wait out DSQL's transaction limit. In exchange no single continent's loss stops claims.
- We accept that a lost continent's identity facts have RPO equal to the cross-continent apply lag and that its identity writes recover in hours through `reconstitute`, except revocations, which the registry holds, so none that was acknowledged comes back. A healed authority's unreplicated commits are stated loss. `Open` homes escrow secrets and credential hashes to another continent, which is a residency cost, and `Resident` homes have no escrow and lose identity with their continent. Today's alternative, one North American `global`, would have no recovery path at all.
- We accept that every org-scoped authority transaction bumps the org row's version, which serializes one org's membership, team, and grant changes [guess: a few dozen per second per org], in exchange for an admin's removal and a concurrent grant that can never both commit.
- We accept DynamoDB as a third AWS store in managed only, three logs per follower, cross-ocean S3 board reads every second at roughly $27,000 a month [guess], a home fixed at creation, and 422 on transfers between owners homed apart until Milestone 7, in exchange for worldwide identity writes. Every install, Paired included, keeps the registry in `core` and gains no new store.
- We accept that a fork network is never split, so the largest network must fit one cell, and that a slot move carries every network in the slot, in exchange for one-transaction merges for every pull request and ids that route by arithmetic.
- We accept that a compromised data cell can mint installation tokens for the accounts whose index cell it is and job tokens for the repositories in its slots, until its `kid` is revoked, and that a compromised front cell can assert any principal, in exchange for token minting and verification with no shared service on the path. A compromised data cell cannot replay a principal to another cell, because each assertion names its target cell and lives 10 s.
- We accept that an account's index cell is a service-wide dependency for that account's new installation tokens, stars, notifications, feeds, org-runner registration, and cross-cell listings, in exchange for minting that a compromised cell can do only for its own accounts and listings that read one cell.
- We accept synchronous cross-cell calls for GraphQL queries that span cells and for org-runner job claims, with partial results on failure.
- We accept that a destination cell that stays down grows parked inter-cell partitions in every source cell's `aux`, in exchange for notifications that are never dropped.
- We accept that single-cell installs run an applier that copies tables within one cluster, in exchange for one code path in every mode.
- We accept that Tributary runs only in Regions with Aurora DSQL and is tied to an AWS-only engine, in exchange for a self-hosted install with no database server to operate.
- We accept up to 60 s of write freeze per slot move (the 30 s transaction horizon plus the delta drain), in exchange for a move that needs no dual-write mode and a fence that no stale front, worker, or runner can cross.
- We accept that `refs/pull/N/head` and `refs/pull/N/merge` lag a push by seconds, as derived refs, in exchange for a push transaction with no per-PR fan-out and no cap on PRs per branch.
- We accept that Regional cells do not meet fact 9, because Regional recovery launches node capacity in the recovery Region and promotion may roll refs back within the stated RPO, in exchange for a single-Region cost for self-hosted installs. Identity facts other than revocations share the `dr` RPO, and a Regional install without `dr` accepts the backup interval as its RPO. Paired cells meet fact 9 and are the managed and BYOC default.
- We accept an operator role in every install, with leases and cursors in both `core` and the control buckets, intents under two keys, a watchdog, a deployer role for `apply:infra`, and status documents to build and test, in exchange for rollouts, renewals, backups, and recovery that survive the one-hour session cap, a revoked deploy role, a week-long vendor outage, an air gap, and an impaired `core`.
- We accept a customer-only key for restores, promotions, failbacks, uninstall, config that changes endpoints, buckets, or the identity provider, and halts during a revocation, so in BYOC those wait for a customer with KMS access even when the vendor's SRE is ready, in exchange for a deploy role that cannot reach data or delete state through the operator.
- We accept that operator processes run the previous release until after the soak, so new operator code soaks less than the serving roles, in exchange for an operator that never upgrades itself mid-rollout.
- We accept that a restore calls DSQL's control plane, takes two customer-signed intents, and leaves every node's caches cold, and that install DDL on authority-schema and git-path tables waits for a rehearsal on a restored backup copy, in exchange for never serving rewound state and a shadow canary in every install.
- We accept that an install with `dr` must provide peering or a transit gateway between its Regions, that an air-gapped promotion moves traffic by a private DNS change, and that uninstall ends in a customer-run `tributary uninstall --finalize`, in exchange for recovery with no public endpoint and a teardown that never runs inside the install it destroys.
- We accept that a single-node evaluation install takes a short outage for each node image change, carries no availability SLO, and skips drills that take a node out of rotation, and that air-gapped installs get new actions only from signed packs, in exchange for a one-instance trial and Actions with no outbound route.
- We accept that third-party secret scanners will classify a leaked Tributary token as a GitHub token, may try to validate it against `api.github.com` and so send it to GitHub, and will name the wrong issuer [inference], in exchange for GitHub's token prefixes (`ghp_`, `github_pat_`, `gho_`, `ghu_`, `ghs_`, `ghr_`), which Renovate branches on (`research/clients.md` implication 6). Tributary runs its own push-time secret scanning for these prefixes and documents the collision for customers' security teams.

## Alternatives considered

- **S3 write-ahead log with a CAS manifest per repository (the Continuity and walgit shape).** Refs live in an S3 manifest updated by `If-Match`, and metadata lives in a separate database (`research/git-storage.md#29`-`#31`). It lost because refs and pull requests then live in two stores with no shared transaction, so a merge needs an ordered two-step write with a repair path, and the outbox needs a third coordination point. Its cross-Region story is also weaker: S3 offers no synchronous cross-Region CAS, so push RPO zero needs a second mechanism on top of the log. Its interface is deeper for git alone and shallower for the whole product, because every consumer of ref state must also learn the manifest protocol.
- **Spokes-style replica quorum on local NVMe** (`research/git-storage.md#2`-`#6`, `#23`). Three replicas across three AZs vote on each ref transaction through the reference-transaction hook, with a placement database and repair sweepers. It lost on operability and on BYOC: every node holds canonical state, so every deploy needs fencing, replica catch-up, and quorum checks that the vendor's machinery lacks (`research/byoc-grounding.md` item 7), and self-hosters would repair replicas at 2am. It still needs a separate database for PRs, so ref and PR state can diverge.
- **The same refs-as-rows shape on Aurora PostgreSQL with a Global Database.** It would remove the 3,000-row limit and keep triggers and full PostgreSQL. It lost on facts 1 and 9: unplanned cross-Region failover loses seconds of commits, the failover is an RDS control-plane call, and Aurora does not guarantee to fence the old primary (`research/uptime.md#24`, `#25`). It is a database variant of this design, not a different shape, and it is the fallback if milestone 1 shows DSQL cannot carry hot repositories.
- **Refs in DynamoDB MRSC with metadata elsewhere.** RPO zero across three Regions (`research/uptime.md#29`), but no transactions, so a merge cannot commit the ref, the PR, and the event together.
- **Isolated managed tenants, one GHES hostname each.** This document's earlier managed reading put every user namespace inside a tenant and every tenant inside one cell, with no global user graph, no cross-tenant fork, and no global router, and it rejected a github.com-style shared namespace. That shared namespace is now the requirement (`FRAME.md`, "Operator decision, 2026-10-24"), so the isolated-tenant shape lost. BYOC and self-hosted keep it, one namespace per install.
- **Owner-home cells with forks in the fork owner's cell.** Each owner's repositories and identity live in the owner's cell under a thin global directory. `bob/widgets` and `acme/widgets` then sit in different clusters, so the merge of bob's pull request reads a head ref in one cluster and moves a base ref in another, which needs a saga and loses the one-transaction merge for the most common public pull request.
- **Owner-home cells with passports minted by the caller's home (round 2, candidate 2).** It keeps forks with their network, but a user whose home is down and who holds no cached passport cannot authenticate anywhere, and its authorizing org mirror (`OrgAuthority`) has unbounded lag while its cell is cut off (`arena/round2/SYNTHESIS.md`).
- **A `graph` cluster read on cold authentication, token minting, listings, and stars (round 2, candidate 3).** It puts one remote store back on the request path, and push and merge authorization moves to a cache up to 15 minutes stale. Its one-hour quarantine before a released login can be reclaimed is a client-visible deviation that `Lookup::Behind` and `NameEpoch` make unnecessary.
- **One global DSQL cluster for everything, no cells.** One cluster is one blast radius for bad query plans, migrations, and engine regressions, the database incidents that dominate GitHub's core outage minutes (`research/uptime.md#43`, `#44`), and DSQL's 10,000 connections per cluster (`#27`) would cap the whole service.
- **A synchronous global identity service behind caches.** This is GitHub's shape. The store's load scales with requests and with every cache setting, which is the February 2026 failure (`research/uptime.md#47`) and the May 2023 App token outage (`#44`).
- **Everything in DynamoDB global tables (round 3, candidate 2).** MRSC has no transactions, so every change needs a fence item and later materialization, and no stream yields a cross-item watermark, so "no" holds only against acknowledged writes, for up to 6 s. Every identity write, North American ones included, waits on another continent for each MRSC step plus a 0.5 to 1.5 s coverage wait, an org fence caps changes at a few per second per org, the edge reads S3 on every projection miss, and relays, buckets, compactors, and two lease kinds run in every mode (`review/round3-judge.md`). It survives a continent loss better, and it is the flip target if Milestone 0's authority gate fails.
- **Keep one North American `global`** (the round-2 shape). European and Asian identity writes cross an ocean, a North American Region-set event stops identity writes worldwide, and no identity fact is stored in its owner's geography.
- **Owner homes with no registry**, where a geography's authority claims logins by asking the other two. That is two-phase commit across three DSQL clusters, and it lost to one MRSC conditional write. **The registry stream as the projection source for names** lost too, because it is ordered per item only, so a front could never prove a login absent.
- **An MREC freshness board in every serving Region** (round-3 candidate 1). One writer per row makes last-writer-wins harmless, but the S3 boards do the job with no DynamoDB store in any install, at a similar managed cost [guess: tens of thousands of dollars a month for either] (`arena/round3/SYNTHESIS.md`).
- **The vendor's deploy tool driving every stage from outside the account.** It is the existing machinery's shape, but a Paired rollout outlives the one-hour chained session, a revoked role or a vendor outage strands the rollout mid-AZ, an air-gapped install has no path in, and an observer limited to API Gateway cannot read a process behind an NLB (`review/byoc-walk.md` findings 1, 2, 10, and 12). API Gateway with IAM auth and a VPC link per Region would fix only the last.
- **A registry of two replicas and a witness, or token hashes only in home-geography fronts.** The first leaves one continent with no local endpoint. The second makes a traveler's every request depend on a remote front, so hashes of 177-bit secrets replicate instead.
- **Human sealing of a lost geography instead of writer leases.** A human cannot tell a cut from a loss, and an unfenced minority side could keep committing.

## Open questions and risks

- Can DSQL carry the hottest repositories? Merge queues and bot fleets on one `main`, plus the 40 shard rows, are where optimistic concurrency could thrash. Milestone 0 measures this before any git code exists. If it fails, should hot repositories get a per-repository write serializer in the `git` role, or should the base switch to `arena/candidate-2` (the S3 write-ahead log) or to Aurora PostgreSQL and give up RPO zero?
- What is DSQL multi-Region commit latency for the Region trios customers need, and what are MRSC write and strongly consistent read latencies on us-east-2, eu-central-1, and ap-northeast-1? AWS publishes neither (`research/uptime.md` open question 3, `review/round3-judge.md`), so Milestones 0 and 1 measure them.
- Is Aurora DSQL available in every Region where BYOC and self-hosted customers need it? A missing Region blocks an install outright, because this design has no second database engine.
- How does AWS roll out DSQL engine upgrades: cluster by cluster in waves that customers can see and stage, or under every cluster at once? [unverified] A fleet-wide rollout is the one failure no bulkhead covers, and an answer of "not staged" switches the base to `arena/candidate-2` (Milestone 0).
- Is the per-byte cost of inline packs and of CDC export acceptable at managed scale, and is 1 MiB the right inline threshold?
- Is the signed pin map an acceptable answer for security teams that pin SHAs, or will they see any substitution as rewriting?
- Does DSQL CDC deliver to the `dr-apply` role in the recovery Region, one whole source transaction at a time, with a lag that supports the stated 5-minute Regional RPO? [unverified]
- Is Regional, which does not meet fact 9, an acceptable self-hosted default, or should self-hosted default to Paired where the customer has three Regions?
- Does returning `GitHub lives!` and GitHub documentation URLs, which VS Code Pull Requests and other clients check, raise trademark issues for the vendor?
- Where this direction is weakest: Actions leases, step updates, and cache metadata are high-churn, low-value state, and a key-value store would be cheaper than DSQL for them. The `aux` cluster keeps that churn off `core`, but it is still DSQL, writing leases only near expiry, so the comparison stays honest. Would a key-value store for Actions churn be worth a third stateful system?
- Does any GHES-targeted client assume 40-character installation tokens?
- How long does a Paired N to N+4 skip take through the operator role, and is a 15-minute watchdog deadline long enough for a 10-minute clone drain and a gate on a slow AZ? [guess]
- Does AWS Backup cover Aurora DSQL clusters with point-in-time restore and cross-Region copy, does a restore always create a new cluster with a new endpoint, as the two-intent `Restore` assumes, and how long does a restore of a large `core` take? [verify in Milestone 0]
- Can a Paired DSQL cluster gain a new Region after one is lost for good? The OpenTofu state now replicates to the peer Region, but re-pairing has no procedure [unverified].
- Does every service in the derived air-gapped endpoint list, AWS Backup and Route 53's private-zone API included, offer a VPC interface endpoint in every install Region, are ARC routing-control endpoints reachable only publicly, and does EC2's store-image task work in every install Region? [unverified]
- Will BYOC customers keep the customer-only key usable by someone on call at 2am, or hand it to the vendor and undo the separation? [guess]
- Does DSQL detect write-write conflicts on a log partition head row so that a retried append always starts after the winner's commit, and how many appends per second does one head sustain on a multi-Region cluster? The log's gap-free and monotonic-time claims rest on it [unverified]. Milestone 0 measures it.
- How far apart are DSQL snapshot times in three separate clusters and ClockBound's bounds on EC2, and is ClockBound available on every instance type the node image runs on? The clock margin and the leases rest on both [unverified].
- Does DSQL enforce its 5-minute transaction limit from `BEGIN` on the server, so that `Quiet` is a hard fence? [unverified]
- Does a DSQL read expose a snapshot time that a follower can use as its watermark? [unverified] Without one, a leased ticker writes at most one entry per idle partition per second (Milestone 0). Do the freshness boards cost what the estimate says, roughly $27,000 a month at about 1,000 members in about 12 Regions [guess]? How often does a create have to name a lagging member, and how often does a writer that cannot read a member's board answer 503 after committing? [guess]
- Does MRSC support PITR and on-demand backup, and how long does a `RegistryGeneration` copy of about 600 million items [guess] take?
- Is one hour of source-key grace after a slot's Flip enough? A job that started before the Flip and runs past that hour loses its `GITHUB_TOKEN` [inference].
- How large do front projections grow (names, repository entries, and credential hashes, a guessed 100 GB at GitHub scale), and how long does a front node take to boot from S3 at that size?
- Can the largest public fork network fit one cell's DSQL and cache limits, and what happens when it cannot?
- Is the escrow of `Open` European secrets in North America acceptable under GDPR transfer rules? [inference: probably with standard contractual clauses, unverified] Does GitHub restrict managed users to public reads outside their enterprise, as the `Resident` model assumes? [unverified]
- Index cell hot spots: an account that stars or watches millions of repositories, or receives millions of notifications, concentrates on one cell.
- Can DSQL CDC feed each authority's shadow at production write rate within the per-cluster stream quota? [unverified]
