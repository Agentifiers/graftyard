### 1. [critical] SSH key squatting lets one tenant capture another tenant's SSH traffic
**Location**: DESIGN.md:190 (also :515, :610, :783)
**Finding**: SSH ignores the hostname and picks the tenant from the offered key's fingerprint, which must be unique within a cell. Owner and repository names are scoped per tenant. Managed cells share one host key set. Nothing requires proof that the person registering a key holds the private key: `gh ssh-key add` and the web UI upload only the public half (`rest:users` and `rest:deploy-keys` at :572 and :542). (measured from the text)
**Evidence**: Here is the attack (inferred). An attacker self-serves a tenant `evil` on the same managed cell as `acme`. They copy Alice's public key from any public source and register it to their own user in `evil`. In `evil` they create org `acme` and repo `payments`. Alice later runs `git clone git@acme.tributary.cloud:acme/payments.git`. The key resolves to the attacker's principal in `evil`, the path resolves inside `evil`, and the host key matches Alice's `known_hosts` because all managed cells share it (:190). She gets attacker-controlled code, and her pushes of acme code land in the attacker's tenant. Her attempt to add the key in `acme` fails with "Key is already in use" (:610), which reads like a harmless error. github.com gets away with no possession proof because its namespace is global, so the same path always means the same repository. Here it doesn't. The same squatting also gives an attacker a way to block any victim tenant's cell migration, since Flip is refused on key conflicts (:190). There is a harmless version too: a user whose ssh-agent offers another tenant's key first gets routed to the wrong tenant.
**Suggestion**: Require proof of possession before a key becomes active. For example, keep it pending until the user runs `ssh -T git@HOST verify <code>`. That step proves possession and also tells the server which tenant the key belongs to. Alternatively, give each tenant its own SSH listener address in managed mode.

### 2. [critical] A merge can land a stale head: write skew against pushes to the head branch, and the journey reads the lagging derived ref
**Location**: DESIGN.md:98, :100, :125, :380-385, :388
**Finding**: Journey 2 reads `refs/pull/17/head` (:98). The design says that ref is derived and lags by seconds (:361-362, :782). The type section says the head should come from the head branch's own row. Even with the right row, the merge transaction only reads the head ref and never writes it. The protection against write skew covers only PR-scoped inputs through `review_version` (:125), and pushes deliberately make no per-PR writes (:254, :388). (measured)
**Evidence**: The merge takes its snapshot with head = H1, checks pass, and the plan builds on H1. A push then moves the head branch to H2 and commits. The merge transaction still commits, because it wrote no row the push touched (DSQL OCC catches write-write conflicts, `research/uptime.md#27`). The PR ends up `Merged{final_head: H1}`, H2 is silently left off main, and the PR UI says merged. GitHub rejects this case with "Head branch was modified". That contradicts ":388 Not any state that decides something". The `expected_head` parameter (:380) is checked only against the stale snapshot. `SYNTHESIS.md:45` claims the derived-ref change kept the merge invariant intact, but Journey 2 was never updated.
**Suggestion**: Inside the merge transaction, do a conditional write on the head ref row: either a no-op `UPDATE ... WHERE target = H1` that rejects on rowcount 0, or `SELECT ... FOR UPDATE`. Read the head branch row, not `refs/pull/N/head`.

### 3. [critical] Outbox dispatch blocks behind any failing consumer, so a search outage stops webhooks, Actions triggers, PR sync, and revocations
**Location**: DESIGN.md:464-468 (contradicts :477, :669)
**Finding**: `dispatch` runs one query: `SELECT pending rows ... ORDER BY id LIMIT 500` with no cursor. Rows are deleted only when every bit is set. (measured)
**Evidence**: When OpenSearch is down, the `SearchIndex` bit never sets, so the oldest 500 rows in every partition stay pending forever. Every loop re-reads the same 500 rows, the other consumers skip them as already done, and nothing newer is ever reached. Webhooks, `ActionsTrigger`, `RunOwner`, `CacheHint`, and the jti deny list (:297) all stall. That covers credential revocation (:336) and stateless `ghs_` revocation, so revoked installation tokens stay valid until `exp`. :477 claims "other consumers move on", and :669 claims search touches nothing else, but the pseudo-code makes it the other way. Also, `pr-sync`, which the merge and PR invariants depend on (:90, :124, :388), is missing from the `Consumer` enum (:453).
**Suggestion**: Give each consumer its own pending index or cursor (for example `(partition, consumer_pending, id)`), and add `PrSync` as a named consumer.

### 4. [critical] Tenant migration is fenced only by eventually consistent edge maps, so writes accepted by the old cell after Flip are deleted at Forget
**Location**: DESIGN.md:176-182, :166-169, :666
**Finding**: Freeze and Flip are map generations written to a separate S3 object in each cell. Nodes keep the last known good map when a fetch or validation fails. Nothing in either DSQL cluster refuses writes for a frozen or moved tenant, and nothing confirms that every node has adopted the new generation before Flip. (measured)
**Evidence**: Map writes are rejected when more than 1% of routes change (:666). Any cell with fewer than 100 tenants therefore can't apply even one Freeze or Flip, and neither can a dedicated cell (one tenant) or a new empty cell (inferred arithmetic). A node that keeps the old map, or can't reach the control bucket, keeps routing the tenant as `Serving` to the old cell's DSQL. Until the DNS TTL passes, most traffic still arrives there (:179). Pushes acknowledged there after the delta drained are never copied. Forget then deletes them after 7 days (:180), and acknowledged pushes are lost. SSH resolves the tenant through the old cell's key index, which still holds the rows, so SSH routes there too.
**Suggestion**: Store the freeze in the old cell's database, as a tenant-state row checked by every write path. Have nodes acknowledge the map generation in DSQL before Flip. Base the change-rate guard on absolute counts per operation, not a percentage.

### 5. [critical] Regional-class recovery yields refs pointing at packs that never replicated, and it depends on launching capacity
**Location**: DESIGN.md:277, :642 (vs :29, :708)
**Finding**: Metadata reaches the DR cluster through CDC with about 5 minutes of lag. Bucket packs reach the DR bucket through S3 RTC with up to 15 minutes of lag. Recovery has no step that reconciles the two. (measured)
**Evidence**: CDC usually runs ahead of S3 RTC (inferred), so the promoted DR cluster holds `ref` and `pack` rows whose bytes aren't in the DR bucket. Clones of those repos then fail with missing objects. Later pushes are thin against the missing commits, fail the connectivity check, and the repo stays broken until someone repairs it by hand. That is worse than the stated RPO. Whether CDC applies whole source transactions is not stated. If it doesn't, a recovered cell can hold a ref moved by a merge whose PR isn't marked merged, breaking the core invariant. Separately, RTO "still has to launch" node capacity (:642), which violates TASK fact 9 ("Recovery must never depend on launching new capacity", `arena/TASK.md:25`). :29 claims fact 9 is answered. Regional is the self-hosted default (:708).
**Suggestion**: Make promotion roll each repo's refs back through `ref_log` to the newest state whose packs all resolve in the DR bucket, and state that as the RPO. Specify CDC apply per source transaction. Either pre-provision recovery capacity or say plainly that Regional does not meet fact 9.

### 6. [critical] The reachability invariant is enforced per pack id, but objects can vanish
**Location**: DESIGN.md:274, :87, :284, :548
**Finding**: ":274 Every ref target is reachable from the network's live pack set, because the pack row commits with the ref." That isn't true for ref updates whose objects were written earlier: the Git Data API writes blobs, trees, and commits as a small pack, then moves the ref later through `commit_push` (:548). It also isn't true for pushes that are thin against objects advertised before a concurrent ref deletion. Connectivity is checked "against the cache" (:87). The cache still holds superseded packs, and `commit_push` never checks that dependencies sit in live packs. (measured)
**Evidence**: Renovate's `platformCommit` flow (inferred): `POST /git/commits` creates commit C, the weekly full repack (:284) runs from a snapshot where C is unreachable and leaves it out, and C's pack is superseded. Then `PATCH /git/refs` passes the connectivity check on the cache and commits. Seven days later GC deletes the superseded pack (:274). The acknowledged ref now points at a missing object. The design names a `Cruft` kind (:218) but never says compaction keeps unreachable objects, or for how long. The GC second check compares pack ids, not object reachability.
**Suggestion**: Make compaction keep unreachable objects in cruft packs for a grace period well beyond the longest push or API-to-ref window. Or check in `commit_push` that every new tip's dependencies resolve in packs that are `Live` in the same snapshot.

### 7. [warning] "Skip up to four releases with zero downtime" conflicts with the N±1 schema window
**Location**: DESIGN.md:693, :695, :711
**Finding**: "Release N runs against schema N-1 and N+1" (:693), yet BYOC and self-hosted "may skip up to four releases" with hot-swap, zero-downtime upgrades (:695). (measured)
**Evidence**: Going from N to N+5 means applying the contract phases of N+1 through N+4 while binary N is still serving and draining. Binary N then hits dropped columns and returns 5xx. The other option is running every intermediate release, which is not a skip. The milestone 6 gate (:763) only tests one release step.
**Suggestion**: Either define skip upgrades as a sequential roll through intermediate schema steps, or limit contract phases so that N+k still works with N's schema.

### 8. [warning] Large pushes cannot win OCC on busy repositories
**Location**: DESIGN.md:122-124, :249-256
**Finding**: A 1,000-ref push touches about all 32 user shard rows, issues one `UPDATE` per ref (:250), runs under a 2 s request deadline (:123), and gets 3 retries. (measured)
**Evidence**: Any concurrent push that bumps a shared shard during the transaction makes it abort with 40001 (inferred). At the design's own target of 50+ pushes per second per repo (:751), a mirror push or a 1,000-tag release almost certainly collides on each of its 3 attempts and fails. Also, 1,000 sequential statement round trips can exceed 2 s by themselves (inferred). The deviation table promises that 1,000 refs succeeds (:608).
**Suggestion**: Use one set-based `UPDATE ... FROM (VALUES ...) RETURNING`. Serialize large batches per repo through a lease, as merge queue does (:390). Set the deadline by batch size.

### 9. [warning] The `commit_push`/`refresh` row protocol can't create refs and can't produce deltas cheaply
**Location**: DESIGN.md:250-251, :237, :261, :268, :281
**Finding**: The steps update refs only with `UPDATE ... WHERE target IS NOT DISTINCT FROM expect`. A new ref has no row, so rowcount is 0 and every branch creation is rejected as `Stale`. Deletes keep NULL rows, which pile up as tombstones. `ref.version` is a counter per ref, and the only index is `(tenant, repo, shard)` (:268), so "changed since `have`" (:237, :261) means scanning and diffing whole shards. (measured)
**Evidence**: On a busy repo the shards change between almost every pair of fetches. Each fetch then scans every changed shard in full. That can be tens of thousands of rows each for `refs/pull/*` on a large monorepo with 8 pull shards (inferred). This lands on the path the design calls hottest (:281).
**Suggestion**: Add an insert path for `expect = None`. Stamp each ref row with the shard version that wrote it, index `(tenant, repo, shard, shard_version)`, and give tombstones a cleanup step.

### 10. [warning] Webhook payloads are rendered when consumed, not at event time
**Location**: DESIGN.md:450-451, :471-472, :477
**Finding**: Outbox events carry references (`PrPayloadRef`, `IssueRef`, `JobId`), and the webhook consumer renders the payload into S3 when it runs. (measured)
**Evidence**: After a consumer backlog (finding 3) or a 3-day retry window, `pull_request.synchronize` payloads show a later `head.sha`, labels, or state than the event that triggered them. CI systems such as Jenkins (an oracle at :574) build `pull_request.head.sha` from the payload, so they build the wrong SHA or skip some. `issues.edited` `changes.from` can't be rebuilt at all. GitHub payloads are snapshots taken at event time (inferred).
**Suggestion**: Render or capture the payload-relevant fields inside the producing transaction. The 10 MiB transaction limit leaves room.

### 11. [nit] 1,000-byte ref names exceed DSQL's 1 KiB key limit in `ref_log`
**Location**: DESIGN.md:129, :205, :268
**Finding**: The `ref_log(tenant, repo, name, push_id)` key is 4 + 8 + 1,000 + 8 (or 16 for a ULID) = 1,020 to 1,028 raw bytes, before any encoding overhead (measured arithmetic; overhead inferred). The `research/uptime.md#27` limit is 1 KiB.
**Evidence**: A push with a ref name near the limit fails inside the transaction with a database error instead of a clean `ng`. With `--atomic`, the whole push fails.
**Suggestion**: Cap ref names at about 900 bytes, or key `ref_log` by a hash of the name.

### 12. [nit] The reconnect limiter exceeds DSQL's cluster-wide rate for new connections
**Location**: DESIGN.md:641 (vs :128)
**Finding**: Line :641 sets reconnects at "60 per second per node class". Managed cells have 4 classes (:483), which gives 240/s. DSQL allows 100 new connections per second per cluster (`research/uptime.md#27`). (measured arithmetic) Line :128 says the limiter is client-side, so nothing coordinates across nodes.
**Evidence**: After an AZ loss, the reconnect storm runs over the cluster quota, and the extra connects fail and retry exactly when capacity is shortest. The hot swap at deploy time, which starts new processes with fresh connection pools across a whole AZ (:689), adds bursts of the same kind.
**Suggestion**: Split the 100/s budget across the cell and node count. Have the new process take over pooled connections at hot swap, or open them gradually.
