# Interrogate verdict on DESIGN.md

## Intent

> `DESIGN.md` is the synthesized design for Tributary, an AWS-native code host that unmodified GitHub clients treat as GitHub Enterprise Server 3.22. It ships as one artifact in managed, BYOC, and self-hosted modes. Availability of git reads and writes, pull request merge, and the REST and GraphQL APIs ranks first, and zero lost acknowledged pushes ranks second. Its core bet is that one Aurora DSQL database per cell holds every canonical fact, with larger packs in S3 and node disks used only as caches.

## Reviewers

- Reviewer A: `pstack-panel-a`, 12 findings (6 critical, 4 warning, 2 nit).
- Reviewer B: `pstack-panel-b`, 12 findings (4 critical, 8 warning). B ran one git experiment and measured that two branch creations at an existing commit send byte-identical empty packs.
- Reviewer C: `pstack-panel-c`, 12 findings (6 critical, 6 warning).

All three seats ran the same model, because no panel models are configured. Agreement across seats is therefore agreement across independent runs, not across model families.

## Act on

Each item below is resolved in `DESIGN.md` under "Review resolutions". The resolution text here is the contract the revision follows.

**ACT-1. Merges can commit a stale head or bypass a withdrawn approval.** Raised by A, B, and C. Journey 2 reads the derived `refs/pull/N/head`, which lags by seconds. The merge transaction never writes the head ref, so a push that commits during the merge does not conflict. `check_protection` runs on a snapshot taken before `run_tx`, a review that commits between that snapshot and `BEGIN` never conflicts, and a 40001 retry re-runs the closure without re-checking protection. Resolution: the merge reads the head branch's own ref row. Inside the `run_tx` closure, on the transaction's own snapshot, it re-runs `check_protection`, compare-and-sets the head ref row against the plan's head (a version bump with `WHERE target = plan.head`), compare-and-sets the PR row with `WHERE state = 'open' AND review_version = :seen`, and compare-and-sets the base ref. Any changed input returns a non-retryable error with GitHub's text ("Head branch was modified. Review and try the merge again." or the protection failure), never a silent retry into success.

**ACT-2. One failing outbox consumer blocks every other consumer.** Raised by A, B, and C. Dispatch re-reads the oldest 500 rows of a partition, and a row leaves only when every consumer bit is set, so a search outage stops webhooks, Actions triggers, run status, `pr-sync`, and revocation hints. `PrSync` is also missing from the `Consumer` enum. Resolution: drop the shared `done` bitset. The producing transaction inserts one `outbox_pending(tenant, partition, consumer, event_id)` row per consumer subscribed to that event kind, from one static subscription table. Each consumer leases partitions and reads only its own pending rows, deletes its row on success, and parks a row after N failures in a per-consumer dead-letter state visible to the observer. Only deployed consumers subscribe, so a self-hosted install without OpenSearch has no search rows. Event rows are retained for redelivery and removed by retention, not by consumer progress. `PrSync` is a named consumer.

**ACT-3. Tenant migration is fenced only by eventually consistent edge maps.** Raised by A, B, and C. An edge that keeps a stale map, an expired `Frozen { until }`, in-flight receive-packs, workers, and connected runners can all write to the old cell after the drain, and Forget deletes those writes. The 1% route-change guard also blocks every placement and freeze in cells with fewer than 100 tenants, including dedicated cells. Resolution: a `tenant_state` row in the source cell's DSQL is the write fence. Every `run_tx` for a tenant, including worker, broker, and background transactions, reads it and refuses when it is not `Serving`. Every tenant transaction has a hard 30 s deadline enforced by `run_tx`. Freeze commits `Frozen { generation }`, then the drain waits out that horizon before it reads the change stream to its end. `Frozen` never expires. Unfreezing is an explicit signed operation. The map guard becomes an absolute cap on route changes per generation, plus a signed override for planned placement and migration.

**ACT-4. Pack identity and compaction can lose acknowledged objects.** Raised by A, B (measured), and C. `PackId` is the content checksum, so the second branch created at an existing commit inserts a duplicate empty pack and fails. Treating the duplicate as success makes a new ref depend on a superseded row that GC later deletes. Compaction gives no retention rule for unreachable objects, so a Git Data API commit that becomes reachable after a full repack can point at a deleted object. Packs uploaded before a failed commit become orphans that nothing deletes. Resolution: `PackId` is a fresh placement id, and the content checksum is an attribute. A zero-object pack writes no row and no object. Compaction follows git's cruft-pack model: it never drops an object, it writes unreachable objects into cruft packs with per-object times, and a later compaction rescues any that became reachable. Only GC deletes, only objects unreachable in its own snapshot and older than 14 days. A sweeper deletes S3 objects that no row references after 24 hours.

**ACT-5. Regional disaster recovery can produce refs whose packs never replicated.** Raised by A, B, and C. CDC metadata (5-minute target) runs ahead of S3 replication (15-minute bound), CDC atomicity per source transaction is unstated, compaction deletes inline rows before the replacement object reaches the recovery Region, the CDC applier is not a named component, and recovery launches capacity, which TASK fact 9 forbids. Resolution: the CDC applier is a named `dr-apply` worker role with a lag alarm and an observer route, and it applies whole source transactions. In Regional cells, compaction deletes inline rows only after the replacement object is confirmed in the recovery bucket. Promotion runs a mandatory reconcile that walks `ref_log` and moves each ref back to its newest value whose packs exist in the recovery Region, and it records each rollback as stated loss within the RPO. The design states plainly that Regional recovery launches capacity in the recovery Region and so does not meet fact 9. Paired does.

**ACT-6. SSH tenant resolution by key lets one tenant capture another tenant's SSH traffic.** Raised by A and C. The lead introduced this in synthesis. Public keys are public, so an attacker registers a victim's key in their own tenant on the same cell, creates the same `owner/repo` there, and receives the victim's clones and pushes. The shared host key hides it. A contractor with two keys loaded in one agent can push one company's code into the other's repository by accident. Resolution: in managed multi-tenant cells each tenant gets its own SSH endpoint. A per-tenant NLB with listeners on 22 and 443 forwards to the shared edge fleet on a per-tenant target port, so the edge knows the tenant from the port before the SSH handshake and presents that tenant's own host key. Keys are unique per tenant only, as on GHES. Host keys are per tenant and move with the tenant. BYOC, self-hosted, and dedicated cells hold one tenant and need nothing extra. Proof-of-possession activation is rejected, because a key unusable until verified is a client-visible deviation, and the capture path still exists before the victim registers.

**ACT-7. Paired failover depends on inputs that live in one Region, and on health checks that are never specified.** Raised by B and C. The tenant map has one control bucket, signing keys and certificates are decrypted at node start from one Region, and the edge returns well-formed 503s while DSQL is down, so a shallow health check keeps traffic on a broken Region. Resolution: one control bucket per cell Region, both written with `If-Match`, each edge reading its own Region's copy. Nodes persist the last known good map, certificates, and wrapped keys to local disk. Keys use KMS multi-Region keys. Route 53 health checks target a deep regional endpoint that commits a canary DSQL write and reads a canary S3 object through the Region's own endpoints, and they rely on Route 53's fail-open when every target is unhealthy. A drill boots a node in the peer Region with the home Region blocked.

**ACT-8. Webhook delivery differs from GitHub in two client-visible ways.** Raised by B and A. Delivery workers retry for 3 days, but GitHub never redelivers automatically (`research/wire-census.md#37`), so receivers that do not deduplicate run builds and deploys twice. Payloads are rendered when consumed, so a delayed `pull_request.synchronize` shows a later `head.sha`. Resolution: one automatic attempt, as on GitHub, with manual redelivery through the API for the retention window. Automatic retries are an opt-in listed under known deviations. The producing transaction captures every mutable field a payload needs (PR head and base SHAs, state, labels, `changes.from`). Immutable git content, such as a push's commit list, is rendered later from the SHAs.

**ACT-9. Stateless installation tokens outlive revocation and break on tenant migration.** Raised by B and C. Uninstall, suspension, repository removal, and permission downgrade leave outstanding `ghs_` tokens working until expiry, the server never stores the jti it would deny, and per-cell signing keys cannot verify tokens after a tenant moves cells. Resolution: each installation carries a `not_before` epoch in the pushed deny list, and uninstall, suspension, repository removal, and permission changes bump it. `authorize` intersects token claims with installation rows on every request that already reads a DSQL snapshot. `GITHUB_TOKEN` jti values are recorded per job and denied at job end. Signing keys are per tenant, wrapped by the cell key, and move with the tenant. JWKS publishes the current and previous epochs.

**ACT-10. Six mechanical corrections.** Each is a contradiction or an arithmetic error in the text.
- (a) Raised by A. `commit_push` only updates rows, so it cannot create a ref, and `refresh` scans whole shards. Resolution: an insert path for `expect = None` (a unique violation means `Stale`), deletes remove the row and write a tombstone, and each ref row records the shard version that wrote it, indexed `(tenant, repo, shard, written_at)`, so `refresh` reads only changed rows and tombstones.
- (b) Raised by A. A 1,000-ref push cannot win OCC on a busy repository. Resolution: one set-based `UPDATE ... FROM (VALUES ...)` per shard, a deadline scaled by batch size, and pushes above 100 refs serialized per repository under the merge-queue lease row.
- (c) Raised by B and C. The broker's `label_set_hash` index cannot do subset matching. Resolution: a per-tenant in-memory table of distinct queued label sets, a subset test in broker memory, then a query by the matching hashes. Labels are normalized to lowercase.
- (d) Raised by A and C. Reconnect limits exceed DSQL's 100 new connections per second per cluster. Resolution: one cell-wide budget of 100 per second divided across nodes, and new processes in a hot swap ramp their pools gradually.
- (e) Raised by A and C. 1,000-byte ref names leave no room under DSQL's 1 KiB key limit. Resolution: a 900-byte cap, `ref_log` keyed by a hash of the name, and Milestone 0 measures DSQL's key encoding.
- (f) Raised by A and B. "Skip up to four releases" contradicts the N-1 and N+1 schema window. Resolution: the deploy tool steps through every contract boundary in order, automatically, and CI tests every pair in the window.

## Consider

- **Git availability equals DSQL availability.** Raised by the cross-judge, not by these reviewers. Milestone 0 tests the load side. The failure side, a cell-level DSQL incident taking git down with it, is the price of one transaction boundary. Candidate 2 avoids it at the cost of split ownership. It stays the named fallback.

## Agreement map

Five findings were raised by all three reviewers: merge correctness, outbox head-of-line blocking, the migration fence, pack identity and compaction, and Regional DR. Four were raised by two: SSH capture, Region-independent boot inputs, label matching, and the connection and key-size arithmetic. The single-reviewer findings (webhook retries and payload timing, token revocation, set-based updates, the refs create path) each cite a concrete line and a research fact, and none was contradicted by another reviewer. No reviewer attacked the core bet itself. That matches the cross-judge, which scored availability lowest for this base and named the DSQL hot-repository benchmark as the condition that would flip it.

## Second pass: the core bet

The trail review (`review/trail-review.md`, flag 1) found that the first pass was told not to question the core bet, because the brief put it in the intent. A second pass on all three seats was told to attack it under failure, not load (`review/corebet-a.md`, `review/corebet-b.md`, `review/corebet-c.md`). All three recommended keeping the base and adding bulkheads. None recommended a flip. All three named the same strongest counterargument: a DSQL engine regression that AWS rolls out under every cell at once stops git writes, merges, and the API everywhere, and only candidate 2 keeps git writes through it.

**ACT-11. Split each cell into a `core` and an `aux` DSQL cluster.** Raised by A, B, and C. `core` holds `tenant_state`, refs, packs, `push`, `ref_log`, credentials, permissions, teams, branch rules, PRs, reviews, `check_suite`, `check_run`, and the outbox. `aux` holds Actions runs, jobs, runners, runner sessions, leases, the cache index, artifacts, the log index, `hook_delivery`, notifications, and audit. `completejob` commits in `aux` and reaches `check_run` in `core` through an idempotent relay keyed by job attempt. Cost: a second cluster per cell (a second multi-Region setup in Paired cells), a second migration stream, self-hosters run two clusters, and check conclusions reach the merge decision seconds later. "One database holds every canonical fact" narrows to "one database holds every fact git, merges, and auth depend on".

**ACT-12. Freeze the schema and query set of the git path.** Raised by B and C. The `core` tables that git, edge, and merge touch take DDL only in a release dedicated to that change, after two weeks on the canary cell, and the migration runner refuses any other DDL on them. Git, edge, and merge run only a fixed set of prepared statements, and CI checks their plans against a production-sized fixture.

**ACT-13. Reserve DSQL connections per role.** Raised by A, B, and C. Each role runs as its own OS process with its own DSQL database role. Edge, git, and api reserve 3,000 of the cell's 4,000 connections and 60 of the 100 new connections per second on `core`. Workers, migrations, and `dr-apply` share the rest and are shed first. The pool code enforces the split, because server-side per-role limits are unverified. CI checks that the sums stay under DSQL's quotas.

**ACT-14. Serve bounded stale git reads while `core` is unreachable.** Raised by A, B, and C. The edge authenticates git requests from a credential and permission snapshot written to S3 and local disk. If the `core` snapshot read fails or exceeds 200 ms, the git role serves upload-pack from its cache at its last proven refresh, for at most a signed per-tenant limit (default 2 hours). Writes return 503. This reverses "no stale reads" for git fetches only, freezes revocations for the length of the outage, and is a fallback mode, so a weekly drill blackholes `core` on the canary cell and a failed drill blocks deploys. During a partial partition a node can serve a fetch that misses pushes committed through other nodes. The design states that as a tradeoff.

**ACT-15. Add a failure gate to Milestone 0 and name the correlated risk.** Raised by A, B, and C. Next to the load test, Milestone 0 blackholes `core` for 30 minutes while clones run (fetch success at or above 99 percent), builds an index on a 100-million-row `aux` table at peak push load (push p99 within 1.5 times baseline), and opens 150 new connections per second from the `aux` role (zero git errors). If the failure gate fails, or if AWS cannot stage DSQL engine upgrades cluster by cluster, the base switches to candidate 2. "Tradeoffs accepted" names the fleet-wide engine regression that no bulkhead covers, and "Open questions" asks AWS how DSQL engine upgrades roll out.

## Third pass: the global namespace layer

Three reviewers attacked the integrated namespace layer and were allowed to attack the choice of layer (`review/ns-reviewer-a.md`, `review/ns-reviewer-b.md`, `review/ns-reviewer-c.md`). Five findings came from all three. Most of the critical ones share one premise: freshness is a per-partition watermark that advances only through `global`'s log, and followers write heartbeats into `global` to move it. When `global` is slow or down, or one cell is cut off, that premise turns every "no" into a 503 everywhere, lets stale "yes" answers run with no bound, and piles heartbeats onto the log heads. The fixes below replace the premise instead of compensating for it. None of the reviewers showed a failure the rejected shapes avoid that the replaced freshness rule does not also avoid, so the base stands.

**NS-ACT-1. Freshness is relative to the fleet, not to `global`'s clock.** Raised by A, B, and C. A follower's watermark is the snapshot time of its last successful read of all 64 partitions in one query, which sees every commit up to that time because appends are commit-ordered. No follower writes heartbeats into `global` [unverified that DSQL exposes a usable snapshot time; the fallback is one leased ticker writing at most one entry per idle partition per second]. Every follower publishes its watermark every second to a per-Region freshness board in S3 and reads the board. A replica may answer "no" when its watermark passes `asked_at`, or when no follower in the fleet has seen a newer `global` commit, because then no newer fact exists to miss. So when `global` itself is down, negative answers are immediate and correct. When one cell or one edge is cut off while the fleet advances, its negative answers wait and then 503, its write-class grants fail closed once it lags the board by more than 30 s, its private reads continue under ACT-14's limit, and an edge that lags by more than 30 s fails its health check and leaves DNS and NLB rotation. An anonymous git request for a repository that is not visibly public gets git's 401 challenge at once, because a challenge is not a final answer.

**NS-ACT-2. Revocation coverage counts edges, and the projection guard cannot freeze credentials.** Raised by B and C, and A on coverage. `revoke` reports `covered` only when every serving edge's applied watermark passes the commit, read from the freshness board, not when publishers do. The projection delta guard applies only to slot-map moves. Credential, revocation, suspension, and tombstone-expiry records are exempt. Removal limits are absolute and relative, with a signed override. A refused segment never blocks later ones: the edge reloads a verified snapshot and alarms.

**NS-ACT-3. Replica apply is never fenced, and rows cannot revert.** Raised by A, B, and C on the fence, and A on reverts. The `global-apply` follower writes only `g_*` rows, outside the slot fence, so a frozen slot never stops replication. Webhook events that a `global` change causes for a slot are written as per-slot pending-emit rows that the slot's current owner drains, so a move neither loses nor wedges them. Every `global` row carries a commit version, and appliers upsert an after-image only when it is newer, so a row whose log partition changes with its owner cannot revert. Revocation-class records go to their own partitions, which apply independently under the same version rule.

**NS-ACT-4. Renames bump one row.** Raised by A, B, and C. An owner rename or a login reclaim bumps one `name_epoch` on the account. A cached route is valid only when both the account epoch and the repository epoch in the serving cell's replica match. No rename touches more than a few rows, whatever the owner's repository count.

**NS-ACT-5. Index cells and cross-cell trust are stated and narrowed.** Raised by A, B, and C on index cells, and A on assertion replay. GraphQL goes straight to the target cell when every root field resolves to one cell, and only queries that span cells enter at the caller's index cell. Sign-in runs in any cell, because it is a `global` write. Installation tokens stay minted by the installation account's index cell, and the failure rows state that a cell outage blocks new installation tokens, stars, notifications, feeds, and cross-cell listings for accounts indexed there, service-wide. Front assertions are bound to the target cell as audience and live 10 s, so a compromised data cell cannot replay a principal to another cell.

**NS-ACT-6. Slot moves keep jobs and tokens alive.** Raised by B and C. A target cell honors the source cell's verifying keys for the moved slot for one hour after Flip, and runner endpoints route by the job's slot, so in-flight jobs keep their `GITHUB_TOKEN`s and renew through the move.

**NS-ACT-7. Residency survives transfers.** Raised by A, B, and C. A transfer that would move a resident network's owner outside its residency, or bring an outside network into a resident org, is refused with a 422 that names the residency rule, and "Known deviations" lists it. Resident orgs' Actions secrets are stored in their residency's cells.

**NS-ACT-8. Rate limits and card subscriptions are specified.** Raised by B on limits and C on cards. Each front node enforces its share of a Region-wide limit, as candidate 3 described, so limits do not multiply with node count. A grant, membership, or star change makes the account's index cell subscribe to or drop the repository's cards and pull a resync from the owning cell.

## Fourth pass: the worldwide global tier, and BYOC and self-hosted installs

The operator asked for a pass that proves BYOC and self-hosted installs work. Two walkthroughs played a self-hoster in eu-west-1 (`review/selfhost-walk.md`, 12 findings) and the vendor SRE running BYOC with the existing machinery (`review/byoc-walk.md`, 12 findings). A third reviewer attacked the round-3 global tier (`review/global-tier-review.md`, 8 findings). The walkthroughs found five blockers.

Most install findings share one premise: the vendor's deploy tool, running outside the customer's account, drives every lifecycle step. That premise breaks on the one-hour chained-session cap, on a customer revoking the deploy role mid-rollout, on a week-long vendor outage, on air-gapped installs, and on observation through a role that can call only API Gateway. IN-ACT-1 replaces it: the install operates itself, and operators only submit signed intents and read status. The same mechanism serves managed, BYOC, and self-hosted, which is what "one artifact" requires.

### Global tier

**GT-ACT-1. A Region loss must not make survivors lag.** Raised by the tier review (blocker). A member that can read its authority and whose own watermark is younger than `MAX_LAG` is current, because its snapshot time proves it. Boards matter only when a member cannot read the authority. Each board member holds a short board lease it renews by writing its row, and a member that cannot renew stops answering "no" and stops granting writes for the affected geography. Survivors excuse a Region once every member lease in it has expired. "Failure modes" gains board rows, and Drills gain a permanently dead Region for managed and Paired installs.

**GT-ACT-2. "No" is never wrong after acknowledgment.** Raised by the tier review. Creates (signup, token creation, fork, repository creation, membership and grant additions) wait for the same coverage as `revoke` before they return. A member named lagging stops answering "no" for that geography until it catches up. The design states the guarantee as "never 'no' about a fact whose write was acknowledged", keeps "no" immediate during an authority outage, and states that two observers can disagree for up to 5 s between a commit and its acknowledgment.

**GT-ACT-3. Revocations survive a continent cut.** Raised by the tier review. A revocation-class write also commits one conditional MRSC item before it returns, so it is durable on a second continent. Appliers and `reconstitute` apply these items. Revocations are rare, so the added write is cheap.

**GT-ACT-4. `reconstitute` fences the old authority and has complete inputs.** Raised by the tier review. Its first step seals the lost geography in the registry, so lease renewal and creation fail for good. After-images order by `(geo_epoch, version)`. A healed authority rejoins through a defined procedure that records its unreplicated commits as stated loss. Every authority table carries a recovery class (`Replicated`, `Projected`, `Escrowed`, or `Lost`) checked in CI, and `reconstitute` builds its input set from it. Credential hashes and secret ciphertext are escrowed. Index cells are reassigned, and the old cell is recorded for `kid_allowed`.

**GT-ACT-5. One bad board row cannot fail the fleet closed.** Raised by the tier review. Readers drop rows stamped later than ClockBound `latest()` plus the margin. A lead of more than `MAX_LAG` counts only if two front cells corroborate it or the reader finds the named commit in the authority. The board layout and its cost are specified.

**GT-ACT-6. A Regional promotion cannot bring back revoked credentials.** Raised by the tier review. Before `revoke` returns `covered` in a Regional install, it writes a create-only record to the `dr` Region's control bucket, and promotion applies every such record before traffic moves.

**GT-ACT-7. MRSC is managed-only.** Raised by the tier review and the BYOC walk. Every BYOC and self-hosted install, Paired included, keeps the claim registry as a table in `core`'s `authority` schema, with no writer leases, because an install has one geography. The Paired preflight checks only that the Region trio sits inside one DSQL Region set, so customers whose Regions are outside the MRSC list are accepted.

### Installs

**IN-ACT-1. The install operates itself.** Raised by the BYOC walk (blockers 1 and 2, majors 4, 10, 11, and 12) and the self-host walk (majors 5 and 8). An in-account `operator` role, part of `worker`, owns every lifecycle step under a lease row in `core`: rollout stages, migrations, node and image rolls, certificate renewal, key rotation, mirror sync, backups, `dr` promotion, and failback. Operators submit signed, create-only intents (rollout plans and commands from an allowlist) to the install's control bucket in each Region, and read signed status documents from a `status/` prefix there. The vendor's deploy tool submits an intent and then polls with fresh short sessions, so no stage outlives the one-hour chained session. Every stage is idempotent and resumable from a cursor in `core`, with a safe point after each AZ gate, and a node-local watchdog swaps a new process back if it receives no "gate passed" within its deadline. A customer who revokes the deploy role stops new submissions only. The observer role reads the status documents through `s3:GetObject` in every install Region, so no API Gateway is needed and a private NLB is fine. The status documents include a `nodes` report (binary digest, image id, git version, role-process state), and <vendor-fleet-app> gains Tributary gate checks (`nodes-at-version`, `storage-healthy`, `outbox-fresh`, `dr-fresh`) in place of `components-healthy` and `lambda-code-matches`. The installation record lives in `core`. Managed cells use the same path, with the vendor as the only submitter.

**IN-ACT-2. Trust roots are split.** Raised by the self-host walk (blocker 2) and the BYOC walk (majors 9 and 12). The vendor's release key signs only releases, action packs, and pin maps. Each install has its own config key, a KMS asymmetric key that the bootstrap creates in the customer's account, which signs per-install config and intents. In BYOC, the deploy role and the customer may both use it. In self-hosted, only the customer can. `tributary config sign` and `tributary config apply` change endpoints, certificates, the stale limit, and other customer-signable settings, which the design lists, with last-known-good rollback.

**IN-ACT-3. Releases carry everything an install needs, offline too.** Raised by the self-host walk (blocker 3, major 10) and the BYOC walk (major 8). Each signed release carries per-Region AMI ids and the image digest, and a signed actions pack: the `actions/*` mirror, the `tributary-actions/*` forks, the pin map, and runner tarballs. A `publish:image` stage, or `tributary release import-ami` for self-hosters, copies the AMI into each install Region, re-encrypts it with the install's key, and grants the Auto Scaling service-linked role its use. Nodes verify the digest at boot. `tributary actions import` loads a pack, and an in-install sync job pulls new packs when the install has outbound access. The install serves `RunnerRefresh` download URLs itself, and each release publishes the next runner floor one release ahead. An air-gapped section lists the offline bundle transfer, the VPC endpoints required, and health checks through CloudWatch alarms instead of public Route 53 checks.

**IN-ACT-4. Backups and restore are defined.** Raised by the self-host walk (major 4). Both DSQL clusters back up through AWS Backup [verify in Milestone 0]. S3 noncurrent-version retention is at least as long as backup retention, and GC and superseded-pack retention cover the restore window. `tributary admin restore --to <t>` restores both clusters to one point in time, re-signs endpoints with the config key, restores pack versions, and runs the push-durability replay as its verification.

**IN-ACT-5. Regional installs work with and without a recovery Region.** Raised by the self-host walk (blocker 1, majors 6 and 11) and the BYOC walk (major 5). `Regional { home, dr: Option<Region> }`. With no `dr`, RPO is the backup interval and the evaluation profile uses it. With `dr`, the install keeps a KMS multi-Region key replica there, pre-stages wrapped keys, certificates, and host keys in the `dr` control bucket, and rotates key epochs at promotion. `tributary dr promote` and `tributary dr failback` are intents the operator role runs. A Milestone 6 gate promotes a loaded Regional install and checks its stated RPO and the `ref_log` reconcile output. A preflight checks DSQL, CDC, instance types, quotas, SES or SMTP, and certificate format in every install Region, and the quickstart inventory is corrected.

**IN-ACT-6. Monitoring and the 2am runbook exist for self-hosters.** Raised by the self-host walk (major 5) and the BYOC walk (major 12). Every install exports CloudWatch metrics and alarms and a Prometheus endpoint, and can send alarms to a customer SNS topic. A runbook for an impaired DSQL gives a decision tree keyed on AWS Health, CDC lag, and the stale-limit clock, ending in `tributary dr promote` or waiting, and self-hosters are told to drill a promotion every quarter.

**IN-ACT-7. The deploy role is scoped, and the bootstrap matches the product.** Raised by the BYOC walk (major 3). The bootstrap takes a `product` variable that selects Tributary's name prefixes and the PassRole services it needs (EC2 and Auto Scaling), and creates the service-linked roles it needs explicitly. A Tributary deploy policy replaces `PowerUserAccess`. It denies reading repository data (pack-bucket `GetObject` and connecting to DSQL as a data role) and deleting stateful resources (DSQL clusters, pack buckets, tables, and KMS key deletion), which stay with the customer.

**IN-ACT-8. Migrations and rollbacks have a defined order.** Raised by the BYOC walk (majors 6 and 7) and the self-host walk (major 8). A release is expand, then `roll:nodes` across every Region and the `dr` node group, then a soak, then contract. Contract runs only when the `nodes` status shows every process at version N or later and no swap-back pending, and it removes only the previous release's deprecated shapes. The backfill cursor lives in `core`. The release record gains `phase`, which the compatibility check reads. Resources leave only two releases after the code stops using them, and stateful resources carry `prevent_destroy`, so a tool rollback never destroys them. Contract-phase releases are always retained, and recovery after a barrier is roll-forward only. A long skip is a `steps[]` chain the operator role walks with a resumable journal. A single-node evaluation install takes a short outage for an image change, and the design says so.

**IN-ACT-9. Installs have instance sign-in and a site admin.** Raised by the self-host walk (major 7). Installs choose built-in accounts, SAML, or OIDC at instance scope at launch, and LDAP at T1, as GHES offers. A `SiteAdmin` actor has audited bypass. `tributary admin bootstrap` runs on a node through SSM and prints a one-time sign-in link.

**IN-ACT-10. GHES import works the same in every mode.** Raised by the self-host walk (major 9). Imports assign new ids and keep a `legacy_id` index in every mode, so slot bits stay valid. The design maps the `ghe-migrator` archive, defines how credentials are re-issued, and adds an import gate to Milestone 6, because replacing GHES is a self-hosted buyer's first step.

**IN-ACT-11. The evaluation profile and uninstall are defined.** Raised by the self-host walk (minor 12). The evaluation profile is one AZ and no `dr`, with no availability SLO, and documents scaling `perAz` up with its cache warm-up. `tributary uninstall` exports data, disables protections, empties versioned buckets, schedules key deletion, and destroys the bootstrap last.

**IN-ACT-12. Vendor dependencies are listed.** Raised by the BYOC walk (major 12). The Deployment modes section gains a vendor-dependency table: each thing an install takes from the vendor (releases, action packs, pin maps, the deploy principal, <vendor-fleet-app>, alarms), how the install behaves while the vendor is unreachable for a week, and the step that removes it when a customer leaves BYOC to self-host.

## Fifth pass: re-walking the installs

Two fresh agents re-walked the self-hosted and BYOC installs against the revised design (`review/selfhost-rewalk.md`, `review/byoc-rewalk.md`). Of 24 install findings, 11 were resolved, 13 partial, and none still fully open. All 8 global-tier findings were resolved. The re-walks found 2 new blockers and 8 new majors, all about the operator role from IN-ACT-1. The operator role is still the right shape. Its recovery path, its permissions, and its own upgrade need these fixes.

**OP-ACT-1. Recovery does not need `core`.** Raised by the self-host re-walk (blocker N1). Recovery-class commands (`SwapBack`, `Halt`, `Abort`, `Config`, `Restore`, `DrPromote`, `DrFailback`) take their lease and keep their journal in the acting Region's control bucket, written with `If-Match`, so they run while `core` is impaired. Nodes load signed config straight from the bucket with no operator step. The operator holds one reserved `core` connection and is not shed with other workers. A Milestone 6 gate runs swap-back and a config change with `core` blackholed.

**OP-ACT-2. Infrastructure applies and release bytes have an owner inside the account.** Raised by both re-walks (blocker N1 in BYOC, major N3 in self-hosted). The deploy tool, or the customer's CLI, copies each verified release create-only into `releases/` in every control bucket, so the operator never needs registry access. `Stage::ApplyInfra { step }` applies that step's OpenTofu module as a short-lived in-account task under its own deployer role, which no serving node can assume. A `steps[]` chain applies each step's module just before that step's stages, so a later module never removes a resource that a running release still uses. The OpenTofu state bucket replicates to the peer or `dr` Region. A chain's preflight checks registered runners against the final step's runner floor.

**OP-ACT-3. The submitter is the key, and destructive intents need the customer's key.** Raised by both re-walks (BYOC major N2, self-hosted partial 2). Each install has two signing keys. The config key, usable by the vendor's deploy role and the customer, signs rollouts and routine config. A customer-only key signs `Uninstall`, `Restore`, `DrFailback`, `Halt` and `Abort` during a revocation, and any config that changes endpoints, buckets, or the identity provider. The operator derives the submitter from the key that signed an intent, never from a field. The operator signs nothing but its status documents, so a restore or promotion carries its new endpoints in the customer-signed intent. The delete denies also go in the workload boundary, and the deploy role is denied `ssm:StartSession` and `ssm:SendCommand`.

**OP-ACT-4. Restore never serves rewound state.** Raised by the self-host re-walk (major N2). A restore bumps a `restore_epoch` in `core` and the control bucket, and nodes drop reftables, caches, and auth snapshots when it changes. Shard versions restart above the pre-restore maximum. Revocation records are always written to the home control bucket as well as `dr`, and a restore replays every record newer than its target time. The design states that restore, unlike `dr` promotion, calls DSQL's control plane, and Milestone 6 gates a restore under load.

**OP-ACT-5. A rollout can be halted.** Raised by the BYOC re-walk (major N4). The allowlist gains `Halt { intent }`, which stops at the next safe point, and `Abort { intent }`, which swaps back to the last safe point. Intents carry a short `not_after`. The runbook for revoking the deploy role is: revoke the role, then submit `Halt` signed with the customer-only key.

**OP-ACT-6. The operator cannot upgrade itself mid-rollout, and late nodes cannot run old code.** Raised by the BYOC re-walk (majors N3 and N5). Operator processes leave `roll:nodes` until after the soak, and the cursor and journal follow the two-release format rule. A node boots the binary that the release pointer in `core` names, or in the control bucket while `core` is unreachable, and refuses to serve below the schema's minimum release. Contract also requires every launch template at N.

**OP-ACT-7. Uninstall finishes outside the install.** Raised by the self-host re-walk (major N4). The operator's `Uninstall` stage only exports data and disables protections. The customer then runs `tributary uninstall --finalize` with its own admin role, which destroys the install, empties the buckets, deletes replica keys and then primary keys, and destroys the bootstrap last.

**OP-ACT-8. The air-gapped endpoint list is derived, and `dr` has a network path.** Raised by the self-host re-walk (major N5). The VPC endpoint list is derived from the stage table, which adds AWS Backup, `ssmmessages`, and `ec2messages`. An install with `dr` requires inter-Region connectivity (peering or a transit gateway) for `dr-apply`. Air-gapped installs move traffic at promotion by a private DNS change instead of ARC. The preflight probes every endpoint, and the air-gapped Milestone 6 gate adds a backup and a promotion.

**OP-ACT-9. The partial findings are closed.** Raised by both re-walks.
- Private installs replace <vendor-fleet-app>'s unauthenticated `liveness` check with a status-document liveness check.
- The deploy policy's PassRole covers FIS, and it denies `kms:DisableKey` and admin DSQL connections.
- An install's authority-schema and git-path DDL first runs against a restored copy of the install's latest backup in the preflight, the install's form of the managed shadow canary.
- `comparedWith` is computed per release line, so a customer pinned at N-2 keeps its rollback, and security fixes get an expedited lane outside the waves.
- `publish:image` belongs to the deploy tool, which shares the source AMI and grants its KMS key per account and Region, and AMI retention follows `retention=customer`.
- The internal mTLS CA is named: a per-install private CA key held by the operator's KMS key, rotated with the key epochs.
- A Paired install's lost home Region has a procedure and an RTO for the deploy machinery: the replicated state bucket and the peer Region's operator take over.
- The actions pack carries an allowlist of third-party actions, and admins can add any public action to the install's mirror, as GHES's `actions-sync` does [unverified].
- The evaluation profile skips drills that take a node out of rotation.
- ARC scale sets stay T1, with `config.sh` runners at T0 in self-hosted installs, and the design says so.

## Sixth pass: the round-4 foundation

### Intent

> `DESIGN.md` builds Tributary fresh on DynamoDB chains (round 4's candidate 3 with eight grafts) for less downtime first and better scale second, keeping GHES 3.22 wire compatibility, never losing an acknowledged push, giving read-your-writes on the journeys clients rely on, and shipping managed, BYOC, and self-hosted from one artifact.

### Reviewers

- Reviewer A: `pstack-panel-a`, 10 findings (`review/round4-review-a.md`).
- Reviewer B: `pstack-panel-b`, 10 findings (`review/round4-review-b.md`).
- Reviewer C: `pstack-panel-c`, 10 findings (`review/round4-review-c.md`).

Every seat runs the same model, so agreement is weaker evidence than it looks. Six findings were raised by all three.

### Act on

**FD-ACT-1. The token re-check reads the local replica, and `global` has a re-protection path.** Raised by A, B, and C. Graft 3's strong re-check made every write in every cell depend on a quorum of a three-continent table. A write-class request whose cached token entry is older than 5 s re-reads it from the local `global` replica with an eventually consistent read, from its own per-node budget, and alarms when replication lag passes 2 s. If the local replica fails, the cached entry serves up to 60 s. `global` joins the stated blast radius and the SLOs. After a permanent Region loss, `global` and each Paired cell are re-protected by planned copies: a new `global` trio that edges read beside the old one until cutover, and slot moves out of the degraded cell.

**FD-ACT-2. Multi-chain operations commit where no follow-up can be refused.** Raised by A, B, and C. A transfer first appends a `Reserved` `RepoName` on the destination owner's chain, which `decide` treats as taken. That entry is the commit point. `Settings { owner }`, the `Live` name, and the old owner's `Alias` follow and cannot be refused. A fork names its abort path: if `ForkAdded` meets a sealed or taken-down network, the finisher tombstones the fork's name. An untouched signup is finished by a sweeper that reads the `global` stream. Every multi-chain operation names its commit point, its finisher, and its abort path.

**FD-ACT-3. Slot moves hand over chain by chain, with everything the slot owns.** Raised by A, B, and C. A chain is served by the target as soon as the target has caught up to that chain's `Sealed` entry, and fronts follow the entry's target, so no chain waits on its slot-mates. Work-table items for the slot (check runs, jobs and leases, stars, notifications, cards, cursors) move under the same seal. `IdBlock` items are keyed by slot and move with it, so ids never repeat. While the source still owns the slot, an `Unsealed` entry aborts the move. Home cells derive from the account id's slot instead of a stored field.

**FD-ACT-4. Each Region's dispatcher writes its own markers.** Raised by A, B, and C. Markers are keyed by dispatcher Region, so no two Regions write one item and MRSC raises no conflict on the normal path. Consumers read both Regions' marker partitions, and only the consumer's lease holder writes its cursor. Cross-cell deliveries keep a cursor per consumer, chain, and destination cell, so a down home cell holds back only its own deliveries (B finding 10).

**FD-ACT-5. Single-cell stale mode is a real mode.** Raised by A, B, and C. It starts cell-wide on sustained failure (three failed tail reads over 10 s, or a signed flag) and never on latency alone. Reads take a `ReadView` that is `Fresh` or `Stale`. `decide` and write authorization take only `Fresh`. While stale, edges keep expired positive token and session entries for the signed limit. The weekly drill runs with live traffic on a canary install, and Milestone 3 re-gates it with token-authenticated private fetches. A stale read may miss a write acknowledged in the seconds before the outage, and "Known deviations" says so.

**FD-ACT-6. Authorization never reads another cell on the request path.** Raised by A and C. Each owner has two chains: `Authz` (members, teams, grants, policies, installations, rulesets) and `Identity` (credentials, sessions, SSO, audit), so sign-in churn never touches what gates requests and one partition no longer caps an org's writes. A `Mirror` consumer copies an owner's `Authz` entries into every cell that hosts its repositories, and those cells authorize from the local mirror. A revocation-class `Authz` entry is acknowledged only after every hosting cell has applied it. A hosting cell that cannot refresh an owner's mirror for 30 s fails writes closed for that owner's repositories in that cell only. Enterprise policy is an `Authz` chain of the enterprise, a third dependency for enterprise-owned orgs.

**FD-ACT-7. Deletes are tombstones, and repairs stay inside the chains.** Raised by C and A, with B on the restore cutover. Deleting a repository or an org appends a `Deleted { retain_until }` entry, 90 days by default, and its name entry becomes `Deleted`, so undelete is chain-local. `RestoredTo` names a ref set and leaves metadata alone. A whole-fold reset is a separate admin intent. Point-in-time restore is kept for damage outside the chain model, and journey 7 uses undelete and `RestoredTo` instead of rewinding the install. After a full restore, the cutover re-creates the `dr` replica on the restored tables and runs `Remark` from 24 hours before the restore time, and `DrPromote` refuses tables that the current `restore_epoch` does not name.

**FD-ACT-8. S3 objects named by chain position become content-addressed.** Raised by B. Spilled bodies, snapshots, and archives are keyed by a ULID or digest that the entry or checkpoint names, as packs already are. Racing writers and restored timelines can then never collide on a key.

**FD-ACT-9. A `dr` promotion cannot collide with a live old home.** Raised by A. Entry keys carry the promotion epoch (`e#<epoch>#<seq>`), so writes from the two sides of a partition never land on one item, and a divergence shows as a fork in the chain. Home nodes stop writing as soon as they read a higher epoch in any control bucket, and promotion still truncates each chain at its first gap.

**FD-ACT-10. A hot chain's read budget counts bytes.** Raised by B. Each AZ's preferred node is the only node that tail-reads a chain. Other serving nodes in that AZ fetch entries from it, under a single flight that started after their own request arrived, and fall back to their own strong read if it is slow. The serving cap and the inline rule count readers times bytes. The Milestone 0 throttle test uses the full serving set and real entry sizes.

**FD-ACT-11. Required checks stay on the chain but bounded.** Raised by A and C. Only conclusions for SHAs that are heads of open pull requests, merge-queue refs, or protected branch tips are appended, and `apply` prunes the row when the pull request closes or its head moves. Commit statuses that a rule requires take the same path. C's alternative (pin check versions at plan time) reopens the race graft 1 closed, so it is not taken.

**FD-ACT-12. Entry formats are gated by every reader.** Raised by A and B, with C on refolds. A new entry format is enabled only when every cell that can read the chain reports a release that reads it, from the fleet's `nodes` reports. Each entry carries its tier tag outside the encoded body, so an older node skips an unknown metadata event and the core tier never stalls. Once a format is enabled, swap-back below the reading release is refused and pages. Each fold-schema refold is built once by the chain's preferred node and published as a snapshot that other nodes load. The per-node miss budget times the front fleet stays below each Region's table read maximum.

### Consider

- The 2-hour stale limit is shorter than journey 7's 3-hour impairment (A finding 6). The limit is signed config that a customer can raise, as in rounds 1 to 3.

### Noted

- A table's maximum read throughput is per replica, so the miss budget is bounded fleet-wide (B finding 9), folded into FD-ACT-12.

### Dismissed

- Deleting the `RequiredCheck` chain write (C finding 7). It would bring back the race between a failing required check and a merge that graft 1 closed.

### Agreement map

All three seats found five of these problems on their own: the cross-continent token re-check, transfer commit order, slot-move handover, cross-Region marker writes, and the stale-mode trigger. A and C found the sixth, the owner chain as a cross-cell dependency. Each seat also found one problem the others missed. B found the S3 key collision and the byte-based read budget, and A found the unfenced `dr` promotion. The brief told every seat not to challenge the foundation, so none did, and the seventh pass covers that gap.

## Seventh pass: the foundation attacked, and installs walked on it

The trail review (`review/trail-review-4.md`) found that the sixth pass was forbidden to question the foundation and that no one had walked the BYOC and self-hosted installs on it, which the operator requires (`FRAME.md`, "Operator decision, 2026-10-24, last"). Three fresh seats ran. `pstack-panel-c` attacked the pick (`review/round4-foundation-attack.md`, 7 findings, verdict "holds with changes"). `pstack-panel-a` walked a self-hosted install in eu-central-2 (`review/round4-selfhost-walk.md`, 9 findings, 1 blocker). `pstack-panel-b` walked a vendor-operated BYOC install (`review/round4-byoc-walk.md`, 9 findings, 3 blockers).

The foundation holds. After the sixth-pass fixes, candidate 3 and candidate 1 tie on the rubric, and the base stays on two tie-breaks: chains per repository instead of one head per fork network, and epoch-keyed promotion instead of last-writer-wins heads. The attack also found five changes worth making.

### Foundation

**FA-ACT-1. `fresh` probes the exact next key.** Raised by the foundation attack. AWS documents that a strong read on MRSC returns the latest version of an item, and it does not document that a range Query sees every item created before it. `fresh` is therefore a strong GetItem on `e#E#(applied + 1)`, the key whose `attribute_not_exists` put is the commit point, repeated until the key is absent. Query only fetches entries in bulk. Milestone 0 adds a phantom-read test.

**FA-ACT-2. The mirror lease runs on a heartbeat.** Raised by the foundation attack. The home cell writes a timed heartbeat per home and hosting cell pair, outside Streams, and a hosting cell's mirror lease runs from it. `Mirror` code ships in the last wave. Failure modes gains a "stopped mirror" case, and a stall of the event path can no longer fail writes closed in other cells.

**FA-ACT-3. Mirrored denials verify, and revocations wait at most the lease.** Raised by the foundation attack. A denial that rests on a mirrored fact makes one strong read of the home `Authz` tail, coalesced per owner per node, so a grant acknowledged before the request is never refused. A revocation's 204 waits at most 30 s, the lease, because a hosting cell that has not applied it by then has fenced itself. The lease covers only decisions that read a mirrored fact (installations, teams, org roles, rulesets). Owner and collaborator checks read the repository chain. Reads in a cut-off cell close after a signed limit.

**FA-ACT-4. Milestone 0 races the list engines.** Raised by the foundation attack. On the same synthetic repository, Milestone 0 runs candidate 1's DynamoDB index items beside the fold engine with a page-completeness check, and measures merge p99 on a cold node after an AZ drop. The list engine is chosen from those numbers, and the chain commit core stays either way. Review verdicts move into the core tier, so a merge never waits for a metadata load.

**FA-ACT-5. The selection rationale says what is true now.** Raised by the foundation attack. "Synthesis decision" and "Alternatives considered" state that the sixth-pass fixes brought candidate 3 and candidate 1 to a tie, and name the two tie-breaks. "Tradeoffs accepted" lists every mechanism that exists because of the chain-per-aggregate shape, so growth in that list is visible.

### Installs

**IW-ACT-1. `dr` promotion loses no acknowledged write.** Raised by the self-host walk (blocker 1) and the BYOC walk (major 8). Every home put requires a "no promotion" read of the `dr` control bucket from the last 10 s, cached per node, and promotion waits that window plus the clock error before it takes writes, so no write acknowledged at the old home after promotion exists. The failover health check follows a CloudWatch alarm on a metric that only `DrPromote` and `DrFailback` publish, so it is sticky and uses only the data plane. Entries from the old epoch that arrive late are re-scanned and recorded. The Milestone 6 gate becomes zero acknowledged entries lost after promotion, and the write RTO is stated as the wait plus the promotion. A customer may pre-authorize the config key to sign `DrPromote`.

**IW-ACT-2. Every install key is multi-Region.** Raised by the BYOC walk (blocker 2) and the self-host walk (major 2). The bootstrap creates the CMK, the config key, the customer-only key, the status-signing key, and the CA-wrapping key as multi-Region keys, with replicas in every install Region and in `dr`, and the preflight checks it. KMS cannot convert a single-Region key later.

**IW-ACT-3. Installs can re-protect and change class.** Raised by the BYOC walk (blocker 3) and the self-host walk (majors 2 and 5). A `Reprotect` intent, signed with the customer-only key, creates a new table set (a new MRSC trio, or Single to Paired), copies every chain while serving, hands each over with `Sealed` between table sets inside the one cell, swaps Regions in config, and removes a dead Region from the target and the OpenTofu state. An `EnableDr` stage runs S3 Batch Replication for existing packs, and `dr-fresh` requires a complete pack inventory. `DrFailback` is specified step by step. A Paired install running on one replica and the witness may enter stale mode. The quickstart and preflight say that Zurich has no MRSC trio and no in-country `dr`, and "Deployment modes" states the offer and SLO for Regions outside the MRSC list, such as Sydney. The quarterly drill and a Milestone 6 gate cover `Reprotect`.

**IW-ACT-4. The permissions model matches what the stages do.** Raised by the BYOC walk (blocker 1, majors 4 and 5) and the self-host walk (major 3). Tables are created only by `apply:infra` under the deployer role, which holds the data-plane permissions that replica creation needs. The first apply creates only the control buckets, the keys, and a deployer launcher that the customer authorizes once. Boundaries deny `DeleteTable`, `DeleteTableReplica`, and `DeleteGlobalTableWitness`, `dynamodb:PutResourcePolicy` on install tables, `kms:DisableKey`, `ScheduleKeyDeletion`, `PutKeyPolicy`, and `RevokeGrant` on install keys, and lifecycle, versioning, and bucket-policy changes on install buckets. Launch templates change only through the deployer. Turning off deletion protection moves to `uninstall --finalize` under the customer's admin role. Restore and finalize adopt tables created at runtime into state, a customer-only intent retires superseded tables, and the restore cutover re-applies tags, alarms, and policies. The deny on reading data is described as protection against the deploy principal, not against vendor code, which already runs in the account through signed releases.

**IW-ACT-5. The release pointer and format state are signed.** Raised by the BYOC walk (major 6). The operator holds a pointer-signing key that cannot sign intents, and nodes verify the `ReleasePointer` and the enabled formats with it. `formats:enable` is an intent under the config key that the operator executes and records in the signed pointer. The deploy role's bucket policy is limited to `intents/*` and `releases/*`.

**IW-ACT-6. The core-tier refold rehearsal is an operator stage.** Raised by the BYOC walk (major 7) and the self-host walk (major 4). `Stage::RehearseRefold` restores into a `trib-rehearsal-*` table, which the boundary lets the operator delete, and reports to the status document, and the rollout gates on its result. The core tier reads both schemas until each chain's refold snapshot is published.

**IW-ACT-7. Air-gapped installs work end to end.** Raised by the self-host walk (major 6) and the BYOC walk (minor 9). LFS, cache, and artifact bytes go through the install, or the install requires S3 interface endpoints with private DNS. An install with `dr` requires inter-Region connectivity or a replicated control bucket. The endpoint list is generated from the stage table, AWS Backup and Route 53 included. The Streams endpoint URL per Region is customer-signable config, and the preflight calls `DescribeStream` through it.

**IW-ACT-8. The 2am runbook covers a long impairment.** Raised by the self-host walk (major 7). A branch raises the stale limit to AWS's projected recovery time. Nodes snapshot positive token and session entries to S3 every minute, so stale-mode authentication works on any node, including one replaced during the outage.

**IW-ACT-9. Small install gaps close.** Raised by the self-host walk (minors 8 and 9). `RepoRestore` brings back noncurrent pack versions, so its window matches the 35-day backups. The vendor shares each release's AMI with a self-hoster's account at registration, and the release names AMIs by digest. The preflight checks that opt-in Regions are enabled, the target gains an AZ count, and the open question on Route 53 failover in private hosted zones is answered, because Route 53 supports CloudWatch-alarm health checks there.
