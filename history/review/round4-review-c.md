### 1. [critical] `global` is a cross-continent dependency for writes in every cell, and journey 5 permanently weakens it
**Location**: DESIGN.md:344-347 (also 273, 334, 397, 761, 802, 105, 1003)
**Finding**: Graft 3 makes a write-class request do a strong read of `global` whenever its cached token entry is more than 5 s old, and answers 503 if that read fails (344-345). Managed `global` is one MRSC table in us-east-2, eu-central-1 and ap-northeast-1 (334), so each re-check is a cross-continent round trip that needs a quorum of the worldwide table. That makes one table a service-wide dependency for pushes, merges and API writes. The blast-radius list (273) leaves it out, and so do the per-cell push and merge SLOs (761-767), which is the same shape as the auth-database incidents the design says it contains. Journey 5 loses us-east-2, which also holds a `global` replica. MRSC cannot add a replica, so from then on every write in the service rests on eu-central-1 and ap-northeast-1 with no re-protection plan; the open question at 1003 covers installs only. Re-checks also draw on the compiled budget of 200 strong reads per second per node (347). A node that sees more than about 1,000 distinct write tokens per 5 s therefore returns 503 to legitimate writes, and only a new release can raise the limit.
**Evidence**: Measured from the design text. AWS V2globaltables_HowItWorks says MRSC "write and strongly consistent read latencies… require cross-Region communication". `research/dynamodb.md#18` says no replica can be added. The 503 behavior under load is inferred.
**Suggestion**: The design is inconsistent here. A cache miss trusts an eventually consistent read of the local replica (342), but a re-check insists on a strong cross-continent read. Do the re-check as a local-replica read and alarm on replication lag; that keeps the 5 s bound as long as replication lag stays well under it. Then add `global` to the blast radius and the SLOs, and design how `global` is re-protected after losing a Region.

### 2. [critical] Recovering one deleted org rewinds the whole install and drops acknowledged pushes
**Location**: DESIGN.md:107, 1001
**Finding**: Journey 7 fixes "a script deletes the org `acme`" with a PITR restore of all five tables, `global` included, to time `t`. Every push, merge, token, SSH key and signup made by any other tenant after `t` is lost. "Durable: every commit before t" admits this, and it breaks "never lose an acknowledged push". The design never defines what deleting an org or a repository does (no entry type, no retention period). So `repo-restore` for the 3 deleted repositories also has no way to undo the owner-chain `RepoName { entry: None }`. The revocation journal in the control bucket (1001) exists only to patch the side effects of rewinding everything.
**Evidence**: Measured: journey 7 text and the "Backups and restore" paragraph. A grep for deletion semantics found none.
**Suggestion**: Make deletes tombstone entries kept for a retention window. Undo becomes chain-local: an undelete or `RestoredTo` on the owner chain that keeps revocation-class events applied, a re-put of the login if it is still `Former`, and a `RepoRestore` for each repository. Keep PITR for items destroyed outside the system, and delete the revocation journal.

### 3. [critical] Git and authorization reach across cells for every repository not in its owner's home cell
**Location**: DESIGN.md:196, 173, 562, 1249, 273
**Finding**: Every fetch proves `fresh(Owner, Core)` (196), and every commit re-proves the owner chain just before its put (173). Owner chains live in the owner's home cell, but repositories live in their network's cell. That covers every user-owned fork (`bob/widgets` sits in `acme`'s cell, 28/272), any fork of a resident network "by anyone" (1021), networks placed off-home when the home cell lacks headroom (248), and every slot moved to a dedicated cell (272), which are exactly the hottest repositories. For each of these, every clone and push makes a strong read in another cell, possibly on another continent. Line 562 admits only "org-owned fork… write path", 1249 drops even that, and 273 says a down home cell blocks only tokens, stars, notifications, feeds and listings. In fact it stops git for every repository its accounts own anywhere. Creating a fork also needs a `RepoId` leased from the network cell's `IdBlock` (226-227) while deciding in the home cell, which is an unlisted cross-cell write. The design never says how a node reads a peer cell's `log`.
**Evidence**: Measured: the cited lines. The consequences are inferred.
**Suggestion**: Push an authorization-only owner projection into each cell that hosts the owner's repositories, and acknowledge revocations only after those mirrors apply them. Otherwise, list home cells in the blast radius and the SLOs.

### 4. [warning] Owner chains mix authorization with high-churn secrets, and one partition caps an org's writes
**Location**: DESIGN.md:438, 393, 466, 1023
**Finding**: Owner chains have only a core tier (438). That tier holds TOTP seeds, password hashes, sessions, sign-in history with IP addresses, SCIM tokens and the identity audit log (1023), plus an `Sso` entry for each member's SSO authorization (393). Every authorization in the org folds and applies all of that churn, so the cold load is not small. "Writes always re-prove" (466) means every write in every repository of an org is an uncoalesced strong Query on one partition, which allows 3,000 RCU/s. That partition also carries the read proofs, roughly 1,000/s by 466's formula, so an org's total write rate is capped near 2,000/s. Going over it throttles fetches for the whole org. With finding 3, a resident enterprise's managed user who forks an outside network gets these secrets folded onto NVMe in another geography, which contradicts 1023.
**Evidence**: Measured: the cited lines and `research/dynamodb.md#8`. The ceiling arithmetic is inferred.
**Suggestion**: Do what graft 5 did for repositories. Split the owner chain into an authorization chain (members, teams, grants, policy, installations, `not_before`) and an identity chain that stays home. `deps()` names only the authorization chain. Writes re-prove through the same single flight as reads, which is just as fresh because that read started after `decide`.

### 5. [warning] A transfer commits before its destination name is reserved, so it can never finish
**Location**: DESIGN.md:192, 270, 266
**Finding**: A transfer commits at `Settings { owner }` on the repository chain, and only afterward appends the new owner's `Live RepoName`, whose `decide` "rejects a taken key with 422" (266). If the new owner creates or receives a repository with the same name between those two puts, the transfer is committed but the name can never be written. The repository then belongs to the new owner on its own chain, can't be reached by name there, and stays `Live` under the old owner. `Audit` retries it forever. Forks have the same flaw: they commit at the fork owner's `RepoName`, but `ForkAdded` can then hit a network that was sealed by a slot move or taken down (158), and there is no failure branch.
**Evidence**: Measured: the text gives the order. The race is inferred.
**Suggestion**: Reserve the destination name first with a pending `RepoName` that `decide` treats as taken, then commit `Settings`, then promote the name to `Live`. Give every multi-chain operation an explicit abort path that the finisher can take.

### 6. [warning] A slot move seals chains before it flips the slot, and has no abort
**Location**: DESIGN.md:252-258, 156, 1130, 236, 340
**Finding**: Until the `SlotItem` compare-and-swap, fronts still resolve the slot to the source, and the source refuses writes to every sealed chain. A chain sealed early therefore waits for every other chain in the slot plus the catch-up, so the gate's "seal-to-serve gap under 1 s" for each chain (1130) cannot hold for a slot of thousands of chains. If the compare-and-swap loses or the target fails, `Sealed` ("no entry ever follows it", 156) leaves those chains unwritable for good. The move also never rewrites `LoginItem.home` or `AccountItem.home` (236, 340), so home routing and home deliveries keep pointing at the source after it forgets the slot at 7 days.
**Evidence**: Measured: the `move_slot` steps. The outage and stranding are inferred.
**Suggestion**: Hand over chain by chain: the target serves a chain as soon as it has caught up to that chain's `Sealed` entry. Add an unseal step that is valid while the source still owns the slot. Derive the home cell from the account id's slot instead of storing it.

### 7. [warning] `RequiredCheck` grows with CI volume, bloats the core tier, and is not needed
**Location**: DESIGN.md:418-420, 427, 440, 462
**Finding**: The design appends a chain entry for every conclusion of any check that a rule requires "for any branch" (419): every PR push, every queue group, every rerun. In journey 1 these swamp the 60 ref moves a minute. The `required_check(sha, …)` rows (440) are never pruned, so the "small" core tier that alone gates git (462) grows by one row per required check per SHA, which erodes graft 5's fast cold load. Meanwhile 427 already accepts read-then-put on a second store for fork heads as "a valid ordering". The same argument makes it correct to read `checks` strongly at plan time and pin `(run, version)` in `Merged`.
**Evidence**: Measured: the text. The linearizability argument is inferred: a check update that overlaps the merge may be ordered after it.
**Suggestion**: Delete the chain write and have `Merged` record the pinned check versions. If the entries stay, limit them to heads of open PRs and queue refs, and prune them when the PR closes.

### 8. [warning] Dispatchers in both Regions write the same marker items, which MRSC rejects
**Location**: DESIGN.md:535, 521-525, 313
**Finding**: Both Regions' dispatchers read identical streams "at once" (535), so the same `Dirty` item is updated from two Regions within a moment of each other, for every subscribed consumer. MRSC answers concurrent cross-Region writes to one item with `ReplicatedWriteConflictException`. The design routes chain writes to a preferred Region precisely to avoid that (313), then builds the conflict into fan-out. The design never says which Region advances `Cursor` or deletes markers.
**Evidence**: `research/dynamodb.md#18` (measured). How often the writes collide is inferred.
**Suggestion**: Assign each stream shard and each consumer bucket to one Region by the chain-preference hash. The peer takes over only when the lag alarm fires, which is safe because `max_seq` makes repeated raises harmless.

### 9. [warning] Single-cell stale mode starts on latency alone and can't authenticate during the outage
**Location**: DESIGN.md:321, 341-343, 899, 1005
**Finding**: Stale mode starts when tail reads "exceed 200 ms" (321). A latency blip with no outage then serves a fold behind an acknowledged push, which breaks journey 1's read-after-push promise. During a real impairment, `global` sits on the same failed endpoint (899), positive cache entries live 60 s (343), and each node caches separately behind the NLB. After about a minute, only principals cached on whichever node the NLB picks can authenticate, and session cookies also need `sessions_not_before` (340). Journey 7's 3-hour impairment therefore gives anonymous reads only. The weekly drill runs on a node out of rotation (1005), so it never exercises real cache coverage.
**Evidence**: Measured: the cited lines. The impact on user traffic is inferred.
**Suggestion**: Start stale mode only on sustained failure. Serve expired cache entries under the same signed limit, and run the drill with live traffic.

### 10. [nit] A schema refold has no single builder
**Location**: DESIGN.md:468, 455
**Finding**: A fold schema change "refolds lazily per aggregate" (468), but nothing says one node builds the new-schema snapshot and the others load it, as checkpoints do (455). Every node that serves a chain (at least 3 per Region) would refold it from the S3 archive on its own, multiplying the refold load.
**Evidence**: Inferred from the text.
**Suggestion**: Have the preferred node refold and publish a snapshot that the other nodes load.
