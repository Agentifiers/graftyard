## 3. New findings

### Finding 1. Blocker. A `verify` refusal deposes whichever leader is refused, so a regression on the rolling site, or the accepted two-site residual, stalls groups on every site

- **Lines:** 185, 197 to 201, 205, 225 to 229, 258, 400, 414, 419, 465, 533, 738, 797.
- **Walk step:** a BYOC site day for `trib-site-b` that fails at 10%. Self-hosted is the same.
- **Failure path (a), the rolling site refuses.** B is drained and 10% of its members run N+1 (414). N+1 carries a regression in decoding, or in the fold that `verify` compares each `expect` against (227), so those members refuse valid N entries [inferred: this is the bad-deploy class that site days exist to contain, 112]. For a group led on A, B's refusal arrives before C's ack, because weur answers enam before apac does [inferred]. The rule has no condition on which release refused (225 to 229) [measured]. So A truncates, persists `no_lead_until` against its own release, and transfers to B. A transfer "stops appending and serving `fresh`" (197 to 198), B is drained and refuses to campaign (258), pre-vote refuses drained candidates (400), and no transfer deadline is stated [measured]. When C is later elected (205), the next entry that B's regression refuses makes C bar itself the same way [inferred]. Then A and C are barred until their own releases change (185), and no member can lead until B is undrained, after which only B, the member running the regression, can lead [inferred]. Rolling B back to N clears neither bar, and A's and C's next site days wait on "zero refusals" (414) [measured]. About 10% of all groups, on all three sites, lose reads and writes, because every group has a member on B [inferred].
- **Failure path (b), the stated residual.** A and B run N+1 and C runs N, and A's N+1 leader writes a shape N cannot read. This is the residual the design accepts with "recovery is a roll forward" (419, 465, 797) [measured]. B's ack beats C's refusal, so the entry commits [inferred from enam to weur being nearer than enam to apac]. C's refusal still makes the leader transfer to C, which can never store the committed entry, so the transfer never completes and the leader stays stopped (197 to 198) [inferred]. The residual is a stalled group, not a two-member group that rolls forward.
- **Evidence:** the only refusal test is an N+1 leader with N followers (738) [measured].
- **Fix:**
  1. Depose the leader only when the refuser runs an older release than the leader and the refused entry is uncommitted. Members already report their release for `formats:enable` (582).
  2. On any other refusal (same or newer release, or a committed entry), keep the leader, mark the refuser as unable to follow that group, alarm, and have `trib-ops` halt the site day.
  3. Pick a transfer target that is not drained and holds the leader's last index. Abandon a transfer that has not completed within one `LEASE`, and resume leading.
  4. Clear `no_lead_until` when the `Release` group records a rollback of the refusing site's release, as well as when the member's own release changes.
  5. Add two Milestone 0 rows: an N+1 follower that refuses valid N entries during a site day at 10%, and the two-site residual. Each passes only if no group is without a leader for more than one lease.

### Finding 2. Major. Revoking the vendor token leaves the vendor able to drive `trib-ops`, and no entry can remove or rotate a registered key

- **Lines:** 137, 251 to 257, 262 to 265, 622, 642, 650, 652, 657, 658, 765.
- **Walk step:** BYOC, the customer revokes the vendor token mid-roll, then rotates each secret.
- **Failure path:** B is at 10% when the customer revokes the vendor's Cloudflare token, signs `Halt`, and later `Resume` (657). The vendor intent key stays registered, because genesis names it (650) and `ReleaseEntry` has no variant that changes the key set (254 to 257) [measured]. "Intents take the vendor or customer intent key" (251), and `trib-ops` executes them "with a customer-created deploy token" (622) [measured]. So after `Resume`, a vendor-signed `SiteDay` to any earlier uploaded version whose release signature verifies, or a `ReplaceMember`, `RestorePlacement`, or `Rotate`, still runs under the customer's token [inferred]. Revoking the Cloudflare token stopped only uploads. Before revocation, that token is not upload-only either. Line 642 gives the vendor "Workers Scripts Edit for `wrangler versions upload` only", but that permission "Grants write access to Cloudflare Workers scripts", and the permissions page lists nothing narrower (https://developers.cloudflare.com/fundamentals/api/reference/permissions/) [measured]. It can deploy every site script at 100% at once, or delete one, outside intents, release signatures, drains, and site days [inferred].
- **Rotation:** the runbook (658) covers API tokens, export tokens, and the installation-token signing key. It has no step for the customer intent key, the vendor intent key, the release-signing key, the drain-only key, or the Ed25519 ring keys (137) [measured], and the `Release` group has no entry that could carry a new one (254 to 257).
- **Fix:**
  1. Add `ReleaseEntry::Keys { customer, vendor: Option<KeyId>, release, drain }`, signed by the current customer key, and also by the new customer key when that key changes. The group and `trib-ops` refuse any entry signed by a key absent from the latest committed `Keys`.
  2. Make the revocation runbook: revoke the vendor token, sign `Halt`, sign `Keys` with `vendor: None`, then sign `Resume` or `Abort`.
  3. Give the vendor no Workers permission. It writes signed bundles into one install-account bucket with an R2 "Object Read & Write" token, which R2 scopes to "specific buckets" (https://developers.cloudflare.com/r2/api/tokens/) [measured], and `trib-ops` uploads them with the customer's deploy token after the release signature verifies.
  4. Add every key above to the rotation runbook, with `Keys` as the mechanism.
  5. Extend Milestone 5's gate (765): a vendor-signed intent submitted after `Keys { vendor: None }` is refused.

### Finding 3. Major. A self-hosted install can never sign `FormatsEnable`, so no new record format can be enabled

- **Lines:** 227, 251 to 253, 419, 582, 650, 652.
- **Walk step:** self-hosted, the customer's own account with no vendor key, rolling a release that adds a format.
- **Failure path:** release N+1 adds format F, and every site and lifeboat reports N+1. `FormatsEnable` "takes both" keys (252), "both keys sign it" (582), and the customer key gives "the second signature" (652) [measured]. Self-hosted installs "register no vendor key" (253), and genesis omits the vendor intent key (650) [measured]. So no `FormatsEnable` can verify, `verify` refuses any entry in a format that is not enabled (227), and every feature that needs F stays off in self-hosted for good [inferred]. Line 652 also says the vendor intent key "signs releases", while 650 lists a separate release-signing key that self-hosted keeps, so the text does not say which key signs a self-hosted release [measured].
- **Fix:** make `FormatsEnable` take the release-signing key, which every mode registers (650), plus the customer intent key. The vendor ships a `FormatsEnable` pre-signed with the release-signing key inside each release that may enable a format, and the customer adds its signature once the gate at 582 passes. Change 652 to say that the release-signing key signs releases and the vendor intent key signs only vendor intents.

### Finding 4. Major. Spare sites are not bound by the surviving site scripts or the edge, so `ReplaceMember` needs new script versions during a region loss

- **Lines:** 105, 112, 116, 119, 359, 397, 398, 532, 538, 654, 766, 844.
- **Walk step:** BYOC and self-hosted, `SiteLost` for A (enam), then `ReplaceMember` onto the wnam spare.
- **Failure path:** `ReplaceMember` adds a member on the wnam spare through a `Joint` config (398). Leaders on B and C must send it entries, and the edge must reach it once it can win an election. Each site script binds only "the member classes of the other two scripts", the edge binds "all three member classes" (119), and open question 844 covers only "three site scripts" [measured]. A binding lives in a script version, and any new site-script version, binding included, is a site day (112, 654) [measured]. So the replacement needs new versions of `trib-site-b`, `trib-site-c`, and the edge [inferred]. That is the control-plane call that 105 ("a replacement needs no control-plane call") and 532 ("spare sites exist from install") rule out, and it cannot run during a concurrent API outage. It is also two site days, one a day, on the only two voters left, while every new entry needs both of them (397) [inferred]. The edge tees packs to "the three site buckets" (359), and `ReplaceMember` copies into "the spare's bucket" (538), so the spare's bucket needs a binding as well [inferred].
- **Fix:** at install, every site script, the edge, and the script that runs the Workflows bind the member classes and buckets of all six sites (three active and three spares, plus any residency sites), and the compiled hint table (116) covers the spares. State this at 119 and widen 844. Milestone 6's drill (766) runs `ReplaceMember` with every account API token revoked, and passes only if no script version is created.

### Finding 5. Major. The vault exports by org, so a whole-install restore lacks `Names`, `Tokens`, user `Identity`, and user-owned repositories

- **Lines:** 167 to 168, 304 to 305, 386, 514, 589, 590, 623, 659, 660 to 664, 670, 767, 808.
- **Walk step:** BYOC and self-hosted, a whole-install restore from the vault after an account compromise.
- **Failure path:** the vault pulls "with an org-signed export token" (659), and its scope "comes from an org-signed export token, and the install alarms when an org has no vault cursor" (590) [measured]. `Names` and `Tokens` are install-wide shards, with token shards chosen by secret hash per home family rather than by org (167 to 168, 304 to 305) [measured], and `Identity` and `Authz` are keyed by `AccountId`, which covers users as well as orgs (167) [inferred]. A per-org export token cannot select them [inferred]. Self-host F10 found the same gap for the lifeboat, and the design fixed it only there (670) [measured]. After the restore (660 to 664), no name resolves `acme/monorepo`, no PAT or SSH key authenticates (SSH keys resolve on `Tokens`, 386), users have no logins or MFA, and user-owned repositories are gone [inferred]. The RPO row's "Vault lag" (514) and "The vault account bounds the data loss to the vault lag" (808) overstate what the vault holds.
- **Second gap:** step 2 builds members from "the source's newest snapshot plus its log tail" (662), and the vault pulls through the install's own edge (659). A compromised account can commit forged entries through the normal `commit` path, and bucket locks then keep them (589) [inferred]. The procedure names no cutoff before the compromise.
- **Fix:**
  1. Make the vault export install-scoped and signed by the customer key, covering every `ChainId`, including `Release`, `Names`, `Tokens`, `Identity`, and user-owned repositories. Keep per-org tokens for managed tenants.
  2. Have step 1 name an operator-chosen cutoff minute and step 2 use the newest snapshot at or before it plus the tail up to it. The RPO row then reads "vault lag, or the time from the chosen cutoff to the loss after a compromise that wrote through the protocol".
  3. Name self-hosted at 514 and 659, as 623 already does.
  4. Extend Milestone 7's restore gate (767): after the restore, a developer's PAT and SSH key, a user-owned repository, and an org name all work.

### Finding 6. Major. Site days gate only on refusals, so a release that breaks followers passes every step and the next site rolls

- **Lines:** 230, 414, 418, 533, 652, 657, 736, 765, 797.
- **Walk step:** a BYOC site day that fails at 10%, as the vendor SRE.
- **Failure path:** N+1 throws while applying one event kind. On drained B, its N+1 members stop at that index and stop acking those groups, which keep committing on A and C [inferred]. A throw in apply is not a `Refusal`, which only `verify` returns (230), and no gate is stated between the 1%, 10%, 50%, and 100% steps (414) [measured]. The only gate is "zero refusals" over the 1% day (414, 533, 797) [measured], so B's day passes and C rolls. Once C's members reach N+1, every group whose log carries that event kind has both followers stopped, and its leader on A cannot commit [inferred]. Rollback is "`trib-ops` redeploys N on a signed intent" (533), and in BYOC the vendor SRE cannot sign `Halt` or `Abort`, which take the customer key, kept offline (652, 657) [measured]. So `trib-ops` goes on to 50% and 100% unless the customer is reached [inferred].
- **Fix:**
  1. Gate each deploy step and the 1% day on N+1 members' apply lag, apply and verify exceptions, and ack rate against the N members of the same site, plus zero `STEP_DOWN` trips on N+1 leaders.
  2. Carry a pre-signed rollback `SiteDay { site, version: N }` in each release intent, as the edge carries a pre-signed `EdgePointer` (418), and have `trib-ops` run it on a gate breach with no human signature.
  3. Add a Milestone 0 row next to 736: a release whose followers throw on one event kind is stopped at 1% and rolled back with no failed write.

### Finding 7. Major. `trib-front` and `trib-ops` have no release path, yet one carries every request and the other mints every installation token

- **Lines:** 89, 262 to 264, 310, 327, 354, 475, 500, 557, 576 to 583, 622, 653, 858; reference `DESIGN.md` line 392.
- **Walk step:** BYOC day 0 (Wrangler ownership), then a release that changes `trib-front` or `trib-ops`.
- **Failure path:** Wrangler uploads `trib-front` and `trib-ops`, and `trib-ops` "deploys them" (653) by executing signed intents (622). `Intent` has variants only for site days, container days, edge rolls, replacement, placement, and rotation (262 to 264) [measured], so neither script has a signed intent, a percentage plan, or a swap-back [inferred]. `trib-front` runs on every request (354) and is the swap mechanism for the edge (557), so a bad `trib-front` at any percentage fails that share of every journey until someone rolls it back through the API, which a 41-hour control-plane outage blocks (475) [inferred]. The edge "mints through" `trib-ops` (310), installation tokens include Actions `GITHUB_TOKEN` (reference `DESIGN.md` line 392, reused at 327), and the signing key is unwrapped with a Secrets Store key (89), a beta product [measured]. A bad `trib-ops` or a Secrets Store failure then stops every Actions job start and every GitHub App token install-wide, against the 99.9% job-start target (500) [inferred]. Line 858 says Secrets Store is "off the request path", and the release-control rows (576 to 583) treat `trib-ops` only as a rollout tool [measured].
- **Fix:**
  1. Add `Intent::FrontRoll { version, percent }` and `Intent::OpsRoll { version, percent }`, run at 1% for a day and then 100%, with N kept in the deployment. State the residual that a control-plane outage freezes a bad `trib-front` percentage.
  2. Have the edge call `trib-ops` with a version override from a signed `OpsPointer`, the mechanism `trib-front` already uses for the edge, so a bad `trib-ops` swaps back with no API call.
  3. Cache the unwrapped signing key per `trib-ops` isolate for at most an hour.
  4. Add a front-door failure row for minting, and correct 858.

### Finding 8. Major. The lifeboat's acceptance rests on stored hashes, but the host receives live write tokens and holds a DNS token for the production zone

- **Lines:** 28 to 29, 49, 596, 633, 658, 669 to 672, 803.
- **Walk step:** the self-hosted and BYOC lifeboat during a Cloudflare-wide outage: enroll and credentials.
- **Failure path:**
  - `tributary lifeboat enroll` "writes the developer's existing token into gh's hosts file and a git credential helper for the lifeboat host" (669, 28) [measured]. Every lifeboat request then carries that token, which is valid for writes on the main host, and the lifeboat must see it in plaintext to compare it with its stored hashes (670) [inferred]. The design accepts a runtime that "is not a hardened sandbox" because a stolen copy of the hashes "cannot be reversed offline" (633) [measured]. A compromised lifeboat host collects live write tokens from every developer who uses it, which that argument does not cover [inferred].
  - "The certificate comes from ACME DNS-01 against the zone" (671), and the lifeboat is outbound only (49), so the host runs the ACME client and holds a Cloudflare token that writes TXT records in the zone [inferred]. DNS permissions are "DNS Read" and "DNS Write" at zone scope, with nothing narrower listed (https://developers.cloudflare.com/fundamentals/api/reference/permissions/) [measured]. That token can repoint `git.acme.example` and pass DNS-01 for it [inferred].
  - The lifeboat reads R2 from outside Cloudflare (596), which needs an R2 credential. The rotation runbook (658) names neither that credential nor the DNS token [measured].
- **Fix:**
  1. Have `enroll` mint a new per-developer token with a `lifeboat:read` scope that the main edge refuses and the lifeboat accepts. The lifeboat then stores hashes of those tokens only and never receives a main-host token.
  2. Delegate `_acme-challenge.lifeboat.acme.example` by CNAME to a validation zone in a separate account, and give the host a DNS Write token for that zone only.
  3. Give the lifeboat an R2 "Object Read only" token scoped to the export bucket (https://developers.cloudflare.com/r2/api/tokens/) [measured that the scope exists].
  4. Add the lifeboat token, the DNS token, and the R2 token to the rotation runbook, and add the live-token point to 633 and 803.

### Finding 9. Minor. Automatic drain measures the sick site from inside it, and the one-drain rule switches it off for every site day, including one held for 41 hours by an API outage

- **Lines:** 123, 203 to 206, 258, 400, 410, 414, 475, 580.
- **Walk steps:** BYOC automatic drain during a gray WEUR incident, and a 41-hour Cloudflare API outage mid-roll.
- **Failure path (a):** `trib-ops` drains on "that site's member error rate" and "reads the rates from the members over bindings" (400) [measured], which reads as the members of the site it judges [inferred]. The design added `suspect` because "a leader that cannot measure its own sickness" must still lose its lease (400) [measured]. In that case, reads of the sick site's own rates time out or undercount, and the text gives the drain no rule except the general one that a failing or erroring check is a no-op (123, 410, 580) [inferred].
- **Failure path (b):** `trib-ops` "never drains a second site while one is drained" (400) [measured]. Every site day drains its site and undrains only after 100% (414), and during an API failure rollouts "wait" (580, 410) [measured]. A 2023-11-02-class outage of about 41 h (475) that starts with B at 10% holds B drained for 41 h. Automatic drain is then off install-wide, and if A turns gray, step-down and `suspect` can move leaders only to C, because B refuses to campaign (258) [inferred]. That is one site leading every group, the state the rule exists to prevent.
- **Fix:**
  1. Compute each site's burn from its callers. Edges and members on the other two sites already detect missed deadlines for `suspect` (203 to 206). Have them count misses per target site into a health object on their own site, and drain when both other sites report the burn.
  2. Let an automatic drain of a sick site preempt a site day: `trib-ops` stops the deploy steps, appends `Normal` for the rolling site with its N+1 members held to the 1% lead limit (414), then drains the sick site.
  3. When a site day cannot advance for an hour because the API fails, undrain the rolling site under the same limit, and drain it again when the API returns.
  4. Add a Milestone 0 row: a gray site during another site's day.

### Finding 10. Minor. A dead or retired lifeboat blocks `formats:enable` for good, and no key is named for `LifeboatDecoder`

- **Lines:** 251 to 257, 582, 592, 597, 633, 668.
- **Walk step:** self-hosted and BYOC lifeboat decoder gating.
- **Failure path:** two lifeboat hosts are recommended (592), each reports `LifeboatDecoder { host, release }` (256), and `formats:enable` "waits for every registered lifeboat" (668, 582) [measured]. `ReleaseEntry` has no entry that removes a lifeboat and states no expiry (254 to 257), and 251 to 253 name no key that signs `LifeboatDecoder` [measured]. A host that dies, or is rebuilt under a new name, keeps its last release in the group, so no later format can be enabled until that host returns [inferred]. In self-hosted this adds to finding 3. If the host signs its report with some install key, a host on a runtime that "is not a hardened sandbox" (633) holds a key that appends to the `Release` group [inferred].
- **Fix:** register each lifeboat at `tributary lifeboat init` with its own key in a customer-signed entry, accept `LifeboatDecoder` only under that key, add `LifeboatRemove { host }` signed by the customer key, and alarm when a registered lifeboat has not reported for 7 days.
