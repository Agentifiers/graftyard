### 1. [critical] Merge checks the head branch and reviews in one snapshot, then commits without re-checking them
**Location**: DESIGN.md:98, DESIGN.md:100, DESIGN.md:123, DESIGN.md:125, DESIGN.md:379-385
**Finding**: The merge reads the PR, head, reviews and checks in one snapshot (step 2). It then calls the git role for a plan (step 3) and commits in a new transaction (step 4). Only the base ref is compare-and-set. The head branch ref is not guarded at all. `review_version` is only "bumped", and the trick at :125 ("the merge transaction also writes, so the two conflict") works only if the two transactions overlap in time. The design rules that out: the git work must finish before `BEGIN` (:123).
**Evidence** (inferred from the doc's own steps): Under DSQL's OCC, only concurrent transactions that write the same rows conflict (`research/uptime.md#27`). Two failure paths:
- A reviewer submits "request changes", or an admin dismisses the approval, while `merge-tree` runs. That transaction commits before the merge's `run_tx` starts. The merge's later write to `review_version` overlaps nothing, so it never conflicts, and a PR whose required approval was withdrawn gets merged.
- A user's push to the head branch is acknowledged during the plan. The merge then records `Merged{final_head: old}` and leaves out commits that were acknowledged before the merge committed. GitHub rejects this case with "Head branch was modified".

Step 2 also reads `refs/pull/17/head` (:98). That contradicts :361-362, which says the head is the branch's own ref row, and `pr-sync` moves `refs/pull/N/head` seconds late (:609). So "push, then `gh pr merge`" can merge the stale head even with no race. `expected_head` is `Option` (:380) and does not cover this.
**Suggestion**: In the merge transaction, compare-and-set the head ref row (`WHERE target = snapshot_head`) and `review_version` (`WHERE review_version = snapshot_value`), and fail with GitHub's head-modified error. Always read the head from the branch row.

### 2. [critical] The tenant-migration freeze is enforced only by edge maps that propagate eventually, so two cells can both accept writes
**Location**: DESIGN.md:161, DESIGN.md:175-182, DESIGN.md:666
**Finding**: Who owns a tenant's writes is decided by `RouteState` in two separate S3 tenant maps, one per cell. Freeze, then Flip, writes the "new map generation in both cells". Those are two independent writes guarded by `If-Match`, with no atomic hand-off. Edges load maps asynchronously and keep the last known good one. Nothing in the old cell's DSQL blocks the tenant's writes.
**Evidence** (inferred):
- An old-cell edge that has not yet loaded the `Frozen` generation (for example after an S3 read failure, where it keeps its last known good map per :664 and :666) keeps acknowledging pushes after the delta has "drained". Those pushes are never copied, and Forget deletes them 7 days later (:180). That is lost acknowledged pushes.
- The fleet orchestrator crashes after writing `Serving` to the new cell but before writing `Moved` to the old cell. The old cell is left in `Frozen { until }`, and the design never says what happens at `until`. If it reverts to Serving, both cells take writes for the tenant while clients' DNS is split between them.

The research rule is that authority changes are fenced at write time (`research/uptime.md` implication 11). Here the fence covers the map write, not the authority it grants.
**Suggestion**: Keep a per-tenant write fence row in the old cell's DSQL that every `run_tx` for that tenant reads and conflicts with. Freeze means committing that row. The drain reads the change stream up to the fence commit. Unfreezing must be an explicit operation, never a timeout.

### 3. [critical] Compaction can drop objects that a later ref update depends on, and the durability replay would not notice
**Location**: DESIGN.md:263-265, DESIGN.md:274, DESIGN.md:284, DESIGN.md:548, DESIGN.md:630
**Finding**: "Compaction supersedes only the pack ids it read, so a push that lands during compaction stays live" protects the new push's own pack. It does not protect objects already stored in packs that compaction consumed. The weekly full repack with bitmaps (:284) leaves out objects that are unreachable from the refs compaction saw. The design gives no cruft-pack retention or freshening rule, even though `PackKind::Cruft` exists.
**Evidence** (inferred): `rest:git` is T0 (:548). Renovate's `platformCommit` creates a blob, then a tree, then a commit, then updates the ref, in separate API calls. If a full repack reads refs after the blob's pack commits but before the ref update, it leaves out the blob (unreachable at that moment) and supersedes the blob's pack. The ref update then succeeds, because the blob is still on the node's cache disk. Seven days later GC deletes the only S3 copy, and the branch points at a missing object. The merge path has the same exposure: the plan's pack relies on head objects that are not guarded (finding 1). The durability replay checks only that "its pack resolves" (:630). A superseded pack still resolves for 7 days, and an empty push pack always resolves, so the replay passes while the repository is already corrupt.
**Suggestion**: Make compaction keep every object it consumed: unreachable objects go to cruft packs whose expiry is longer than any multi-call flow, and objects get freshened when a write references them. Change the replay to run `git fsck --connectivity-only` from the live pack set for each ref a push touched.

### 4. [critical] One stalled outbox consumer blocks every other consumer, so a search outage stops Actions and webhooks
**Location**: DESIGN.md:453, DESIGN.md:465-467, DESIGN.md:477
**Finding**: Dispatch selects "pending rows in partition ORDER BY id LIMIT 500" and deletes a row only when every consumer bit is set. If `SearchIndex` stalls, the same 500 oldest rows come back on every pass, and newer rows never reach `Webhooks`, `ActionsTrigger`, `RunOwner`, or `CacheHint`. That directly contradicts :477 ("the other consumers move on").
**Evidence** (inferred): When OpenSearch is down, each partition passes 500 unfinished rows within minutes in a busy cell. From then on, workflow runs stop triggering, run status and `needs` stop advancing, webhooks stop, and credential-revocation hints stop. The design claims search is isolated (:668-669, `research/uptime.md` implication 18).
- The self-hosted quickstart lists no OpenSearch domain (:35). If `SearchIndex` is registered there, its bit is never set and every partition blocks permanently.
- `pr-sync`, which the design relies on (:90, :388), is missing from the `Consumer` enum (:453).
**Suggestion**: Give each consumer its own cursor, or index pending rows per consumer (partial indexes per consumer bit), and query per consumer. Only consumers that are actually deployed may count toward the "all bits set" deletion rule.

### 5. [critical] Choosing the SSH tenant from the key ignores the hostname, so a push can land in another tenant
**Location**: DESIGN.md:190, DESIGN.md:610, DESIGN.md:783
**Finding**: In a multi-tenant cell, the first key `ssh-agent` offers that is registered anywhere in the cell decides the tenant. The hostname the user typed plays no part. Owner names are scoped per tenant (:190), so `org/repo` can exist in two tenants of one cell.
**Evidence** (inferred): A contractor has key K_A in tenant A and K_B in tenant B, both loaded in the agent, which is the default setup. They run `git push git@b.tributary.cloud:infra/terraform.git`. OpenSSH offers K_A first, the server accepts it as tenant A, and if tenant A has `infra/terraform` the push lands there. Company B's code is now in company A's repository. If the names don't collide, `git clone` against tenant B fails with "Repository not found" for anyone with two keys loaded. github.com avoids this because repository paths are global there, so the claimed parity with github.com (:190) does not hold. Every managed tenant also shares one host key (:783), so `known_hosts` cannot catch the mix-up.
**Suggestion**: Make the destination address carry the tenant: a per-tenant SSH endpoint address or port, published in `/meta` and in clone URLs. Alternatively, refuse SSH in managed multi-tenant cells until such an endpoint exists.

### 6. [critical] Regional DR recovers refs that point at pack bytes that never arrived, can contain half-applied transactions, and relies on a component the design never specifies
**Location**: DESIGN.md:35, DESIGN.md:50, DESIGN.md:277, DESIGN.md:642, DESIGN.md:708
**Finding**: Metadata, including ref and pack rows, replicates through DSQL CDC with a 5-minute target. Bucket packs replicate through S3 RTC with a 15-minute bound. Refs therefore reach the recovery Region before their pack bytes. Nothing reconciles them at promotion, and no rule keeps CDC application atomic per transaction.
**Evidence** (inferred): Home Region lost → the warm cluster has `ref` rows whose `pack` objects haven't replicated → `git clone` fails on those repositories for everyone, which is far worse than the stated "push RPO up to 15 minutes". If the CDC applier applies rows one at a time and the stream ends mid-transaction, a merge can arrive half-applied (PR `Merged` without the base ref moving), breaking :8 in exactly the case where it matters. The applier isn't in the crate map (:491-502) or the failure-mode table, and its lag isn't in the observer route (:697). The quickstart picks `regional` with a `drRegion` while promising "one Aurora DSQL cluster" (:35, :50). Regional is the self-hosted default (:708), and "nothing to repair by hand" (:58) fails at the first DR event.
**Suggestion**: Apply CDC one whole transaction at a time. On promotion, run a mandatory reconcile that walks `ref_log` and moves each ref back to its newest value whose packs exist in the recovery bucket, and record those rollbacks as stated losses. Specify where the applier runs, how it fails over, and alarm on its lag.

### 7. [warning] Region-loss survival depends on boot-time inputs that the design places in only one Region
**Location**: DESIGN.md:164, DESIGN.md:337, DESIGN.md:715, DESIGN.md:737, DESIGN.md:783
**Finding**: Every node start reads three things: the tenant map from a single bucket `s3://trib-<cell>-control` (no Region named), signing keys decrypted with KMS "once at node start" (:337, :737, :783), and certificates. Encryption is "Vendor CMK per cell" or "Customer CMK", in the singular (:715). KMS keys are Regional unless multi-Region keys are chosen, and the design never mentions multi-Region keys.
**Evidence** (inferred): After a permanent Region loss, which is the motivating case (:7, `research/uptime.md#38`), any node start in the surviving Region fails if the control bucket or key lives in the lost Region. That covers an ASG replacement, a crash restart, and each new process in the hot-swap deploy (:689). Without the signing key, the node cannot verify `ghs_` tokens, mint OIDC tokens, or present the SSH host key. Regional DR must launch new nodes in the recovery Region (:642), so it is blocked outright.
**Suggestion**: Use one control bucket per Region named by `Durability`, KMS multi-Region keys (or keys wrapped under a key in each Region), and certificate copies in each Region. Add a drill that boots a node in the peer Region with the home Region blocked.

### 8. [warning] Content-addressed pack ids as primary keys break when the same pack appears again, failed pushes leave S3 objects nobody deletes, and GC checks then deletes without a fence
**Location**: DESIGN.md:89, DESIGN.md:216-220, DESIGN.md:268, DESIGN.md:274
**Finding**: `pack(tenant, network, pack_id)` is keyed by the pack's checksum, and its state only moves one way, Live → Superseded. Byte-identical packs do recur, and the design doesn't say what happens then.
**Evidence** (inferred):
- **Repeated pack id**: after a force-push revert and compaction, re-pushing the same commits produces the same objects and plausibly the same pack, whose id collides with the Superseded row. Also, git sends a 0-object pack, whose checksum is a constant, for every tag or branch created at an existing commit, and the design doesn't say whether empty packs are stored. Either way the `INSERT` hits a unique violation and the push fails. If the implementation "revives" the row instead, GC's "second check that no live row has the same id", followed by `DeleteObject`, is check-then-act and can delete a live pack, the same enactor race the design cites (`research/uptime.md#32`).
- **Orphans**: bytes go to S3 before `BEGIN` (:89). Every push that then loses its compare-and-set, is rejected by a rule, or crashes leaves 2-3 objects that no row references, and GC only walks Superseded rows. Milestone 0's benchmark, where half the writers contend on `main`, produces these on purpose.
**Suggestion**: Key packs by a fresh placement id with the checksum as a separate attribute. GC should first commit a `Deleting` state in DSQL that conflicts with any revive or reference, then delete. Sweep objects that no row references after a grace period.

### 9. [warning] Per-cell signing keys break tokens and OIDC when a tenant migrates
**Location**: DESIGN.md:296-301, DESIGN.md:337, DESIGN.md:737, DESIGN.md:176-182, DESIGN.md:781
**Finding**: Stateless `ghs_` tokens (including `GITHUB_TOKEN`) and OIDC tokens are signed by a per-cell key. Migration carries ids, rows and the SSH host key, but no signing keys.
**Evidence** (inferred): After Flip, the target cell can't verify tokens signed by the source cell, and its JWKS under the tenant's issuer (`https://HOST/_services/token`) lacks the old key ids. Renovate, ARC and running jobs get 401s for up to the 1-hour installation-token lifetime, or the job's lifetime, and OIDC exchanges in flight fail. The design advertises at most 30 s of disruption (:759, :781).
**Suggestion**: Use signing keys per tenant that move with the tenant, or have the target cell trust and publish the source cell's current key epochs until they expire.

### 10. [warning] The broker's index on a label-set hash cannot match jobs whose labels are a subset of the runner's
**Location**: DESIGN.md:401, DESIGN.md:436
**Finding**: A job matches a runner when the job's `runs-on` labels are a subset of the runner's labels. An index on `label_set_hash` supports only exact equality.
**Evidence** (inferred): A runner labelled `{self-hosted, linux, x64, gpu}` must find jobs labelled `[self-hosted]`, `[self-hosted, linux]`, and so on. To use this index it must probe all 2^k subsets of its labels on every poll: 256 probes for 8 labels, per runner, with a DSQL poll every 2 s per broker node. "Oldest first" across tenants and label sets then needs a k-way merge. Either self-hosted runners don't match their jobs, or broker reads multiply.
**Suggestion**: Index queued jobs by each individual label, or keep a per-runner-shape match table that is maintained when jobs are queued.

### 11. [warning] The DSQL reconnect limits exceed the cluster's 100 new connections per second
**Location**: DESIGN.md:128, DESIGN.md:641, DESIGN.md:483, DESIGN.md:689
**Finding**: Reconnects queue "at 60 per second per node class" and the limiter is client-side (:128). Managed cells have four node classes (:483), giving 240/s. A client-side limiter can only limit its own node, so the real total is 60 × the node count.
**Evidence** (arithmetic from the research, measured): The cluster accepts 100 new connections per second (`research/uptime.md#27`). After an AZ loss, about 1,333 of the 4,000 connections reconnect at once, and the excess is refused, which feeds retries exactly when the 10% retry budget is under pressure. The hot-swap deploy also starts a new process per node "beside the old one" (:689) that must fill its own pool, which is the same burst on every AZ wave.
**Suggestion**: Set the per-node rate to about 100 divided by the node count in each Region, or coordinate a per-cell token bucket, and ramp new processes' pools slowly during hot swap.

### 12. [warning] A 1,000-byte ref-name cap leaves almost no room under DSQL's 1 KiB key limit
**Location**: DESIGN.md:129, DESIGN.md:205, DESIGN.md:268
**Finding**: The keys are `ref(tenant u32, repo i64, name)` = 4 + 8 + 1,000 = 1,012 bytes, and `ref_log(tenant, repo, name, push_id)` = 1,020 bytes or more. The secondary index on `(tenant, repo, shard)` also carries `name`, so it needs at least 1,013 bytes.
**Evidence** (inferred from `research/uptime.md#27`, "keys are at most 1 KiB"): The margin is 4-12 bytes before any per-column key encoding overhead. A push with a ref name near the cap fails when the `INSERT` commits, after the pack has already been uploaded. The client gets an opaque error instead of the documented ref-name limit.
**Suggestion**: Measure DSQL's key encoding in Milestone 0 and set the cap well below it (for example 900 bytes), or key `ref_log` by a hash of the ref name.
