# Uptime research: AWS mechanisms, AWS outages, GitHub incidents, self-managed upgrades

Research slice for `FRAME.md` quality attributes 1 and 2. Sources were read on 2026-10-23. Scratch copies of every fetched page, the parsed AWS Health Dashboard feed, and the GitHub incident classification (`gh_incidents.json`) are in `/tmp/graftyard-research/uptime/`.

## Answer

AWS's own guidance and its last twelve months of incidents point the same way. Recovery must use only data-plane operations on capacity that already exists. Every request path must avoid control-plane APIs and single-Region global control planes, which for Route 53, IAM, CloudFront and the default STS path live in us-east-1. Blast radius must be bounded by cells, AZ-aligned deploys and shuffle sharding, not by fallback code. The October 2025 us-east-1 event confirmed this. A race in DynamoDB's DNS automation emptied one DNS record, and that cascaded through EC2 lease management, network propagation and NLB health checks for about 14.5 hours. Running EC2 instances were unaffected the whole time. In 2026, war damage made me-south-1 unrecoverable and destroyed mec1-az2, with permanent loss of data kept only there. A region can therefore vanish, and "never lose an acknowledged push" needs a copy outside the region. Three AWS stores now offer RPO zero across regions, each with sharp limits: DynamoDB MRSC (exactly three regions, no transactions, no TTL), Aurora DSQL (3,000 rows, 10 MiB and 5 minutes per transaction, OCC retries) and S3 conditional writes as a CAS primitive. Aurora Global Database failover still loses seconds of data. GitHub's public record from 2023 to 2026 shows a different failure profile. Shared databases, config changes and capacity cause most outages of core git, PR and API surfaces. Dependency failures hit mostly peripheral products. The 2026 incidents came from load growth, coupling through shared auth and user databases, retry storms and failover paths that had never been exercised. GitHub is moving to Azure (58% of platform load by August 2026) and still offers only a 99.9% quarterly SLA. Self-managed GitHub (GHES) still needs maintenance mode for feature upgrades. GitLab offers zero-downtime upgrades only for multi-node Linux-package HA installs, one minor version at a time.

## Findings

### A. AWS guidance

1. Static stability means a system keeps doing everything it did before a dependency failed, even if it stops seeing updates. AWS's stated best practice is to "separate systems along the control and data plane boundary". Source: https://builder.aws.com/content/3K9SiqiJ369TGkkGzqPM95BuYWI/static-stability-using-availability-zones (redirect target of aws.amazon.com/builders-library/static-stability-using-availability-zones/). [doc]
2. The same article rejects "scale up in the surviving AZs" as a recovery plan, because it takes a recovery-time dependency on the EC2 control plane and on config download, discovery registration and credential acquisition. Capacity must be overprovisioned in advance. With three AZs, AWS runs each AZ at no more than 66% of its load-tested level, which is 50% overprovisioning. Source: same URL. [doc]
3. Stateful active-standby systems must have a warm standby in another AZ and must elect a leader from existing standbys, never launch one "just in time". Source: same URL. [doc]
4. When N regional services call each other, a request avoids an impaired AZ with probability (2/3)^N. Zonal-calls-zonal stacks keep it at 2/3, which is why NAT gateway is zonal. EC2 deploys follow a zonal calendar, so two AZs in a Region never receive the same deploy on the same day. Source: same URL. [doc]
5. Amazon "almost never" uses fallback. Fallback is hard to test, can itself fail, often widens the outage, and hides latent bugs for months. The 2001 retail outage happened when every web server's cache failed at once, every server fell back to direct database queries, and the overloaded database stopped fulfillment worldwide. Source: https://builder.aws.com/content/3EuS9Sakq7L3VLQIF3qzfMfke1Y/avoiding-fallback-in-distributed-systems [doc]
6. The approved alternatives to fallback are: make the primary path more reliable; let the caller retry; push data proactively (EC2 IAM role credentials are pushed and stay valid for hours); turn fallback into failover that runs continuously in production; and alarm on retry rates or use constant-work hedging so that retries never become a hidden fallback mode. Source: same URL. [doc]
7. Shuffle sharding gives each tenant a random subset of workers. Route 53 assigns each domain 4 of 2,048 virtual name servers, which yields about 730 billion shards, and guarantees no two domains share more than 2 servers. One tenant's poison request or flood then affects only its own shard. Clients must retry across shard members for this to work. The open-source implementation is Route 53 Infima. Source: https://builder.aws.com/content/3F06NpJ8YeoIGP8VHTw4n81pFn8/workload-isolation-using-shuffle-sharding [doc]
8. A cell is a complete, independent copy of the workload that shares no state with other cells and is selected by a partition key aligned with the service's "grain". A cell router, which AWS calls "the thinnest possible layer", routes requests, and a control plane provisions and migrates cells. Source: https://docs.aws.amazon.com/wellarchitected/latest/reducing-scope-of-impact-with-cell-based-architecture/what-is-a-cell-based-architecture.html (whitepaper published 2023-09-20). [doc]
9. In the cell whitepaper, control planes should be CP (fail rather than serve wrong answers) and data planes should be AP. The recommended router loads cell routes from S3 into memory, so routing keeps working when the control plane, S3 or an AZ is down. Source: .../control-plane-and-data-plane.html (same whitepaper). [doc]
10. More cell rules: keep an override table that can pin any key to any cell; treat the router as the one shared component, and build it cellular and at maximum reliability; size cells by load test and enforce limits with load shedding or token buckets; deploy in waves of cells; start with more than one cell and with a migration mechanism (clone, flip authoritative, redirect, forget) from day one. Source: .../a-warning-for-all-mapping-approaches.html, .../about-resilience-of-the-cell-router.html, .../known-and-respect-your-cells-limit.html, .../cell-migration.html, .../cell-deployment.html, .../best-practices.html [doc]
11. Cells exist to contain load-driven and deploy-driven failures. "They were not designed as failover domains." Survival of an AZ failure by single-AZ cells needs separate replication and DR. Source: .../should-a-single-az-cell-fail-over-in-case-an-az-becomes-unavailable-or-even-in-case-of-gray-failure.html [doc]
12. Well-Architected REL11-BP04 lists these anti-patterns: changing DNS records to re-route traffic, scaling through the control plane to replace impaired components, and multi-API control-plane remediation. It states that Route 53 routing-policy changes use the control plane, which sits in us-east-1 and is outside the Route 53 100% SLA. Source: https://docs.aws.amazon.com/wellarchitected/latest/framework/rel_withstand_component_failures_avoid_control_plane.html [doc]

### B. AWS mechanisms, current status and numbers

13. IAM: the control plane is all public IAM APIs (CreateRole, AttachRolePolicy and similar) and is hosted in us-east-1. The data plane is authentication and authorization in each Region, which keeps working when the control plane is impaired. AWS says a break-glass user must be fully pre-provisioned, never created or granted policies during an incident. Source: https://docs.aws.amazon.com/whitepapers/latest/aws-fault-isolation-boundaries/appendix-a---partitional-service-guidance.html [doc]
14. STS "is a data plane-only service that is separate from IAM". Source: same appendix. Since April 2025, calls to the global endpoint sts.amazonaws.com are served in the caller's Region for default-enabled Regions, though not for opt-in Regions. AWS still recommends explicit Regional endpoints. Sources: https://aws.amazon.com/about-aws/whats-new/2025/04/aws-sts-global-endpoint-requests-locally-regions-default ; https://docs.aws.amazon.com/whitepapers/latest/aws-fault-isolation-boundaries/global-services.html [doc]
15. Route 53: the control plane is every public API (hosted zones, records, health-check CRUD, traffic policies) and is hosted in us-east-1. The data plane is authoritative DNS at more than 200 PoPs plus health checks run from 8 Regions. Health-check-driven routing changes keep working during a control-plane impairment. ChangeResourceRecordSets or weight changes as a failover method are named anti-patterns. Source: .../appendix-b---edge-network-global-service-guidance.html [doc]
16. Control-plane actions in many services depend on the Route 53 control plane in us-east-1. These include creating ELBs, PrivateLink endpoints, API Gateway APIs, ElastiCache, OpenSearch, ECS service discovery and the EKS control plane. S3 CreateBucket and DeleteBucket, and roughly 24 bucket-config PUT and DELETE operations, also depend on us-east-1. AWS says to pre-provision all of these. Source: .../global-services.html [doc]
17. EC2: launching an instance is control plane, covering placement, ENI, EBS, IAM credentials, security groups and propagation. Packet routing and EBS I/O are data plane. The data plane holds locally all the state needed to keep routing during a control-plane impairment. Source: static stability article (finding 1 URL). [doc]
18. KMS: AWS docs separate "cryptographic operations" (Encrypt, Decrypt, GenerateDataKey, ReEncrypt, Sign, Verify and others) from key-management APIs. Each class has independent request quotas. The shared symmetric crypto quota is 10,000/s by default, 20,000/s in some Regions, and 100,000/s in us-east-1, us-west-2 and eu-west-1, counted across the whole account and Region including AWS services calling on your behalf. Sources: https://docs.aws.amazon.com/kms/latest/developerguide/kms-cryptography.html ; https://docs.aws.amazon.com/kms/latest/developerguide/requests-per-second.html [doc]. Treating crypto operations as data plane and CreateKey, PutKeyPolicy and grant management as control plane is my reading. I found no AWS page that uses those words for KMS. [inference]
19. Partitional control planes outside us-east-1 include Route 53 ARC and Global Accelerator in us-west-2, and S3 Multi-Region Access Point control in us-west-2 only. MRAP failover controls are hosted in five Regions and count as data plane. Source: .../global-services.html [doc]
20. ARC zonal shift moves traffic away from one AZ for ALB, NLB (cross-zone on or off), EC2 Auto Scaling groups and EKS. Each shift must carry an expiry of at most 72 hours, which can be extended. A shift does nothing when a load balancer is failing open. AWS recommends starting shifts through the API or CLI ("data plane operations") with pre-stored credentials. Sources: https://docs.aws.amazon.com/r53recovery/latest/dg/arc-zonal-shift.how-it-works.html ; .../arc-zonal-shift.resource-types.html ; .../route53-arc-best-practices.zonal-shifts.html [doc]
21. Zonal autoshift lets AWS shift traffic out of an AZ on its own telemetry. It is meant only for resources "pre-scaled in all Availability Zones", and AWS says "You should not rely on scaling on demand". Practice runs are mandatory and happen about weekly per resource, with blocking alarms and blocked windows. Timeline: zonal shift announced 2022-11-28, GA 2023-01-10; autoshift 2023-11-30; NLB support 2024-10-11; EKS support 2024-10-22. Sources: .../arc-zonal-autoshift.how-it-works.html ; .../arc-zonal-autoshift.how-it-works.start-stop-auto.html ; https://docs.aws.amazon.com/r53recovery/latest/dg/doc-history.html [doc]
22. ARC routing controls are served by a five-Region data-plane cluster. AWS says to hardcode or bookmark all five cluster endpoints and to avoid the console. Source: .../appendix-a---partitional-service-guidance.html [doc]
23. Aurora (PostgreSQL and MySQL) in-Region failover to a replica "is typically restored in less than 60 seconds, and often less than 30 seconds". With no replica, the primary is recreated in "less than 10 minutes". RDS Proxy bypasses DNS caching and cuts Multi-AZ failover time by up to 66%. Source: https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/Concepts.AuroraHighAvailability.html [doc]
24. Aurora Global Database: switchover, previously "managed planned failover", waits for full sync and has RPO 0. Unplanned failover (`--allow-data-loss`) has RPO "typically a non-zero value measured in seconds" and RTO "in the order of minutes". The marketing page claims typical lag under 1 s, RPO 1 s and promotion in under 1 minute. Aurora PostgreSQL can bound RPO with `rds.global_db_rpo` (minimum 20 s), at the cost of stalling commits on the primary. Aurora "attempts to block writes in the old primary Region" during failover but the attempt "is not guaranteed to succeed". Sources: https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/aurora-global-database-disaster-recovery.html ; https://aws.amazon.com/rds/aurora/global-database/ [doc]
25. Both Aurora Global operations are RDS API calls (SwitchoverGlobalCluster, FailoverGlobalCluster), and AWS's own guidance classes those as control plane. Source: finding 24 URL, lines on the API names. [doc] So a regional failover of Aurora depends on the RDS control plane in the surviving Region. [inference]
26. Aurora DSQL reached GA on 2025-05-27. Its SLA is 99.99% single-Region and 99.999% multi-Region. A multi-Region cluster has two read-write Regional endpoints with strong consistency and "zero replication lag on commit", plus a witness Region that stores only the encrypted log and has no endpoint. If the witness is impaired, writes see only slightly higher latency. Sources: https://docs.aws.amazon.com/aurora-dsql/latest/userguide/release-notes.html ; https://docs.aws.amazon.com/aurora-dsql/latest/userguide/disaster-recovery-resiliency.html [doc]
27. DSQL limits as of 2026-10: isolation is fixed at Repeatable Read, using OCC that returns SQLSTATE 40001 (OC000 for data conflicts, OC001 for schema conflicts). DDL and DML need separate transactions, with 1 DDL per transaction. A transaction may modify at most 3,000 rows and 10 MiB and may run for at most 5 minutes. Connections last at most 1 hour, at 100 new connections per second per cluster and 10,000 per cluster. Keys are at most 1 KiB, rows 2 MiB, 24 indexes per table, 1,000 tables, 10 schemas, one database. Temp tables, triggers, PL/pgSQL and TRUNCATE are absent. Collation is C only. Sources: https://docs.aws.amazon.com/aurora-dsql/latest/userguide/CHAP_quotas.html ; .../working-with-postgresql-compatibility-migration-guide.html ; .../working-with-concurrency-control.html [doc]
28. DSQL gaps that older summaries list have closed. Identity columns and sequences arrived 2026-02-13. Foreign keys arrived 2026-08-26, enforced by snapshot checks plus implicit KEY SHARE conflicts at commit. Expression indexes came 2026-08-13, partial indexes 2026-09-15, and CDC reached GA 2026-07-08. Sources: .../release-notes.html ; .../working-with-foreign-key-constraints.html [doc]
29. DynamoDB global tables MRSC reached GA on 2025-06-30. On 2026-09-23 it expanded to 15 Regions and allowed any three of them, including cross-continent sets. An MRSC table must span exactly three Regions, as three replicas or two replicas plus a witness. It must be created from an empty table, and replicas cannot be added or removed later. Writes replicate synchronously to at least one other Region, and RPO is zero. Concurrent cross-Region writes to one item fail with ReplicatedWriteConflictException, which callers can retry. MRSC has no TransactWriteItems or TransactGetItems, no TTL and no LSIs. GSIs are eventually consistent. Sources: https://aws.amazon.com/about-aws/whats-new/2025/06/amazon-dynamo-db-global-tables-multi-region-strong-consistency-generally-available ; https://aws.amazon.com/about-aws/whats-new/2026/09/dynamodb-mrsc-additional-regions/ ; https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/V2globaltables_HowItWorks.html [doc]
30. MREC global tables have RPO equal to replication delay, "usually a few seconds". Transactions in MREC are atomic only in the Region that ran them, and other Regions can observe partial transactions. Source: same HowItWorks URL. [doc]
31. S3 conditional writes: `If-None-Match: *` on PutObject and CompleteMultipartUpload arrived 2024-08-20. `If-Match` (ETag CAS) and bucket-policy enforcement keys `s3:if-match` and `s3:if-none-match` arrived 2024-11-25. Conditional CopyObject and conditional DeleteObject and DeleteObjects in general-purpose buckets arrived 2025-09-16. When writes race, the first to finish wins and the others get 412. A write racing a delete can get 409 (retry PutObject; multipart must restart) or, for If-Match, 404. SigV4 is required. Sources: https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes.html ; https://docs.aws.amazon.com/AmazonS3/latest/userguide/WhatsNew.html [doc]

### C. AWS regional events

32. October 19-20, 2025, us-east-1: the root cause was "a latent race condition in the DynamoDB DNS management system". One of three redundant per-AZ DNS Enactors was delayed. It checked that its plan was newer only once, at the start, then overwrote a newer plan with a much older one. A second Enactor's cleanup then deleted that old plan, which emptied the record for dynamodb.us-east-1.amazonaws.com. The inconsistent state blocked any further automated repair and needed manual intervention. DynamoDB errors ran 23:48 to 02:40 PDT. Source: https://aws.amazon.com/message/101925/ [doc]
33. The dependency chain in the same summary ran as follows. DropletWorkflow Manager, which holds leases on EC2 physical hosts, depends on DynamoDB. Leases timed out. On recovery, lease re-establishment entered "congestive collapse", with no established recovery procedure. Engineers throttled work and restarted DWFM hosts. Network Manager then hit a propagation backlog. New instances launched without network connectivity. The NLB health checker marked those nodes unhealthy, health checks flapped, and automatic AZ DNS failover pulled healthy capacity. Engineers disabled the automatic failover at 09:36. New EC2 launches failed from 02:25 to 10:36, and the event ended at 14:20. Existing EC2 instances "remained healthy and did not experience any impact for the duration of the event". Source: same URL. [doc]
34. Other impact from the same event: STS in us-east-1 had errors from 23:51 to 01:19 and again from 08:31 to 09:59, the second time because of NLB. IAM console sign-in failed. A Redshift defect called an IAM API in us-east-1 to resolve user groups, which broke IAM-credential queries in all Regions. Lambda's SQS poller "failed and did not recover automatically". Support Center failed over as designed but was blocked by invalid responses from an account-metadata subsystem. DynamoDB global table replicas in other Regions stayed writable, with replication lag. Source: same URL. [doc]
35. AWS's remediation list for the event: disable DNS Planner and Enactor worldwide and add protections against applying stale plans; add an NLB "velocity control" that limits how much capacity health-check failover can remove; add scale tests of the DWFM recovery workflow; and rate-limit EC2 propagation by queue size. Source: same URL. [doc]
36. The AWS post-event-summary index lists no 2026 event. Its newest entry is 101925. Source: https://aws.amazon.com/premiumsupport/technology/pes/ (fetched 2026-10-23). [doc] The 2026 facts below come from the public Health Dashboard feeds `https://health.aws.amazon.com/public/currentevents` and `https://history-events-us-west-2-prod.s3.amazonaws.com/historyevents.json`, which are the data behind health.aws.amazon.com. [doc]
37. ME-CENTRAL-1 (UAE), from 2026-03-01: the event began as a "localized power issue" in mec1-az2 and grew to "two of our three Availability Zones (mec1-az2 and mec1-az3) remain significantly impaired". ### D. GitHub availability

40. October 21, 2018: a 43-second partition between US East hub and primary data center let Orchestrator, which runs on Raft, promote US West MySQL primaries across the country. The East side held writes that had never replicated, for example 954 writes on one busy cluster, so failing back would have lost data. GitHub chose to "fail forward". Restoring multi-terabyte backups from remote blob storage took hours, and replica catch-up followed a power-decay curve, not a linear one. The incident lasted 24 h 11 min. About 200,000 webhook payloads outlived an internal TTL and were dropped. The fixes: forbid cross-region primary promotion, build active/active/active N+1 sites, and per-component status. Source: https://github.blog/news-insights/company-news/oct21-post-incident-analysis/ [doc]
41. GitHub published 45 monthly availability reports from January 2023 to September 2026. URL pattern: `https://github.blog/news-insights/company-news/github-availability-report-<month>-<year>/`, cited below as GHAR <month> <year>. Source: GitHub blog WordPress API, posts search "GitHub availability report". [doc]

An LLM classifier assigned each a primary root cause, and I spot-checked about 30 by hand. Config changes, including feature flags, LB, DNS and secrets: 41. Dependency (cloud provider, third party, model provider): 23. Database: 22. Capacity or load: 15. Deploy: 14. Hardware or power: 6. Other: 15. [inference] Data: `/tmp/graftyard-research/uptime/gh_incidents.json`.

None of the 23 dependency incidents was classified as core. Those mostly hit Copilot, Codespaces and Actions hosted runners. [inference] Same data.

### E. Self-managed upgrade downtime

53. GHES high availability (docs version 3.22) is active/passive, with one-way asynchronous replication of git, MySQL, Redis and Elasticsearch to replicas whose application services are stopped. Failover is manual promotion plus DNS (TTL 60 s to 5 min) or an LB change. The docs say explicitly that HA is not a solution for "Zero downtime upgrades". Source: https://docs.github.com/en/enterprise-server@3.22/admin/monitoring-and-managing-your-instance/configuring-high-availability/about-high-availability-configuration [doc]
54. GHES clustering scales horizontally for "tens of thousands of developers". It is sales-gated, needs low latency between nodes, is "not intended for redundancy across geographic locations", and does not support GitHub Packages. Node failure behind the LB is automatic, but the docs warn this "can mask a failure". Sources: .../configuring-clustering/about-clustering ; .../configuring-clustering/differences-between-clustering-and-high-availability-ha (same docs tree). [doc]
55. GHES upgrades: hotpatches (patch releases only) need no maintenance mode but trigger a config run that can cause "a brief period of errors or unresponsiveness". Feature releases need an upgrade package and a maintenance window. Patch packages take "less than five minutes" of downtime. Feature releases with data migrations "may cause a few hours of downtime". In HA, the whole instance stays in maintenance mode until every replica is upgraded, and replication is stopped during the upgrade, so a primary failure in that window loses work. GHES 3.21 added "phased upgrade execution" to isolate the steps that cause downtime. Cluster feature upgrades need a maintenance window during which the cluster is "unavailable for normal use". Sources: .../upgrading-your-instance/preparing-to-upgrade/overview-of-the-upgrade-process ; .../performing-an-upgrade/upgrading-with-an-upgrade-package ; .../configuring-clustering/upgrading-a-cluster (all under docs.github.com/en/enterprise-server@3.22/admin/) [doc]
56. GitLab zero-downtime upgrades apply only to multi-node Linux-package installs. They need an external LB with `/-/readiness` health checks, an internal LB for PgBouncer and Praefect, and HA Consul, Postgres and Redis. Upgrades must go one minor release at a time, with post-deployment migrations, and background migrations must finish between minors. PostgreSQL major upgrades are excluded. The Praefect database has no Linux-package HA, so it needs downtime unless a third-party HA database is used. Components on managed services such as RDS are upgraded separately. GitLab warns that zero downtime is "notably difficult" and "your mileage may vary". Source: https://docs.gitlab.com/update/zero_downtime/ [doc]

## Implications for the design

Each lesson maps to a design rule. All items are [inference].

1. No request-path call to a control-plane API. Banned at request time and in recovery runbooks: IAM CRUD and IAM reads (the Redshift group lookup, finding 34), Route 53 record changes, EC2 RunInstances, ELB, S3 bucket CRUD and bucket config, KMS key management, and RDS failover or switchover APIs. Allowed: STS AssumeRole on a pinned Regional endpoint, KMS crypto operations, and S3, DynamoDB and DSQL data operations. [inference]
2. Credentials and keys are pushed and cached, never fetched per request. STS sessions are refreshed early and are valid for hours. KMS data keys are cached per tenant and per key epoch, so a KMS or STS outage of 2 hours (finding 34) causes no user-visible errors, and normal load stays far below the shared KMS quota (finding 18). [inference]
3. Static N+1 AZ capacity. Every stateless tier runs in three AZs at no more than 66% of its load-tested capacity. Recovery never waits for autoscaling, because autoscaling is the EC2 control plane that failed for 8 hours in October 2025. [inference]
4. AZ evacuation uses zonal shift and autoshift with weekly practice runs on every ALB, NLB, ASG and EKS resource. A practice run that fails blocks deploys. Stateful components (git replicas, databases) need their own AZ-evacuation mechanism, because ARC covers only these four resource types. [inference]
5. Regional evacuation uses only data-plane switches: ARC routing controls with the five cluster endpoints hardcoded, or health checks that read a flag from S3 or DynamoDB. The design never edits DNS records to fail over. [inference]
6. Cells are the unit of blast radius. The partition key is the tenant (org), with large tenants on dedicated cells. The cell router loads its mapping from S3 into memory, keeps serving the last-known mapping if S3 or the control plane is down, keeps an override table, and is itself cellular. Cell migration (clone, flip, redirect, forget) ships in milestone 1, not later. [inference]
7. Shuffle-shard inside each cell for shared fleets (git frontends, pack-serving workers, Actions dispatch queues), so that one repository's pathological push pattern (GHAR June 2023) or one client's tenfold read spike (finding 47) degrades only its own shard. Clients retry across shard members. [inference]
8. No fallback paths. Any secondary path (a second region, a read replica, a cache) carries production traffic continuously or does not exist. Cache-miss load on the primary store is a sized design load, not an emergency mode, which follows from the 2001 Amazon outage and GitHub's 2026 TTL-driven DB overload. [inference]
9. Retry budgets and admission control are mandatory on every internal call. Each call has a fixed deadline, a per-client retry budget, and queue-length-based admission so that a recovering system cannot be pushed into congestive collapse. This covers DWFM, NLB health-check flapping and GitHub's August 2026 retry loop. [inference]
10. Every automated actor that removes capacity (health checks, autoscalers, failover controllers) has a velocity cap, for example at most one AZ or 33% of capacity, and fails open beyond it. This is AWS's NLB fix applied to us. [inference]
11. Every plan or config apply is fenced at write time. Writers use a conditional write on a monotonic version (S3 If-Match, DynamoDB condition, or DSQL row version), never a check at the start and a blind write later. Garbage collection never deletes the currently active generation. This is the DynamoDB Enactor race and applies equally to our ref updates and cell maps. [inference]
12. An acknowledged push survives the loss of a Region. ME-SOUTH-1 and mec1-az2 show that a Region and its data can be lost for good. In managed mode, a push is acknowledged only after the pack is in S3 in at least three AZs and the ref update is committed in a store with RPO zero across Regions (DSQL multi-Region or DynamoDB MRSC), or the SLO must say plainly that cross-Region RPO is non-zero. Aurora Global's seconds of RPO and its control-plane failover rule it out as the ref store under quality attribute 2. [inference]
13. Treat S3 conditional writes as the CAS primitive for objects such as pack manifests and ref snapshots. The 412 and 409 semantics (finding 31) define the retry contract. Multipart uploads must restart on 409. [inference]
14. If DSQL holds metadata (issues, PRs, permissions), every write path must fit 3,000 rows, 10 MiB and 5 minutes, and must retry on 40001. Bulk operations such as repo transfers, org-wide permission changes and large PR synchronizations are chunked into idempotent steps through the outbox. If DynamoDB MRSC holds refs, ref transactions cannot use TransactWriteItems. Atomic multi-ref updates must be one item or a single conditional write on a ref-set version. [inference]
15. The database is the main threat to core surfaces, as GitHub's history shows. Each critical store (auth and session, refs, PR metadata) lives in its own cell-local store with no other tenant of that store. Schema changes are expand and contract, throttled on primary saturation metrics as well as replica lag. 64-bit keys are used everywhere, with overflow alarms at 50%. Every DB call has a deadline shorter than the caller's. [inference]
16. Config is code. Feature flags, LB, DNS, certificates and secrets roll out through the same pipeline as binaries: one cell, then one AZ, then waves, with automatic rollback. Certificate and credential expiry has an alarm at 30 days and a test that fails CI before expiry. [inference]
17. Name resolution must not become a single point of failure. Services cache resolved peer endpoints and keep the last-known-good set if DNS fails. Cell-internal discovery does not depend on a Region-wide DNS plan. [inference]
18. Peripheral subsystems fail soft and stay out of the core path. Git push and fetch, PR review and merge, and the REST and GraphQL write paths never depend synchronously on search, notifications, webhooks, Copilot-like features or Actions. A search outage degrades listings and nothing else (GHAR April 2026). [inference]
19. Merge results are verified before the ref moves. The merge engine checks the invariant that the tree diff equals the expected change set and refuses the update otherwise (the April 2026 merge queue incident). [inference]
20. Exercise failover in production on a schedule. Database leader failover, git replica loss and cell evacuation are drilled weekly in managed mode, because GitHub's March 2026 Redis failover and its 2023 partial-disk failover failed only when production finally triggered them. [inference]
21. The vendor control plane stays off the customer data path in BYOC. BYOC and self-hosted data planes keep serving git, PRs and APIs indefinitely with the vendor control plane unreachable. Cross-account roles are used only for upgrades and telemetry. [inference]
22. Avoid making us-east-1 the home Region for managed cells, or at least for the first cells. When cells do run there, they must not depend on us-east-1-hosted global control planes at runtime. Three us-east-1 events in 12 months (October 2025, May 2026 use1-az4, September 2026 launch deploy) support this. [inference]
23. SLOs must beat GitHub's contract on the same terms. Use GitHub's definition (a minute in which a journey's error rate exceeds 5% counts as down) and set targets above 99.9% quarterly, for example 99.95% for git read and write and 99.9% for PR merge. War and force majeure stay out of the credit definition but stay in the durability design. [inference]
24. Self-hosted and BYOC upgrades never need maintenance mode, which beats GHES (hours of feature-upgrade downtime) and GitLab (multi-node only, one minor at a time). Rules: every release is wire-compatible and schema-compatible with N-1 in both directions; migrations are online and background-only; nodes roll one at a time behind readiness checks; a single-node install upgrades by start-new, drain-old on the same storage; skipping versions is bounded and tested in CI. [inference]
25. Break-glass access is pre-provisioned and statically stable for every mode: stored credentials, no IdP dependency, and Regional SAML endpoints. October 2025 broke console sign-in and Identity Center in us-east-1. [inference]

## Open questions

1. AWS does not use the words control plane and data plane for KMS, so finding 18 is a reading of quota classes. BYOC customers may require customer-managed keys, so the KMS failure model needs confirmation with AWS. [inference]
2. I found no AWS post-event summary for the ME-CENTRAL-1, ME-SOUTH-1 or May 2026 use1-az4 events, so their causes rest on Health Dashboard text and press reports.
3. Neither DynamoDB MRSC nor DSQL publishes commit-latency numbers by Region trio. Push latency (quality attribute 4) under a cross-Region RPO-zero ref store needs a benchmark.
4. Does the ARC zonal shift API depend on any us-east-1 control plane? AWS calls it a data-plane operation, but I found no statement of where it is hosted.
5. The GitHub root-cause counts come from an LLM classifier with a partial hand check. Someone should audit the "other" bucket (15) and the "dependency" bucket before using exact numbers in history/DESIGN.md.
6. GitLab's zero-downtime page covers only the Linux package. I did not verify Helm or Operator behaviour, or the newer Raft-based Gitaly cluster.
7. GHES 3.21 "phased upgrade execution" reduces but does not remove downtime. I did not measure how much downtime it removes.
8. Is GHEC with data residency (GHE.com) on Azure today, and does it carry the same SLA terms? The SLA PDF covers it, but I did not confirm its hosting.
