# Git storage research: prior art, git features, Rust ecosystem, AWS options

Slice owner: GitStorage. Research date 2026-10-23. Scratch files live under /tmp/graftyard-research/git-storage/.

## Answer

Every large host that tried shared network filesystems for live repositories moved off them. GitHub left DRBD and NFS for Spokes. Bitbucket Data Center built Mesh to replace NFS. GitLab does not support NFS or cloud filesystems for Gitaly. The design that dominated for a decade keeps full bare repositories on local SSD and replicates at the git level. It serializes the ref update across a quorum and relies on git's ref transactions to vote. GitHub runs this as Spokes, Bitbucket as Mesh, and Google's Gerrit hosting writes to a majority of cells. GitLab's Praefect is weaker. It uses a primary with a Postgres tracking database, its documented RPO is under one minute, and GitLab has abandoned its Raft and write-ahead-log successor. Since August 2026 a second family has production evidence. Cursor's Continuity makes a write-ahead log in S3 the source of truth, uses an S3 compare-and-swap on a small index object as the linearization point, and treats every local repository as a cache. GitHub is now adding Azure Blob Storage as a quorum member, a "virtual replica", and is moving from per-repository to per-reference serialization. On AWS, S3 Standard with conditional writes (If-None-Match GA 2024-08-20, If-Match GA 2024-11-25) supports the object-store family. It gives regional, multi-AZ durability for every acknowledged push and has no replica routing database. Upstream git stays the engine for pack generation, bitmaps, MIDX, and repacking. gitoxide v0.61.0 still lacks server plumbing, delta compression in pack encoding, bitmap files, push, and reftable. libgit2 has no server either. A Rust service should own orchestration, receive-pack ingest, auth, and the log, and should shell out to git for the heavy object work.

## Findings

### Prior art: GitHub Spokes (formerly DGit)

1. DGit stores three replicas of each repository on fast local SSDs and replicates using git's own protocols. GitHub moved off RAID plus DRBD pairs with manual failover. https://github.blog/engineering/architecture-optimization/introducing-dgit/ [doc]
2. Spokes accepts a write only if a strict majority of replicas, and always at least two, apply it with the same result. Each write takes an exclusive lock on a majority, so Spokes treats every write as an election and has no primary. Replicas on the losing side are marked unhealthy and repaired automatically. Racks serve as availability zones for placement. https://github.blog/engineering/infrastructure/building-resilience-in-spokes/ [doc]
3. Spokes detects failures from live traffic: three consecutive failed requests mark a node offline for reads, and heartbeats only clear that mark. Detection runs MxN, from each app server to each file server. Repair after a server loss copies N-to-N from surviving replicas. Planned reboots first quiesce long-running clones. Same URL as finding 2. [doc]
4. Spokes uses three-phase commit plus replicas acting as a distributed lock, which costs four round trips per update. A reference update takes about a third of a second. The "Spokes checksum" is the XOR of hash(refname, value) over all refs, it is updated incrementally, and replicas compare it after every update. GitHub contributed git ref transactions (`git update-ref --stdin`) upstream so that outcomes are deterministic across replicas. https://github.blog/engineering/infrastructure/stretching-spokes/ [doc]
5. In 2026 Spokes keeps five replicas by default on local disks, and every replica participates in every write, so adding read replicas slows writes. GitHub reports pushes up 4.9x year over year to 3.35 billion per month, and up to 35x write throughput from its new architecture in internal benchmarks. https://github.blog/engineering/architecture-optimization/building-git-infrastructure-for-agent-scale-development/ (2026-10-06) [doc]
6. On 2026-10-21 GitHub said 99.99999% of repositories have replicas in Azure. The quorum waits for every healthy replica up to a timeout and holds a repository-wide lock per write, so the slowest replica sets throughput. GitHub is changing quorum scope to individual references, which gave 3 to 4x throughput in testing. It is adding Azure Blob Storage as a "virtual replica" quorum member, so a write is not acknowledged until it is durable in object storage, and read replicas warm from blob storage without joining the quorum. Spokes also includes "sweepers" for placement, repair, and rebalancing. https://github.blog/engineering/architecture-optimization/the-bridge-to-agent-scale-git-infrastructure/ [doc]
7. GitHub says its end-state design, which still has "a (small) consensus group", will be published at GitHub Universe the week after 2026-10-21. It was not available on 2026-10-23. Same URL as finding 6. [doc]

### Prior art: GitLab Gitaly and Praefect

8. Praefect strong consistency hooks git's reference-transaction hook (git 2.28). Gitaly runs `git receive-pack`, the hook sends the queued ref updates to Praefect, Praefect collects votes from every node, and it replies commit or abort. Votes are a hash of the queued updates. Thresholds lie in [ceil((total+1)/2), total]. The strategies are strong, allowed-failures, primary-wins, and primary-mandatory, and the doc says Praefect uses "Strong". A failed vote schedules replication jobs, and if no up-to-date source exists the cluster goes read-only. gitlab-org/gitaly master doc/design_ha.md lines 351-388, 420-438, 468-515 (https://gitlab.com/gitlab-org/gitaly/-/raw/master/doc/design_ha.md) [source]
9. GitLab's current docs (19.6) state RPO under 1 minute because "writes are replicated asynchronously" to a newly promoted primary. Failover takes ten consecutive failed one-second health checks, giving an RTO under 10 seconds. Strong consistency covers only healthy, up-to-date replicas, outdated ones receive asynchronous replication jobs, and a subset of operations still uses eventual replication. https://docs.gitlab.com/administration/gitaly/praefect/ [doc]
10. Praefect keeps cluster metadata in PostgreSQL and uses it for atomic repository create, delete, and move. Replica paths derive from a Postgres sequence ID. Snapshot backups are not supported because the database and the disks diverge. A documented race lets PostReceiveHook fire before replication, so CI can fail with "couldn't find remote ref". Praefect requires latency under 1 second, ideally single-digit milliseconds, so it is a single-site system. Gitaly Cluster on Kubernetes is beta (19.1) and on ECS is unsupported. Same URL as finding 9. [doc]
11. GitLab's transaction-management design (WAL, MVCC snapshots via hard links, per-partition Raft) is now "rejected". The handbook says the Gitaly-Cluster-without-Praefect direction "has been dropped" and that the code is being removed. Epic 23151 tracks removing the Raft, WAL, and transaction code: MR !8909 (Raft service part 1) is merged and !8895 (365 files) is being split. https://handbook.gitlab.com/handbook/engineering/architecture/design-documents/gitaly_transaction_management/ and https://gitlab.com/groups/gitlab-org/-/epics/23151 [doc]
12. That design doc lists the ACID gaps in plain Gitaly: refs update one at a time, quarantine migration ignores object dependencies, crashes leave stale locks, and fsyncs were missing. Same handbook URL as finding 11. [doc]
13. GitLab supports only local storage for Gitaly and Gitaly Cluster, and says "NFS cannot be used for repository storage". It strongly recommends against EFS, Google Filestore, and Azure Files, because "many small files are written in a serialized manner", and against CephFS and GlusterFS. It cites a "refs not found after a push" bug caused by NFS dentry caching. gitlab-org/gitlab master doc/administration/gitaly/_index.md lines 97-98 and doc/administration/nfs.md lines 24, 196-201, 320-345 [source]

### Prior art: Google JGit DFS, Gerrit, and reftable

14. JGit's DFS layer is abstract. `DfsObjDatabase` requires `commitPackImpl`, `rollbackPack`, `listPacks`, `openFile`, and `writeFile`, and packs become visible when committed (pack written first, then index). `DfsRefDatabase` requires `compareAndPut` and `compareAndRemove`. `DfsReftableDatabase` stores refs as reftables inside the DFS and suggests using `getMaxUpdateIndex()` as a primary key so "one wins, and one will fail". eclipse-jgit/jgit master c2316e2d, org.eclipse.jgit/src/org/eclipse/jgit/internal/storage/dfs/DfsObjDatabase.java lines 431-513, DfsRefDatabase.java lines 274-311, DfsReftableDatabase.java lines 37-48 [source]
15. In 2017 Shawn Pearce wrote that Google was moving its DFS ref storage to reftable because its internal database could not hold huge ref counts (866k). He also noted that readers see multi-ref batches atomically. https://www.eclipse.org/lists/jgit-dev/msg03389.html [doc]
16. Google's Gerrit hosting runs JGit on "filesystem and BigTable". A push or review write reaches a majority of cells before it is acknowledged, and the rest catch up in the long tail. Five data centers on three continents serve it. A lagging data center is drained at the L1 load balancer. https://gitenterprise.me/2017/10/10/gerrit-user-summit-gerrit-at-google/ (transcript of a Google talk) [secondary]
17. Cursor's blog (author Vicent Martí, who calls Pearce his former mentor) says Pearce's earlier object-per-key DHT design for JGit worked for normal operations, but clone performance was bad enough to discard it, because the protocol needs packfiles. https://cursor.com/blog/git-at-any-scale [secondary]
18. The reftable spec targets near-constant-time single-ref lookup, atomic pushes in O(size_of_update), and combined reflogs. Packed-refs for android (866k refs) is 62 MB, and a two-ref update rewrites all of it. Writers lock `tables.list.lock`, append a new table, and rename. Compaction runs independently of updates. git master 7e34d817, Documentation/technical/reftable.adoc lines 10-36, 884-997 [source]

### Prior art: Meta Mononoke

19. Mononoke is Rust. Servers are stateless. Immutable data (file contents, Bonsai changesets, derived data including git trees and commits) lives in a blobstore, and bookmarks, VCS mappings, the commit graph index, and the bookmark update log live in MySQL (SQLite for dev). "multiplexedblob" writes to multiple independent blobstores and a healer job reconciles them. A land service serializes writes to public bookmarks. facebook/sapling main debac660, eden/mononoke/docs/1.3-architecture-overview.md lines 13, 44-57, 375-426 [source]
20. Mononoke has a git smart-HTTP server (`servers/git/git_server/`) that supports clone, fetch, push, and ls-remote. Push converts git commits to Bonsai. Delta manifests precompute delta bases for pack generation, and bundle-uri bundles are precomputed. eden/mononoke/docs/5.1-git-support.md lines 16-46, 120-132, 207-228 at the same commit [source]
21. The open-source build includes MySQL, SQLite, file, and S3 backends. It omits Thrift APIs, MySQL failover, and CacheLib, and is labeled "still in development". eden/mononoke/README.md lines 1-25 [source]. Whether Meta serves external git clients from Mononoke in production could not be verified.

### Prior art: Azure Repos, Bitbucket, CodeCommit, Gitea, Forgejo, Anthropic

22. Cursor's blog states that Azure DevOps stores packfiles in blob storage and references in SQL Server. Microsoft documentation describing Azure Repos' storage backend could not be found. https://cursor.com/blog/git-at-any-scale [secondary]
23. Bitbucket Data Center Mesh replicates repositories (as partitions) to at least three nodes. Writes need a quorum of floor(n/2)+1 consistent replicas, and inconsistent replicas do not count. Reads need one consistent replica. The core app is the control plane that tracks replica state, and repair resyncs lagging replicas. Multi-AZ deployments require round trips under 5 ms and AZ-aware placement, and three replicas in two AZs is called nonredundant. Atlassian says NFS is 10 to 1000 times slower per I/O and still requires a shared NFS for other data, where EFS is allowed. https://confluence.atlassian.com/bitbucketserver103/bitbucket-mesh-whitepaper-1822722174.html [doc]
24. Bitbucket Cloud's repository storage design is not public. I found no primary source.
25. AWS stopped onboarding new CodeCommit customers on 2024-07-25. On 2025-11-24 it reversed course: "CodeCommit is returning to full General Availability, effective immediately". The doc history records that it is available to new customers from 2025-11-25, in 29 regions, with Git LFS on the roadmap for Q1 2026. https://aws.amazon.com/blogs/devops/aws-codecommit-returns-to-general-availability/ and https://docs.aws.amazon.com/codecommit/latest/userguide/history.html [doc]. The CodeCommit doc history showed no LFS entry on 2026-10-23, so LFS shipment is unverified.
26. AWS says CodeCommit "is built on highly scalable, redundant, and durable AWS services such as Amazon S3 and Amazon DynamoDB". https://aws.amazon.com/codecommit/faqs/ [doc]. AWS has not published the internal layout.
27. Gitea Enterprise HA requires git repository storage on "a POSIX volume (NFS/Gluster/NetApp) mounted at the same path on every node", plus Redis for locks and queues. https://docs.gitea.com/enterprise/22/installation/high-availability [doc]. Forgejo's storage settings let attachments, LFS, avatars, archives, and packages use S3, but git repositories are not among them. https://forgejo.org/docs/latest/admin/setup/storage/ [doc]
28. Anthropic replaced git for its monorepo with Scion (2026-10-13). Changesets point to content-addressed blobs, a ref move is a compare-and-swap on one Spanner row, and the design credits Mononoke's Bonsai model. Scion is not git wire compatible for its own clients. https://www.anthropic.com/engineering/redesigning-source-control [doc]

### Prior art: object-store write-ahead log (Cursor Continuity, walgit)

29. Cursor's Continuity stores each push as a WAL entry in S3 and acknowledges only after the push is persisted. A push becomes visible when its ref transaction is prepared on a local repository and a pointer is CAS-written into a WAL index object, which linearizes pushes. Any node may accept a push, with rendezvous hashing picking a preferred primary. Reads do a conditional GET on the index ETag, and Cursor says a 304 takes under 10 ms on average. Gossip over UDP is only a hint. Only the primary compacts, and replicas download compacted packs. Idle repos are evicted from disk and rematerialized from the WAL. https://cursor.com/blog/git-at-any-scale (2026-08-18) [doc]
30. Cursor reports up to 120 pushes/s on S3 Standard and over 300 pushes/s on S3 Express One Zone for its monorepo, with push batching to avoid one S3 write per push. Read throughput scaled linearly in tests up to 100 replicas. Local copies are normal git repositories on NVMe. Same URL. [doc]
31. walgit (Rust, created 2026-08-23, not a production service) implements the Continuity shape. Its layout is `manifest.pb` (the CAS linearization point), immutable `log/<seq>.pb`, content-addressed `wal/<checksum>.pack|.idx|.bitmap|.commit-graph`, checkpoints, and TTL leases. On a 412 it re-validates each ref's old value and retries. It group-commits concurrent pushes into one CAS. Upstream git does upload-pack and repack, and walgit does receive-pack. github.com/tobi/walgit at 80e9a20b, README.md "How it works" and "Invariants" [source]

### AWS storage options

50. EBS gp3: 99.8 to 99.9% annual durability (0.1 to 0.2% AFR), up to 64 TiB, 80,000 IOPS, and 2,000 MiB/s. io2 Block Express: 99.999% durability, up to 256,000 IOPS, 4,000 MiB/s, average latency under 500 microseconds for 16 KiB I/O, and multi-attach. https://docs.aws.amazon.com/ebs/latest/userguide/ebs-volume-types.html [doc]. An EBS volume attaches only to instances in its own AZ. https://docs.aws.amazon.com/ebs/latest/userguide/ebs-volumes.html [doc]
51. Instance-store data persists across reboot but not across stop, hibernate, terminate, or failure of the underlying disk. https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/instance-store-lifetime.html [doc]. I8g (Graviton4, third-generation Nitro SSD) offers up to 45 TB, and I8ge up to 120 TB. AWS claims 50% lower I/O latency than I4g. https://aws.amazon.com/ec2/instance-types/i8g/ [doc]. I7i and I7ie use third-generation Nitro SSD with fifth-generation Xeon. https://aws.amazon.com/ec2/instance-types/i7i [doc]. I did not re-read I4i and I7ie maximum capacities from primary sources.
52. EFS Regional stores data across multiple AZs, and One Zone stores it in a single AZ. Best-case latency is about 1 ms for reads and 2.7 ms for writes. https://docs.aws.amazon.com/efs/latest/ug/performance.html and https://docs.aws.amazon.com/efs/latest/ug/features.html [doc]. A git ref listing can need about 5,000 I/Os (Bitbucket example, finding 23), so a millisecond per I/O becomes seconds. [inference]
53. FSx for OpenZFS Multi-AZ uses an HA pair across two AZs with a floating IP. It fails over on AZ disruption, typically in under 60 seconds. https://docs.aws.amazon.com/fsx/latest/OpenZFSGuide/availability-durability.md [doc]. FSx for ONTAP Multi-AZ replicates writes synchronously to a standby in another AZ, and failover typically completes in under 60 seconds. https://docs.aws.amazon.com/fsx/latest/ONTAPGuide/high-availability-AZ.html [doc]. Both are NFS from git's point of view, so the GitLab warnings in finding 13 apply. [inference]
54. S3 Standard: 99.999999999% durability, 99.99% designed availability, data in at least three AZs. Strong read-after-write consistency since 2020. Updates to one key are atomic, there are no atomic multi-key updates, and without conditions the latest timestamp wins. At least 3,500 writes and 5,500 reads per second per partitioned prefix. https://docs.aws.amazon.com/AmazonS3/latest/userguide/storage-class-intro.html, https://docs.aws.amazon.com/AmazonS3/latest/userguide/Welcome.html, https://docs.aws.amazon.com/AmazonS3/latest/userguide/optimizing-performance.html [doc]
55. S3 conditional writes: If-None-Match (create only if absent) went GA on 2024-08-20 for PutObject and CompleteMultipartUpload "in both general purpose and directory buckets". If-Match (ETag compare-and-swap) went GA on 2024-11-25, also for both bucket types. Failures return 412 Precondition Failed or 409 Conflict. Bucket policies can enforce conditional writes. https://aws.amazon.com/about-aws/whats-new/2024/08/amazon-s3-conditional-writes/, https://aws.amazon.com/about-aws/whats-new/2024/11/amazon-s3-functionality-conditional-writes/, https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes.html [doc]
56. S3 Express One Zone uses directory buckets in one chosen AZ. It offers single-digit millisecond latency, up to 10x faster than Standard, with 99.95% availability and 11 nines of durability within that AZ. It "doesn't store data redundantly across Availability Zones". https://docs.aws.amazon.com/AmazonS3/latest/userguide/directory-bucket-high-performance.html and the storage-class table URL in finding 54 [doc]
57. S3 Express One Zone supports appends (2024-11-21). An append uses `x-amz-write-offset-bytes` equal to the current size, with up to 10,000 parts per object, after which it returns TooManyParts. RenameObject is atomic within a directory bucket (2025-06-18). https://docs.aws.amazon.com/AmazonS3/latest/userguide/directory-buckets-objects-append.html, https://aws.amazon.com/about-aws/whats-new/2024/11/amazon-s3-express-one-zone-append-data-object/, https://aws.amazon.com/about-aws/whats-new/2025/06/amazon-s3-express-one-zone-atomic-renaming-objects-api/ [doc]
58. I found no current AWS document that gives S3 Standard first-byte latency as a number. The "up to 10x" Express claim implies tens of milliseconds for Standard. [inference]

## Implications for the design

1. [inference] Rule out EFS, FSx, and any NFS mount as the live repository store in all three modes. Each major host abandoned shared filesystems (findings 1, 13, 23, 27), and FSx Multi-AZ does not fix git's small-file I/O pattern.
2. [inference] Two structurally distinct storage cores are viable, and they suit the P5 alternatives requirement. (A) A Spokes or Mesh quorum of three replicas across three AZs on local NVMe or EBS, voting on ref transactions through the reference-transaction hook, plus a placement database and sweepers. (B) A per-repository write-ahead log in S3 Standard, with an If-Match CAS on a small manifest as the commit point and every local repository a cache, as in Continuity and walgit. GitHub's 2026 move toward object storage plus per-ref ordering (finding 6) points toward B.
3. [inference] Option B fits the stated priorities for an AWS-native product. An acknowledged push is in S3 Standard, so it survives an AZ loss (priority 2). Losing a node or an AZ is a cache miss, not a quorum loss (priority 1). The one artifact needs only S3 in managed, BYOC, and self-hosted modes, with no replica-routing database to run (priority 5).
4. [inference] Option B's write ceiling is one CAS chain per repository: about 120 pushes/s on Standard (finding 30), shared by user pushes and bookmark refs such as PR merge refs (finding 4). The design needs group commit, per-ref validation on 412 retry (finding 31), and bot ref updates kept off the user-facing path, coalesced and lower priority (finding 4).
5. [inference] Do not make S3 Express One Zone the only durable copy of an acknowledged push. It is single-AZ (finding 56), which violates "never lose an acknowledged push" when an AZ is lost. It can work as a low-latency cache or log tier only if each write also lands in S3 Standard before the acknowledgment, which brings back Standard latency.
6. [inference] A regional S3 outage stops writes under option B, and cross-region replication of the log is asynchronous, so cross-region RPO is above zero. Option A is no different within a region, and GitHub's 25 ms cross-region quorum shows the cost of making it synchronous (finding 6). Region failure belongs in the uptime design as a separate decision.
7. [inference] Avoid Praefect's model: an async primary with a Postgres tracking database. Its documented RPO of under one minute contradicts priority 2 (finding 9), and GitLab could not retrofit a WAL and Raft successor (finding 11).
8. [inference] Keep upstream git (2.45 or later, ideally 2.54 or later) as the object engine for upload-pack, pack-objects with bitmaps and MIDX bitmaps, index-pack, geometric repack, cruft packs, and fsck. gitoxide lacks delta compression, bitmaps, server plumbing, push, and reftable (findings 44-47). Rust owns HTTP and SSH framing, auth, receive-pack orchestration, the log and manifest, placement, and maintenance scheduling. gix can read objects, revwalk, and parse the protocol client-side.
9. [inference] Make the manifest or log the authoritative ref store and materialize packed-refs or reftable locally. That puts ref atomicity under Graftyard's control instead of per-disk lock files, and it sidesteps gix's missing reftable support. The type sketch for ref transactions (P4) should carry, per ref, the expected old value, the new value, and a sequence number.
10. [inference] Run maintenance once per repository under a lease, publish the result into the log, and have replicas download compacted packs (findings 29, 31). Spokes found repacking on every replica a failover risk.
11. [inference] For CI fan-out, serve clone bytes from S3 or CloudFront through bundle-uri (git 2.38+) and packfile URIs (2.28+). Client support for the server-advertised forms depends on client git version, so the conformance oracle should pin the git clients that must pass.
12. [inference] For caches, use instance-store NVMe (I8g, I7ie) in managed mode and gp3 in small self-hosted installs. Durability lives in S3, and instance-store loss on stop (finding 51) is tolerable only because of that.

## Open questions

1. GitHub's end-state architecture post (due around 2026-10-28) was not out. It may define per-ref ordering on object storage more precisely.
2. Microsoft has not documented Azure Repos storage, so the one source (Cursor) is secondary. Bitbucket Cloud's storage is undocumented.
3. AWS documents no sustained If-Match CAS rate or latency distribution for a single hot key in S3 Standard or Express. Per-repository push throughput should be benchmarked in this account.
4. Whether conditional headers combine with Express appends or RenameObject is not stated in the docs I read.
5. Whether Meta serves external git clients from Mononoke in production, and Cursor Continuity's implementation language, are unverified.
6. Whether CodeCommit shipped Git LFS in 2026 is unverified.
7. Git 3.0 timing, and when common clients default to SHA-256 and reftable, will affect the compatibility tier for SHA-256 repositories.
