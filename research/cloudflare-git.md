# Research: a git host on Cloudflare only

Grounding for a Cloudflare-only Graftyard. Docs were fetched as Markdown (`<page>/index.md`) on 2026-10-26 into `/tmp/graftyard-cf/`. blog.cloudflare.com answered `curl` and the reader with a bot challenge or HTTP 429, so the Artifacts launch post was read from a verbatim GitHub mirror and is cited by its blog URL with that note. Labels: [doc] official Cloudflare page, [secondary] anything else, [measured] I ran it, [inference] my reasoning.

## Answer

Cloudflare now ships its own git server. Artifacts (open beta 2026-10-01) is a smart-HTTP git service built as a Zig-to-WASM engine inside one Durable Object per repository. New repositories are capped at 1 GB, receive-pack is protocol v1 only (which no unmodified client notices, since git has no v2 push), and `filter` is documented as unsupported among v1 capabilities, with v2 undocumented (`research/artifacts-recheck.md`, 2026-10-26). No WASM git library can serve git with delta compression or bitmaps. Every Workers-native server, Cloudflare's included, gets around that by storing the client's deltas instead of computing them. Upstream git runs in Containers (Firecracker microVMs, at most 4 vCPU, 12 GiB, and 20 GB of ephemeral disk), but disk does not survive sleep. Inbound bytes pass through a Worker whose request body limit is 100 MB on Free and Pro, 200 MB on Business, and up to 5 GB on Enterprise. Public SSH needs Spectrum, and Spectrum can only reach an IP origin, never a Worker. "Cloudflare Basin" is real. It is the October 2026 rename of the analytics stack and is not a git or transactional store.

## Findings

### Cloudflare Basin
1. Basin exists and went GA on 2026-10-01: "Basin, formerly the Cloudflare Data Platform, is now generally available." It is Basin Pipelines (formerly Pipelines), Basin Catalog ("formerly R2 Data Catalog, manages ... Apache Iceberg tables"), and Basin SQL ("formerly R2 SQL, is a serverless, distributed SQL engine for querying large Apache Iceberg tables"). https://developers.cloudflare.com/changelog/post/2026-10-01-basin-ga/ [doc]
2. Basin is an analytics platform ("an end-to-end analytics platform ... then query it to answer analytical questions"), the same changelog [doc]. The closest real products for git state are Durable Objects with SQLite, R2, D1, and Artifacts (findings 3 to 9) [inference].

### Prior art: git servers on Workers, Durable Objects, and Containers
3. Cloudflare Artifacts: "Cloudflare Artifacts allows developers to store and version files, code, and projects behind a Git-compatible interface" and it "requires a Workers Paid plan." https://developers.cloudflare.com/artifacts/ [doc]. Open beta on 2026-10-01, with billing from 2026-10-14. https://developers.cloudflare.com/artifacts/platform/changelog/ [doc]
4. Artifacts engine: "The entire git protocol engine is written in pure Zig (no libc), compiled to a ~100KB WASM binary ... It implements SHA-1, zlib inflate/deflate, delta encoding/decoding, pack parsing, and the full git smart HTTP protocol." "Files are stored in the underlying Durable Object's SQLite database", "large Git objects are chunked and stored across multiple rows", and R2 holds snapshots while KV holds auth tokens. "We avoid calculating our own git deltas, instead, the raw deltas and base hashes are persisted alongside the resolved object." It supports "ls-refs, shallow clones (deepen, deepen-since, deepen-relative), and incremental fetch with have/want negotiation" and git-notes. https://blog.cloudflare.com/artifacts-git-for-agents-beta/ (2026-04-16, read via the mirror github.com/zeke/agents-week-fomo/blob/main/data/blogs/2026-04-16-artifacts-git-for-agents-beta.md) [doc]
5. Artifacts wire support: upload-pack v1 and v2. Receive-pack is v1 only ("Artifacts does not support v2 receive-pack"). "Some optional v1 capabilities, such as `filter` and `include-tag`, are not supported." The remote is `https://<ACCOUNT_ID>.artifacts.cloudflare.net/git/<namespace>/<repo>.git`, and tokens are repo-scoped `read` or `write`. https://developers.cloudflare.com/artifacts/api/git-protocol/ [doc]
6. Artifacts limits: "Maximum storage per repository: 1 GB for repos created on or after 2026-09-29. Repos created earlier have a 10 GB limit." "Git request rate, per artifact: 2,000 requests per 10 seconds." Storage per account is 1 TB, raisable. https://developers.cloudflare.com/artifacts/platform/limits/ [doc]
7. Artifacts durability: "Cloudflare replicates repo data synchronously across multiple data centers and copies it asynchronously to object storage and snapshots." https://developers.cloudflare.com/artifacts/concepts/how-artifacts-works/ [doc]. Price: "$0.15 per additional 1,000 operations" after 10,000, and "$0.50 per additional GB-mo" after 1 GB. https://developers.cloudflare.com/artifacts/platform/pricing/ [doc]. Cloudflare ran a contest "to see who can build the next GitHub on Cloudflare using Workers and Artifacts", with entries open until 2026-10-14 (changelog above) [doc].
8. git-on-cloudflare (zllovesuki, MIT, created 2025-09-07 per the GitHub API, self-described "vibe-coded"): "A Git Smart HTTP v2 server running entirely on Cloudflare Workers — no VMs, no containers, just Durable Objects and R2", with DO refs, packs in R2, "Streaming receive writes packs directly to R2 with atomic metadata commit", and "queue-driven compaction". Its claimed "10-50 MB/s" clone speed is unverified. https://github.com/zllovesuki/git-on-cloudflare [secondary]
9. dgit / `durable-git` (littledivy, MIT, created 2026-08-18): "Each repository is a Durable Object" holding objects and refs in SQLite, with pack bytes optionally in R2. A push "is stored as the packfile the client sent ... so the client's compression is preserved rather than re-derived", and a full clone is cached in R2. Its README admits the ceiling: "A Workers request is bounded at 128MB of memory and five minutes of CPU, so a very large history lands as a series of smaller pushes", and a full clone of millions of objects "can exceed the CPU bound the first time". https://github.com/littledivy/durable-git [secondary]
10. R2G2 (r2g2.dev) describes itself only as "An edge-native Git forge, built end-to-end on Cloudflare". I could not read more (client-rendered page) [secondary]. I found no Cloudflare example of upstream `git` serving a remote from Containers. Artifacts' Sandbox example points the other way, with a sandbox acting as a client. https://developers.cloudflare.com/artifacts/llms.txt [doc]

### WASM git libraries, cross-checked with `research/git-storage.md` findings 44 to 49
11. gitoxide (v0.61.0, 2026-10-22) has no server plumbing, no delta compression on write, no bitmap file, and no reftable (`git-storage.md` findings 44 to 47). Nothing I found changes that.
12. libgit2 transports are client-side (finding 48). wasm-git is "a port of libgit2 to WebAssembly, not a new git library" used through the `lg2` CLI for clone and push as a client. https://github.com/petersalomonsen/wasm-git [secondary]
13. isomorphic-git (`main`, read 2026-10-26): `src/commands/pack.js` writes each object whole (deflate of the full object, no delta) and pushes chunks into an in-memory array. `src/commands/uploadPack.js` only builds the ref advertisement, and it is not in `src/api/`. There is no receive-pack server. [measured, read source]. Artifacts documents it as a client in Workers ("Push commits to Artifacts repos from Workers"). https://developers.cloudflare.com/artifacts/llms.txt [doc]
14. Every Workers-native server above (Artifacts, git-on-cloudflare, dgit) serves stored client deltas or whole objects. None computes new deltas, and none mentions bitmaps (findings 4, 8, 9) [inference]. This matches finding 49, which says production hosts run upstream git or JGit. The Artifacts Zig engine is not open source. Only ArtifactFS was released (https://github.com/cloudflare/artifact-fs, Apache-2.0) [doc, plus my GitHub API check].
15. Hard Worker and DO bounds for an in-isolate server: "Each isolate can consume up to 128 MB of memory, including the JavaScript heap and WebAssembly allocations." CPU time is "5 min (default: 30 seconds)" on Paid. https://developers.cloudflare.com/workers/platform/limits/ [doc]. SQLite DO: "Storage per Durable Object 10 GB", "Maximum string, BLOB or table row size 2 MB", and "An individual Object has a soft limit of 1,000 requests per second." https://developers.cloudflare.com/durable-objects/platform/limits/ [doc]

### Upstream git in Cloudflare Containers
16. Instance types run from `lite` (1/16 vCPU, 256 MiB, 2 GB disk) to `standard-4` (4 vCPU, 12 GiB, 20 GB). Custom types max out at "4" vCPU, "12 GiB", and "20 GB" disk. "Image size: Same as instance disk space". "Total image storage per account: 50 GB". Account concurrency is "6 TiB" memory, "1,500" vCPU, and "30 TB" disk, all "defaults and can be increased." https://developers.cloudflare.com/containers/platform/limits/ [doc]
17. Runtime and lifecycle: "Each container instance runs in a Firecracker microVM with its own kernel and network." "Container cold starts can often be in the 1-3 second range, but this is dependent on image size." "All disk is ephemeral by default. When a Container instance goes to sleep, the next time it starts, it uses a fresh disk from the container image." Stop is `SIGTERM`, then up to 15 minutes, then `SIGKILL`. https://developers.cloudflare.com/containers/concepts/architecture/ [doc]. "A host server restart happens on an irregular cadence. Cloudflare does not guarantee that any container instance will run for a set period." "Containers do not use swap memory." https://developers.cloudflare.com/containers/faq/ [doc]
18. Persistence options: snapshots (`durable_object` policy only) have a "Maximum snapshot size 20 GB" and "30 days" retention, and they capture the filesystem but "not its memory or running processes." https://developers.cloudflare.com/containers/guides/snapshots/ [doc]. R2 can be mounted with FUSE, "though you should not expect native SSD-like performance". (FAQ above) [doc]
19. Image size: `alpine/git:latest` for amd64 is 37,472,241 bytes compressed (Docker Hub API, updated 2026-10-25) [measured]. Images must be `linux/amd64` (architecture page) [doc].
20. Price on Workers Paid: "$0.0000025 per additional GiB-second" of memory, "$0.000020 per additional vCPU-second" of CPU, and "$0.00000007 per additional GB-second" of disk. Memory and disk bill on provisioned size, CPU on active use. Egress is "$0.025" per GB in North America and Europe after 1 TB. https://developers.cloudflare.com/containers/platform/pricing/ [doc]. A `standard-4` running flat out costs about $0.108 for memory, $0.288 for CPU, and $0.005 for disk per hour, so about $0.40 an hour or $290 a month [inference, arithmetic].
21. Reaching the container: a DO calls `ctx.container.getTcpPort(port)`, which returns a "`Fetcher`: Object used to send HTTP requests or TCP connections to the container port." https://developers.cloudflare.com/containers/api/durable-object-container/ [doc]. Container SSH is admin-only: "SSH does not expose a publicly accessible port on the Container." https://developers.cloudflare.com/containers/guides/ssh/ [doc]
22. Streaming a multi-GB clone: response bodies have "No enforced limit". HTTP Worker duration has "no hard limit ... As long as the client remains connected". DO RPC and HTTP wall time is "Unlimited" while the caller stays connected. On a runtime update, "existing Workers requests and connections" get "up to 20 minutes to finish." (Workers limits page) [doc]. So a clone of several GB from a container can stream through Worker and DO, but a transfer that runs past 20 minutes can be cut at a runtime update, and the container itself can be stopped by a host restart [inference; not run against a real account].

### Push and clone size through Workers
23. "Request body size limits depend on your Cloudflare account plan, not your Workers plan": Free "100 MB", Pro "100 MB", Business "200 MB", and Enterprise "Up to 5 GB (self-serve)", with more through the account team. Larger bodies get `413`. https://developers.cloudflare.com/workers/platform/limits/ [doc]. I could not confirm whether chunked `git push` bodies count the same way [unverified].
24. R2 single uploads max out at "5 GiB (single-part) / 4.995 TiB (multi-part)", and the R2 limit "does not apply to subrequests." "Maximum concurrent writes to the same object name (key): 1 per second". https://developers.cloudflare.com/r2/platform/limits/ [doc]

### SSH for git
25. Workers cannot accept public TCP: "Direct inbound TCP connections from the public Internet ... are not supported at present. A `connect()` handler only receives connections forwarded from another Worker over a service binding." https://developers.cloudflare.com/workers/runtime-apis/handlers/connect/ [doc]
26. Spectrum is "Paid add-on" on Pro and Business with "SSH (one app allowed)". Generic TCP is "Paid add-on" on Enterprise only. https://developers.cloudflare.com/spectrum/protocols-per-plan/ [doc]. Spectrum proxies to `origin_direct` IPs or `origin_dns` (Enterprise), or through a Cloudflare Tunnel virtual network that requires "exactly one address" and no Proxy Protocol. https://developers.cloudflare.com/spectrum/reference/configuration-options/ [doc]. Spectrum cannot target a Worker, DO, or Container directly, so public `ssh://` needs either a Tunnel connector that can reach a container or a non-Cloudflare origin [inference, unverified end to end].

### Data residency

(R2 data location, above) [doc]. DO jurisdictions are `eu`, `us`, and `fedramp`, but "A DurableObjectId will be logged outside of the specified jurisdiction" and "Workers may still access Durable Objects constrained to a jurisdiction from anywhere in the world." https://developers.cloudflare.com/durable-objects/reference/data-location/ [doc]

Artifacts accepts `eu` or `us` per namespace, and "You cannot change the jurisdiction after creating the namespace." https://developers.cloudflare.com/artifacts/guides/data-localization/ [doc]

The Data Localization Suite is an "Enterprise-only paid add-on" made of Geo Key Manager, Customer Metadata Boundary, and Regional Services ("which Cloudflare data centers are allowed to decrypt and process your HTTPS traffic"). https://developers.cloudflare.com/data-localization/ [doc]. ## Implications [inference]

1. Artifacts is the strongest prior art and a competitor, not a foundation. It shows that one DO per repository, with synchronous multi-datacenter replication, works for git on Cloudflare. Its 1 GB cap on new repositories and its single logical instance per repository rule it out as Graftyard's object store for GHES-compatible hosting (findings 4 to 7). Corrected on 2026-10-26 by `research/artifacts-recheck.md`: v1-only push limits no unmodified client, because git has no protocol v2 push, and `filter` is documented as unsupported only among v1 capabilities, so neither is a deciding reason.
2. The per-repository chain maps onto one SQLite DO per repository. The DO's single-threaded storage replaces the DynamoDB conditional put as the commit point. The 1,000 requests-per-second soft limit and 10 GB storage per object take the place of DynamoDB's partition ceiling. Pack bytes go to R2 (findings 15, 24).
3. Upstream git stays the object engine only in Containers. Each repository cache is ephemeral, at most 20 GB, and can be lost on any host restart. R2 must stay canonical, with a snapshot or rehydrate path. A large monorepo (over about 15 GB of packs) does not fit one instance (findings 16 to 18).
4. A pure WASM path means writing a server: receive-pack, upload-pack, and pack generation within 128 MB and 5 minutes of CPU. Storing client deltas, as Artifacts and dgit do, avoids delta compression but gives up repacking and bitmaps, so clone cost grows with history (findings 11 to 15).
5. GHES-sized pushes (hundreds of MB to GB) need an Enterprise zone, or a client-side split that unmodified git does not do (finding 23).
6. SSH is the weakest surface. Spectrum gives one SSH app below Enterprise and cannot target Workers, so an SSH front end needs a Tunnel to containers or must stay out of scope (findings 25, 26).
7. Actions runners fit Containers for most jobs. Docker works as rootful DinD with host networking. Jobs that need KVM (Android emulators, VM-based tests) have no documented home (findings 27 to 29).
8. Self-hosted mode on workerd loses replicated DO storage and the managed R2, D1, and Artifacts. Graftyard would have to supply its own durable DO storage (celld-like) and S3-compatible backends, which makes it a second storage engine (findings 38, 39).
9. A Zurich-only install (as in `history/DESIGN.md`'s eu-central-2 example) has no Cloudflare jurisdiction. `eu` is the tightest guarantee for R2, DOs, Containers, and Artifacts, and DO ids still leave the jurisdiction (findings 40 to 42).
10. A vendor-operated install in a customer account has to combine an account API token, Terraform for most resources, and Wrangler for Containers, because no Terraform container resource exists (findings 34 to 36).
