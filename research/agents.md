# Agents: what AI coding agents need from a git host in 2026

Research date 2026-10-26. This file answers the operator's question about Cloudflare's post https://blog.cloudflare.com/next-git-platform-on-cloudflare (published 2026-10-01): "why not artifacts? how can we take it a step further and make sure this is agent-friendly?" It covers the agent half. The Artifacts storage recheck is a separate slice, and `research/cloudflare-git.md` findings 3 to 7 hold the earlier Artifacts facts.

Labels. [doc] is a vendor document, blog post, dataset card, or issue as the record of what its author said. [measured] means the research run read the code, schema, or page itself and reports what it contains or how it responded. [inference] is the run's reasoning from cited facts. "Could not verify" marks gaps. Quotes are verbatim and short. The lead re-read these sources on 2026-10-26 to confirm the quoted text: findings 1.3, 1.6, 1.9, 2.2, 2.3, 3.6, 3.7, 4.13, 7.1, and the GitHub MCP server README.

Compatibility scope comes from `FRAME.md` and `research/clients.md`. Graftyard must look like GHES 3.22 to unmodified clients: one HTTPS host on port 443, `/api/v3/`, `/api/graphql`, `/login/oauth/*`, `/login/device/code`, `X-GitHub-Request-Id`, `X-GitHub-Enterprise-Version: 3.22.x`, and the published 3.22 REST and GraphQL schemas (`research/clients.md`, implications 1 to 3).

## Answer

1. None of GitHub's own agents runs against GHES 3.22. That covers Copilot cloud agent (formerly Copilot coding agent), Agent HQ with Claude and Codex, mission control, the agent tasks REST API, and the remote GitHub MCP server. The backends live in GitHub's cloud, so no work on Graftyard's side can point them at another host (findings 1.1 to 1.5, 1.12) [doc].
2. GHES 3.22 already carries agent fields in its wire contract. The GraphQL schema has `agentAssignment` on four assignment mutations plus `suggestedActors` and `actorLogins`. The audit log has `actor_is_agent` on many events and `agent_session_id` on `pull_request.create` (findings 1.3, 4.13) [measured]. Graftyard can run its own agents inside the 3.22 wire format by filling those fields.
3. Third-party agents reach a GHES host in one way. An admin creates a GitHub App on the host, the agent vendor mints installation tokens, receives webhooks, and reads and writes check runs and commit statuses. Local CLIs fall back to `git` plus `gh` with `GH_HOST`. Claude Code, Codex (legacy cloud), Cursor, Devin, and Factory document this path. Amp, the new Codex Cloud, and Jules do not support GHES (section 2) [doc]. All of it is already inside Graftyard's wire scope.
4. Agents are the main load driver GitHub names. GitHub plans for "30X today's scale" and moved its git writes to per-reference serialization because "agents and developers pushing to their own branches" no longer need to wait on each other (findings 3.1, 3.2) [doc]. The Cloudflare design serializes pushes, merges, and bot ref moves through one consensus group per repository and sizes bot ref moves at 50 a minute (`design/DESIGN.md` line 388) [measured]. That load model predates agent fleets [inference].
5. Every prompt-injection incident found used text the host stores and serves: issue bodies, PR titles, HTML comments (findings 4.8 to 4.11) [doc]. The host is the one party that knows both the raw text and the author's access level [inference].
6. The agent layer Graftyard should add is additive. It means agent actors with their own branch namespaces, coordination leases, session provenance, opt-in agent merge gates, and a remote MCP endpoint on the 2026-07-28 spec. None of it needs to change a GHES 3.22 response. Three requirements conflict with GHES compatibility if done the obvious way and must stay opt-in or out of band. These are agent-specific merge gates on by default, rewriting the `body` fields that clients read, and markdown conversion on API paths (section 9).

## 1. GitHub's agent surfaces and how they reach a host

| Surface | Works on GHES 3.22 | What Graftyard must implement |
| --- | --- | --- |
| Copilot cloud agent | No | Keep the 3.22 GraphQL agent fields. Return `suggestedActors` without `copilot-swe-agent`. Expose no `/agents/*` routes |
| Agent tasks REST API | No (github.com, API version 2026-03-10) | Nothing for parity. A Graftyard analogue would be additive |
| GitHub MCP server, local stdio | Yes, with PAT or host-registered OAuth or GitHub App | GHES path layout, `raw.<host>/_ping` behavior, `X-OAuth-Scopes` on `HEAD /api/v3/`, OAuth device and web flows, every REST and GraphQL call its toolsets make |
| GitHub MCP server, remote | No | Nothing. A Graftyard-hosted remote MCP endpoint is additive |
| GitHub Agentic Workflows (gh-aw) | Partial | Actions with Docker-capable Linux runners, the v3 artifact backend or v4, scoped `GITHUB_TOKEN`, OIDC, `GET /rate_limit` |
| Agent HQ, Claude and Codex on GitHub, mission control | No | Nothing for parity |
| Copilot CLI offline mode | Yes, technical preview | An appliance-side model proxy whose HTTP contract is unpublished |

### Copilot cloud agent

1.1. Copilot is not part of GHES. "GitHub Copilot is available on GitHub's cloud-hosted platforms: GitHub.com and GHE.com." https://docs.github.com/en/enterprise-server@3.22/copilot/copilot-on-ghes/about-copilot-on-ghes [doc]. The agent itself "only works with repositories hosted on GitHub. It cannot work on repositories stored on other code hosting platforms." https://docs.github.com/en/copilot/concepts/agents/cloud-agent/about-cloud-agent [doc]
1.2. `gh` refuses agent features on enterprise hosts. `gh issue create` documents "`@copilot`: assign Copilot (not supported on GitHub Enterprise Server)" (https://cli.github.com/manual/gh_issue_create) [doc]. `pkg/cmd/agent-task/agent_task.go` returns `errors.New("agent tasks are not supported on this host")` when `auth.IsEnterprise(host)` (https://raw.githubusercontent.com/cli/cli/trunk/pkg/cmd/agent-task/agent_task.go) [measured].
1.3. The GHES 3.22 GraphQL schema already has the assignment input. `ReplaceActorsForAssignableInput` lists "`agentAssignment` (AgentAssignmentInput): Configuration for assigning an AI agent to this issue." `AddAssigneesToAssignableInput` and `CreateIssueInput` list "Configuration for assigning Copilot to this issue." https://docs.github.com/en/enterprise-server@3.22/graphql/reference/issues [measured, lead re-read]. The GHES 3.22 REST issue and assignee pages do not mention `agent_assignment` [measured].
1.4. On github.com, assignment goes through REST `POST /repos/{o}/{r}/issues/{n}/assignees` with `"assignees": ["copilot-swe-agent[bot]"]` and an `agent_assignment` object, or through GraphQL `updateIssue`, `createIssue`, `addAssigneesToAssignable`, and `replaceActorsForAssignable`. Discovery is `suggestedActors(capabilities: [CAN_BE_ASSIGNED])`, and the bot login is `copilot-swe-agent`. A `GraphQL-Features: issues_copilot_assignment_api_support` header is required, and "Make sure you're authenticating with the API using a user token". https://docs.github.com/en/copilot/how-tos/use-copilot-agents/cloud-agent/use-cloud-agent-via-the-api [doc]. The API shipped on 2025-12-03 (https://github.blog/changelog/2025-12-03-assign-issues-to-copilot-using-the-api) [doc].
1.5. The agent tasks REST API is github.com only. It covers `GET` and `POST /agents/repos/{owner}/{repo}/tasks`, `GET /agents/tasks`, and `GET /agents/repos/{o}/{r}/tasks/{id}`, with states "`queued`, `in_progress`, `completed`, `failed`, `idle`, `waiting_for_user`, `timed_out`, `cancelled`". It needs an "Agent tasks" fine-grained permission, and "GitHub App installation access tokens are not supported for this endpoint." https://docs.github.com/en/enterprise-cloud@latest/rest/agent-tasks/agent-tasks?apiVersion=2026-03-10 [doc]. It reached Business and Enterprise on 2026-05-13 (https://github.blog/changelog/2026-05-13-start-copilot-cloud-agent-tasks-via-the-rest-api/) [doc]. The GHES 3.22 docs path `/en/enterprise-server@3.22/rest/agent-tasks/agent-tasks` returned HTTP 404 [measured].
1.6. The agent runs on GitHub Actions with a special workflow. "A `copilot-setup-steps.yml` file looks like a normal GitHub Actions workflow file, but must contain a single `copilot-setup-steps` job." Runners must be Ubuntu x64 or Windows 64-bit, and the agent calls `api.*.githubcopilot.com` and `uploads.github.com`. https://docs.github.com/en/copilot/how-tos/copilot-on-github/customize-copilot/customize-cloud-agent/customize-the-agent-environment [doc]. Sessions are capped: "Each Copilot cloud agent session has a maximum execution time of 59 minutes." (about-cloud-agent page) [doc]
1.7. The agent's guardrails, which Graftyard can copy for its own agents. "a new `copilot/` branch is created for Copilot, and the agent can only push to that branch." It "cannot mark its pull requests as "Ready for review" and cannot approve or merge a pull request." Workflows wait until a writer clicks "Approve and run workflows". "The commit message for each agent-authored commit includes a link to the agent session logs". https://docs.github.com/en/copilot/concepts/security-governance-and-network-settings/risks-and-mitigations [doc]. Session URLs have the form `https://github.com/OWNER/REPO/pull/123/agent-sessions/<uuid>` (cli/cli `agent_task.go` help text) [measured].
1.8. github.com has no agent webhook event. A grep of every event heading on https://docs.github.com/en/webhooks/webhook-events-and-payloads for "copilot" and "agent" found none [measured]. Agent work shows up as ordinary `issues` (assigned), `pull_request`, `push`, `pull_request_review`, and `workflow_run` events [inference].

### GitHub MCP server

1.9. GHES support is local only, through `--gh-host` or `GITHUB_HOST`. "For GitHub Enterprise Server, prefix the hostname with the `https://` URI scheme. HTTPS is required and enforced". Also, "GitHub Enterprise Server does not support remote server hosting." https://raw.githubusercontent.com/github/github-mcp-server/main/README.md [doc, lead re-read]
1.10. Host classification and URL layout. `pkg/utils/api.go` `classifyHost` treats `github.com` and `*.github.com` as dotcom, `*.ghe.com` as GHEC, and everything else as GHES. For GHES it builds REST `https://<host>/api/v3/`, GraphQL `https://<host>/api/graphql`, and OAuth `https://<host>/login/oauth`. It probes `https://raw.<host>/_ping` with a 5 s timeout and assumes subdomain isolation only on HTTP 200. Without isolation, uploads use `/api/uploads/` and raw content uses `/raw/` (https://raw.githubusercontent.com/github/github-mcp-server/main/pkg/utils/api.go) [measured].
1.11. It calls REST through go-github v92 and GraphQL through githubv4 (`go.mod`) [measured]. It filters tools by classic scopes read from `HEAD` on the REST base with `X-GitHub-Api-Version: 2022-11-28`, parsing `X-OAuth-Scopes`. "Fine-grained PATs don't return the X-OAuth-Scopes header" (`pkg/scopes/fetcher.go`) [measured]. The recommended PAT scopes are `repo`, `read:packages`, and `read:org` (README) [doc].
1.12. OAuth on GHES needs an app registered on the host. "users must **bring their own app** registered on that host and pass `--oauth-client-id`." The server falls back to the device code flow when no browser callback is reachable. https://raw.githubusercontent.com/github/github-mcp-server/main/docs/oauth-login.md [doc]
1.13. The default toolsets are `context`, `repos`, `issues`, `pull_requests`, and `users`. 22 local toolsets exist, including `actions`, `git`, `governance`, and `projects` (README) [doc]. The Copilot tools fail on GHES. `request_copilot_review` returns "Copilot code review is not available on GitHub Enterprise Server." When `suggestedActors` lacks the bot, `assign_copilot_to_issue` returns "copilot isn't available as an assignee for this issue." (`pkg/github/copilot.go`) [measured]
1.14. GitHub steers GHES users to the local server. "Users can configure their local GitHub MCP server so that Copilot can connect to your instance and perform actions like opening issues or pull requests." (about-copilot-on-ghes, 3.22) [doc]

### GitHub Agentic Workflows (gh-aw)

1.15. gh-aw exists and is in public preview. "The `gh-aw` GitHub CLI extension compiles each agentic workflow into a standard GitHub Actions workflow." https://raw.githubusercontent.com/github/gh-aw/main/README.md [measured]. "GitHub Agentic Workflows are in public preview and subject to change." https://docs.github.com/en/copilot/concepts/agents/about-github-agentic-workflows [doc]
1.16. Its writes go through separate jobs. "The agent job runs with minimal read-only permissions, while write operations are deferred to separate jobs that execute only after the agent completes." The runtime containerizes the agent behind a Squid proxy and launches the GitHub MCP server through the Docker socket. https://github.github.com/gh-aw/introduction/architecture/ [doc]
1.17. GHES support is a compatibility mode. "gh-aw includes a GHES compatibility mode toggle (`aw.json` `ghes` or `gh aw compile --ghes`) for GHES releases that require the v3 artifact backend." https://github.github.com/gh-aw/reference/enterprise-configuration/ [doc]. The Copilot engine on GHES needs "GitHub Connect, enterprise Copilot licensing, and outbound HTTPS to `api.githubcopilot.com`" (https://github.github.com/gh-aw/troubleshooting/common-issues/) [doc]. The `copilot-requests` permission appears in github.com workflow syntax and not in the GHES 3.22 page [measured].

### Agent HQ and third-party agents on GitHub

1.18. Agent HQ was announced on 2025-10-28. "coding agents from Anthropic, OpenAI, Google, Cognition, xAI, and more will become available directly within GitHub as part of your paid GitHub Copilot subscription". https://github.blog/news-insights/company-news/welcome-home-agents/ [doc]. Claude and Codex reached public preview on 2026-02-04. "Assign an issue to Claude, Codex, Copilot, or all three using the Assignees dropdown." https://github.blog/changelog/2026-02-04-claude-and-codex-are-now-available-in-public-preview-on-github [doc]
1.19. Partner agents are hidden app installs that inherit Copilot's guardrails. "the GitHub Apps themselves will not be visible in your account's list of GitHub App installations." "Coding agents consume **GitHub Actions minutes** and **AI credits**." https://docs.github.com/en/copilot/concepts/agents/about-third-party-agents [doc]. The GHES 3.22 Copilot docs contain only two articles, and neither covers agents [measured].

### Other 2025 to 2026 agent additions

1.20. Custom agents live in `.github/agents/*.agent.md` or the org `.github` repo (https://github.blog/changelog/2025-10-28-custom-agents-for-github-copilot/) [doc]. The cloud agent reads `.github/copilot-instructions.md`, `.github/instructions/**/*.instructions.md`, and "`AGENTS.md`, `CLAUDE.md` or `GEMINI.md` files" (https://docs.github.com/en/copilot/reference/custom-instructions-support) [doc]. These are ordinary repository files, so a host only stores and serves them [inference].
1.21. A github.com ruleset rule targets agents. "**Require an additional approval for unattributed Copilot pull requests** is enabled by default, for both new and existing rulesets." https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets [doc]. The GHES 3.22 version of that page has no "copilot" or "agent" match [measured]. GHES 3.22 did add per-user ruleset bypass. "Repository and organization rulesets now support bypassing by individual users" (https://docs.github.com/en/enterprise-server@3.22/admin/release-notes, 3.22.0, 2026-09-08) [doc].
1.22. Copilot CLI offline mode is the only Copilot item in the GHES 3.22 release notes. It is a technical preview for "disconnected or air-gapped environments". Admins configure `ghe-config app.copilot-proxy.*` on the appliance, and users set `COPILOT_PROVIDER_GHES_HOST`, `COPILOT_PROVIDER_GHES_TOKEN`, and `COPILOT_OFFLINE`. https://docs.github.com/en/enterprise-server@3.22/copilot/copilot-on-ghes/set-up-copilot-cli [doc]. The HTTP path the CLI calls on the appliance: could not verify.
1.23. GHES 3.22 disables networking in pre-receive hooks by default. "networking-related syscalls will be disabled by default in the pre-receive hook environment." (3.22.0 release notes) [doc]. A policy hook that calls an agent service cannot rely on outbound network on real GHES [inference].

"The app subscribes to `pull_request`, `issue_comment`, `pull_request_review_comment`, `pull_request_review`, `check_run`, and `status` events." Hosted sessions need inbound reachability: "your GHES instance must be reachable from Anthropic infrastructure". The substitute for the MCP server is "use the `gh` CLI configured for your GHES host instead." 2.2. Claude's hosted proxy blocks GraphQL. "the proxy rejects requests to GitHub's GraphQL endpoint with a 403" and "`gh` subcommands that use GraphQL, such as `gh pr` and `gh issue`, get the same 403." https://code.claude.com/docs/en/cloud-environments.md [doc, lead re-read]. Whether this rule also applies to GHES-connected sessions: could not verify.
2.3. claude-code-action reads `GITHUB_API_URL`, `GITHUB_SERVER_URL`, and `GITHUB_GRAPHQL_URL` with github.com defaults (`src/github/api/config.ts`). It revokes tokens with `DELETE ${GITHUB_API_URL}/installation/token` (`action.yml`). https://github.com/anthropics/claude-code-action [measured]. Its default branch prefix is `claude/`, and it commits as `claude[bot]` with `bot_id` 41898282, which is the github-actions[bot] user id (`action.yml`) [measured].
2.4. Codex on GHES. Workspace admins "can set up and publish a GitHub Enterprise app from the ChatGPT app template" (release note dated 2026-05-29, https://help.openai.com/en/articles/10128477-chatgpt-enterprise-edu-release-notes) [doc]. "Create a GitHub App, not a standalone GitHub OAuth App." "ChatGPT uses the hostname to derive GitHub Enterprise endpoints. 2.5. Cursor on GHES. It needs "GitHub Enterprise Server (v3.8 or later recommended)". 2.6. Devin on GHES offers "GitHub App (Recommended)" and a PAT path that "works for all GHES versions". 2.7. Copilot CLI on GHES uses `gh`. "GitHub operations (issues, PRs, repos) via `gh` CLI" are available, while "GitHub MCP server tools" are not. Automation sets `GH_HOST` and `GH_ENTERPRISE_TOKEN`. (set-up-copilot-cli, GHES 3.22) [doc]. "Classic personal access tokens (`ghp_`) are not supported." https://docs.github.com/en/copilot/reference/copilot-cli-reference/cli-command-reference [doc]
2.8. Amp and Jules do not support GHES. Amp says "GitHub Enterprise Server is not supported." Jules says "In the future, Jules will work with more version control systems." (https://jules.google/docs/tasks-repos, search snippet) [doc]. Jules GHES support: could not verify, treated as no.
2.9. Factory connects GHES with an OAuth App requesting "the `repo` and `read:org` OAuth scopes", and "GitHub Enterprise Server supports service accounts through a GitHub App installation." https://docs.factory.ai/enterprise/self-managed-scm.md [doc]

## 3. Agent workload shape

3.1. GitHub says agents drive its capacity plan. "By February 2026, it was clear that we needed to design for a future that requires 30X today's scale." "Since the second half of December 2025, agentic development workflows have accelerated sharply." Its chart shows PRs merged "peaking at 90M" and commits "peaking at 1.4B" a month. https://github.blog/news-insights/company-news/an-update-on-github-availability (2026-04-28) [doc, lead re-read]. The May 2026 availability report says "GitHub's traffic is growing rapidly, driven in large part by AI-assisted and agentic development workflows" (https://github.blog/news-insights/company-news/github-availability-report-may-2026, 2026-06-11) [doc].
3.2. GitHub rebuilt git writes around agents. "The timing and shape of the move were driven by the agentic shift". "most writes to a repository touch different references, for example, agents and developers pushing to their own branches, so they no longer wait on each other." https://github.blog/engineering/architecture-optimization/the-bridge-to-agent-scale-git-infrastructure/ (2026-10-21) [doc, lead re-read; the source uses dashes where this quote uses commas]. The post reports 3 to 4 times higher throughput for writes to different references in internal tests [doc].
3.3. Agent PR volume. AIDev v5 (cutoff 2026-03-31) counts 7,685,281 agent PRs across 961,168 repositories with 80.9% merged. By agent: Codex 3,844,602 (86.2% merged), Copilot 1,581,924 (69.9%), Claude Code 1,567,100 (88.0%), Cursor 317,453 (57.4%), Jules 296,411 (63.4%), Devin 77,791 (59.6%). https://huggingface.co/datasets/hao-li/AIDev/raw/main/README.md [doc]. v4 (cutoff Nov 2025) held 2.7M, so volume grew about 2.8 times in four months [inference].
3.4. Octoverse 2025 counted "1+ million pull requests that were created between May 2025 and September 2025" by Copilot coding agent, against "43.2 million pull requests merged per month". https://github.blog/news-insights/octoverse/octoverse-a-new-developer-joins-github-every-second-as-ai-leads-typescript-to-1/ (2025-10-28) [doc]
3.5. Parallelism per user. Cursor: "On the Pro plan, the limit is 8 concurrent agents." and "You can run multiple agents in parallel on the same repo." (staff reply, https://forum.cursor.com/t/clarification-on-cloud-agent-limits-simultaneous-agents-vs-environments-repos/157584, 2026-04-16) [doc]. "Self-Hosted Machines support up to 200 workers per user and 1000 per team." (https://cursor.com/docs/cloud-agent/self-hosted/pool.md) [doc]. Codex Cloud best-of-N allows `--attempts` "between 1 and 4" (`codex-rs/cloud-tasks/src/cli.rs`, https://github.com/openai/codex) [measured]. The Codex app keeps "your most recent 15 Codex-managed worktrees" (https://developers.openai.com/codex/app/worktrees.md) [doc]. Claude Code ships `claude --worktree <name>` for "an isolated parallel session" (https://code.claude.com/docs/en/common-workflows.md) [doc].
3.6. Share of merged work. Cursor: "Cloud agents now create more than 60% of the pull requests we merge internally." (https://cursor.com/blog/self-hosted-machines, date not visible) [doc]. A SemiAnalysis estimate puts Claude Code at 4% of public GitHub commits as of February 2026, through a secondary report (https://gigazine.net/gsc_news/en/20260210-claude-code-github-commits-4-percent-20-percent) [doc, secondary].
3.7. Rate limits. github.com allows "no more than 80 content-generating requests per minute and no more than 500 content-generating requests per hour", no more than 100 concurrent requests, and 900 REST points per minute per endpoint, signalled with "a `403` or `429` response". https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api [doc]. GHES differs: "Rate limits are disabled by default for GitHub Enterprise Server." The 3.22 page repeats the same secondary numbers as admin-configurable. https://docs.github.com/en/enterprise-server@3.22/rest/using-the-rest-api/rate-limits-for-the-rest-api [doc]
3.8. Agents hit and misread limits. A support escalation shows the MCP server using `"used": 4192` of a 5,000 per hour quota (https://github.com/github/github-mcp-server/issues/933, 2025-08-20) [doc]. ## 4. Security needs

### Identity and tokens

4.1. GHES 3.22 already models both identities an agent needs. A user-to-server token is attributed to the user, and the audit log shows "programmatic_access_type" as "GitHub App user-to-server token". "If you want to attribute app activity to the app instead of to a user, you should authenticate as an app installation instead." https://docs.github.com/en/enterprise-server@3.22/apps/creating-github-apps/authenticating-with-a-github-app/authenticating-with-a-github-app-on-behalf-of-a-user [doc]
4.2. Short-lived, narrowed tokens exist in GHES 3.22. "Installation tokens expire one hour from the time you create them." (https://docs.github.com/en/rest/apps/apps) [doc]. `POST /app/installations/{id}/access_tokens` takes `repositories`, `repository_ids`, and `permissions`, and "The installation access token cannot be granted permissions that the app was not granted." https://docs.github.com/en/enterprise-server@3.22/apps/creating-github-apps/authenticating-with-a-github-app/generating-an-installation-access-token-for-a-github-app [doc]. "The user access token expires after eight hours, and the refresh token expires after six months." (refreshing-user-access-tokens, 3.22) [doc]
4.3. Token format is moving. "Starting April 27, 2026, GitHub began a staged rollout of a stateless format (ghs_APPID_JWT) to all newly minted GitHub App installation tokens" (same 3.22 page as 4.2) [doc]. Whether GHES 3.22 itself mints this format: could not verify. Clients that assume a 40-character token break either way [inference].
4.4. Fine-grained PATs on GHES 3.22 can be limited "to only access specific repositories", and "Organization owners can require approval" for them. They still cannot call the Checks API ("Using fine-grained personal access token to call the Checks API" is listed under major gaps). https://docs.github.com/en/enterprise-server@3.22/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens [doc]
4.5. Actions OIDC exists in GHES 3.22 with issuer `https://HOSTNAME/_services/token`. The newer immutable `sub` format is "not available on GitHub Enterprise Server". https://docs.github.com/en/enterprise-server@3.22/actions/concepts/security/openid-connect [doc]

### Scoping to a repository or branch

4.6. GHES 3.22 rulesets can restrict pushes by branch pattern with users, teams, or apps as bypass actors, and push rulesets can restrict file paths across the fork network. Metadata rules can require commit message patterns: "you can require that commit messages contain a GitHub issue number". https://docs.github.com/en/enterprise-server@3.22/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets [doc]. The same rule can require a provenance trailer on a protected branch [inference].
4.7. github.com protects agent definitions with a push rule: "Use the 1-click push rule to protect the static file path for custom agents (i.e., `.github/agents/*.md`)" (https://github.blog/changelog/2026-02-26-enterprise-ai-controls-agent-control-plane-now-generally-available, 2026-02-26) [doc]. Copilot code review "reads repository custom instructions, agent instructions, and agent skills from the head branch" (https://docs.github.com/en/copilot/concepts/agent-capabilities/agent-powered-workflows-and-operations/code-review) [doc]. A pull request can therefore rewrite the instructions its own reviewer follows [inference].

### Prompt injection

4.8. Invariant Labs' GitHub MCP "toxic agent flow". "The vulnerability allows an attacker to hijack a user's agent via a malicious GitHub Issue, and coerce it into leaking data from private repositories." The suggested fix "restricts an agent to working with only one repository per session". https://invariantlabs.ai/blog/mcp-github-vulnerability (2025-05-26) [doc]
4.9. Nx s1ngularity began as shell injection, not prompt injection. "Attacker created a PR with a malicious title containing shell commands." The payload then "attempted to use local AI tools (like Claude and Gemini), and uploaded the results to a public GitHub repo via the GitHub CLI." https://nx.dev/blog/s1ngularity-postmortem (2025-09-05) [doc]
4.10. PromptPwnd (Aikido, 2025-12-04) names the pattern "Untrusted user input → injected into prompts → AI agent executes privileged tools → secrets leaked or workflows manipulated." and says "At least 5 Fortune 500 companies are impacted". https://www.aikido.dev/blog/promptpwnd-github-actions-ai-agents [doc]
4.11. "Comment and Control" (2026-04-15, accepted at ACM CCS 2026) hid a payload "inside an HTML comment that GitHub's rendered Markdown hides" on an issue assigned to Copilot, then exfiltrated over git push because "`github.com` is whitelisted". https://oddguan.com/blog/comment-and-control-prompt-injection-credential-theft-claude-code-gemini-cli-github-copilot [doc]
4.12. GitHub's mitigations sit at the host. "text entered as an HTML comment in an issue or pull request comment is not passed to Copilot cloud agent." "Comments from users without write access are never presented to the agent." (risks-and-mitigations page) [doc]. Both use facts only the host holds: raw markdown and the author's permission [inference].

### Audit, approvals, and caps

4.13. GHES 3.22 audit events already carry agent fields. `pull_request.create` lists "`actor_is_agent`, `agent_session_id`, `oauth_application_id`, `public_repo`, `pull_request_id`". Most events carry `actor_is_bot`, `programmatic_access_type`, `token_id`, and `token_scopes`. https://docs.github.com/en/enterprise-server@3.22/admin/monitoring-activity-in-your-enterprise/reviewing-audit-logs-for-your-enterprise/audit-log-events-for-your-enterprise [measured, lead re-read]. On github.com, agent events set `actor_is_agent` true with the human as `user`, and "A new `agent_session.task` event also captures when sessions have started, finished, or failed to complete." (2026-02-26 changelog in 4.7) [doc]
4.14. The GHES 3.22 GraphQL reference has Copilot agent session subscription channels on `User`: "Channel value for subscribing to live updates for session creations." https://docs.github.com/en/enterprise-server@3.22/graphql/reference/copilot [doc]. Whether a real GHES instance returns data for them: could not verify. Graftyard must still serve these fields to match the 3.22 schema [inference].
4.15. GHES 3.22 merge gates cover required approvals, code owners, and stale review dismissal. They also include "you can require an approval from someone other than the last person to push to a branch before a pull request can be merged." (available-rules page, 3.22) [doc]. The github.com rule for unattributed Copilot PRs is absent on GHES 3.22 (finding 1.21) [measured].
4.16. Spending caps. Copilot billing moved to pooled AI credits with budgets. "ULBs always enforce a hard stop", other budgets stop only if a flag that "is off by default" is set, and "You cannot create a budget for an individual app or installation." https://docs.github.com/en/copilot/concepts/billing-and-usage/organizations-and-enterprises/budgets [doc]

## 8. Implications for the design

All items in this section are [inference] from the findings above.

8.1. The agent question is mostly answered by being GHES. Third-party agents need the GitHub App manifest flow, installation tokens narrowed per repository, `DELETE /installation/token`, webhook delivery, check runs, commit statuses, and the combined status rollup. They also need branch protection reads and `gh` at `/api/v3` and `/api/graphql`. All of it is already inside the conformance scope in `research/clients.md`. The extra test is to run Claude Code's GHES manifest flow, Cursor's GHES app, Codex's app template, and the local GitHub MCP server against Graftyard as conformance oracles.
8.2. REST must stand alone for agent paths. Claude's hosted proxy forbids GraphQL and steers agents to `gh api` REST (finding 2.2). Every PR, issue, review, and check operation an agent needs should work through REST alone, which GHES already provides.
8.3. The commit path's load model needs agent numbers. The Cloudflare design puts pushes, merge-queue merges, and bot ref moves on one group per repository and sizes bot ref moves at 50 a minute. Its `decide` step checks `expect` per ref, so writes to different refs never conflict, but they share the group's entry pipeline. GitHub's own fix for agent load was per-reference serialization (finding 3.2). A fleet of 200 Cursor workers, each pushing its own branch, should be an explicit journey with a number. Whether the group-commit pipeline matches per-ref throughput at that rate is a Milestone 0 measurement, not a known.
8.4. Forks may be the cheapest agent workspace. In the Cloudflare design a fork's refs live on the fork's own group and share the network's packs (`design/DESIGN.md` journey 2). Artifacts' fork-per-task pattern (finding 6.11) maps onto GHES forks with no new wire format, and it spreads ref writes across groups.
8.5. Artifacts' agent features are reproducible above Graftyard's own store. Fork, repo-scoped TTL tokens, file reads, and push events correspond to GHES forks, narrowed installation tokens, the contents API, and `push` webhooks. What Artifacts lacks matters more for GHES. It has no ref-update hook, merge, or synchronous rejection, so rulesets, required checks, and merge semantics stay Graftyard's code either way (finding 6.11). The storage reasons in `design/DESIGN.md` line 856 (1 GB cap, receive-pack v1 only, no `filter`, single-instance repos) are rechecked in a separate slice.
8.6. Host-side injection defense is Graftyard's unique lever. Only the host knows the raw markdown, hidden content, and the author's permission. Exposing them as extra fields or MCP tool output, without changing GHES `body` fields, gives every agent the protection Copilot built in (findings 4.11, 4.12).
8.7. Reachability is a deployment requirement. Claude Code, Cursor, and Codex call a GHES host from their own clouds and receive webhooks there. A BYOC or self-hosted install behind a firewall must allowlist vendor IPs or use a tunnel. Cursor names Cloudflare Tunnel as an option (finding 2.5).
8.8. Rate-limit headers are part of the agent contract. GHES disables limits by default, but agent clients parse `x-ratelimit-*`, `retry-after`, and 403 or 429 (findings 3.7, 3.8). Managed mode behaves like github.com and needs content-creation limits on by default. Self-hosted keeps GHES's default of off.

## 9. Requirements for Graftyard

Tags. **wire-compatible** means GHES 3.22 already has it, so implementing it is part of compatibility. **additive** means a new surface that unmodified clients ignore. **conflicting** means doing it the obvious way would change a GHES 3.22 response or default, so it must be opt-in, renamed, or out of band.

R1. Serve the GitHub App manifest flow, app settings (public apps, user-to-server token expiry opt-out), installation tokens with `repositories`, `repository_ids`, and `permissions` narrowing, and `DELETE /installation/token`. Keep the `ghs_` prefix and accept variable token length. **wire-compatible** (findings 2.1, 2.3, 2.4, 2.6, 4.2, 4.3)
R2. Deliver `installation`, `installation_repositories`, `push`, `pull_request`, `pull_request_review`, `pull_request_review_comment`, `issues`, `issue_comment`, `check_run`, `status`, `workflow_run`, and `workflow_job` webhooks to app endpoints, signed as GitHub does. **wire-compatible** (findings 2.1, 2.4, 2.5)
R3. Serve the Checks API, the Statuses API, the combined status rollup, and branch protection and ruleset reads through REST alone. **wire-compatible** (findings 2.1, 2.2, 2.5)
R4. Serve the local GitHub MCP server's needs: consistent `raw.<host>/_ping` behavior, `/raw/` and `/api/uploads/` paths, `X-OAuth-Scopes` on `HEAD /api/v3/`, OAuth device and web flows for host-registered apps, and every call in its default toolsets. Add the MCP server to the conformance oracles. **wire-compatible** (findings 1.9 to 1.13)
