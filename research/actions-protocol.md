# Actions protocol: what an unmodified runner and toolkit need from a server

Research date 2026-10-23. Sources were read at these pins: actions/runner v2.338.1 (2026-10-22), actions/toolkit main 0c3a9c3 (2026-10-21; @actions/cache 6.3.0, @actions/artifact 6.3.1, @actions/core 3.1.0), actions/cache v6.1.0, actions/upload-artifact v7.0.2 and v3.2.2, actions/download-artifact v8.0.2, actions/actions-runner-controller gha-runner-scale-set-0.15.1 with actions/scaleset v0.5.0, actions/languageservices release-v0.3.61, actions/runner-images c87f6f63, ChristopherHX/runner.server v3.14.0, ChristopherHX/github-act-runner v0.13.0, go-gitea/gitea v28.2.0 (2026-10-18), gitea.com/gitea/runner v5.2.2 (renamed from act_runner), code.forgejo.org/forgejo/runner c4a92ff (2026-10-02), @azure/storage-blob 12.34.0. Scratch clones are in /tmp/graftyard-research/actions/.

## Answer

An unmodified `actions/runner` can be driven by a non-GitHub server today, and runner.server proves it, but the server must speak one of two whole protocol families. The legacy family is Azure DevOps "distributedtask": a VSS location service (`_apis/connectionData` plus GUID-addressed resources), session plus long-poll message queue, job request renew and finish, timeline, log and attachment uploads. The newer family is GitHub-specific JSON: `/actions/runner-registration`, `/actions/runners/register`, a broker (`session`, `message`, `acknowledge`), a run service (`acquirejob`, `renewjob`, `completejob`), a launch service that resolves action tarballs, and a twirp results service that hands out signed blob URLs for logs and step summaries. The server, not the runner, picks the family (`use_v2_flow` in the registration response), and the newer family needs no VSS location service at all. Both families carry the same job message (`AgentJobRequestMessage`), whose steps and container specs are serialized object-template tokens that the runner evaluates; the server owns triggers, matrix expansion, concurrency, reusable workflows, environments, approvals and token permissions. The toolkit is the hard part. Every first-party artifact and cache client classifies the host with `isGhes()`, which treats anything other than `github.com`, `*.ghe.com` and `*.localhost` as GHES. On such a host `upload-artifact@v4` and later throw `GHESNotSupportedError` before any network call, and `actions/cache` is forced onto the legacy v1 REST cache API. GHES itself still does not support artifact v4 or cache v2 as of GHES 3.22. A Graftyard host will therefore be classified as GHES, so the realistic compatibility target is the GHES subset: legacy artifact v1 for `upload-artifact@v3.2.2`, cache v1 for `actions/cache@v4+`, and the runner protocol. Gitea's 2026 runner works around the gate by rewriting downloaded action bundles; a Graftyard server could do the equivalent when it serves action tarballs, at a trust cost. The Azure Blob dependency matters only for twirp v2 uploads: artifact v4 always issues Put Block and Put Block List, cache v2 issues Put Blob up to 128 MiB and Put Block above it, and the runner's own results-service log upload issues Append Block unless the server reports a non-Azure blob type.

## Findings

### A. Runner registration and host classification

1. The runner's hosted test is `UrlUtil.IsHostedServer`: host equals `github.com`, `www.github.com` or `github.localhost`, or ends with `.ghe.localhost` or `.ghe.com`. Env `GITHUB_ACTIONS_RUNNER_FORCE_GHES` forces GHES. `src/Runner.Sdk/Util/UrlUtil.cs:9-22`. [source]
2. When `GitHubUrl` is empty (JIT-configured runners), `RunnerSettings.IsHostedServer` infers from `ServerUrl` (`*.actions.githubusercontent.com`, `*.codedev.ms`) or `ServerUrlV2` (adds `*.githubapp.com`, `*.ghe.com`, `*.actions.localhost`, `*.ghe.localhost`) and otherwise defaults to hosted. `src/Runner.Common/ConfigurationStore.cs:62-116`. [source] A JIT config from a Graftyard server must therefore set `GitHubUrl` or `IsHostedServer=false` explicitly, or the runner treats it as github.com. [inference]
3. What "hosted" changes in the runner: API base becomes `https://api.{host}/...` instead of `https://{host}/api/v3/...` (`ConfigurationManager.cs:746-767,829-836`, `RunnerDotcomServer.cs:74-81,191-223`); network endpoint checks run only when hosted (`JobServer.cs:81`); the ghcr.io token fallback for container pulls is hosted-only (`Runner.Worker/ContainerOperationProvider.cs:522-526`); on non-hosted servers the worker fills `github.server_url`, `api_url` (`/api/v3`) and `graphql_url` (`/api/graphql`) from the configured URL if the server left them empty (`Runner.Worker/JobExtension.cs:225-235`). [source]
4. Non-hosted URLs are built as `$"{Scheme}://{Host}/api/v3/..."` from a `UriBuilder`, which drops any non-default port. `ConfigurationManager.cs:835`, `RunnerDotcomServer.cs:80`. [source] runner.server's README says official runners need the server on port 80 to register (`runner.server/README.md:189`). [source] Graftyard must serve `/api/v3` on the default port of the web host. [inference]
5. `config.sh --url URL --token T`: POST `{api}/actions/runner-registration` with header `Authorization: RemoteAuth T` and body `{url, runner_event}`; response `GitHubAuthResult {url, token_schema, token, use_v2_flow}`. `ConfigurationManager.cs:825-886`, `Configuration/CredentialManager.cs:80-92`. [source]
6. If `use_v2_flow` is true ("runner admin flow"), the runner skips the VSS connection, lists groups and runners via `{api}/{scope}/actions/runner-groups` and `.../runners?name=`, registers with POST `{api}/actions/runners/register` body `{url, group_id, name, version, updates_disabled, ephemeral, labels, public_key}` (plus `runner_id, replace`), deletes with DELETE `.../runners/{id}`, all with `RemoteAuth`, and then always uses the broker. `ConfigurationManager.cs:156,183-186,218-221,287-349,560-563`; `RunnerDotcomServer.cs:45-110,112-128`. [source]
7. Otherwise registration uses the legacy distributedtask agent APIs, and a service can still force broker mode by returning agent property `UseV2Flow`. `ConfigurationManager.cs:434-438`. [source]
8. Credentials are OAuth JWT-bearer client credentials: the runner signs an assertion with its RSA key and exchanges it at `authorizationUrl` (or `authorizationUrlV2` in broker mode). `Configuration/OAuthCredential.cs:27-47`, `Sdk/WebApi/WebApi/OAuth/VssOAuthConstants.cs:39-70`. [source]
9. JIT config (`run.sh --jitconfig B64`) is base64 JSON mapping file names (`.runner`, `.credentials`, RSA params) to base64 file contents, written verbatim into the runner root. `src/Runner.Listener/Runner.cs:234-268`. [source] Any server that can mint those three files can drive ephemeral runners without the registration endpoints. [inference]

Risk rating, registration: version controlled by Graftyard through runner pinning, except that a new runner release may change discovery. Churn since 2024-10-23: ConfigurationManager.cs 10 commits, ConfigurationStore.cs 5, UrlUtil.cs 2, RunnerDotcomServer.cs 2; `UseV2Flow` was split into `UseRunnerAdminFlow` on 2025-09-03 (#4013) and hosted inference changed 2025-10-22 (#4086) and 2026-02-18 (#4254). [source: git log] Rating: medium. [inference]

### H. Hostname heuristics (isGhes and equivalents)

43. `@actions/cache` `isGhes()`: `GITHUB_SERVER_URL` hostname uppercased; not GHES if equal to `GITHUB.COM`, or ends with `.GHE.COM` or `.LOCALHOST`. Effect: forces cache v1 (ignores `ACTIONS_CACHE_SERVICE_V2`) and skips the client-side 10 GB size check. `packages/cache/src/internal/config.ts:1-20`, `cache.ts:544-549`. [source]
44. `@actions/artifact` `isGhes()`: identical tests. Effect: upload, download, list, get and delete all throw `GHESNotSupportedError`. `packages/artifact/src/internal/shared/config.ts:27-38`, `internal/client.ts:123,146,183,220,256`. [source]
45. `actions/cache` action `isGhes()`: identical tests; effect is only a warning text ("supported on GHES >= 3.5") when no cache URL env is present. `cache/src/utils/actionUtils.ts:6-17,69-88`. [source]
46. Bare `localhost` does not pass these tests; only names ending in `.localhost` do. [inference from the `endsWith('.LOCALHOST')` code above]

## Implications for the design

1. [inference] Implement the newer protocol family (runner-registration with `use_v2_flow: true`, `/api/v3/actions/runners/register`, broker, run service, launch, results) and skip the VSS location service. Keep a legacy distributedtask shim only if a pinned runner version needs it; runner.server is the reference if so.
2. [inference] Pin and ship a tested runner version per Graftyard release, the way GHES pins minimums. Treat each runner upgrade as a conformance gate, because the runner's protocol churns about monthly while Graftyard controls when to adopt.
3. [inference] Accept that Graftyard is "GHES" to the toolkit. The default conformance oracle should be the GHES subset: `actions/cache@v4+` on cache v1, `upload-artifact@v3.2.2` and `download-artifact@v3` on legacy artifacts, and checkout, setup-* actions. State plainly that `upload-artifact@v4+` and `attest-build-provenance` fail, as they do on GHES.
4. [inference] Three options for artifact v4 on Graftyard, all with costs: (a) wait for toolkit PR #2123 or similar, which does not cover a new vendor name unless Graftyard is added; (b) serve rewritten tarballs for known actions from the launch resolver, as Gitea's runner does, which breaks the expectation that a pinned SHA runs exactly those bytes; (c) mirror patched forks under a Graftyard org and document substitution. Option (b) needs an explicit security review before adoption.
5. [inference] Implement both cache v1 and v2 server-side. v1 is required on a GHES-classified host. v2 matters only if the gate opens, and needs Put Blob, Put Block, Put Block List and `x-ms-request-id`; downloads can be S3 presigned URLs because non-Azure hosts get a plain GET.
6. [inference] Put an Azure-Blob-dialect shim in front of S3 for uploads (block staging to S3 multipart or to temporary objects, commit on Put Block List). Artifact v4 uses 8 MiB blocks and cache v2 uses 64 MiB blocks, both under S3's 5 GiB part limit and above its 5 MiB minimum, so blocks can map one-to-one onto multipart parts if block IDs arrive in order.
7. [inference] For results-service logs, return `BLOB_STORAGE_TYPE_UNSPECIFIED` and Graftyard-signed URLs that accept `comp=appendblock` and `seal=true`; no Azure emulation is needed on this path.
8. [inference] Serve the web host and `/api/v3` on port 443; the runner drops non-default ports when building the registration URL.
9. [inference] For ARC compatibility, implement `_apis/runtime/runnerscalesets`, sessions, message queue, `acquirejobs`, `generatejitconfig` and `pools/0/agents`. Scale-set churn is GitHub-controlled and customers upgrade ARC independently, so pin a supported ARC range.
10. [inference] Port the C# `GitHub.Actions.WorkflowParser` (MIT) to Rust for server-side semantics, using the shared `workflow-v1.0.json` as data; use `@actions/workflow-parser` only as a differential oracle in tests. Encoding the job message requires a faithful port of the template-token and context-data JSON converters.
11. [inference] Mint OIDC tokens with GHES-style issuer `https://HOST/_services/token` and the legacy `sub` format by default; offer the immutable `OWNER@ID/REPO@ID` format as opt-in.
12. [inference] Runner images are not reusable on AWS as-is; plan either a ported Packer source or a smaller curated AMI for managed runners.

## Open questions

1. Does GHES 3.22 use the broker and run service, or the legacy distributedtask flow? Not verified; GHES does not publish this.
2. Will toolkit PR #2123 or issue #2439 land, and would a vendor flag accept Graftyard? Both are open as of 2026-07-31 with no maintainer response visible.
3. Is it acceptable for the launch resolver to serve rewritten bundles of `actions/*` actions? This is a security and trust decision, not a protocol one.
4. The claim that GHES 3.13+ has an artifact v2 backend came from a third party and was not confirmed in GHES docs.
5. GitHub's stateless `ghs_` installation token format (reported by WireCensus, dotcom only since 2026-10-02) may matter if actions parse `GITHUB_TOKEN`; GHES is reported unaffected. Not checked against toolkit code here.
6. The exact history of the `isGhes()` hostname list could not be read because the partial toolkit clone failed on pickaxe searches.
7. The Forgejo runner's full protocol was not read beyond go.mod and the cache handler; its server-side artifact v4 code (inherited from Gitea) was not inspected.
