# Clients: how each one targets GHES

## Answer

Every client in scope finds a GHES host with one of a few cheap signals. A host is "enterprise" when it is not `github.com`, not `*.ghe.com`, and not `github.localhost`. REST then lives at `https://<host>/api/v3/`, GraphQL at `https://<host>/api/graphql`, uploads at `/api/uploads/`, and OAuth at `/login/oauth/*` and `/login/device/code` on the bare host. Clients that probe instead of trusting configuration look for the `X-GitHub-Request-Id` header (GCM, GitHub Desktop, VS Code Pull Requests, Dependabot) and read the version from `X-GitHub-Enterprise-Version` (Desktop, VS Code Pull Requests, JetBrains, Renovate) or from `/api/v3/meta` `installed_version` (gh, GCM, VS Code auth). Version floors are low: GCM and JetBrains need 3.2 or later. Renovate and gh gate features by version, and Renovate refuses fine-grained tokens when the header is missing. GHES ships GitHub's own first-party OAuth apps preinstalled. The docs list them by name only (GitHub CLI, Git Credential Manager, GitHub Desktop, Visual Studio Code, JetBrains IDE Integration, and others). The client ids that matter are hardcoded in client source, so Graftyard must seed those exact ids with GHES-era callback URLs. GraphQL is load-bearing for gh, VS Code Pull Requests, JetBrains, Renovate, and terraform-provider-github (branch protection). VS Code Pull Requests (`.gql` files) and JetBrains (`.graphql` files) are easy to harvest statically. gh is only partly harvestable because it builds many queries by reflection or from field lists at runtime. No other forge got far with GitHub API compatibility. GitBucket went furthest with about 105 REST routes under `/api/v3` and no GraphQL, while Gitea and Forgejo copy webhook headers and workflow syntax but not the API. GPUI works for a native app on macOS, Windows, and Linux under Apache-2.0. It is pre-1.0, and crates.io lags a year behind Zed's repo. GitHub's own web UI is React with SSR on Primer React, and styled-components is now gone.

### gh CLI

1. gh classifies hosts with three constants: `github.com`, `github.localhost`, and tenancy suffix `ghe.com`. Any other host is GHES (`IsEnterprise`). Source: go-gh `pkg/auth/auth.go` lines 26-28, 161-173. [source]
2. `NormalizeHostname` maps any host ending in `.github.com` to `github.com` and any `*.github.localhost` to `github.localhost`. A Graftyard host under `github.com` is impossible, and `*.ghe.com` gets dotcom-style `api.` subdomain routing. Source: go-gh `pkg/auth/auth.go` lines 178-195. [source]
3. For GHES, gh derives REST `https://<host>/api/v3/`, GraphQL `https://<host>/api/graphql`, gists `https://<host>/gist/`, and the web prefix `https://<host>/`. Dotcom and tenancy use `api.<host>`. `garage.github.com` is special-cased like GHES. Source: cli `internal/ghinstance/host.go` lines 32-107. [source]
4. gh rejects hostnames containing `:` or `/` in `auth login --hostname`, `api --hostname`, and prompts, so gh cannot target a non-443 port. Only `github.localhost` gets plain http. Source: cli `internal/ghinstance/host.go` lines 36-44, 102-107; `pkg/cmd/auth/login/login.go` line 163. [source]
5. Config knobs: `gh auth login --hostname <host>`, `GH_HOST` for the default host, and `GH_ENTERPRISE_TOKEN` or `GITHUB_ENTERPRISE_TOKEN` for GHES tokens (`GH_TOKEN` applies only to dotcom, tenancy, and localhost). gh also infers the host from git remotes, keeping only authenticated hosts. Remote paths must be exactly `owner/repo`. Source: go-gh `auth.go` lines 19-23, 63-82; cli `pkg/cmd/root/help_topic.go` lines 49-55; `context/remote.go` lines 37-48; `internal/ghrepo/repo.go` lines 61-72. [source]
6. OAuth: gh's "GitHub CLI" OAuth app is client id `178c6fc778ccc68e1d6a` with embedded secret `34ddeff2b558a23d38fba8a6de74f086ede1cc0b`, and the minimum scopes are `repo read:org gist`. Source: cli `internal/authflow/flow.go` lines 22-25, 45. [source]
7. gh tries device flow first (`/login/device/code`) and falls back to web flow (`/login/oauth/authorize`, `/login/oauth/access_token`) when the device endpoint answers 401, 403, 404, 422, or 400 `unauthorized_client`. Source: cli/oauth `oauth.go` lines 36-46, 105-111; `device/device_flow.go` lines 92-96. [source]
8. gh sends callback `http://127.0.0.1/callback` to dotcom but `http://localhost/` to GHES. A code comment says "the OAuth app on Enterprise hosts is still registered with a legacy callback URL." gh can now request refresh tokens (`offline_access`) through `oauth.Refresh`. Source: cli `internal/authflow/flow.go` lines 125-132; `internal/authflow/refresh.go` lines 33-78. [source]
9. Version detection: on GHES only, gh reads `installed_version` from `GET /api/v3/meta` and probes the GraphQL schema with `__type(name: ...)` introspection for Issue, PullRequest, Repository, ProjectV2, Release, and others. Projects v1 is treated as removed from 3.17.0. Source: cli `internal/featuredetection/feature_detection.go` lines 189-206, 332-347, 570-585. [source]
10. gh reads `X-Oauth-Scopes` to report missing scopes and sends `X-GitHub-Api-Version: 2022-11-28` and `GraphQL-Features` headers. Source: cli `api/client.go` lines 19-23, 328-347; `pkg/cmd/auth/shared/oauth_scopes.go` line 56. [source]

### git, Git Credential Manager, git-lfs

Source: GCM `GitHubHostProvider.cs` lines 402-468; `GitHubRestApi.cs` lines 206-227; `GitHubConstants.cs` line 38. [source]

### GitHub Desktop

15. Desktop classifies endpoints as dotcom (`github.com`, `api.github.com`), GHE (`*.ghe.com`), or GHES (everything else). For GHES it uses `https://<host>/api/v3`, keeps any non-default port, and derives the web URL from the origin. Source: desktop `app/src/lib/endpoint-capabilities.ts` lines 47-68; `app/src/lib/api.ts` lines 2333-2376. [source]
16. To decide whether a URL is a GitHub host, Desktop matches `(^|\.)github\.` and excludes known third-party hosts and `bitbucket.`/`gitlab.` names. Failing that, it sends `HEAD /api/v3/meta` with a 2 s timeout and `redirect: 'error'` and checks for `x-github-request-id`. Source: desktop `api.ts` lines 2433-2512. [source]
17. Desktop reads the GHES version only from the `x-github-enterprise-version` response header. If the header is unknown it assumes 3.1.0, and it gates features by semver (for example avatars need >= 3.0.0). Source: desktop `endpoint-capabilities.ts` lines 33-41, 120-140; `api.ts` lines 2424-2430. [source]
18. Auth is web flow only: `/login/oauth/authorize?client_id=...&scope=repo user workflow&state=...` with no `redirect_uri`, so the app's registered callback decides the redirect. Desktop registers the `x-github-desktop-auth` protocol and exchanges the code at `/login/oauth/access_token` with a client secret. It asks for `offline_access` only off GHES. Source: desktop `api.ts` lines 144, 2403-2421; `app/src/main-process/main.ts` lines 108-112; `app/src/lib/oauth-token.ts` lines 146-156. [source]
19. The production client id is injected at build time (`DESKTOP_OAUTH_CLIENT_ID`), and the source carries only a dev id, `3a723b10ac5575cc5bb9`. A user log in desktop issue #17721 shows the production id `de0e3c7e9973e1c4dd77` in the authorize URL. Source: desktop `app/app-info.ts` lines 5-6, 19-21; https://github.com/desktop/desktop/issues/17721. [source] for the dev id, [secondary] for the production id.
20. Desktop uses GraphQL once, for Copilot info, and skips it on GHES. The rest of its API use is REST. Source: desktop `api.ts` lines 2159-2184. [source]

## Implications for the design

1. [inference] Graftyard should present the GHES URL shape exactly: one bare HTTPS hostname on port 443 with `/api/v3/`, `/api/graphql`, `/api/uploads/`, `/login/oauth/*`, `/login/device/code`, and `owner/repo` paths. Port 443 is required because gh rejects ports. Subdomain isolation (`raw.`, `gist.`, `uploads.`) should be optional, because GCM strips those prefixes.
2. [inference] Every response, including git smart-HTTP, `HEAD` on repo URLs, `/status`, `/api/v3/meta`, and `/api/v3/rate_limit`, should carry `X-GitHub-Request-Id` and `X-GitHub-Enterprise-Version`. GCM, Desktop, VSPR, and Dependabot key on the first. JetBrains and Renovate break or degrade without a parseable `3.x.y` second.
3. [inference] Graftyard must advertise a real GHES version (for example `3.22.0`) in the header and in `/meta installed_version`, and the REST and GraphQL schemas must match that GHES release's published schema. Clients gate features on the number and on `__type` introspection, so the advertised version is a contract. Bumping it is a release event.
4. [inference] Both `GET /status` (Dependabot) and `GET /api/v3/status` (VS Code Pull Requests) must return 200, and the latter needs a body starting `GitHub lives!`. `GET /api/v3/` must return the root hypermedia document with `rate_limit_url`. Unauthenticated 401s should carry `X-GitHub-Media-Type` and a `documentation_url` under `https://docs.github.com/enterprise`.
5. [inference] Identity must seed first-party OAuth apps with the hardcoded ids: gh, GCM, VS Code, and Desktop production, plus Desktop dev for testing. They need GHES-era callbacks (`http://localhost/` for gh and GCM, `x-github-desktop-auth://...` for Desktop), device flow enabled, and either the embedded secrets or public-client handling that ignores the secret for these ids. The exact Desktop callback URI is unverified.
6. [inference] Token formats are part of the wire contract. Renovate branches on `ghp_`, `ghs_`, and `github_pat_` prefixes, and gh reads `X-Oauth-Scopes`. Graftyard tokens should use GitHub's prefixes and scope headers.
7. [inference] GraphQL cannot be deferred if VS Code Pull Requests, JetBrains, gh PR commands, Renovate automerge, or terraform branch protection are targets. GraphQL errors must use GitHub's `extensions.code` values (VSPR falls back to its limited query set on `undefinedField`).
8. [inference] A static GraphQL conformance gate is cheap. Validate every operation in VSPR's `.gql` files, JetBrains' `.graphql` files, Renovate's query strings, and gh's raw strings against Graftyard's introspected schema and against `github/docs` `ghes-3.22`. Cover gh's reflection queries by recording a gh acceptance run through a proxy.
9. [inference] Naming customer hosts `github.<domain>` makes GCM and Desktop detect them without a network probe. That naming should be a recommendation, never a requirement. Hosts must never end in `.github.com` or `.ghe.com`.
10. [inference] Dependabot and ARC compatibility depend on the Actions control plane (registration, `_apis/runtime/runnerscalesets`, and Dependabot-labelled runners), so they belong with the `actions-protocol.md` tier and not the REST tier.
11. [inference] GPUI is viable for a native client on all three desktop OSes, but the team should vendor it by git rev or `gpui-pre` and budget for breaking changes. A React web UI on Primer React, which GitHub itself uses, is the parity path for the browser.
12. [inference] No prior forge reached unmodified-client compatibility. GitBucket's subset shows that REST alone is not enough for today's clients, so Graftyard should not plan on copying a prior forge's API layer.
