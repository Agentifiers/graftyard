# F47: the wasm `unreachable` in `host::commit_tx`

F47 (`decisions/OPEN-QUESTIONS.md`) asks what raises the wasm `RuntimeError: unreachable` that site c's member of `repo:196628` hit 8 times during BF-20, with no Rust panic message before it. Each one makes workers-rs 0.8.7 rebuild the wasm instance, which resets every member in that isolate.

**Answer.** The isolate ran out of memory. Four things in the site script held a second large copy of a member's state beside the member itself, and pushed the isolate's wasm memory to 128 to 141 MB. At that size the next allocation on the JS side of a wasm-bindgen import failed with `RangeError: Invalid array buffer length`. wasm-bindgen turns a failed import into `Critical error` and marks the instance terminated. The next import shim's check then executes `unreachable`. Nothing in Rust panicked.

- `Member::restore` cloned the stored log window and fold it was handed. Restoring a `repo:65536` member held both copies, up to 118 MB of live heap.
- The fold audit's replay (`/fold {"replay"}`, run by the site cron every 15 minutes) collected every log row before it refolded them, up to 131 MB.
- Even reading one row at a time, the replay's in-memory refold of `repo:65536`, with 2,000 entries and 102.6 MB of log, grew to 110 MB of live heap. `REPLAY_MAX` bounds the entries a replay reads, not their bytes.
- A reset member's tick loop kept its `Host` alive. After `ctx.abort()` the object's timers never fire, so the loop parked on its `Delay` never ended, and its `Rc<Host>` kept the reset member's log window and fold in the isolate. The next request restored a second member beside it. One isolate held 1, 2, then 3 live hosts, at 40, 82, then 124 MB of live heap.

The fixes are `c3e9fa1`, `6e89c6e`, and `e5c6021`. On `graft-m2b` the old code lost 13 instances in 3.24 h. Under the same load the final build lost none to memory in 1.28 h (see "Evidence it is gone").

Run on 2026-11-05 on the `graft-m2b` install (`tests/m2/results/install-m2b.md`), never on `graft-m1`. The raw data is in `tests/m2/raw/2026-11-05/f47/`, which is not committed, like the earlier raw data.

## Reproduction

- **Install.** `graft-m2b-site-a/b/c` (enam, weur, apac), `test-faults`, and the BF-20 repository `repo:65536` seeded to 1.33 M metadata rows and 3.99 GB on each member.
- **Load.** `tests/m2/bf20/bf20d.sh 300` (one snapshot run to its commit) then `bf20c.sh 300` (three phases: baseline, metadata snapshot running, baseline), both at 300 commands per second, with the driver variables in `install-m2b.md` (`tools/after.sh`).
- **First abort.** At 03:08:12Z, site c's member `27e9657c` on version `61888006` (a plain `test-faults` build with no instrument) lost its instance on a `/raft` POST during the snapshot phase. A wasm `unreachable` at `call1` in `host::commit_tx`, under `Host::flush`, ended the request with "Promise will never complete." This is m1's stack (below), so `graft-m2b` reproduces F47 without any probe. The only large request in that isolate before it was a cron `/fold` audit at 03:00:39Z [inference: Workers Logs for `27e9657c`, 02:45 to 03:08].
- **Amplifier.** `tools/amp.sh` runs the fold audit once a minute through `/bench_seed {"audit"}` (the cron's code path, test installs only) and resets site c's member every 5 minutes, so it restores. It runs beside the load. It makes the replay and restore paths run more often than the cron does (every minute against every 15 minutes) and adds no path of its own. The per-hour rates below are therefore higher than an install without it would see [inference].

## The stack

`workers/site` has no `console_error_panic_hook` crate, and needs none. workers-rs 0.8.7 installs a panic hook that logs `Rust panic: …` (`worker-0.8.7`, `src/init.rs`), and no abort was preceded by one. The release wasm keeps its name section, so Workers Logs and `wrangler tail` give symbolized wasm frames.

One instrument was added to throwaway builds: `tools/probe-patch.py`. It patches the generated glue's catch handler to log the exception that marks the instance terminated, with its stack, its `cause`, and the wasm memory size, before the glue sets the terminated flag.

The 03:18:50Z abort on site c, on probe build `c8ee11ac`, from `before/tail-c.jsonl` (tail timestamp 1793848730447), with Rust's crate hashes dropped:

```
F47 terminating exception: Error: Critical error
    at __wbindgen_rethrow_critical (index.js:1203:11)
    at graftyard_site.wasm.Ref(String) -> Externref externref shim
    at graftyard_site.wasm.<worker::sql::SqlStorage>::exec::<Vec<SqlStorageValue>>
    at graftyard_site.wasm.<graftyard_site::host::commit_tx::{closure#1} ...>::into_js_function::{closure#0}
    at graftyard_site.wasm.wasm_bindgen::convert::closures::_::invoke::<Result<JsValue, JsValue>, true>
    ...
  cause: RangeError: Invalid array buffer length
  wasm memory: 138.1 MB

F47 terminating exception: RuntimeError: unreachable
    at graftyard_site.wasm.<js_sys::Function<_>>::call1::__wbg_call_a410eb4b59ed5965 externref shim
    at graftyard_site.wasm.<js_sys::Function>::call1
    at graftyard_site.wasm.graftyard_site::host::commit_tx
    at graftyard_site.wasm.<graftyard_site::host::Host<Repo>>::flush
    at graftyard_site.wasm.<graftyard_site::member::Routes<Repo>>::fetch::{closure#0}
  wasm memory: 138.1 MB
```

How the generated glue (wasm-bindgen 0.2.130) turns this into `unreachable`:

1. Inside `transactionSync`'s callback, `SqlStorage::exec` passes its query string to JS through the `Ref(String) -> Externref` shim, which reads the string out of wasm memory. That read failed with `RangeError: Invalid array buffer length` at 138.1 MB of wasm memory.
2. The shim's catch calls `__wbindgen_rethrow_critical`, which is `function(e){throw new Error("Critical error",{cause:e})}`.
3. The glue's catch handler sets the instance's terminated flag (`Q()[D]=1`) and rethrows.
4. `transactionSync` rethrows into `call1`'s shim. The shim checks the terminated flag on its way back into wasm and executes `unreachable`. That is the `RuntimeError: unreachable` at `call1`, the frame m1 logged (offset `0x439402` in m1's `ddf232c9` build, the same check).
5. workers-rs logs `Critical`, the request ends "Promise will never complete.", and the next request reinitializes the wasm instance, which resets every member in the isolate.

The `/fold` losses take the same route through a different import. Site a's 06:38:56Z loss on probe build `593c15c7`, which already had `c3e9fa1`, threw `Critical error` from `<js_sys::Uint8Array>::copy_to` under `<worker::sql::SqlCursorRawIterator>::next` in the replay, with cause `RangeError: Invalid array buffer length` at 135.5 MB of wasm memory (`probe3/stack-a-063856.txt`). A failed import that `transactionSync` does not wrap surfaces as the terminated instance's next call, "memory access out of bounds", instead of `unreachable`.

So the five causes F47 listed reduce to one. It was not a panic with `panic=abort`, not an `abort` in std, and not a `RefCell` double borrow. It was not a Rust allocation failure or a stack overflow either: Rust's allocator got its memory, and the failure was the JS side's next allocation once the isolate was near its 128 MB.

m1's Workers Logs (`before/m1-critical-workers-logs.json`) hold the same `Critical error` on `graft-m1-site-c` on 2026-11-04, in 22 requests. Twelve were on member `eda74661`: 10 `/raft`, 1 `/read`, and 1 `/status`, which include the 8 F47 counted. Ten were `/fold` on member `6b6dd5f5`, in sets about 5 s apart at 07:32, 13:31, and 19:46 [inference: the cron fold audit and its retries].

## Root cause

A throwaway build (`tools/heap-probe.diff`, never committed) wrapped the global allocator to count live heap bytes. It logged a JS stack at every new 4 MB high-water mark above 40 MB. An isolate's wasm memory only grows, so its high-water mark is set by its largest request, and every later request starts from there.

| Path | What it held | Peak live heap | Where |
| --- | --- | --- | --- |
| `Host::restore` → `Member::restore`, old code | `Self::build(.., stored.log.clone(), stored.fold.clone(), ..)`: a second copy of the log window and fold that `load` read back, beside `stored` | 118.4 MB on site c, 109.9 on b, 76.3 on a | every restore: a new isolate, a `/reset`, a deploy |
| `snap::replay`, old code | `rows(..)` collected every log row through `applied` into a `Vec`, then refolded them into a second, in-memory fold | 130.9 MB on c, 126.8 on b, 122.7 on a | the site cron's fold audit, on the leader of each chain the site homes |
| `snap::replay` on `c3e9fa1`, one row at a time | the in-memory refold: every row the log wrote, re-encoded and hashed (`encode_entry`, `row_hash`) into a `MemStore` fold | 109.6 MB live and 133.8 MB of wasm memory on b, 109.6 and 132.6 on a, 109.4 and 133.6 on c (`probe3/heaplog.txt`) | the same |
| `Host::kick`'s tick loop after a reset, old code and `6e89c6e` | the reset member's whole `Host`: its `Rc` lived in a task parked on a `Delay` that `ctx.abort()` never lets fire | one more member per reset: 40, 82, then 124 MB of live heap in isolate `ba5cc76c` (`leak/resets5.log`) | a `/reset`, a storage-write failure, a test-faults kill: every `ctx.abort()` |

Every loss on the old code came in one of these paths, or in the first request after one of them had raised the isolate's wasm memory:

- Site a's 8 losses, site b's 04:30:26Z loss, and site c's 04:15:23Z loss were `/fold` replays. Site c's ended at 130.9 MB of live heap and 134.3 MB of wasm memory.
- Site c's two `/raft` losses, 03:08:12Z and 03:18:50Z, each came in an isolate whose largest earlier request was a cron `/fold` replay, at 03:00:39Z and 03:15:50Z (Workers Logs for `27e9657c`). The replay raised the isolate's wasm memory, and the next large `/raft` input needed more than it had left [inference: no heap probe ran before 03:18:50].
- Restores reached 118.3 MB of live heap on site c at 04:02:56Z, in `<LogEntry as ToOwned>::to_vec` under `Host::restore` (`before/tail-c.jsonl`), close enough to the limit that the next large input would fail the same way.
- Site b's 05:55:16Z alarm loss came with 141.5 MB of wasm memory and a heap peak of 125.4 MB, set by an audit replay at 05:46:37Z in the same isolate.
- On `6e89c6e`, with the replay skipped, site c lost its instance at 07:15:40Z on the `/isolate` request after a `/reset`. Its isolate `e1f4da48` had stepped from 89 to 127 MB of wasm memory at the 07:04:57Z reset, with no replay and no snapshot step in between (`/tmp`'s memory monitor, `after2/site-c-071540.txt`).

**How the leak was found.** Probe builds on `graft-m2b` counted live `Host`s (constructor minus `Drop`), live `Member` objects, and live spawned tasks by the function that spawned them (`leak/probe7.diff`), and reset site c's member every 30 to 40 s under load (`leak/resets.sh`):

| Build | After reset 1 | After reset 2 | After reset 3 |
| --- | --- | --- | --- |
| `6e89c6e` plus counters (`leak/resets5.log`) | 1 member, 1 host, 40.0 MB live | 2 members, 2 hosts, 81.1 MB | 1 member, 3 hosts, 124.3 MB, 3 `kick` tasks |
| `e5c6021` plus counters (`leak/resets6-fixed.log`) | 1 member, 1 host, 39.7 MB | 1 member, 1 host, 40.8 MB | 2, 2, 82.5 MB, then 1 host and 39.9 MB on the next read |

On the old code a host outlived its `Member` object, and each leaked host matched one `kick` task still alive. With the loop holding a `Weak`, a host can outlive its object only while an input it was serving is still running. Its count returns to 1 by the next read.

The first place the system went wrong is the extra copy, not the `transactionSync` call that surfaced it. A member that holds its log window once, an audit that never refolds more log in memory than an isolate can hold, and a reset member that leaves nothing behind stay under the limit.

Two other holders were measured and are not causes. The snapshot alarm (`snap::step`) holds 3 to 4 copies of an 8 MiB part, at most 75 MB of live heap. `Host::load` reads the log window once, 30 MB, before the clone. Restore's own replay check (`RESTORE_CHECK_MAX`) does not run for tiered folds such as `repo:*`.

## The fix

Commit `c3e9fa1`:

- `crates/raft/src/member/mod.rs`: `Member::restore` takes `Stored<C::Fold>` by value and moves its state, base, log, and fold into the member, so no second copy exists. Callers that keep their disk (`crates/raft/tests/common/{cluster,sim}.rs`, `crates/identity/tests/common/mod.rs`, `crates/git/src/standin.rs`) pass a clone, as before.
- `workers/site/src/host.rs`: `Host::restore` passes `stored` by value. This is one line.
- `workers/site/src/snap.rs`: `replay` reads the log one row at a time through `SqlStorage::exec(..).raw()` instead of `rows(..)`.

Commit `6e89c6e`:

- `workers/site/src/snap.rs`: `replay` first reads `SUM(length(row))` of the log through `applied`. Past `REPLAY_BYTES`, 16 MB [guess], it returns `{"skip": "<n> log bytes, past the 16000000 one request refolds"}`, as it already did past `REPLAY_MAX` entries. `fold_audit` already reports a skip as the chain's result and asks no member for a digest. At the measured ratio of 63 MB of refold for 102.6 MB of log, 16 MB of log is about 10 MB of refold.

The protocol is unchanged. `restore` does the same work on the same values. The long sweep and Porcupine pass (see "Checks").

Commit `e5c6021`:

- `workers/site/src/host.rs`, `Host::kick`: the tick loop holds a `Weak<Host>` across each `Delay` and upgrades it only to tick. A task parked on a timer that never fires now holds nothing. The loop's behavior while the object lives is unchanged. This is 8 changed lines.

**What the byte bound costs.** The fold audit no longer refolds a chain whose log through `applied` is over 16 MB. On `graft-m2b` that is `repo:65536`, whose audit now answers `"skip": "107734367 log bytes, past the 16000000 one request refolds"` (`after2/amp-after2.log`). Such a chain is audited by the members' digest comparison only after a refold that does not hold the whole fold in memory exists. A refold into a scratch SQLite table, or across several requests the way `refold_page` resumes, would remove the bound. Neither is in this change.

## The test

`crates/raft/tests/restore_memory.rs`, `restore_holds_no_second_copy_of_the_stored_log_or_fold`. It is committed before the fix (`7a47f94`).

- It commits 200 entries of 20 KB through a three-member cluster, clones a follower's disk (12.1 MB of live heap), and restores a member from it.
- It counts the thread's live heap with a counting global allocator.
- It requires restore to raise the live heap by less than a quarter of what it was handed.

| Tree | Result |
| --- | --- |
| `7a47f94` (old `restore`) | **Fails**: "restore raised the live heap by 12216788 bytes over 12147815 bytes stored" |
| `c3e9fa1` (fix) | Passes |

The replay changes and the tick loop have no local test. `snap::replay` runs only on `SqlStorage` inside a Durable Object, a `Host` needs a Durable Object `State`, and the leak needs `ctx.abort()` dropping a timer. The workspace has no local Durable Object runtime: `workers/site`'s native tests cover only pure functions (`answer`, `tier`, `sweep`). The evidence for these changes is the hosted counters above and the run below.

## Design sentences this contradicts

`design/SHARED.md`, "Folds", says `fold_audit` "Refolds sampled chains from genesis on each release and daily, compares `fold_digest`, and alarms on any mismatch." After `6e89c6e`, a sampled chain whose stored log is over 16 MB is not refolded. It is reported as skipped, as a chain with more than `REPLAY_MAX` entries or a truncated log already was. The audit's coverage of large chains needs a refold that does not hold the whole fold in one isolate's memory. That is a design question for the owner of `design/SHARED.md`; this change does not edit the design.
