# M0-WP12: leases, the activity feed, and the core tier (2026-10-30)

Rows: L0-01, L0-12, L0-13, L0-16, LF-12, and LF-13 (`build/BUILD-PLAN.md`, M0-WP12). Raw files are `results/raw/wp12-<row>-<run>-<phase>.json`, with each runner's log beside them as `results/raw/wp12-<row>-<run>.log`. This file is written row by row as runs finish.

## What was built

**Members** (`src/wp12/member.ts`, `types.ts`, `faults.ts`, `sha256.ts`, `health.ts`), deployed as `graft-wp12-a` (enam), `graft-wp12-b` (weur), and `graft-wp12-c` (apac). This is a copy of the M0-WP9 member (`src/wp9/`), which is itself a copy of the M0-WP2 Raft member. Everything M0-WP9 lists under "What was built" is kept: admission, staging, inline packs, leader-fed learners, and feed polls served only by following members. The copy adds the following.

- **Agent-layer commands in group commit.** `XOp` commands are decided by `decideX` (`src/wp12/lease.ts`) inside the leader's entry. `decideX` is pure. It reads only `CoreView`, the core tier with an overlay of unapplied entries and earlier commands of the same entry, plus `at`. The commands are `LeaseAcquire`, `LeaseRenew`, `LeaseRelease`, plan blocks, task cancel, agent pushes and REST ref writes under `AgentsExclusive`, `Merge` (approved review on the head, green required check, `AgentGate` for agent PRs, compare-and-set on the base), and metadata-only writes. Followers recheck ref compare-and-sets and every Exclusive acquire against their own fold in `verify`, and count a mismatch as an alarm.
- **Types with the design's names** (`src/wp12/lease.ts`, `fleet.ts`): `Lease`, `LeaseHolder`, `ActorId`, `LeaseMode`, `LeaseEnforce` (`Enforce`), `PathGlob` and `RefPattern` (the M0-WP10 glob code, copied), and the lease constants `LEASE_TTL`, `EXCLUSIVE_MAX`, `LEASES_PER_HOLDER`, `LEASES_PER_APP`, `PLAN_LEASES_PER_REPO`, and `LEASES_PER_REPO`. `ActorKind` comes from the M0-WP10 rule, copied: a Graftyard-run App, or a flagged App with `confine`, is `Agent`; a flagged App without `confine` is `Bot`; `Graftyard MCP` and user tokens are `User`. Expiry is `at < expires` on the entry's `at`. A lease reads as Shared past `EXCLUSIVE_MAX`. A lease whose holder fails the `Authz` read (installation inactive or without push, user without write, or an Exclusive lease whose task is final or whose installation is inactive) counts as released. Exclusive globs are indexed by literal prefix (`x_lease_px`).
- **Two tiers.** The core tier is the SQLite tables `x_lease`, `x_lease_px`, and `x_row` (tasks, collaborators, `AgentPolicy`, `Authz` rows, PR heads, review verdicts, required checks, gates) plus the ref register. The metadata tier is `x_meta`. In a group whose name holds `core-`, `apply` writes no metadata rows and the feed ring stays empty until something calls `loadMeta`. `loadMeta` refolds the tier from the log and counts the load against the path that asked (`metaLoads`). No method of `CoreView` reads `x_meta`.
- **`ExtendLeases` and `stalled_since`** (`design/DESIGN.md`, Shape, "Chains"). A member persists `stalled_since` at the earliest of its own markers: a follower's first `suspect` about the leader it follows, a candidate's campaign start, or the leader's first entry that no quorum acknowledged within `CALL_DEADLINE`. Followers report their marker in AppendEntries replies and votes. The first entry a leader builds after a marker, including a new term's `Noop`, carries `extend: { since, by: at - since }` inside its body, so the chained digest covers it. `apply` moves every lease with `expires > since` by `by` on every member, then clears the marker. Entry `at` never decreases: a new leader stamps `max(now, last at)`.
- **Feed.** Ring rows carry the entry's leader `at`, the paths its events touch (a push's changed paths, a lease's globs), and the event kinds, including `Lease:Expired` at the first entry with `at >= expires`. `paths` are `PathGlob`s matched by the overlap rule. A poll returns the ring rows past its cursor (`ev`, with each row's `at`), so the client measures event latency from the leader's stamp. A member that stops following (a gap in AppendEntries, a new term, or an `InstallSnapshot` in progress) answers its held polls at once with their cursor and no events, and refuses new ones. A full member answers `full` with `retryAfter` = `FEED_BATCH_ALL`. The edge tries up to three serving members and then answers 429.
- **`InstallSnapshot`.** A group whose name holds `snapN-` compacts its log to the last N applied entries. A leader whose follower needs a compacted entry first sends an AppendEntries that starts past the compaction, which leaves a gap on the follower, and then sends the fold at `applied`: registers, request rows, the core tier, and the feed ring.
- **Fork groups.** A group named `...fork-of-<base>` reads, before deciding an entry, the task rows, `AgentPolicy`, live Exclusive leases, collaborators, and `Authz` rows from the base group's leader. It does this once per entry through `fresh` (`baseDeps`), as `Push::deps()` does in fork mode. If the read fails, its pushes get 503.
- **`STEP_DOWN`** as `design/DESIGN.md` now states it in the `Health` doc comment: errors over 5% to both followers in 10 s (with the M0-WP4 link probe), or at least `confirm_slow_min` storage confirmations over 500 ms in the window. That count was 3 as briefed, and 6 (the design's current value) from the 11:22Z redeploy on. The transfer target is a follower outside RESET_QUARANTINE of its `stepped_down_at`, then the one with the fewest failed calls, then the most caught up, copied from `src/raft/member.ts` at the same redeploy. L0-01 `r1` ran before it and `r2` after.
- **Faults.** `src/wp12/faults.ts` is a copy of `src/faults.ts` with a regex `re` per rule. Each group reads its own `FaultControl` object, `wp12:<group>`, in `graft-wp12-load`, so one plan never touches another group. A plan older than 3 s is awaited, not refreshed in the background, so a member never acts on an old plan on its first call after an idle stretch. The edge's member calls go through the same plan, labelled `edge><site>:<method>`. `graft-m0-tools` and its plan "plan" are never read.
- **Probes.** `clock()` and `clockProbe()` measure member clock offsets by round trip, member to member and edge to member. `leaseDump`, `ringDump`, `mintToken`, `xread` (lease list, lease check, and a metadata list as the L0-16 control), and `kill` (`ctx.abort`) are the others.

**Load** (`src/wp12/load.ts`, `graft-wp12-load`). This is the M0-WP9 `Load9` load client (journey 9 / A1 at 500 agents, 30 clients pinned by hint on enam, enam, wnam, weur, and apac, run from Durable Object alarms), copied and extended per spec:

- `kind`: agent pushes become `Push` commands from that actor kind's credential, with changed paths under the agent's own scope.
- `leases`: an Exclusive lease per agent on `pkg/<a>/**` at its first push, renewed every `renewEvery`.
- `mergePrs`: queue merges become `Merge` commands on seeded PRs.
- `allPaths`: every poller sends `paths`.
- `pollSite`: polls go to one voter.
- `seenIdx`: pollers keep the ring indices they received.
- `sideMeta`: agent side commands become metadata-only writes.
- `pushAttempts`: an agent retries a failed push at once.
- `forkGroup`: pushes go to a fork group.

An alarm-driven `beginRenew` renews one lease every 5 minutes for 5 h 10 min, so L0-13's long case survives the orb sleeping.

**Runner** (`run/wp12.ts`, `run/wp12-lib.ts`, `run/wp12-rows.ts`). It provides `deploy`, `smoke`, `clocks`, one subcommand per row, and `delete`. Each row runs as named phases. A phase's raw file is its checkpoint, so a rerun with the same `--run` resumes at the next phase. Configs are in `wp12/`. Long runs ran as `amp orb service` jobs.

**The bed** (`src/wp12/fleet.ts`). One install has five actor kinds: a Graftyard-run App (101, its tokens carrying the `task` claim), a confined vendor App (201, `confine: refs/heads/claude/**`, sending `X-Graftyard-Agent-Session`), a flagged App without `confine` (301), `Graftyard MCP` (401, user-to-server tokens of writers), and human writers' user tokens sending the session header. Each fleet gets 500 tasks (its kind's session form), and `AgentPolicy.leases` is `AgentsExclusive`. A Graftyard-run `victim` task holds an Exclusive lease on `victim/**`. Tasks `idleA` and `idleB` are for the idle case. 200 open PRs are each approved on their head with a green check.

## LF-13: held polls on a follower that stops following (run `t3`, group `snap10-lf13-t3`)

**Run.** A1-shaped load at 50 agents (one push every 20 s each), 10 load clients, 90 s, with 1,000 long-pollers pinned to follower `b`, each sending `paths: pkg/**` and keeping every ring index it received. The group keeps 10 log entries (`snap10-`). 30 s in, every `append` and `installSnapshot` call to `b` failed for 5 s (fault rule `^[abc]>b:(append|installSnapshot)`, plan `wp12:snap10-lf13-t3`). The leader's first AppendEntries after the drop started past its compacted log, which left a gap on `b`, and the leader then sent `InstallSnapshot` (`results/raw/wp12-lf-13-t3-run.json`).

| Check | Result |
| --- | --- |
| Polls held on `b` before the drop | 915 (1,000 pollers; the rest were between polls) |
| Gap seen by `b` | one, 86 ms after the drop ended: `prevIndex` 161 against `last` 156, with 1,000 polls held |
| Held polls answered at the gap | 1,000 of 1,000, with their cursor and no events, received by the pollers 117 ms after the gap at p50, 280 ms at p99 and max |
| New polls while behind | 640 refused `behind` by `b`, 1,021 answered 429 by the edge; 0 accepted |
| `InstallSnapshot` | 5 sent by the leader, one installed on `b` (index 171, 352 ms from start to installed) |
| Events lost | 0 missing of 208,489 (poller, ring row) pairs checked, against the leader's ring, for 1,000 pollers that all polled across the gap; 0 duplicates; 0 ring rows the leader holds that `b` lacks up to its applied index |

**Verdict: Pass.** The fault itself is invisible to the follower while it lasts: no AppendEntries arrives, so `b` keeps serving from its applied log until the first one after the drop shows the gap. That is the row as written ("so the next one leaves a gap"), and those polls see only committed rows, so it loses nothing.

Two earlier runs failed on bugs in this copy, not in the design, and were fixed before `t3`. Run `t2` lost 47,142 of 231,196 pairs: the ring was empty after a snapshot or a restart (it was not in the snapshot or in storage), compaction ran past a follower that was still following, and 2,367 polls failed on workerd's limit of 10,000 active timeouts per isolate ("You have exceeded the number of active timeouts you may set"), because each held poll kept its timers after it was answered. The ring now lives in `x_ring` and in the snapshot, compaction never passes a follower that acked within 2 s, and an answered poll clears its timers. The timeout limit bears on `FEED_HELD_MAX` (see "Proposed design edits").

The design's metadata tier lives in metadata child groups (`design/SHARED.md`, "Folds"), so this row shows that the core paths never read metadata. It does not measure the cost of a real load.

## L0-12: leases and the feed

One group per actor kind, `l012-<kind>-r1`, each seeded with that kind's 500 tasks, 200 approved PRs, and the `victim` task's Exclusive lease on `victim/**`. The phases run in order per kind: the A1 replay with a lease per agent and two leader kills (`a1`), 100 conflicting pushes and 100 conflicting REST ref writes into `victim/**` (`conflict`), the 30-minute stall (`stall`), the idle 60 s lease and the late acquire (`idle`), member clock offsets (`clocks`), and the members' overlap and revival counters (`final`). The row says "then" between the A1 replay, the stall, the idle case, and the conflicts; the conflicts run right after the replay because they need the replay's leases and none of the later phases depend on them.

**Why the feed p99 sits just over 2 s.** A poll with `paths` returns FEED_BATCH (1 s) after its first matching event, so that event waits 1 s by design. An event that commits while the poller is between polls, or during that batch, then waits for the next poll's own FEED_BATCH. Add the follower's apply after the leader's `at` (one replication round, 100 to 250 ms here) and the reply's trip to a client on another continent, and the tail lands at 2.0 to 2.3 s. Clock offset is not the cause: edge-to-member offsets were under 10 ms (below). The 2 s line cannot be met with FEED_BATCH at 1 s on a `Tri` group with clients spread over three continents, so this cell fails by design, not by load (see "Proposed design edits").

## What is real and what is modeled

Real:
- Durable Object members on three Cloudflare sites (enam, weur, apac hints) with SQLite storage and their real placement, call latency, storage confirmations, and resets (`ctx.abort`).
- Clocks: `Date.now()` in each member and in the edge.
- Alarms that drive the load clients.
- Platform limits: workerd's 10,000 active timeouts per isolate, the default 10,000 subrequests per invocation, and Durable Object "overloaded" queues.
- Fault injection: the faults are injected, but they act on real calls.

Modeled:
- The edge and the git and REST surfaces. Load clients call members over RPC, standing in for graft-edge. "git" and "REST" differ only in the refusal shape (`ng` line versus 422).
- Packs and receive-pack.
- Tokens. Credentials are structured values, not signed tokens. Minting checks the task row and the installation `Authz` row and returns no token.
- The metadata tier, which is tables in the same object (L0-16).
- `place_learners`. The runner computes it from the members' reported peaks and sets the slots; no controller runs it.
- Fault shapes. A leader kill is `ctx.abort` plus 15 s of failed calls to the site. The stall is a hang on every member-to-member call, with the edge still reaching members. Gray enam is a 30% error rate on calls to and from `a`.
- Clock offsets are measured by round trip, so a bound is |offset| + rtt/2.

## LF-12: what drove the request rate in `r3` (diagnosis from the load clients' own counters)

Summed over the 100 load clients of each no-learner phase (`results` of runs `r2-nolearn` and `r3-nolearn`):

| Counter | `r2` no learners (passed) | `r3` no learners (failed) |
| --- | --- | --- |
| `suspect` reports sent (2 member calls each, after a commit or read missed `CALL_DEADLINE` of 1 s) | 0 | 13,674 |
| `notLeader` redirects followed (each a retried commit or read) | 0 | 55,909 |
| Commands given up after retries | 0 | 1,165 |
| Commit and read errors (deadline, overloaded) | 0 | 23,000 or more, spread over every client colo |
| Client timeouts per 30 s (code 3) | 0 | 373, 575, 175, then under 20 |
| Leader term at the end | 2 (no change) | 10 |

The first deadline misses in `r3` came 1.0 s into the run, on commits to leader `a` (EWR), before any poll was full. Each missed receipt makes the edge send `suspect` to both other members. Reports from two colos within 10 s make a follower withhold its promise, so the leader loses its lease and the group elects again. Then every client's next commit and read goes to a member that is no longer the leader, gets `notLeader`, and retries. The reads (276 a second, every one on the leader) and commits follow the leader around, so each new leader takes the whole backlog at once and some of its followers' AppendEntries replies queue past the platform's limit ("Durable Object is overloaded. Requests queued for too long."). The voters holding no polls in the placed phases were in the same position: they were the leader or the next leader. In `r3`'s placed phases, `notLeader` redirects were 3,994 and 1,273 and suspects were 1,660 and 108, against 0 in every phase of `r2`.

So the request rate came from **edge retries after missed deadlines** (suspects, `notLeader` redirects, re-sent reads and commits), not from held polls and not from the edge's three tries per poll. Feed tries do add load: in `r3` with no learners, 84,010 polls found every member full, about 250,000 member calls in 300 s. That load lands on the followers, though, and the overloaded replies came after the elections started, not before.

Two things in the prototype make this worse than the design would:
1. **One `suspect` per missed call, from each of 100 load clients.** These clients run in about 20 colos, so `SUSPECT_COLOS` (2) is met within a second of any leader slowdown. A real edge is one Worker per colo, but each colo sends many requests, so the same reports would come from many colos. This is the design's rule, and it behaved as written.
2. **No backoff on reads after `notLeader`.** `Caller.read` retries at once on a named leader (src/wp12/load.ts). The design's edge rule is the same ("the edge follows `ReplyMeta`"), so this too is the design, not a prototype bug.

What remains open is why `r3`'s first second had commit deadline misses at all when `r2`'s had none. The placements differed (`r2` ATL, MRS, SIN; `r3` EWR, MAD, SIN). The two reruns below record per-member request counts by method, `reqs`, reset at the start of each phase, so the next difference can be read off the members.

## Fourth pass (2026-10-30): the feed's lag rule (edit 11)

**What changed in `src/wp12/`.** Adopted edit 11 says a member holds polls only while following, and following now also needs the member to have applied an entry within FEED_BATCH (1 s) of the leader's `at` on it. In `member.ts`, each batch `applyUpTo` applies is judged by its newest entry: delay = member clock at apply − leader's `at` (clock offsets under 52 ms, F3). A follower whose delay passes FEED_BATCH:
- turns `lagging`;
- answers its held polls at once with their cursor (`lagStopped`);
- refuses new polls with `notServing: "lagging"` (`lagRefused`), so the edge tries up to two others, as on a gap. `load.ts`'s `Caller.poll` already moves on after `notServing` and stops only at `full`.

It follows again once an entry applies within FEED_BATCH. An idle group applies nothing, so it keeps its last judgement. Each member keeps two histograms, both bucketed at 50/100/200/300/500/750/1k/1.5k/2k/3k/5k/10k ms and above:
- `lagAtAppend`: the apply delay per batch;
- `lagAtPoll`: the delay each poll arrived under, which is 0 while not lagging.

The runner (`run/wp12-rows.ts`) now reports these per member. `node run/wp12.ts delete` now empties the bucket through the R2 API before deleting it, which fixes the third pass's "not empty" failure.

**Runs.** A fresh bed (new bucket `graft-wp12-stage`), driven by service `wp12-pass4` running `wp12/pass4.sh`. L0-12 A1-with-kills feed phase, run `t4`, one fresh group per kind (`l012-<kind>-t4`). Then LF-12 run `r10` on fresh groups per phase.

## Fifth pass (2026-10-30): the edge's last resort (proposed edit 13)

**What changed in `src/wp12/`.** This tests the fourth pass's edit 13, which is a proposal and not yet the design.
- **Member** (`member.ts`):
  - `feed` takes a `lastResort` flag. A member refusing as `lagging` now says how far behind it is (`lagMs`, its last apply delay).
  - A follower that is lagging, but has no gap and is not catching up, holds a poll marked `lastResort` instead of refusing it.
  - FEED_HELD_MAX still applies, so such a poll can still get `full`.

- **Edge** (`load.ts`, `Caller.poll`): when every member it tried refused as `lagging`, the edge sends the poll once more, marked `lastResort`, to the least-lagged of them. **What changed in `src/wp12/member.ts`.**
- **The design's `STEP_DOWN` target rule,** ported from src/raft/member.ts. A target must be undrained, able to follow, and outside RESET_QUARANTINE of its own `stepped_down_at`. Beyond that, it depends on the trip:
