## What was built

  `@modelcontextprotocol/sdk` 1.32.2 as `sdkv1`). `src/wp15/node_modules` is a symlink to them, so Wrangler resolves
  them from the Worker sources.
- The Python SDK client runs from a virtualenv outside the repository, `~/.cache/wp15-venv` (`mcp` 2.3.0).
- `src/wp15/host/oauth.ts` and `ghes.ts`: GHES's user-token surface (`/login/oauth/authorize`, `/login/oauth/access_token`
  with ghu_ plus ghr_ and rotation, `DELETE /applications/{client_id}/token` and `/grant`, `DELETE /installation/token`)
  and the grant endpoints `/api/graftyard/v1/mcp/grants` (POST, GET, `/{id}/generation`, DELETE). `LAYER=off` turns off
  every `/api/graftyard/` and `/_graftyard/` path, the agent media type, the feed edge, Code Mode, and the `AgentApp` rows.

  (`frame-ancestors 'none'`, `X-Frame-Options: DENY`, same-origin POST only), a `__Host-` SameSite=Lax cookie set only after
  consent and bound to the upstream `state`, `McpToken`/`McpRefresh`/codes sealed with AES-GCM, narrowed refresh with the
  grant generation, and RFC 8693 token exchange to a narrowed host token. The tools are `call`, and each makes one REST
  call over the `EDGE` service binding. `src/wp15/seal.ts` does the sealing.
- `src/wp15/aux.ts` (`graft-wp15-aux`): the CIMD documents (plus `big`, `redirect`, `wrong-id`, `slow` negatives) and a
  webhook sink that checks `X-Hub-Signature-256`.
- Clients: `wp15/ts-client.ts` (v2 and v1), `wp15/py_client.py`, `wp15/goclient/` (binary built to `~/.cache/wp15/`),
  and `run/wp15-browser.ts`, which plays the user's browser through consent with fetch.

### Findings while building (L0-08)

- **The SDK clients request every scope the PRM advertises.** `@modelcontextprotocol/client` 2.4.0, with no scope
  configured, asked for `write:read write:write write:write_approve_merge tools:...` because the protected resource
  metadata listed them all, and a user who clicks Allow grants approve and merge. `graft-mcp` now advertises only
  `write:read` in `scopes_supported`, so a client that asks for nothing more gets a read grant. Write scopes must be
  requested explicitly. See the proposed edit to A7 step 2.

## L0-08, MCP: clients (run 2026-10-30, raw `results/raw/wp15-l008-clients.jsonl`)

Each client is unmodified SDK code. The drivers supply only token storage and the "open a browser" step, which
`run/wp15-browser.ts` scripts: load the consent page, click Allow, sign in to the host with bob's session, and hand
the client its callback URL. The SDK's own `auth()` performs discovery from `WWW-Authenticate`, RFC 9728, RFC 8414,
CIMD as `client_id`, PKCE S256, RFC 8707 `resource`, and the RFC 9207 `iss` check.

Which clients implement 2026-07-28: the TypeScript SDK v2 (2.x, `server/discover` and the per-request `_meta`), the
Python SDK 2.x, and the Go SDK v1.8.0 (`protocolVersion20260728` is its latest), as their source shows. The
TypeScript v1 line (1.32.2) and `fastmcp` 4.1.4 stop at 2025-11-25. The Rust SDK `rmcp` 3.8.0 also has
`V_2026_07_28`, but no Rust toolchain is in the orb, so it was not run. Three 2026-07-28 clients exist and ran.

**Tool overhead p50.** Inside a Worker, `Date.now()` advances only across I/O, so graft-mcp's own `Server-Timing`
(`mcp` minus `edge`) reads 0 ms for every call. That reading is not a measurement. The usable number is client-side:
the p50 of a tool call through graft-mcp minus the p50 of the same REST request sent straight to the host from the same
process, interleaved call by call. That gives **1 to 9 ms** (TS v2 1 ms, TS v1 7 ms, Python 9 ms, Go 2 ms, with
direct p50s of 86 to 89 ms). Pass is at most 50 ms. The figure covers one extra Worker hop over a service binding, MCP
framing, and JSON-RPC parsing. It does not cover the sealed-token open, which is AES-GCM on under 1 KB.

### L0-11 verdict: partial (pass against the prototype; not measured against GHES)

The bytes are identical except request ids and times: 0 of 1,011 after the mask, and 0 body differences even before it. That meets the Pass value as worded. The verdict is partial because the base is the prototype host, not GHES 3.22. What this shows is that switching the agent layer off changes no byte a non-opted-in client sees. It does not show that either side is GHES. ## Proposed design edits

None of these are applied; design/ is not edited by this package. Each quotes the current sentence exactly.

1. **PRM must advertise only the read scope.**
   - File and section: `design/AGENT-LAYER.md`, Journeys, A7 step 2.
   - Current: "That metadata names `mcp.<host>` as the authorization server, whose RFC 8414 metadata advertises PKCE S256 and Client ID Metadata Documents (7.1)."
   - Proposed: "That metadata names `mcp.<host>` as the authorization server, whose RFC 8414 metadata advertises PKCE S256 and Client ID Metadata Documents (7.1). Its `scopes_supported` lists only the read write scope, because SDK clients request every advertised scope, so `Write` and `WriteApproveMerge` are granted only when a client asks for them by name [measured]."
   - Evidence: L0-08 build finding. `@modelcontextprotocol/client` 2.4.0, with no scope configured, requested `write:read write:write write:write_approve_merge tools:...` when the PRM listed them all. With only `write:read` listed, the four clients got read grants.

2. **Say what authenticates the generation call at refresh time.**
   - File and section: `design/AGENT-LAYER.md`, API reference, the `/mcp/grants` block.
   - Current: "/mcp/grants:   # Basic client_id:client_secret of the install's Graftyard MCP, and X-Graftyard-User-Token: ghu_"
   - Proposed: "/mcp/grants:   # Basic client_id:client_secret of the install's Graftyard MCP, and X-Graftyard-User-Token: ghu_ (POST and GET only; `/{id}/generation` takes the client credentials alone, because at refresh time `graft-mcp` holds only the sealed `ghr_`, and the generation check must run before the upstream refresh rotates it)"
   - Evidence: building `graft-mcp`'s refresh path (`src/wp15/mcp.ts`, `grant_type=refresh_token`). The narrowed `ghu_` from the last exchange may have expired, and the only way to get a live user token is to spend the `ghr_`. Checking the generation after that refresh would rotate the `ghr_` even for a replayed `McpRefresh`. The prototype accepts the client credentials alone (`src/wp15/host/oauth.ts`), and the L0-08 replay cell passed that way: a replayed refresh revoked the grant, and the upstream refresh never ran.

3. **The `ghr_` cell stays open.**
   - File and section: `design/AGENT-LAYER.md`, Journeys, A7 step 5, and `decisions/OPEN-QUESTIONS.md` A4.
   - Current: "Whether the `ghr_` refresh token survives that delete is a Milestone 0 row [unverified]."
   - Proposed: no change to the sentence or its tag. Add to OPEN-QUESTIONS A4: "M0-WP15 could not settle this: it needs a GHES 3.22 instance, and the prototype only models survival (`tests/m0/results/m0-wp15.md`, L0-08)."
   - Evidence: L0-08 verdict, `ghr_` cell untested.

4. **Codex's documented App cannot read check runs.**
