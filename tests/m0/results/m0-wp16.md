# M0-WP16: prediction and provenance (2026-10-30)

Rows L0-05, L0-06, and L0-10 (`build/BUILD-PLAN.md`, M0-WP16). Everything runs as its own scripts and buckets: `graft-wp16-shard` with bucket `graft-wp16-net` for the predictor, and `graft-wp16-prov` and `graft-wp16-vault` with buckets `graft-wp16-inst-a`, `graft-wp16-inst-b`, `graft-wp16-rest-a`, `graft-wp16-rest-b`, and `graft-wp16-vault` for provenance. No other bed shares a script, a bucket, or a binding.

## What was built

**Replay of a real monorepo** (`wp16/topics.py`, `wp16/replay.py`). The repository is torvalds/linux, read through a bare repository whose alternates point at the WP9 agent's clone. That clone was used read-only. Each agent branch is a real topic branch: the second parent of a merge into master between v7.1 and v7.3, with 1 to 12 non-merge commits. Each push is one of its real commits, at the commit's committer time. A branch leaves the fold when master merges it, and every push's `base` is master's real tip at that moment. The window runs from 2026-07-01 to 2026-08-16. It holds 3,134 pushes on 805 agent refs, with up to 205 refs live at once (median 168). Each push's `PathSet` is the real changed paths from the merge base, truncated to directories past `PATHS_MAX` (1,000).

**Predictor** (`src/wp16/shard.ts`, `wp16/shard/main.go`, `wp16/Dockerfile`). One container class, `PredictShard`, under the `durable_object` scheduling policy. Each object starts a `standard-4` container (4 vCPU) with `enableInternet: false` and the weur hint, and streams the replay network into it from R2. The network is one pack of 493,825 objects (791 MB, `wp16/netpack.sh`), with a `shallow` file at v7.0-rc4 and the 80 older commits that topic branches fork from. Loading took 45 to 75 s per container (`results/raw/wp16-load.txt`).

`POST /predict` is one `InsightJob`, `head` against up to `PREDICT_PAIRS` other refs, run in four steps:
1. Land the head on the current base: `git merge-tree --write-tree base head`, then `commit-tree` with parents (base, head).
2. Check that each other ref lands on the base.
3. Run `git merge-tree --write-tree --name-only <landed head> <other>`, with git's own merge base.
4. Report `Stale` for a side that conflicts with the base itself, split here into `HeadStale` and `OtherStale`.

A semaphore of `PREDICT_CPU × 4` = 2 git processes for the whole container enforces the CPU cap. The cgroup's `usage_usec` is read before and after. `POST /leads` marks the shard's site as the leading site, stored in the object. While it is set, `predict` answers `Stale` for every pair without touching the container. The overlap check is the `PathGlob` rule over the fold's live `PathSet` rows (`wp16/jobs.py`). It runs on the head SHA at push time, from the fold alone, before any PR exists.

**Runner** (`run/wp16.ts`). It sends each push as one job at its place in the replay, compressed to A1's rate of 4.17 pushes/s. The 46-day window becomes 12.5 minutes. Jobs are spread over k shards by a hash of the ref. The runner times push to verdict from the moment the job is sent until all its verdicts return. It reads every shard's cgroup CPU every 2 s and scores each verdict against ground truth.

**Ground truth** (`wp16/truth.py`). For each pair, the merge a queue would make on the current base: land the head as a merge commit on the base, then merge the other branch into it with real `git merge-tree --write-tree`. The reverse order gave the same verdict on all 15,700 overlapping pairs. Truth is computed for every overlapping pair of every push, and for 1,000 sampled pairs: 522 drawn from overlapping pairs and 478 from all live pairs. The earlier method, `wp16/predict.py`, merged two landed trees with `--merge-base=base`. Its container runs are kept as `results/raw/wp16-landed-a1-k7-size.json` and `results/raw/wp16-landed-a1-k7-recent.json` because they found a design gap ("What the replay showed about `predict`").

**Provenance install** (`src/wp16/prov.ts`, `src/wp16/gitobj.ts`). One Durable Object, `ProvRepo`, per repository group, holding:
- a digest-chained log (`prev`, `digest` as in `LogEntry`) and a SQLite fold: refs, `AgentTask` rows, PRs with `AgentMeta` and `Merged`, provenance rows, packs, and an object index;
- a snapshot every 1,000 entries, under a `snapshot/<chain>/core/0-<to>-<digest>` key in two buckets;
- each push's objects as one stored pack in two buckets, keyed by its SHA-256 `checksum`.

A push runs these steps:
1. `validate` checks every object's SHA-1 and that every link is present.
2. The M0-WP10 trailer parser parses new commits' messages, and `refs/notes/ai` blobs become `AiNote` (`src/wp16/provenance.ts`, a copy of `src/agent/provenance.ts` that differs only in its import path).
3. `decide` links `Source::Session` only when an App installation token pushes a commit whose `Graftyard-Session` URL names an `AgentTask` of that App. It writes `refs/graftyard/sessions/<id>` only for `graftyard-workspace` with that task's claim.

`resolve` follows journey A6 for each commit:
- `session:<id>` when the fold links a session and the session's host-owned ref, its commit, its tree, and its `log.json` blob all read back from the buckets;
- otherwise `pr:<n>` through `Merged` (a squash commit) or through the PR on the commit's ref;
- otherwise `none`.

**Vault** (`src/wp16/vault.ts`). Its own script and bucket, with no binding to the install. It reaches the install's edge only over public HTTPS, with an export token that reads `/export/*` and nothing else. `POST /pull` copies the next entries, every pack they name (checking the SHA-256 against the entry's `checksum`), and every new snapshot, then moves its cursor. `POST /restore` rebuilds a new group, `mono-r`, with new buckets, from the vault alone. It is called step by step, so each call stays inside one Worker invocation.

**Commits** (`wp16/provgen.py`). 10,000 real git objects of agent commits, built with `git fast-import`. Each takes the real message and trailer block of one of the 10,000 newest non-merge linux commits before v7.3, plus its first path. File contents are synthetic. The provenance trailer is appended to the message's own trailer block. 997 sessions of 5 to 15 commits each push 1 to 4 commits at a time and open a draft PR after their first push:

| Kind | Commits | Provenance | Pushed by | Expected to resolve to |
| --- | --- | --- | --- | --- |
| Graftyard-run | 3,834 | `Graftyard-Session` URL, `AgentTask`, session log under `refs/graftyard/sessions/` | `graftyard-run` App | its session |
| Vendor (Claude) | 3,121 | `Claude-Session` | `claude` App | its PR |
| Vendor (notes) | 2,021 | `Co-Authored-By`, plus a `refs/notes/ai` note per commit written by a human or by `notes-bot`, an App that is not an `AgentApp`. The vendor App's own attempt to write the note, once per session (201 in all), must be refused | `vendor-x` App | its PR, never through the note |
| Forged | 1,024 | `Graftyard-Session` naming another live task | a human | its PR, never a session |

Half the PRs, 489, merge by squash onto `main`, and their branch is then deleted. The 489 squash commits must resolve to their PR, so the check covers 10,489 commits. The messages come from the network pack built for the predictor (`wp16/netpack.sh`), whose history reaches 32,552 non-merge commits behind its newest tip. The WP9 clone it was first built from was removed during the run.

### What the replay showed about `predict`

The design says `predict` runs "`git merge-tree --write-tree --name-only` of `head` against" each overlapping ref (`design/AGENT-LAYER.md`, Shape, `GitCacheShard::predict`). Read literally, that is a tip-against-tip merge with git's merge base. It is wrong on a moving base:

| Method on the 1,000 sampled pairs | Conflict | Of which the queue merges clean | Queue conflicts it misses |
| --- | --- | --- | --- |
| Tip against tip, `merge-tree head other` | 33 | 32 (24 are another ref that conflicts with the base, 4 a head that does, 4 clean) | 0 of 1 |
| Both landed on base, then `--merge-base=base` (`wp16/predict.py`) | 9 | 8 | 0 of 1 |
| Queue order: head landed on base as a merge commit, then `merge-tree <that commit> other` | 1 | 0 | 0 of 1 |

- **Tip against tip** counts the base's own drift between the two merge bases as a change on one side. On an earlier run it called 5 pairs that share no file "conflicts".
- **Merging two landed trees with `--merge-base=base`** counts a commit that both branches carry, as stacked topic branches do, as a change made twice. Over all 15,700 pairs it reports 201 conflicts, but 124 of those merge cleanly under queue truth. Those would be 62% false conflicts and would fail the 5% bar (`results/raw/wp16-landed-a1-k7-size.json`, `landedTruthConflicts`).
- **The queue-order method** checks both orders and agreed on every pair. It is the method that passes, and it costs one `commit-tree` per job.

So `predict` needs `base` as an input, has to land the head on it, and should report a side that conflicts with the base itself as `Stale`, not `Conflict`. That side is the test merge's finding, not an overlap.

**Order within `PREDICT_PAIRS`.** Under queue truth both orders found every conflict at cap 8. Every conflict sat in the first 5 places by shared-path count: 18, 18, 11, 17, and 13 at ranks 0 to 4. At cap 4 the size order finds 64 of 77 and the recency order 59. Under the landed-tree method, which counts more conflicts, recency order at cap 8 missed 62 of 201 and size order missed none (`results/raw/wp16-landed-a1-k7-recent.json`). The design's order passes this replay, but with no margin to spare when a push has more than 8 overlapping refs. Ranking by shared paths within each priority class costs nothing, and it moves conflicts to the front.

**CPU per merge.** The design prices one prediction at the base's merge constant, 1.5 vCPU-s (`scripts/cost_agents.py`, `PREDICT_VCPU_S = cf.MERGE_VCPU_S`). On linux it measured:
- in containers: 61 ms (recency order), 118 ms (landed method, size order), and 233 ms (queue method, size order) of container CPU per git process, landing steps included;
- on the orb, one process at a time: 35 ms mean, 80 ms p95, and 270 ms max per raw `merge-tree` (`results/raw/wp16-l0-05-cpu-r1.txt`).

Per predicted pair, the padded L0-06 run used 0.37 container vCPU-s: 8,449 s over 23,013 pairs, with landing, `commit-tree`, process start, and the landed-tree cache all included. The guess is about 4 times too high per pair on linux. Raw `merge-tree` alone runs 6 to 40 times under it.

## L0-06: predictor under the A1 replay, then with its site leading

**Setup.** The second warm site is 7 `standard-4` shards with the weur hint. They landed in ams, mad, lhr, and lis (`results/raw/wp16-load.txt`), which is the design's k = 7 for A1 (`design/AGENT-LAYER.md`, A1, step 5). The replay sends all 3,134 pushes at A1's 4.17 pushes/s, spread over the shards by a hash of the ref. At 80% of the replay, the runner sets every shard's site to "leading" for 60 s of pushes (250 pushes) and then clears it. Merge-trees run while leading are counted from each container's own process counter, read once the site leads and drained and again just before it stops leading.

The share is the cgroup's `usage_usec` delta over wall time, divided by the site's 28 vCPU. That is the predictor's CPU alone. The containers run nothing else, so the site's other git work (10.2 vCPU in A1) is not on these shards.

| Run | Pairs run | Second-site CPU share over the run | Worst 60 s of the site | Worst 2 s of one shard | Merge-trees while leading | Pushes while leading, answered `Stale` without the container | Raw file |
| --- | --- | --- | --- | --- | --- | --- | --- |
| Overlapping pairs only, overlap-size order | 5,637 | 8.5% | 16.3% | 55.9% of its 4 vCPU | 0 | 251 (146 with overlapping refs), 11 truth conflicts reported `Stale` | `results/raw/wp16-l0-06-a1-k7.json` |
| Overlapping pairs only, recency order | 6,187 (all pushes, no leading window) | 7.4% | | | | | `results/raw/wp16-l0-05-a1-k7-recent.json` |
| Every push padded to 8 pairs | 23,013 (5,645 overlapping, 17,368 padding) | 32.1% (hottest shard 47.7% of its own 4 vCPU) | 49.8% | 86.6% (p99 53.3%) | 0 | 250 of 250 | `results/raw/wp16-l0-06-a1-k7-pad8.json` |

The padded run is the design's pricing case, with every head push at the full 8-pair budget (`design/AGENT-LAYER.md`, Cost). It fills each push's pairs with the most recently pushed refs, overlapping or not. The 2 s peaks above 50% come from the runner timestamping each `/cpu` read on arrival: a delayed reply shortens the window it closes. The p99 of 53% and the whole-run shares are the honest figures [inference]. A shard's 2 s peak sits at about 50% of its own 4 vCPU because the semaphore allows `PREDICT_CPU × 4` = 2 git processes at once. Each `merge-tree` is a single-threaded process, so the cap holds per shard with no help from the scheduler.

**At the full budget the cap binds.** With every push at 8 pairs, the predictor used 8,449 container CPU-seconds for 3,134 pushes, 2.7 vCPU-s a push. At 4.17 pushes/s that is 11.2 vCPU, against a cap of 14 (50% of 28). The design's estimate is "50 vCPU demand at 8 pairs" with "28% of pairs at peak" (`design/AGENT-LAYER.md`, A1 limits table), but every pair ran here. Hashing refs to shards is uneven, though. The hottest shard averaged 47.7% of its 4 vCPU, with its 2 slots almost always busy, and jobs queued behind it: push to verdict was p50 22 s, p95 127 s, and up to 377 jobs in flight. In this padded case the 30 s and 120 s bars of L0-05 would fail. Real overlap sets are smaller (2.1 refs a push at cap 8) and stay well inside both bars. The cap protects the shard, as intended, and the verdict latency pays for it.

**Leading.** Leading is a flag that a test sets on the shard objects. It stands in for the group's leader moving to the predictor's site, which is not modeled. The flag lives in Durable Object storage, so `predict` reads it before it starts the container. Pushes already in flight when the flag is set finish first: 2.0 s to drain on 7 shards, 209 s in the padded run, where the queue was long. After that, no merge-tree runs until the flag is cleared.

## L0-10: provenance through a vault restore

**What "vault restore" means here, compared with the design.** The design's whole-install restore (`design/DESIGN.md`, Install operations, Vault and Whole-install restore) has five steps:
1. Build a new install account from a cutoff.
2. Rebuild each chain from the vault's newest snapshot at or before the cutoff plus its log tail, checking the `prev` digest chain.
3. Copy every referenced pack to two site buckets and verify each `PackRef.checksum`.
4. Re-apply revocation-class entries.
5. Open writes only at the cutoff's index.

The prototype does steps 2, 3, and 5 for one repository chain and keeps the vault's separation:

| Design | Prototype |
| --- | --- |
| Vault Worker in a vault account the install's tokens cannot reach, pulling `export/batches` over HTTPS with an install-scoped export token | `graft-wp16-vault`, same account, its own script and bucket, with no binding to the install. It pulls over public HTTPS with an export token that reads only `/export/*` |
| Bucket lock rules of 35 days on the vault | Not set. The harness empties the vault before a run |
| Every `ChainId`, the `Release` group, `Names`, `Tokens`, `Identity` | One repository chain, `mono`, holding refs, tasks, PRs, `AgentMeta`, `Merged`, provenance rows, and packs |
| Loss: account compromise or destructive deploy | `POST /wipe`: the group's Durable Object storage is deleted and both its buckets are emptied |
| New install account and sites, customer-signed genesis | A new group, `mono-r`, in a new Durable Object with two new buckets (`graft-wp16-rest-a`, `graft-wp16-rest-b`). Same account and script |
| Step 2: newest snapshot at or before the cutoff plus log tail, `prev` chain checked | The same. The snapshot's digest is checked against the vault's copy of that entry. Each tail entry must follow, chain its `prev`, and hash to its `digest`, or the restore stops |
| Step 3: copy every referenced pack, verify `PackRef.checksum`; a chain with a missing pack stays read-only | The same. A pack whose SHA-256 differs is refused, and `open` refuses while any referenced pack is uncopied |
| Step 4: re-apply revocation-class entries newer than the cutoff | Not done. The cutoff is the vault's last entry, so nothing is newer |
| Step 5: open writes only at the cutoff's index | The same, plus "every pack copied" |
| A Raft group of three members | One member. Replication is M0-WP8's subject |

**Cutoff.** The cutoff is the vault's cursor when the loss happens. The runner lets the vault catch up to the install's last entry before the wipe, so the RPO here is zero by construction. During the replay the vault trailed the install by 0 entries at the median and 79 at most, over 413 samples.

**Resolution rule.** This is journey A6 (`design/AGENT-LAYER.md`), run in `resolve`:
- A commit resolves to `session:<id>` only when `decide` linked `Source::Session`, and the session's host-owned ref, its commit, tree, and `log.json` blob all read back from the install's own buckets.
- Otherwise it resolves to `pr:<n>`, through `Merged` for a squash commit or through the PR opened on the commit's ref, whose `AgentMeta` names the App.
- Otherwise it resolves to `none`.

Resolution never reads `refs/notes/ai`. Under the decision "Agents do not write `refs/notes/ai`" (`decisions/DECISIONS.md`), the vendor App in the "notes" kind tries once per session to push the note itself, and `decide` refuses it. A human, or `notes-bot` (an App that is not an `AgentApp`), then writes the note, and the `AiNote` rows go through the restore like any other row.

**Run** (`run/wp16-prov.ts`, `results/raw/wp16-l0-10.json`):

## What is real and what is modeled

| Part | Real | Modeled |
| --- | --- | --- |
| Repository and branches | linux's real history, real topic branches, real commit times, master's real tip at each push | Agents are replayed topic branches. A branch is live from its first commit until master merges it |
| Ground truth | Real `git merge-tree --write-tree` on the current base, in queue order, both orders checked | Only textual conflicts. No build or semantic conflicts |
| Predictor | Real git (Alpine 3.22 package) in real `standard-4` containers with `enableInternet: false`, network streamed from R2, cgroup CPU counters | The insights consumer, `InsightVerdict` commits, check runs, labels, and priority classes (no PR is approved or queued in the replay) |
| A1 load | A1's push rate and k = 7, on 7 real shards in weur | Only the predictor runs on the shards. Push time is compressed 5,300 times, so branches stay live for minutes, not days |
| Site leading | The pause path in the shard object and the container's own count of merge-trees | Leadership is a test flag. No group leader moved |
| Provenance parsing | The M0-WP10 parser, copied, on 10,000 real linux messages and trailer blocks, with real git commit, tree, and blob objects (SHA-1 checked) | File contents, sessions, and PRs are generated. Vendor session URLs are not dereferenced |
| Install and vault | Separate scripts, Durable Objects, and buckets; HTTPS between them; digest chain, snapshot, and `checksum` checks; a real wipe of storage and buckets | One member per group, one chain, same account, no bucket lock, no revocation re-apply, no new genesis |

## What limits the result

- **L0-05.** 77 conflicts across 11 ref pairs is a small set. linux topic branches are cut to merge clean, which is why most overlaps are clean. An agent fleet editing the same files would conflict far more often. The completeness check rests on 478 non-overlapping sampled pairs with 0 conflicts. It does not prove that no non-overlapping pair ever conflicts: a rename, or a file added on both sides under a truncated directory, could.
- **L0-06.** The share counts the predictor alone. The ref-to-shard hash is uneven (24% to 48% per shard in the padded run), and the cap on the hottest shard sets the verdict latency. With the full 8-pair budget on every push, p95 is 127 s, which is over L0-05's 120 s fail line. The design does not say what happens to a verdict that waits: it should report `Stale` past a deadline, not queue without bound.
- **L0-10.** The cutoff is the vault's last entry, so the RPO is zero by construction. The restore is one chain, not an install. Copying 6,186 small packs (one per push, about 10 KB each) took 2,069 s through one vault Worker, 3 packs/s at 8 copies at a time. Restore time scales with the number of packs, not their bytes, so an install with promoted or geometric packs would restore far faster than per-push packs do [inference].

## Not tested

- Build, test, and semantic conflicts. Renames across branches, and `planned` paths from leases.
- Approved, queued, and human-requested PRs running first, because the replay opens no PR.
- A real leader move to the predictor's site, and the predictor on a site that also carries test merges and index-pack.
- Bucket lock on the vault, a cutoff earlier than the loss, revocation re-apply, and the restore of `Names`, `Tokens`, and `Identity`.
- `Graftyard-Session` values pushed by the matching App but on another App's task. `decide` refuses those by the same check that keeps forged values `Claimed`.

## Proposed design edits

1. **`design/AGENT-LAYER.md`, Shape, "Overlaps and prediction", the `GitCacheShard::predict` doc comment.**
   - Change "`git merge-tree --write-tree --name-only` of `head` against up to PREDICT_PAIRS refs whose PathSet rows overlap," to "Lands `head` on `base` as a merge commit (`git merge-tree --write-tree base head`, then `commit-tree`), then runs `git merge-tree --write-tree --name-only` of that commit against each of up to PREDICT_PAIRS refs whose PathSet rows overlap, with git's own merge base, as the queue would merge them. A side that conflicts with `base` itself is `Stale`, never `Conflict`,".
   - Evidence: this file, "What the replay showed about `predict`". On 1,000 sampled linux pairs, tip-against-tip merges called 33 conflicts, of which the queue merges 32 cleanly. Merging two landed trees with `--merge-base=base` called 201 conflicts across all overlapping pairs, of which 124 merge cleanly (62% false). The queue-order method gave 77 conflicts, all real, and missed none.
2. **`design/AGENT-LAYER.md`, the same doc comment.**
   - Change "PRs that are approved, queued, or requested by a human run first." to "PRs that are approved, queued, or requested by a human run first, and within each class refs that share the most paths with `head` run first."
   - Evidence: every queue-truth conflict ranked in the first 5 by shared paths, and at cap 4 the size order found 64 of 77 against 59 for recency. Under the stricter landed-tree count, recency order at cap 8 missed 62 of 201 and size order missed none (`results/raw/wp16-l0-05-offline.json`).
