# B0-16: deploy with an account-owned token (2026-10-27)

**Result: Pass, under the `durable_object` scheduling policy, which the design now uses for git cache shards and the SSH front (`decisions/DECISIONS.md`, "Git cache shards run under the `durable_object` scheduling policy").**

- Token: `graft-m0-b0-16-deploy`, an account-owned API token with exactly two permission groups, Workers Scripts Write and Workers Containers Write (the dashboard calls these "Edit"). It was deleted after the test.
- `wrangler deploy` of `graft-m0-container` with that token as the only credential built `b0-16/Dockerfile` (Alpine with git), pushed it to `registry.cloudflare.com`, created the container application, and uploaded the Worker. Exit 0.
- The container started and answered on port 8080 with `git version 2.49.1`, 3.9 s after `ctx.container.start()` (`results/raw/b0-16-run.json`).

## The `default` scheduling policy was refused

The first deploy used the config the design then described: `max_instances`, an `image`, and no `scheduling_policy`, which selects `default`. Cloudflare refused it:

```
Error creating application due to a misconfiguration:
  VALIDATE_INPUT
  scheduling_policy This account cannot create applications with the "default" scheduling policy. Use "durable_object" instead.
```

This is not a permission error, because the same token then deployed under `durable_object`. The operator confirmed that `default` will not be offered.

## Follow-up measurements under `durable_object` (B0-38)

- Placement (`results/container-placement.json`): 90 containers, 30 per hint, each started from a Durable Object created with that hint. All 90 reported `CLOUDFLARE_REGION` equal to the hint (ENAM, WEUR, APAC). Start p50 was 185 to 328 ms, and p99 was 1.7 to 5.1 s.
- Survival across a deploy (`results/container-survival.json`): three containers ran on one Worker version. A new version with a changed image was then deployed. All three kept their boot id and their startup image, while the configured image changed.
