# M0-WP14: Sandbox containment and agent CI (2026-10-30)

Rows L0-02 and L0-04 (`build/BUILD-PLAN.md`, M0-WP14). Everything runs as its own scripts, all named `graft-wp14-*`, in this account. No other bed shares a script, a binding, or a bucket, and the bed has no bucket. Every request target is a Worker this package deployed. The only exceptions are RFC 5737 and RFC 3849 documentation addresses, which route nowhere.

## What was built

**Controller** (`src/wp14/controller.ts`, `wp14/graft-wp14-controller.jsonc`, image `wp14/Dockerfile`). A Worker with one Durable Object class, `Sandbox`. It starts a real Sandbox: a `durable_object`-policy container, `standard-2`, `enableInternet: false`, holding Alpine, git, curl, and python3. It registers `OutboundRouter`, a `WorkerEntrypoint` of the same script, with `interceptOutboundHttps("*")` and `interceptAllOutboundHttp()`. That routes every HTTPS request on port 443 and every HTTP request on port 80 through the router. The container has no other way out (https://developers.cloudflare.com/containers/configuration/outbound-traffic/, "Non-HTTP traffic"). The router reads both installation tokens and the model key from the controller's secrets, so none of them enters the sandbox. The harness runs in the background in the container and writes one file per escape class, so a dropped client, an evicted object, or an orb reboot loses no finished class.

**Router** (`src/wp14/router.ts`). This is the prototype of `outbound` and its `Allowed` arms (`design/AGENT-LAYER.md`, Shape, "Controller"). It denies by default:
- Before any arm, it refuses plain HTTP, any port other than 443, `CONNECT`, and percent-encoded, dot-segment, or empty-segment paths.
- `GraftyardHost` allows smart HTTP on the base and the push target only, plus REST under `/api/v3/repos/{base or push target}/`. It removes `Authorization`, `Cookie`, `Host`, `Proxy-Authorization`, and URL userinfo, then attaches the `graftyard-agent` token for the base or the `graftyard-workspace` token for the push target (A3 step 5). It refuses receive-pack on the base, any receive-pack command outside the task's prefix (it parses the pkt-line command list), and every status or check-run write, including `X-HTTP-Method-Override`. GraphQL, gists, uploads, and every other owner path are refused.
- `ModelInference` allows one path on the model host, POST only. It parses the JSON body and refuses `mcp_servers`, any tool whose `type` is not a client tool, and file and batch endpoints. It forwards the body it checked, re-serialized, never the sandbox's bytes. The model key is attached here.
- `Registry` allows a plain GET of a Go proxy path on the registry host. The module path is decoded with Go's `!x` case-escaping and must equal a listed module.
- The router never follows redirects (`redirect: "manual"`). A 3xx goes back to the sandbox, and the sandbox's next request passes through the router again.

**Stand-in targets.** Each target is permissive on purpose, so the router is the only control under test. Each one counts every request that reaches it, by kind, in a `Hits` Durable Object (`src/wp14/counter.ts`, `GET /m0/hits`). That count checks on the server side what the harness sees from inside the sandbox.
- `graft-wp14-host` (`src/wp14/host.ts`, `wp14/host/hostd/main.go`). Real `git http-backend` in a container with `enableInternet: false`, holding three bare repositories. `acme/app` is the base and `acme-agents/app` the push target. `acme/secrets` is "another repository on the host" and accepts any non-empty credential, which models a token the sandbox holds that would work there. Receive-pack is enabled. Gists, GraphQL, statuses, and check runs answer 2xx to any request. `/api/v3/repos/{repo}/redir` is an open redirect.
- `graft-wp14-model` (`src/wp14/model.ts`). A stub inference endpoint. It answers 200 with a `usage` block to any request that carries the model key, including `mcp_servers` and server tools.
- `graft-wp14-registry` (`src/wp14/registry.ts`). A Go proxy that answers 200 for any module path, as a proxy that fetches upstream on demand would.
- `graft-wp14-canary` (`src/wp14/canary.ts`). The unlisted host. It answers `WP14-CANARY-REACHED` to anything that arrives.

**Harness** (`wp14/harness/attempts.py`). Runs inside the Sandbox and makes 100 attempts for each class. An attempt counts as succeeding only if the escape worked: a 2xx for the forbidden request, the canary's marker, a git credential found inside the sandbox, or a push that git reports as accepted. The harness first runs positive controls: a clone of the base, a push inside the prefix to the push target, a clean model call, and a fetch of a known Go module. If those pass, the refusals come from the policy, not from a broken path. **Token scan** (`POST /scan` on the controller). The object streams the sandbox's environment, every process's `environ` and `cmdline`, and every regular file under 2 MB out through `exec`. It searches those bytes outside the sandbox for the three secret values, raw and base64-encoded, so the values never enter the container.

**Runner** (`run/wp14.ts`): `deploy`, `run [--fresh]`, `wait`, `collect`, `delete`. Raw output is in `results/raw/wp14-l0-02.json`.

**What the first runs found.** None of these was a containment failure:
- `/etc/hosts` is read-only in a deployed Sandbox (`EROFS`), which crashed the `hosts-file-pin` attempt.
- The first DNS check counted any UDP answer as an escape and reported 8 "successes". The answers came from the container's own DNS stub: placeholder `11.9.0.1` for every name, including a nonexistent `.invalid` name sent to 1.1.1.1. That matches the docs: "DNS lookups never reach a public resolver, so DNS cannot carry data out of the container" (https://developers.cloudflare.com/containers/configuration/outbound-traffic/, "Non-HTTP traffic"). The check now counts only a real resolver's answer: the canary's real address, or NXDOMAIN.
- `kill -0` reported the finished harness alive, because pid 1 (`sleep infinity`) never reaps it. Liveness now reads the process state.

**What the Sandbox SDK does and does not give the design** [measured unless tagged]:
1. **There is no Sandbox object with its own egress policy.** `@cloudflare/sandbox` 1.0 "does not start, stop, or monitor the container" (https://developers.cloudflare.com/sandbox/reference/). A Graftyard Sandbox is a `durable_object`-policy container on `ctx.container`, as built here. The design's "Sandbox outbound handler" is a `WorkerEntrypoint` registered with `interceptOutboundHttps("*")` and `interceptAllOutboundHttp()`. It is default-deny only because the container starts with `enableInternet: false`. This prototype did not use the `@cloudflare/sandbox` package.
2. **Interception covers ports 80 and 443 only.** Any other port has no route out under `enableInternet: false` (8080, 22, 8443, 2083: timeout or connect failure). HTTPS to a bare IP fails while the `*` intercept is registered, as the docs say. So IP-literal attempts never reach the router. The platform drops them, and the router's own host check is a second layer, not the only one.
3. **Raw TCP to any address on 80 or 443 reaches the router.** A hand-written HTTP request to the canary's IPv4 or IPv6 address on port 80 came back as the router's `PlainHttp` 403. The same bytes, plaintext, on port 443 came back as the router's `UnlistedHost` 403. Its `Content-Length` of 78 is exactly the length of that refusal text, against 31 for the `PlainHttp` text. So plaintext on 443 reaches the router as an `https:` URL, and the router cannot tell from `url.protocol` that the container's leg was cleartext. That leg stays on the machine, and the router's own `fetch` is HTTPS, so no credential crosses the Internet in clear [inference].
4. **The router must not follow redirects**, because a Worker's `fetch` follows them by default. With `redirect: "manual"`, the 302 went back to the sandbox, and the follow-up request went through the router again and was refused.
5. **One intercept for everything, not one per host.** A container has 128 intercept entries, and an intercept cannot be removed while the container runs (Durable Object Container API, "Intercept limit"). The design's arm list therefore belongs inside one `*` handler, with the task in its props, as built. That is also the docs' recommended pattern for a changing host set.
6. **The CA is per container and ephemeral** (`/etc/cloudflare/certs/cloudflare-containers-ca.crt`). Every client in the harness had to be pointed at it (`--cacert`, `GIT_SSL_CAINFO`). A harness template has to set these, or install the CA in its entrypoint.
7. **`exec` processes do not inherit `start()`'s `env`**, and every process has root's capabilities whatever its `user`. A credential passed through `env` would therefore be readable by every process, which is the design's reason for keeping it in the router [doc].

**Model tokens per harness.** Not measured. The stub returns a fixed `usage` of 15 tokens, which says nothing about Claude Code, Codex, or OpenCode. Measuring them needs real model calls through `ModelInference` for each harness on a fixed task, which this package did not make. The router's `ModelInference` arm already sees every response, so `TaskBudget` counting is a small addition when that run happens.

## L0-04: agent CI under `ci: AutoReadOnly` (policy part only)

**Built** (`src/wp14/ci.ts`). The policy part of a dispatcher for a workflow run caused by an agent push, as a pure function of the workflow, the trigger, `AgentPolicy`, and the PR's fold row:
- `dispatch` gives a run fork-PR semantics until `AgentGate` holds for that head. Every agent run gets a token of `contents: read` and `metadata: read`, whatever the workflow declares, including `permissions: write-all`, and every job gets an empty secret map.
- Under `AutoReadOnly` the run is `queued` at once. A job that references a secret waits, and the other jobs start. Under `Approve` the run is `action_required`.
- `secretRefs` finds `secrets.X`, `secrets['X']`, `toJSON(secrets)`, `secrets: inherit`, and a bare `${{ secrets }}`.
- `release` fills a waiting job's secrets only when `gateHolds` holds for that job's own head at that moment. `gateHolds` follows `Merge::decide`'s rule (A3 step 9): an `AgentGate` for this exact head, which is still the PR's head, from a writer who is neither the requester nor anyone who pushed to the PR.
- The secret map is filled only in `release`, so a reference the scanner misses makes the job fail for lack of the secret. It never leaks one.

**Replay** (`run/wp14-ci.ts`, raw output in `results/raw/wp14-l0-04.json`). The A1 pushes are M0-WP16's replay of real linux topic branches, used as agent refs (`results/m0-wp16.md`): 3,134 pushes on 805 agent PRs. Each PR carries `AgentMeta` with alice as the requester. Each push dispatches two workflows. `ci` has `build` and `lint`, which use no secrets. `release` has `deploy` (`write-all`, `secrets.DEPLOY_KEY`), `publish` (`secrets['NPM_TOKEN']`), `sign` (`secrets: inherit`), `dump` (`toJSON(secrets)`), and `computed` (`secrets[format(...)]`, which the scanner cannot see). Human events are added per PR by a hash of the ref name: 193 PRs get a valid approval from bob. 72 get an approval from the requester alice, 87 from mallory, who is not a writer, and 79 from dave after dave pushed to the PR. 28 get bob's approval of the previous head, and 346 get none. Waiting jobs are re-checked after every push and every approval.

The leak check is a separate oracle, not `gateHolds`. When a job first holds secrets, its head must be the PR's current head, with a gate for that head from someone other than alice or mallory who did not push to the PR. The oracle was itself checked. A mutant dispatcher whose release ignores the gate's head (`--mutant`) gives **2,476 leaks** under `AutoReadOnly`, so the zero below does not come from an oracle that cannot fire.

**Verdict: partial.** Measured, with 0 leaks of 1,292 releases: the policy half of the pass condition ("a read-only token and no secrets, and jobs that reference secrets wait") and the fail condition ("any secret reaches an agent-push job before `AgentGate` holds for its head"). Not measured, because no Actions engine exists:
1. **"Start within 30 s".** Here "start" means only that `dispatch` returns `queued` in microseconds. No workflow run is created from a real push event, no job is queued to a runner, and no runner picks it up.
2. **Real token minting.** The read-only token is a `PermSet` value. No installation token is minted with that ceiling, and no job used one against the host.
3. **Real secret injection.** Secrets are a map in memory. No runner receives them, and no job's environment or log was checked.
4. **Workflow parsing.** `secretRefs` is a regex over job text, not a parser of GitHub's expression language. Reusable workflows (`secrets: inherit` to another file) and composite actions were not followed.
5. **The A1 rate and real human timing.** Events run in replay order, not at 4.17 pushes/s, and the approvals are synthetic and assigned by hash.
6. **Human re-runs.** `decide` refuses agent re-runs (M0-WP10). A human re-run of an agent run was not modeled. The dispatcher judges a run by its trigger's head, so a re-run on a gated head would be trusted.
