# F59: `Audit` finishes repository create and delete

F59 closes the crash window left by `m3-repos`: an edge can commit a repository's name and then die before its owner row, settings, or tombstone. The implementation is on branch `f59`; the evidence here is in-process and local. No hosted proof has run.

## The gap

`decisions/OPEN-QUESTIONS.md`, **F59**, asks: "What finishes a repository create or delete that an edge crash cut short?" Before this branch, create ran `CreateRepo`, `RepoOwner`, the optional README push, and `InitRepo` in band; delete ran the repository tombstone and then the name's `Deleted`. `Audit` owed only transfers and enterprise changes. A crash could therefore strand a taken `Live` name with no usable repository group, or a deleted name resolving to an already-deleted chain. F59 puts both follow-ups behind log-borne commit points and lets the existing `Audit` cursor finish them.

## The design

- **Create's commit point.** `AuthzOp::CreateRepoWith` in Authz format **0x12.11** commits the name's `Live` and an `AuthzEvent::RepoCreate` in one entry. The latter carries `key`, `repo`, and `init`, the JSON settings the request asked for (`crates/identity/src/authz.rs`, `AuthzOp::CreateRepoWith` and `AuthzEvent::RepoCreate`). The event does not change the fold: it remains in the log for `audit::authz_owed` to turn into `Owed::Create` (`crates/identity/src/audit.rs`, `authz_owed`). This replaces the edge's old `CreateRepo` on installations that enable 0x12.11 (`workers/edge/src/repos.rs`, `create`).
- **Delete's commit point, and the reversed order.** The edge now turns the owner's name `Deleted` first, carrying `repo` and `retain_until`, and only then appends the repository's tombstone (`workers/edge/src/repos.rs`, `delete`). That reverses `m3-repos`' repository-first order. A crash after the first commit leaves a safely deleted name and a tombstone that `Audit` can still supply; the old order could leave the name alive after the chain was gone.
- **Create finisher.** `finish::create` submits `RepoOwner` on `Names` first. Once that row commits and the repository chain has been read, it submits `RepoStep::Init`; `lifecycle::of_step` turns that into `Lifecycle::Init` in repository format **32.17**, which writes the first `Settings` and `Created` together (`crates/identity/src/finish.rs`, `create`; `crates/git/src/lifecycle.rs`, `Lifecycle::decide`). Initialization uses the owner's current `Authz` enterprise, not stale ownership data in the request JSON. An existing edge initialization wins and the finisher's retry is a no-op.
- **Create abort.** If no `Created` has committed after `CREATE_ABORT_AFTER` = **600 s [guess]**, the finisher sends operator-only `AuthzOp::AbortCreate`, releasing the name only if it is still `Live` for that repository (`crates/identity/src/finish.rs`, `CREATE_ABORT_AFTER` and `create`; `crates/identity/src/authz.rs`, `AbortCreate`). The life check precedes the deadline check, so age cannot abort an already-created or deleted repository. A stale abort cannot release a same-named replacement.
- **Delete finisher.** `audit::authz_owed` turns a matching `RepoEntry::Deleted` into `Owed::Delete`. `finish::delete` owes `Lifecycle::Delete` only while the name is still held for the same repository and exactly the same `retain_until`, the `RepoOwner` agrees, the deadline has not passed, and the chain is not already deleted. `Lifecycle::Delete` repeats the deleted-name and deadline authorization checks before writing `RepoEvent::Deleted` (`crates/git/src/lifecycle.rs`, `Lifecycle::decide`). There is deliberately no delete abort: after the commit point the repository is gone to its routes, and only the tombstone remains owed.
- **No README redo.** The finisher does not recreate an `auto_init` README commit. That push needs the git cache's `validate`, which `Audit` does not call. A cut after `readme` owes only initialization, not another push (`crates/identity/src/finish.rs`, module documentation; `crates/git/tests/f59.rs`, `audit_alone_finishes_every_create_cut`).
- **The edge's late initialization is gated too.** `IssueOp::InitRepo`, still repository format 32.13, now requires an owner `Authz` dependency that names this repository `Live`; a late edge create after `AbortCreate` gets `NotFound` rather than resurrecting the chain (`crates/git/src/issue_ops.rs`, `IssueOp::InitRepo`). `Lifecycle::Init` has the same invariant, plus once-only, owner/enterprise, and not-deleted checks.

## Formats and wire tags

The following are the additions in `git diff origin/main -- crates/git/tests/wire_tags.golden`. The first number on each golden row is the serialized enum variant index; Authz's explicit record tags agree with it. `LifecycleOp` and `LifecycleErr` have no independent repository events: init reuses `Settings` and `Created`, and delete reuses `Deleted`.

| Type | New golden rows and tags |
| --- | --- |
| `id::AuthzEvent` | variant **16**, `RepoCreate`, tag **17** (`0x11`), golden payload `100161020161` |
| `id::AuthzOp` | variants **30** and **31**, `CreateRepoWith` and `AbortCreate`, tags **30** (`0x1e`) and **31** (`0x1f`), payloads `1e01610161` and `1f016102` |
| `id::audit::Owed` | variants **5** and **6**, `Create` and `Delete`, payloads `0502016102016101` and `06020201` |
| `git::lifecycle::LifecycleOp` | **0** `Init` (`0002000000000000000000000000000001`) and **1** `Delete` (`0101`) |
| `git::lifecycle::LifecycleErr` | **0** `NotLive`, **1** `NotDeleted`, **2** `WrongOwner`, **3** `Invalid`, **4** `Gone`, **5** `NotRead` |

The lifecycle command's JSON envelope is `{"lifecycle":{"format":[32,17],"op":...,"request":...}}`; its record starts with `0x4c` (`crates/git/src/lifecycle.rs`, `Wire` and `impl Record for Lifecycle`). `CreateRepoWith` and `AbortCreate` require 0x12.11, and `Lifecycle` requires 32.17. A release that does not list those formats refuses the command as unsupported rather than decoding it as an older operation.

## What a hosted proof would need

1. **A site day on a test install with `GRAFTYARD_AUDIT=1`**, so every Authz member runs this release before its consumer starts. Enable **0x12.11** (18.11) and **32.17** in `FORMATS_ENABLED` along with the install's existing formats. The finisher's 32.17 command must not reach a member that cannot read it.
2. **An edge deployed with `--test-faults`** and the same 18.11 and 32.17 enablement. The edge's create uses `CreateRepoWith` only when 18.11 is enabled; without it, the old log has no `init` for `Audit` to recover.
3. **A driver for all four crash points**, sending `x-graft-kill` values `name`, `repo_owner`, `readme`, and `delete_name` (`workers/edge/src/repos.rs`, `killed`). After a wait beyond `FINISH_AFTER`, assert that `Audit` alone commits `RepoOwner` and initialization for each create cut, commits the tombstone after `delete_name`, and becomes quiescent. Check that the create cut after `readme` gets no duplicate README push, that an aborted no-group create releases its name after 600 s, and that a late `InitRepo` is refused.
4. **History on the first scan.** The first 0x12.11 audit scan must also owe deletes for history: pre-F59 `Deleted` names have no new event to add, but `authz_owed` can read their existing `RepoEntry::Deleted` events and finish any still-retained, missing tombstones. The proof should seed such a cut before enabling `Audit` and verify idempotent completion rather than testing only newly written entries.

## Risks

- **A stuck create holds up the owner's cursor for up to 10 minutes.** Repeatedly refused initialization leaves the Authz `AuditCursor` before that create, so later owed work on the same owner's chain waits behind it until the 600 s abort can commit. This is deliberate cursor safety, but it is visible head-of-line blocking, not an isolated per-repository delay (`crates/identity/src/audit.rs`, `Finisher::want`; `crates/identity/tests/audit.rs`, `a_create_whose_init_never_commits_is_aborted_after_create_abort_after`).
- **Large descriptions can turn a previously accepted create into 422.** `CREATE_INIT_MAX` is 8 * 1024 bytes for the entire serialized `RepoSettings`, not just `description`. A description of roughly 8 KB or more, depending on the other settings, makes `CreateRepoWith` answer `BadRecord`; the edge maps that to repository validation 422 on 18.11-enabled installs (`crates/identity/src/authz.rs`, `CREATE_INIT_MAX`; `workers/edge/src/repos.rs`, `create`). The cap is a [guess], not a GHES compatibility measurement.
- **Changing 32.13 `decide` is compatible because followers verify events; they do not re-decide commands.** `Member::on_append` first advances the follower through the prior committed entry and then calls `verify` on the next one (`crates/raft/src/member/follower.rs`, `on_append`). `verify` creates `scratch_at` from the fold, applies any earlier unapplied events, and for each supplied event calls only `Scratch::check` followed by `Scratch::apply`; it has no command or dependency input and never calls `Command::decide` (`crates/raft/src/member/log.rs`, `verify`). On the repository side, `impl Command for RepoCmd::decide` dispatches `IssueCall::decide` on a leader, while `RepoCmd::replay` only reconstructs duplicate-request output; `RepoScratch::check` checks tier tags and the event-level ref/promotion/archive invariants, returning `Ok(())` for ordinary `Settings`/`Created` events (`crates/git/src/repo.rs`, `impl Command for RepoCmd`, `RepoScratch::check`). Thus an old 32.13 entry remains verifiable after the leader-only `InitRepo` rule changes, which satisfies the no-new-format compatibility condition. It does **not** make an old leader enforce the new abort guard during a mixed rollout: an old leader's events are still verified and applied. Full enforcement follows leader/site rollout.
- **New Authz validation is event-level.** Unlike 32.13's leader-only guard, the new `RepoCreate` marker has an explicit follower event invariant: `AuthzScratch::check` requires the matching `Live` name. The added follower plant test exercises that check directly (`crates/identity/src/authz.rs`, `AuthzScratch::check`).

## Contradictions with the design (quoted, not edited)

- **Delete order.** `design/SHARED.md`, **"Multi-chain operations"**, says: "A delete appends the chain's `Deleted`, then turns the name `Deleted` on the owner's `Authz` chain, held 90 days." F59 deliberately does the reverse: the name is the commit point and the chain tombstone follows (`workers/edge/src/repos.rs`, `delete`). The same section's repository create/delete paragraph still says "no finisher owes the rest" and names `CreateRepo`, not `CreateRepoWith`.
- **Tombstones.** `design/SHARED.md`, **"Repository repair, tombstones, and retention"**, **Tombstones**, says: "Deleting a repository appends `Deleted { retain_until }` to its chain, 90 days by default, and turns its name entry `Deleted`." The implementation retains the 90-day default and both records, but the name now commits first so `Audit` has a durable commit point from which to repair the chain.
- **What the finisher scans and owes.** `design/SHARED.md`, **"Multi-chain operations"**, **Finisher**, says: "It scans `Names` and `Tokens` shards, and keeps an `AuditCursor { through }` on each owner's `Authz` chain (`Authz` format 0x12.4, event tag 16, op tag 29), from which it owes a transfer for a `Reserved` name and an enterprise change for an `Enterprise` event." F59's Authz scan additionally owes `RepoCreate` and `Deleted` work, and the same scan now reads repository chains after their owner rows (`crates/identity/src/audit.rs`, `authz_owed`, `Owed::reads`).
- **Delete has no abort path.** `design/SHARED.md`, **"Multi-chain operations"**, says: "Every multi-chain operation names its commit point, its finisher, and its abort path." Create now names all three. Delete names its commit point and finisher but has no abort: once its name is `Deleted`, the externally visible deletion has committed and neither the finisher nor the edge attempts to roll it back (`crates/identity/src/finish.rs`, `delete`).
