## Item 2: native A1 replay

The test is `crates/git/tests/l004_replay.rs`. It replays the 3,134 A1 pushes on 805 refs from
`crates/git/tests/a1_pushes.tsv` (time, ref, head). That file is regenerated from torvalds/linux by M0-WP14's
`topics.py` and `replay.py` for the window 2026-07-01 to 2026-08-16, and its counts match M0.

**What runs real.** The replay uses real members:
- a repository `World` and a 3-member Actions group;
- each push as a real `Push` by a confined third-party agent App;
- each agent pull request opened from a task whose requester is WRITER;
- runs created through `agent_run(AutoReadOnly, ...)` and `CreateRunWaiting`;
- approvals as real `Review`s, the gate read through `agent_gate_holds`, and the release through `ReleaseSecrets`.

**Scenarios.** Each pull request gets one scenario, picked from its ref's hash:
- 40% none;
- 25% a valid writer (WRITER2) approving the current head;
- 10% the requester approving;
- 10% a reader approving;
- 5% a valid writer approving the stale previous head;
- 10% a pusher scenario, dropped.

**The oracle.** It judges each fork job once, when the job first holds secrets. It uses only the test's own approval
set and the pull request's current head, never an `AgentGate` row.

Run: `cargo test --release -p graftyard-git --test l004_replay -- --include-ignored`, 3 passed in 81 s.

| Count | Real code | Mutant (releases every head of the pull request) |
| --- | --- | --- |
| Agent runs | 6,268 | 6,268 |
| Jobs waiting at creation | 12,536 | 12,536 |
| Gates written (valid) / approvals that must release nothing | 295 / 271 | 295 / 271 |
| `ReleaseSecrets` sent | 295 | 499 |
| Jobs released | 1,196 | 1,624 |
| **Leaks** | **16** | **444** |
| Leaks where another pull request's valid approval is at the same SHA | 16 | 24 |

**Finding (F150).** All 16 leaks on the real code have one cause. `ReleaseSecrets { repo, head }` releases every waiting
job of the repository at that SHA (`crates/actions/src/shard.rs`, `release_secrets`). `release_on` checks the gate
for one branch only. 78 A1 head commits sit on more than one ref. When WRITER2 approves pull request A at such a
commit, pull request B's jobs at the same commit are released too, though nobody approved B. That gives 4 runs of 4
jobs.

Whether this breaks the fail line is a design question: the approved commit is byte-identical, but `AgentGate` is per
pull request. It is recorded as `decisions/OPEN-QUESTIONS.md` F150 for a lead ruling. The candidate fix is a
per-branch `ReleaseSecrets` (an Actions format bump), after which the 16 must go to 0.

**What the tests assert.**
- The full test pins the real leak count to exactly those same-SHA releases (16, all shared-head) and fails on any other
  leak.
- The mutant must leak beyond them.
- The 300-push test, which is not ignored, does the same: real 4 leaks, all shared-head; the mutant 52.

**The `computed` job.** It reads `secrets[format(...)]`. `references()` counts that form, unlike M0's scanner, so in
every agent run it waits (3,134) and reads nothing until it is released. That is the safe side, and the test asserts it.

## F150: per-branch release, built at $0 (2026-11-27, branch `f150-release-branch`)

The lead ruled per-branch, not same-SHA. `ActionsOp::ReleaseSecretsOn { repo, head, branch, pulls }` (tag 30, Actions
0x15.15, plant292) releases a job waiting on `head` only when its run is a `push` run of `branch` or a `pull_request`
run of a gated pull request (`refs/pull/N/merge`). The site sends it after a site day sets `GRAFTYARD_SECRETS_BRANCH`,
which needs a site day that ships 0x15.15's reader first. Until then it sends 0x15.14's `ReleaseSecrets`, which keeps
the gap.

The replay now goes through the site's call and the leader's decode (`runsvc::release_call`, `release_op`), with each
run's `head_ref` set to its pull request's merge ref, as a site's run carries it:

| Release | Releases sent | Jobs released | Leaks |
| --- | --- | --- | --- |
| Per branch (0x15.15) | 295 | 1,180 | **0** |
| Repository-wide (0x15.14) | 295 | 1,196 | 16, all same-SHA across branches |
| Mutant: every head of the pull request, per branch | 499 | 1,588 | 408 |

1,180 is exactly 1,196 minus the 16. The 300-push guard checks all three: 0, 4 (all same-SHA), and 48.

**Hosted proof, driver ready (2026-11-27, branch `l004-same-sha`, not run).** `tests/am3/hosted/l004.mjs`'s `l004`
line adds check (s), the same-SHA negative.
- Before any approval, m3-admin pushes the agent's current head to a second agent-prefix branch
  (`refs/heads/graftyard/l004-same-<t>/work`) and opens a pull request from it. Its run is an agent run, so its

- That pull request has no `AgentMeta`, so no gate ever holds for it.

  `GRAFTYARD_SECRETS_BRANCH=1` is set.
- `l004-row.sh` gains `site3`, which adds that flag, and `state` reports it.
- The second pull request goes with the repository at teardown.
