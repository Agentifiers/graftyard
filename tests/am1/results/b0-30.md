## Blocked on (2026-11-10 02:00Z), and how each is routed around

1. **Member SQLite over 4 GiB cannot be read.** workers-rs 0.8.7's `SqlStorage::database_size()` is
   `self.inner.database_size() as usize`, and `usize` is 32 bits on wasm32, so every reading saturates at
   4,294,967,295 (`tests/m2/results/m2-wp1.md`, "Ceiling", saw the same). The probe of `repo:196627` read exactly that
   on all three members. B0-30's line is 8 GiB, so the gate quantity is unreadable through the binding. **Route:** the
   site reads `ctx.storage.sql.databaseSize` as an `f64` through `js_sys::Reflect` (test routes only: `/fold
   {"log"}` and `/bench_seed`), shipped in this branch's site day.
2. **Nothing counts `SQLITE_FULL`.** A failed storage write resets the member (`Host::fail`) and logs "storage write
   failed". **Route:** members count writes that fail with `SQLITE_FULL` or "database or disk is full" in `/stats`
   (`sqliteFull`, per isolate), and the monitor also queries Workers Logs of all four site scripts for both strings
   every hour, which survives isolate restarts.
3. **The existing 4 GB groups are not usable.** `repo:196628` (BF-20's 3.99 GB tier) had no leader at 01:14Z (sites 0
   and 1 did not answer `/status`, site 2 a follower at term 18), and its repository answers 503 "not leader".
   `repo:196627`'s members are already past the 4 GiB reading ceiling (about 6.6 GB by M2's per-row rate). Both are
   owned by the BF-20 seed accounts, not by `m3org`. **Route:** a fresh `m3org/b0-30` repository, seeded on all three
   members through `/bench_seed` (the comment-row seed BF-20 used; `{"load"}` is the push load, not the seed).
4. **Push rate.** One network validates about 2 pushes/s (`tests/am1/results/am1-runs.md`, "Diagnosis"), and journey
   9 needs 4.17/s. **Route:** as the brief allows, see "Substitutions" (to be filled in when the run starts).

### Blocker 12: precise cause, and the one recovery attempt (2026-11-10 17:45 to 19:45Z)

**The pack that fails.** Archive runs and `PrSync` test merges call the site a shard (`git#0#net:1048586`). Since
15:29Z each one failed on `ingest fd76cbb6…: 422 git index-pack: … fatal: did not receive expected object
4aae47a908f44a35b875b8c7489694a6c079917b`. `fd76cbb6` is the 221-byte inline pack of log entry 9,328, a `PrSync`
`TestMerged` of about 15:25Z. It is thin against `4aae47a9`.

**The push whose pack the shard never got.** `4aae47a9` is the new tip of `refs/heads/b030/42` in log entry 2,857
(term 19, `at` 09:43:53.039Z). That is one m3-admin Human push carrying two inline packs: `b030/41` `772e5e04` →
`1670e5be` (323,327 B, SHA-256 `8d672ced…`), and `b030/42` `2ecd6423` → `4aae47a9` (323,329 B, `35e13014…`). Site a's
fsck at 17:30Z still had both refs at their old values, and the other 500 `b030` refs matched the leader. So the shard
skipped exactly entry 2,857, both its packs and its ref changes, and nothing else on the branch heads.

**Why the shard skipped it, from the code and the Workers Logs of sites a to c:**

1. Entry 2,857 was committed in term 19, then the group lost its leader. Terms 20, 21 and 22 were each one `Noop`
   (2,858 at 09:44:15, 2,859 at 09:44:25, 2,860 at 09:44:51). During those 40 s every site sent bursts of `/suspect`
   (a 40, b 25, c 62 between 09:44:12 and 09:44:26).
2. Site a's shard was catching up behind a `/validate`. At 09:44:20 to 09:44:26 it called `POST /entries?from=2857&to=2858`
   seven times, and site c's shard did the same eight times. Every call was `ok` in 6 to 204 ms. Site b's one call was
   canceled after 31 s. Container calls (`/ingest`) are not in Workers Logs, but the shard has neither the objects nor
   the ref changes, so none of these reads brought it the entry.
3. `/entries` answers any member's stored log only when that member's core says it leads (`workers/site/src/member.rs`,
   `(_, "/entries")`). A non-leader answers `{"error":{"notLeader":…}}` with HTTP 200. `graftyard_lookup::call_opt`
   follows `notLeader` to the named leader. A member that has just won term 20 or 21 but not yet committed its `Noop`
   is a leader whose `commit` is still at the term-19 value, and `Host::entries_json` clamps `to` to the member's own
   `commit` (`workers/site/src/host.rs`, `entries_json`, `let to = to.min(commit)`). A member is `Leader` before it is
   `ready` (`crates/raft/src/member/leader.rs`, `Lead::ready_at`), and `/entries` checks only the role. So a new leader
   whose commit index had not yet reached 2,857 answered `{"entries": []}`, HTTP 200 [inference: the code allows it,
   and it is the only path found that ends a read of 2,857..2,858 without error and without the entry; the reply
   bodies are not logged].
4. `GroupLog::entries` (`workers/site/src/shard.rs`) treats an empty page as the end of the range: `let Some(last) = …
   else { break }`, and returns `Ok` with what it has. Asked for 2,857..2,858, it returned nothing, without error.
5. `ShardHost::catch_up` (`crates/git/src/host.rs`) builds its plan and ref changes from the entries it got. Over an
   empty list that is no packs and no ref changes. It then advances the cursor to the piece's `to` regardless
   (`cursor.advance(*chain, to)`) and saves it. The cursor passed 2,858 with 2,857's packs and refs never applied. The
   next catch-up read from 2,859 (logged at 09:44:51.716).
6. Nothing afterwards repaired it. Later pushes to other branches were thin only against objects the shard had. A
   catch-up never re-reads below its cursor, and the rehydrates that ran later (10:39Z on a pool shard, and site a
   after site day 8) started from the last `Promoted`. Site a's own disk kept its cursor. `PrSync`'s test merge of
   pull requests on `b030/42` (head `4aae47a9`) has answered 409 "commit … is not here" since about 10:30Z. Once
   `PrSync` recorded a `TestMerged` whose pack is thin against `4aae47a9` (entry 9,328), every catch-up that reached
   9,328 failed. `handleIngest` (`containers/git/server/main.go`) returns 409 only for "unresolved delta" or "missing",
   and "did not receive expected object" is neither. So the container answered 422, which `ShardHost::ingest` treats as
   fatal (anything but 200 and 409), and the whole catch-up aborted instead of retrying that pack later. Promotion
   needs a caught-up shard, so archiving stopped at 15:29Z, the first archive run after 9,328.

Site b's shard (`git#1#net:1048586`) is the control. Its one read of 2,857..2,858 failed (canceled at 31 s) instead of
answering empty, so its cursor did not pass 2,857. While site b led (term 77, 17:49 to 17:54Z) its archive runs went
through: 81 ranges, through 2,642. Then the load's `keepHome` moved leadership back to site 0 (term 78), and archiving
stopped again on site a's shard.

So the defect is in step 4 and step 5 together: **a short or empty `/entries` page is taken as the whole range, and the
cursor advances to the range's end anyway.** A catch-up should advance only to the last index it received (or fail when
a page is empty below `to`). `/entries` should also refuse until the leader is `ready`, as reads do. The 422 in step 6
turns one skipped entry into a stuck shard. These go to the follow-up work item "Git cache shards on a hot group with a
multi-GB log". Nothing here changes code on this branch.
