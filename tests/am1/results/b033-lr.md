# B0-33 lr: ln's host question, on the same build, graft-m2b, 2026-11-25

A B0-33-shaped row, not a gate row: B0-33 stays met (`tests/am1/results/b033-closing.md`). The lead approved it on
2026-11-24 after ruling that ln's lower agent line came from the hosts, not the build (`tests/am1/results/b033-ln.md`,
"Why the side writes were refused: the hosts, not the build"). It reruns ln's first 300 s on the build ln ran, and
records learner CPU per request and the leader's CPU per call as host readings.

**Result: the agent line came back with no build change.** On the same build and edge as lnA, lrA admitted 126.6 agent
commands a second over 300 s, against lnA's 99.8 and clA's 112.0. Side writes were refused 8.5% of the time, against
lnA's 29.0% and clA's 13.6%. Every standing gate line holds. So the build was not why ln fell. The stop rule did not
fire: it asks for an agent line under 100/s.

## Host readings (recorded, not gated)

**Learner CPU per request over the first 5 minutes** (DO analytics, `durableObjectsPeriodicGroups` with
`durableObjectsInvocationsAdaptiveGroups`, the four learners together):

| Run | Learner CPU (s) | Requests | ms per request |
|---|---|---|---|
| clA | 601.3 | | 5.8 |
| lnA | 805.7 | 87,657 | 9.19 |
| lrA | 608.9 | 51,496 | **11.82** |

**This reading did not predict the result.** lrA's learners ran at 11.82 ms per request, above lnA's 9.19, yet the
agent line was the best of the four runs. lrA's learners spent about clA's CPU (608.9 s against 601.3 s) on about 59%
of lnA's requests. They shed far less, so fewer reads failed and were retried. CPU per request therefore moves with how
much retry traffic reached the learners, as well as with the host. It is a weak host signal on its own [inference].
The stop rule's "clA-like host" test (at or under about 6.5 ms per request) would have called lrA a slow host. That
did not matter here, because the agent line was over 100/s.

**The leader's CPU per call by minute** (DO analytics, CPU over requests for `repo:131419#1#f0`):

| Minute (load from 01:00:54Z) | Requests | CPU ms per request |
|---|---|---|
| 01:01 | 18,347 | 1.44 |

| 01:03 | 15,155 | 2.14 |

From minute 1 to minute 4 it rises 1.44 → 2.24 ms, the same climb as clA (1.59 → 2.50) and below lnA (2.28 → 3.11 by
minute 5). Over the 5 minutes the leader object read 132.4 s of CPU on 82,735 requests (clA 146.7 s on 76,087). The
host guard's setup reading, 23.5 ms a commit, was the lowest of the three (clA 25.7, lnA 26.4).

The leader Workers Logs (`raw/leaderlogs-lrA.json.xz`) give CPU per invocation over the 300 s: all 1.39 ms (clA 1.41,
lnA 1.65), `/commit` 1.11 (clA 1.26, lnA 1.47), and `/commit` by minute 0.85 → 1.25 ms (clA 1.00 → 1.53, lnA 1.07 →
1.83). On every reading, lrA's leader was at or below clA's.

## What this settles

- ln's lower agent line came from the hosts, as ruled: the same build on another placement did 126.6/s.
- Learner CPU per request alone does not separate a slow host from a fast one, because shed retries feed it back.
  Sheds per learner and side-write 429s by route are the readings that moved with the agent line on all three runs.
