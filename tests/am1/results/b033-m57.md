(`f466a39e`), and graft-m2b's edge was rolled back to that revert.

## The regression

Edge errors by message, 09:45 to 09:57Z, from Workers Logs:

| message | count |
|---|---|
| "Cannot invoke closure from previous WASM instance" | 394 |
| runtime cancel, "code had hung and would never generate a response" | 245 |
| "Promise will never complete." | 199 |
| "memory access out of bounds" | 11 |

All of it falls between 09:52 and 09:55. The m56 row on the same sites, at the same load and with `edge-read-batch`
already on main, had 0 exceptions.

- **First event:** a hung cancel at 09:52:04.590 on a lease renew (wall time 2,545 ms). It was followed at .600 by
  `RuntimeError: memory access out of bounds` in
  `<worker::delay::Delay as Future>::poll::{closure#0}::{closure#0}`, the `setTimeout` callback that wakes a `Delay`.
- **What a trap does:** a trap in that callback is a WASM `RuntimeError`. worker-build's shim (`shim.js`) marks it
  critical, and the next entry reinstantiates the module (`__wbg_reset_state`, `instanceId++`).
- **Why it takes other requests down:** every closure the old instance registered checks its instance and throws
  "Cannot invoke closure from previous WASM instance". That covers every pending `Delay`'s timer callback and every
  promise continuation. Their futures can never be woken, so their promises never complete, and the runtime cancels
  their requests as hung. The cancels come in bursts at one 10 ms tick: 09:52:04.61 ×35, 09:52:49.61 ×37, 09:52:52.51
  ×13 and 09:52:53.89 ×23. So one trap takes down every request in flight in that isolate, which is why the hung
  requests are every write kind: receive-pack 63, task PATCH 63, renew 38, graphql 35, labels 28, upload-pack 9, and
  leases.
- **Why the timer callback faulted is not verified.** An out-of-bounds access in that callback means the timer fired
  into freed closure memory, so a `Delay`'s timer outlived the `Delay`. `Delay`'s drop clears its timer with
  `clearTimeout`. If a `Delay` is dropped while another request's code is running, the clear may miss a timer owned by
  the request that set it [inference]. A local workerd bed (`/tmp/delaybed`, not kept) with the batch's shape did not
  reproduce it: 2,500 writes on 8 keys, one in four cancelled at 1.5 s, gave 0 hung, 0 resets and 0 cross-request
  errors. Workers Logs has no "Reinitializing" line for the window.

## The four questions

1. **What hangs.** The verified part is the chain above: a `Delay` timer callback traps, the instance resets, and every
   request in flight in that isolate hangs. The first hung cancel came 10 ms before the first trap, so whether a
   request hung first and caused the trap, or the logs' order is loose, is open. The trap's root cause is not verified,
   and the bed did not reproduce it.
2. **The poll loop.**
   - "waited past its deadline" began at 09:51:30Z (94 in that half minute), 34 s before the first trap, then ran
     1,040 to 1,314 per half minute. So it is the batch's own cost, not the reset.
   - A write that arrives during a pass must wait that pass out and then share the next one. On these learners a pass
     takes 0.3 to 6 s: up to 3 members at `FOLLOWER_WAIT`/`FOLLOWER_CALL`, and `TIER_STALE` is 6.5 s. That is past the
     write's whole SHED_RETRY_FOR (4 s), so trwait p99 is exactly 4,000 ms.
   - edge-read-batch's identity batch has the same structure, but its reads are one member read answered in single
     milliseconds, with BATCH_STALE at 2 s. On m3fe2 its rcwait p99 was 1,940 ms, and on m56 (which carried it) the
     edge had 0 exceptions. Waiting out an identity read costs milliseconds; waiting out a tier pass costs a full
     learner round under load.
3. **Why sharing was rare.**
   - The key is not too specific: every push reads the same gate query, so pushes share one key per repository.
   - The batch is per isolate, and the load was spread across about 200 to 260 edge isolates per 30 s (member calls by
     `SENT_BY` isolate, `tsave-m57b33`). At about 166 requests a second, an isolate saw under 1 same-key write a second,
     so passes rarely overlapped there, and only 8.6% of passes were shared.
   - The fall in /read per request (2.56 to 1.35) is then mostly writes that stopped reading while they waited and then
     answered 503, not sharing [inference].
   - m3fe2's identity batch shared because its burst put 500 pushes into 1 s in 2 colos.
4. **The leader change** at 09:52:22Z is independent of the edge reset [inference]:
   - CommitErrors counts site a's own member-to-member calls, which do not pass through the edge.
   - Edge inbound to site a held 400 to 700 per 2 s through 09:52:04–22, with no gap or surge at the reset.
   - The leader's confirms reached 738 and 991 ms at 09:52:12–14 just before the trip.
   - m56 tripped the same rule (4 CommitErrors holds) with no edge errors.

## Recommendation

Drop tier-read-batch as built.

- **It cannot share at this load.** The batch is per isolate, so each isolate sees under one write per key per pass.
- **Its rule costs more than it saves here.** "Never the read in flight" makes a write wait out a whole tier pass, which
  is longer than the write's retry window. That produced 7,467 of the 10,662 503s.
- **It coincided with a trap** we cannot yet reproduce, so it should not ship until that is understood.

m56's load growth is better attacked where it starts:
- the writes' own shed retries (one retry pass, or a shorter SHED_RETRY_FOR);
- the far learner's `late` reads: learner 194 shed 9,040 of 21,383 here (F97).

No fix is proposed for the trap, because its cause is not verified. With the revert deployed, graft-m2b no longer runs
the code that showed it.
