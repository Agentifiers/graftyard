My verdict lines said setup took over 120 s against about 14 s on m56 and m57. That was wrong. m56 (`mwn8854t`) and

The m59r33 trace (`raw/tsave-m59r33.jsonl.xz`, learner rows) shows each learner stepped entries to 114 and applied 113
by 12:41:14, then got nothing until load began. The leader's commit was 114. Over site a's whole term the outgoing
leader's `/stats` counts one append sent to each learner. m56 and m57 show the same, at 82 and 81. The wait asks
`applied < lead.commit`, so it never ends.

This is R29 (`decisions/OPEN-QUESTIONS.md`): an idle leader never tells its followers, or here its learners, the last
commit, because a member learns a commit only from an append. Its fix, `r29-commit-heartbeat` (`1edea7858`), is on main
but not in the sites' 1465c208b, which held "held-grant waits for a site day". Whether the wait passes depends on
whether a later append happened to reach the learners after the last setup write [inference]. The learners are one
commit behind with every entry, and load's first append tells them, so the rows' load is not affected. The wait is.

So a rerun gated on "no load until learners caught up" would abort on this site build about half the time, for this
reason alone. A site day from main (which carries R29) removes it.

## Fix: receive-503

- `commit` (workers/edge/src/lib.rs) returns `CommitFail::{Wire(CallErrorWire), NoOutcome(String)}`, and a failed
  create probe is `NoOutcome` too. receive-pack answers `NoOutcome` with `no_outcome`: 503, `Retry-After: 5`, before
