F112, 2026-11-24. The lead cleared one B0-34-shaped row after `g41-moved` merged (main `b587a8cb`). It ran on an edge

**Verdict, as the lead ruled: G41's fix holds.**
- **Line 1 passes.** Site b's maintenance was never held in 12.5 minutes of pre-kill load. Its first hold came at
  kill +2 s. On mt21 it held from 4.7 minutes before the kill.
- **Line 2 passes on the bound reading.** The overdue repack started at the 420 s bound to sample resolution on both
  sites that deferred. The `deferred_s` metric as built measures the wrong thing, and is fixed on branch
  `b034-warm-order` (below).
- **Line 3 passes.** Site b's `max_unkept_held` read 565, under 751.

**The every-clone line failed: 60.6% in kill and 8% in second, against mt21's 100% and 100%.** This is not a code
regression. Placement put mt22's chain on site c, and the edge's fallback order sent the kill's reads to site b. That
fault was on both commits; mt21 passed because its chain site was also next in record order. The fix is
`warm-order`, on branch `b034-warm-order`, and the design question is G42.

**Why line 2 reads on the bound and not on `deferred_s`.** As built, `deferred_s` was now minus `firstHeld`, and
`firstHeld` clears only when a repack completes. So it counted from the first refused start through the granted
overdue run and through the idle after load. Site b read 246.5 s at its first sample past the kill and 426.6 s at the
sample where its overdue repack showed `running`; the bracket is the sample before (411.5 s, not running) and that one.
It then kept counting through the run (427 to 667 s) and after load to 1,485 s. Site a's overdue repack showed
`running` at 431.8 s with the sample before at 372 s. The bound read in the samples is the start of the overdue run,
which is what `maintDeferMax` plus `yieldHold` bounds, and both sites started inside one 15 s sample of 420 s.
`cpu_p99` read 0.96 to 1.0 on site b while it deferred, so the CPU case of the bound applied.

**The metric is fixed** on branch `b034-warm-order`, commit `f00a4943`. `deferred_s` now counts from the first start
refused after the last one granted and resets to 0 when a start is granted. A new `max_deferred_s` keeps the longest
wait a granted start had, from the bound's own clock, so the next row reads the bound directly.
`TestMaintenanceYieldsToMovedLoad` checks `deferred_s` 0 while the granted overdue repack runs; on today's metric it
read 5 there and failed. It also checks 0 after an idle hour and `max_deferred_s` = 2 + 2·`yieldHold`, the wait at the
grant. One caveat: a start refused and never tried again still counts while the shard idles, because `deferred_s` has
no later attempt to close it.

**It is not a code regression.** `git diff a940127a..b587a8cb` touches no compose, chain-site or upload-pack code. It
covers maintenance (`maint.go`, `maint_hold`), the sweep, the log read, member and snapshot code, and the edge's G40
and `moved-mark` changes.

**Placement put mt22's chain on site c.** A network is warm on its home and on the rendezvous-next site among the
others (`warm_sites`: sha256 of `network:{id}` and the slot, first 8 bytes). Its chain buckets, its k and its pool
grants live on those two. With home a, mt21's 1048616 picks b and mt22's 1048617 picks c. Over 10,000 networks with
home a, 50.06% pick c. The compose buckets show it: through the warm, `compose/1048617/` held 17 objects on a and c
and none on b, and at the row's end 5, 5 and 0. On mt21, b held 7 and c none.

**The edge did not follow the chain.** `validate_sites` ordered the sites after the home in record order (a, b, c),
and `shard_order`, `validate`, `validate_streamed` and `shard_read` (clones and fetches) all used it. So once site a
was killed, mt22's reads went first to site b, which held no chain. In the 120 s after the kill:

| | Misses | Stock tail | `caught_up_ms` p50 | `headers_ms` p50 |
|---|---|---|---|---|
| mt22 site b (third, no chain) | 69 | 66 | 7,260 | 6,767 |
| mt22 site c (warm, chain) | 8 | | 897 | 797 |
| mt21 site b (warm, chain) | 36 | | 1,629 | |

Site b had no chain to compose from, so its misses went to stock and waited on catch-up. DESIGN's git caches
data-center row already said "the other warm site already holds k shards"; the order ignored which site that is.
mt21 passed only because its warm site was also next in record order [inference, strongly supported by the numbers
above].

**The fix is `warm-order`,** on branch `b034-warm-order`. `validate_sites` now tries the home, then the network's
other warm site, then the other Full sites in record order. `COLD_SHARD_MS`'s cold-last still applies on top. The
test `a_validate_falls_back_from_the_home_shard_to_the_warm_site_then_the_other_full_sites` reads [0, 2, 1] for
mt22's network with home 0, where b587a8cb reads [0, 1, 2]. `tests/m0carried/plant161.py` plants four wrong orders
and catches 4 of 4. DESIGN's validate order sentence and the git caches data-center row say so, and
`decisions/DECISIONS.md` has "`warm-order`".

**B0-34's design assumes the chain is on the kill's next site,** in the data-center row and in the kill line itself.
That is G42 in `decisions/OPEN-QUESTIONS.md`. It is settled by a B0-34-shaped row on a network whose warm site is
third in record order (such as 1048617 with home a) that serves every clone at least 90% through kill and second.
