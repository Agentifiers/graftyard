## Findings

- **The bundle had no TLS client** (fixed): workerd's `network` service fetches HTTPS only with `tlsOptions`, so the
  puller reached neither the edge nor R2. `lifeboat-tls` (main `a915d4b5`) adds `trustBrowserCas`.
- **The bundle needs a raised open-file limit.** Every chain's copy is a Durable Object with its own SQLite file. At
  workerd's inherited 1,024 the puller failed every pass with `SQLITE_CANTOPEN` once about 1,000 chains were open (34
  failed passes, no copy lost: the state saved at 400 objects resumed). It ran with `ulimit -n 524288`. Nothing in
  `lifeboat bundle`'s output or DESIGN tells an operator this [measured].
- **The stale cycle passed the 5-minute lag alarm.** A stale pass took about 30 s (400 probes, 16 at once, from this
  orb), not the 10 s the turn budget was sized on, so a cycle of 3,236 chains took about 4.5 min, and a cycle with any
  probe that did not answer cleanly does not count [inference, from `pass.rs`'s `cycle_dirty`]. The longest stale lag
  was 767 s, and `current_at` moved at 22:00:52Z and 22:04:48Z. This
  meets `lifeboat-turns`' first flip ("a hosted stale window where the copy doesn't reach current within one alarm
  period") [measured].
- **The hosted feed stopped carrying commits after 21:39:30Z.** Rounds logged `planned=6` or `7`, `read=0: every
  source failed` every ~10 s, and pushes at 21:52Z, 21:59Z and 22:07Z reached no `export/` object. The same line ran
  21:10Z to 21:12Z, before this row's repository existed. The row did not depend on it, since it stopped the feed
  for the lifeboat anyway; the cause is not found [unverified].
- **The leader took one call.** The edge's lookup asked the member it did not know led (the group was idle with no
  leader until the push elected site 0). The leader refused it. Whether a refused call is a "leader read" is the lead's
  call; no leader rows were read.
- **gh in an orb** reads `HTTPS_PROXY` over `NO_PROXY` for a host with a port; `bf53.sh gh` unsets the proxy.
